# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Laminar is an open-source observability platform for AI agents. It provides OpenTelemetry-native tracing, evaluations, AI monitoring, and SQL access to all data.

## Repository Structure

This is a multi-service monorepo with three main components:

- **app-server/** - Rust backend (Actix-web HTTP, Tonic gRPC). SQL query validation + JSON↔SQL conversion run in-process here (`src/query_engine/`, built on `sqlparser`).
- **frontend/** - Next.js/TypeScript web UI
- **pii-redactor/** - optional Rust gRPC service that runs a HuggingFace token-classification PII model on CPU via ONNX Runtime. Standalone — not linked from app-server. Tested with the OpenAI privacy filter (BIOES) and Piiranha (BIO); accepts either scheme via `config.json` `id2label`. See `pii-redactor/README.md` for the gRPC contract, model layout (`model.onnx` + optional `model.onnx_data*` external-data shards + `tokenizer.json` + `config.json`), and the weight-baking Dockerfile.

## Architecture

```
Frontend (5667 prod / 3000 local-dev) ────┐
                                         │
App Server                               │
├─ REST API (8000)  ◄────────────────────┘   # env::server::PORT
├─ gRPC ingestion (8001) ◄─── SDK traces      # env::server::GRPC_PORT
└─ Realtime SSE (8002)                         # env::server::CONSUMER_PORT
         │
         ├──► PostgreSQL (5433) - main database [required]
         ├──► ClickHouse (8123) - analytics/spans [required]
         ├──► RabbitMQ (5672) - async processing [optional, has in-memory fallback]
         └──► Quickwit (7280/7281) - full-text search [optional]
```

- **`PORT` env inheritance can silently break the app-server HTTP listener (8000).** `dotenv::dotenv()` does NOT override an already-set env var, so a shell that exports `PORT` (e.g. an agent sandbox using `PORT=3005`) beats `.env`'s `PORT=8000` and the HTTP server fails to bind — gRPC (8001) and SSE (8002) still come up. The bind error is swallowed (`main` joins the never-returning consumer handle before the http handle), so you get "Spinning up full HTTP server" with no "starting service ...:8000" line and no panic. Launch with an explicit `PORT=8000 ./target/debug/app-server` (or `env -u PORT`) and verify with `tr '\0' '\n' < /proc/<pid>/environ | grep ^PORT`. The same shadowing hits `next dev` (`EADDRINUSE`) — use `PORT=3000 pnpm run dev` — and node `--env-file` (a sandbox-exported `LMNR_PROJECT_API_KEY` wins over the scratch `.env` one → 401s); run `env -u <VAR> node --env-file .env ...`.

## Database Migrations

Database schema is managed with Drizzle ORM. The source of truth is the database itself - do NOT edit schema files directly.

```bash
cd frontend
pnpm db:generate                # Generate migrations AND strip "public". qualifiers (preferred)
# or, equivalently:
npx drizzle-kit generate && pnpm db:strip-schema
# Migrations are applied automatically on frontend startup
```

- `pnpm schema-pull:lint` heavily reformats `schema.ts`, `relations.ts`, and `tsconfig.json`. After running it, revert unrelated formatting changes before committing.
- **Migration SQL must stay schema-neutral (no `"public".` qualifiers).** Tables resolve via the connection `search_path` (`POSTGRES_SCHEMA`, default `public`), so a hardcoded `"public".` would break non-public self-hosted installs. `drizzle-kit generate` re-emits `"public".` prefixes (it has no schema-neutral output mode) on tables, **foreign-key targets**, **enum/type creation**, and **column type changes**. `pnpm db:generate` runs the generate then `pnpm db:strip-schema`, which `sed`s every `"public".` token out of all migration `.sql` files. If you generate by hand, run `pnpm db:strip-schema` (or `sed -i 's/"public"\.//g' <file>`) afterwards. The strip targets only the `"public".` schema qualifier (double-quoted name + dot), so `'public'` string literals, `public_`-prefixed constraint names, and `public_key` columns are left intact. Snapshots/`_journal.json` already record an empty schema.
- `npx drizzle-kit generate` requires a TTY only for its name prompt — pass `--name <slug>` and it runs fine in non-interactive shells (CI, sandbox). It diffs `schema.ts` against the latest snapshot, so apply the DDL to the staging DB and add the table to `schema.ts` first; expect stray index churn in the generated SQL when the DB has drifted from the snapshots — strip unrelated statements before committing.
- When writing migrations manually, also create a `meta/NNNN_snapshot.json`. Copy the previous snapshot, apply the schema change (e.g. add/remove columns), set `prevId` to the previous snapshot's `id`, and generate a new UUID for `id`. Without a snapshot, the next `drizzle-kit generate` will produce a duplicate migration.
- **ClickHouse migrations** (`frontend/lib/clickhouse/migrations/`) are tracked by the migration tool and only run once. Never modify an already-applied migration file — changes won't execute on existing deployments and may cause checksum errors. Always create a new numbered migration file instead.

## Configurable Postgres schema (`POSTGRES_SCHEMA`)

- `POSTGRES_SCHEMA` (default `public`) is the schema all Postgres tables live in. It's applied as the connection `search_path` in BOTH services — frontend `lib/db/drizzle.ts` (`connection: { search_path }` on the `postgres()` client) and app-server `db/mod.rs` (`PgConnectOptions::options([("search_path", …)])`, descriptor `env::database::SCHEMA`). All queries use unqualified table names, so the search_path is the only routing mechanism; the two services MUST be set to the same value.
- The frontend resolves the value via `getPostgresSchema()` in `drizzle.ts`: empty/unset means "no explicit schema" (connection defaults to `public`). For the connection `search_path`, any explicit value — INCLUDING `public` — is applied. For the migrations-tracker location (`migrationsSchema`) and the boot-time `CREATE SCHEMA`, any case variant of `public` is treated like unset (the check is `postgresSchema.toLowerCase() === "public"`).
- **`migrationsSchema` guard (instrumentation.ts):** `migrate()` is passed `migrationsSchema: <schema>` ONLY when an explicit `POSTGRES_SCHEMA` is set AND it is not a case-insensitive `public`. Relocating `__drizzle_migrations` into a schema where it doesn't already exist makes the migrator see "no last migration" and re-run all migrations (non-idempotent `ALTER TYPE … ADD VALUE` / `DROP CONSTRAINT` then errors). So: unset or `public` (any case) → tracker stays in `drizzle` (where existing default deployments have it, so an operator who sets `POSTGRES_SCHEMA=public` "to be explicit" doesn't trip a re-run); any other explicit schema → tracker moves into that schema (lets a Laminar DB coexist with another Drizzle service in the same instance).
- `POSTGRES_CREATE_SCHEMA` (default `true`, frontend-only) gates the boot-time `CREATE SCHEMA IF NOT EXISTS`. Set `false` when the schema is pre-provisioned or the DB role lacks `CREATE`. The data schema is NOT auto-created by the migrator — only the migrations-table schema is — so this DDL is required for a fresh non-public install. The `CREATE SCHEMA` is skipped for any case variant of `public` (it always exists, and quoting `"PUBLIC"` into the DDL would create a distinct schema that the lowercase-folding `search_path` never resolves to).

## Alphabetical sorting in Postgres (collation)

- **`ORDER BY <name>` is collation-dependent and is NOT case-insensitive in general.** Staging (Supabase) is `en_US.UTF-8`, where the ICU-ish ordering already folds case, so a case bug there is invisible; a `C`/`POSIX`-collation instance sorts by raw bytes, putting EVERY capital ahead of EVERY lowercase (`Zebra` before `apple`). Do not verify a name-ordering change against staging alone.
- Sort user-facing names with `ascNameFold(column)` (`frontend/lib/db/utils.ts`), which emits `ORDER BY lower(col), col` — the `lower()` folds case, the raw column is the deterministic tiebreak for names differing only in case. Use it for every project/workspace picker; in raw SQL (app-server) write `ORDER BY lower(p.name), p.name` by hand. Note `lower()` makes the sort non-sargable, so an index on the bare column no longer serves it — fine for these small per-workspace lists, but add a `lower(col)` expression index if a large table ever needs this ordering.

## Comment style

Keep comments short. Don't write multi-paragraph rationale blocks — a single terse line covering the WHY (non-obvious constraint, invariant, workaround) is enough. ClickHouse migration files especially should not carry prose explaining why a statement exists; the SQL is the source of truth. Prefer removing a comment over rewriting it once the identifier names make the intent obvious.

## In-process Query Engine (SQL validation + JSON↔SQL)

- SQL validation and JSON↔SQL conversion run **in-process inside app-server** (`app-server/src/query_engine/`), built on the `sqlparser` crate (`ClickHouseDialect` + `visitor` feature). Keep these three operations in-process — no network hop.
- `QueryEngine` is a plain struct (`query_engine/mod.rs`) with three inherent async methods: `validate_query`, `sql_to_json`, `json_to_sql`. Consumers hold `Arc<QueryEngine>`: HTTP routes (`routes/sql.rs`) and the MCP `query_laminar_sql` tool (`api/v1/mcp.rs`).
- **The validator IS a security boundary**, not just a linter — it is the only thing standing between user SQL and ClickHouse. It enforces SELECT-only, rejects `BLOCKED_FUNCTIONS` and the `project_id` column, blocks non-allowlisted tables, and rewrites allowlisted table refs to project-scoped `_v0` views (e.g. `spans` → `spans_v0(project_id = '<uuid>')`, `traces` → `traces_v0(project_id=…, start_time=…, end_time=…)`). `json_to_sql`'s raw-expression path is also a security boundary. Preserve their rejection semantics when editing.
- **The frontend JSON contract is binding**: route response/request types use `#[serde(rename_all = "camelCase")]` and must keep matching `frontend/lib/actions/sql/types.ts` (e.g. `queryStructure`, `validatedQuery`). The `fn`/`column`/`args`/`alias` metric shape and `dimensions` array are the camelCase wire format the chart builder + SQL editor depend on.
- Tests live in `validator/tests.rs`, `json_to_sql/tests.rs`, and `sql_to_json/tests.rs`. Run with `cargo test --bin app-server query_engine -- --nocapture`. When changing validator/conversion behavior, update the corresponding test rather than relaxing the assertion.
- **`executeQuery` (`frontend/lib/actions/sql`) routes through this validator** — it POSTs to app-server's `/projects/{id}/sql/query`, so any frontend server action that builds ClickHouse SQL is constrained by the validator (SELECT-only, allowlisted-table-only) AND requires app-server HTTP (8000) to be reachable. To aggregate the `scores` JSON-string map on `evaluation_datapoints` (a ReplacingMergeTree → query with `FINAL`), do NOT use a CH-side tuple `ARRAY JOIN JSONExtractKeysAndValues(scores, 'Float64')` aggregate (the validator rejects the tuple element access `kv.1`/`kv.2`). Instead `SELECT` the raw `scores` strings and average per `(evaluation_id, name)` in JS — the same pattern as `getEvaluationTimeProgression` in `frontend/lib/clickhouse/evaluation-scores.ts` and `getScoreAveragesByEvaluationIds` in `frontend/lib/actions/debugger-sessions/index.ts`.
- **All parsing goes through `parse_clickhouse_sql` in `validator.rs`, NOT `Parser::parse_sql`** — it carries two workarounds for upstream `sqlparser` over-strictness: (1) a token-stream rewrite (`wrap_in_placeholder_lists`) that parenthesizes a `{param}` placeholder list after `IN`/`NOT IN`, and (2) a custom `ClickHouseOptionalIntervalDialect` newtype wrapping `ClickHouseDialect` that flips `require_interval_qualifier()` to `false` so `interval '1 day'` (unit inside the string literal, valid in ClickHouse/Postgres) parses. Don't "fix" the interval case at the token level — synthesizing a trailing unit token makes `Interval`'s `Display` emit `INTERVAL '1 day' SECOND` and corrupt the SQL; only the dialect flag yields `leading_field: None` which round-trips verbatim. The wrapper MUST override `dialect()` to return `self.0.dialect()` (ClickHouseDialect's `TypeId`) or `dialect_of!(self is ClickHouseDialect)` checks inside the parser (parametric aggregates like `quantile(0.9)(duration)`, etc.) silently take the non-ClickHouse path. When bumping the `sqlparser` crate, re-check the wrapper's hand-delegated method list against `ClickHouseDialect`'s overrides.

## SQL Editor Schema (autocomplete + AI generation)

- `frontend/components/sql/utils.ts` (`tableSchemas`, `enumValues`) is the frontend source of truth for the SQL editor's autocomplete AND for the schema embedded in the AI-generation system prompt (`frontend/lib/actions/sql/prompts.ts` consumes both). Backend allowlist lives in `app-server/src/query_engine/validator.rs` → `TableRegistry::new`; the two MUST stay in sync — adding a column to the v0 view + the registry without updating `tableSchemas` leaves it absent from autocomplete and invisible to the AI generator.
- `app-server/src/query_engine/schema.rs` (`build_schema_prompt()`) is the single backend source of truth for the SQL schema surfaced to BOTH the MCP `query_laminar_sql` tool description (`api::v1::mcp`, injected at construction in `tool_router_with_descriptions` — NOT from the `#[tool]` doc comment) and the signals-gated Platform Agent prompt (`lmnr-private` `agent::prompts`). It must mirror `validator.rs`'s `TableRegistry` and the frontend `tableSchemas`/`enumValues`; drift breaks generation. The file is PUBLIC (no signals gating) even though its only OSS caller is the MCP tool — `query_engine/mod.rs` declares `pub mod schema;` unconditionally.
- Columns whose runtime CH type is `String` but whose values are constrained (status, span_type, trace_type, signal_runs.status / .mode) carry an `enumType: keyof typeof enumValues` field. The prompt builder appends `Allowed values: '...'` to the column's description, and the editor's `<column> = ` autocomplete filters to those literals. Without `enumType`, the model invents values (e.g. `status = 'OK'` when nothing pins the status column to `'success' | 'error'`).
- `enumValues` is keyed by enum NAME, not column name. A single column can map to one enum (`spans.status` → `status`) or different enums in different tables (`signal_runs.status` → `signal_run_status`). The autocomplete `columnEnumMap` is built by walking `tableSchemas` once at module load, so column→enum wiring stays declarative — never add column names to a hardcoded regex; just set `enumType` on the schema entry.
- The `clusters_v0` view (CH migration; latest is `47_clusters_v0_drop_centroid.sql`) intentionally does NOT expose `centroid` — the embedding vector is an internal `Array(BFloat16)` on `signal_event_clusters`, useless over SQL and expensive to ship. When recreating the view in a new migration, keep the `WHERE level > 0` L0 filter and the 9 user-facing columns (id, signal_id, name, level, parent_id, num_signal_events, num_children_clusters, created_at, updated_at). `clusters` is in `tableSchemas` (autocomplete + AI + docs); `signal_events_all` stays registry-only (queryable) and is intentionally NOT in `tableSchemas`.
- **Two MORE agent-facing table lists are hardcoded and NOT generated from the registry — they drift silently.** (1) The MCP `query_laminar_sql` tool docstring + the `QuerySqlParams.query` field doc in `app-server/src/api/v1/mcp.rs`; (2) `SQL_SCHEMA_HELP` in `lmnr-ts/packages/lmnr-cli/src/commands/sql/schema.ts` (the CLI `sql` command's `--help`). Adding a table/column to the query-engine registry makes it *queryable* but invisible to MCP clients and CLI users until BOTH are hand-updated. So the full sync set for a new SQL-exposed table/column is FOUR places: `validator.rs` `TableRegistry` (execution gate), `tableSchemas` (frontend autocomplete/AI), `mcp.rs` docstring, and CLI `schema.ts`. Descriptions live only in `tableSchemas`; the other three are terse `name (Type)` lists.

## SQL Editor Results Table

- The Table tab renders through `frontend/components/sql/results-table.tsx`. It owns three UX behaviours: per-cell hover copy button (copies the FULL raw value — display uses CSS truncate against the column width), the row-count indicator data (rendered in `editor-panel.tsx` next to the tabs from `results.length`), and column-width persistence.
- Column widths persist to localStorage keyed `sql-results-column-sizing-<projectId>-<templateId>`. Same pattern as chart-builder's `table-chart`: seed `defaults` (with `columnOrder` + stored `columnSizing`) at `InfiniteDataTableProvider` creation, and a thin `ColumnSizingPersistence` child (like `ColumnConfigEmitter`) writes changes back. Writes replace the stored map with the current result's `columnSizing` (prunes keys from prior query shapes — draft keys especially would grow forever under a merge). The provider remounts on every query run (loading unmounts the tree) — persistence is what carries widths across re-runs; don't lift the provider above `renderContent` to "fix" the remount.

## Labeling Queue Items (ClickHouse)

- Queue metadata (`labeling_queues`) lives in Postgres; per-item rows (`labeling_queue_items`) live in ClickHouse as a `ReplacingMergeTree(updated_at)` keyed `(project_id, queue_id, id)` — see `frontend/lib/clickhouse/migrations/42_labeling_queue_items.sql`, which also creates the `labeling_queue_items_v0` SQL view. Registering a column for ad-hoc SQL takes TWO app-server files: the allowlist in `query_engine/validator.rs` AND the column/type/description metadata in `query_engine/schema.rs` (editing only the validator silently desyncs autocomplete + AI generation).
- **`edit` is the canonical current target; `payload` is the insert-time snapshot.** `edit String DEFAULT ''` is seeded equal to `payload.target` on insert by BOTH write paths (Rust `create_labeling_queues_items`, TS `pushQueueItems`) and overwritten by every UI PATCH, so readers never branch on "is `edit` empty?" and `dirty` is a value compare rather than a write-detector — which is what makes reverting an edit correctly drop the dirty flag. The public ingest API does not accept `edit`. Note the two frontend mirrors of this resolution disagree on their fallback: `getEffectiveTarget` (`components/queue/queue-store/helpers.ts`) falls back to `{}`, `effectiveTarget` (`lib/actions/queue/index.ts`) falls back to `null`.
- **All reads must use `FINAL`**; there is no `UPDATE`. `updateQueueItem` (`lib/actions/queue/items.ts`) is a read-modify-write that re-inserts with a fresh `updated_at`, and its narrow input surface deliberately omits `payload` — a caller that thinks it needs to write `payload` is bypassing the immutability invariant. **Caveat: the RMW does NOT preserve `idempotency_key`** — `insertQueueItems` hardcodes `""`, so every UI PATCH wipes it. (Harmless today: ids are derived deterministically, so a same-key retry still collapses.)
- **The frontend write paths MUST pass `async_insert: 0`** (`insertQueueItems`, `copyQueueItemsToDataset`). The shared CH client defaults to `async_insert: 1, wait_for_async_insert: 0` — it never waits at all — so an async write is not visible to the next `FINAL` SELECT, and the read-modify-write would see nothing and re-insert with default `createdAt` / empty `edit`, silently destroying the current target. The table is low-volume (interactive labeling), so synchronous inserts cost nothing. The Rust ingest path uses the client defaults and is fine — it only ever inserts.
- Idempotency is **deterministic id derivation**, not a pre-flight existence check (which leaves a race window between lookup and insert): `id = Uuid::new_v5(&queue_id, idempotency_key)`, so a retry lands on the same RMT sort key and collapses. Items without a key get `Uuid::now_v7()`. **Accepted trade-off:** a same-key retry arriving AFTER the user edited or approved reverts `edit`/`status` to the seed values, because the new write has the larger `updated_at`. Retries normally fire seconds after ingest, so this is rare — but `payload` is not frozen forever.
- **Cancel the pending debounced save before any approve / unapprove / discard / push** (`orchestrator.cancel(id)`; `cancelAll()` for push-all, since windowing means the client cannot enumerate every id). Without it a late `{status: 0}` PATCH lands after approve's `{status: 1}` and RMT last-write-wins silently reverts the approval — same mechanism resurrects a discarded row past its delete tombstone. For the same reason, window eviction must SKIP any id with a pending save (`orchestrator.hasPending(id)`) so a trailing PATCH can't fire against state we no longer hold. The save orchestrator tracks timers per-item-id (`queue-store/save-orchestrator.ts`) — do not collapse it into a single shared debounce, which drops item A's edit when the user tabs to B inside the window.
- **The `new` vs `modified` split is derived in FOUR places** that must agree, using TWO different comparison mechanisms. The three SQL copies — `PROGRESS_EXPR`, `getQueueItemStates` and `getQueueProgresses` (all in `lib/actions/queue/items.ts`; the third inlines its own copy rather than reusing `PROGRESS_EXPR`) — do a raw JSON-**string** compare, `edit = JSONExtractRaw(payload, 'target')`, so they are susceptible to key-order and whitespace drift if a write path ever serialises target keys in a different order (both current paths preserve insertion order). The frontend `deriveItemState` → `isDirty` (`queue-store/helpers.ts`) instead parses `edit` and `lodash.isEqual`s it **structurally** against `payload.target`, and treats empty `edit` as `new` where the SQL would call it `modified`. The frontend is therefore the more forgiving of the two: any serialisation drift shows up as a navigator bar (structural) disagreeing with the queues-table progress counts (string). Changing one mechanism requires changing the other.
- On queue deletion, call `deleteQueueItemsByQueueIds` BEFORE the Postgres `DELETE` — FK cascades only cover Postgres. Deletes are ClickHouse lightweight `DELETE` (a tombstone that `FINAL` reads respect).
- **Bulk push** (`pushItemsToDataset`, from `/push-to-dataset`) goes through `copyQueueItemsToDataset`, which copies server-side via `INSERT INTO dataset_datapoints SELECT … FINAL` so payload bytes never cross the wire, filters to `status = 1` unless `includeUnlabelled: true`, verifies the inserted count before deleting the source rows, and returns that count. Two traps: it returns **200 with `{pushed: 0}`** when nothing matched (e.g. unapproved `itemIds` without `includeUnlabelled`), so UI must gate local removal and success toasts on `result.pushed > 0`, not `res.ok`; and datapoint ids are minted in JS and non-deterministic while `dataset_datapoints` is plain `MergeTree`, so a retry after the verify-passed-but-delete-failed window WILL duplicate rows (the UI gates the button while in-flight and accepts this). The id filter is `toString(id) IN Array(String)` because binding `Array(UUID)` through `command` empirically did not match.
- **The single-item DELETE-with-`datasetId` branch is a SEPARATE implementation** — `removeQueueItem` (`lib/actions/queue/index.ts`) reads the one row, resolves `effectiveTarget` in JS, calls `createDatapoints`, then deletes. It does NOT reuse `copyQueueItemsToDataset`, so: `status` is ignored (an unapproved item is copied as-is), payload bytes DO cross the wire, there is no verify-before-delete, and it returns `{success: true}` rather than a count. Do not reason about this path from the bulk path's semantics.
- **Progress filters are evaluated cross-datastore:** `getQueues` partitions the incoming `?filter=` array, sends progress filters to `findQueueIdsByProgress` (CH `GROUP BY … HAVING`) and feeds the resulting ids into the Postgres query as `inArray(...)`, leaving name/id filters in the Postgres WHERE. **Limitation:** the `GROUP BY` only sees queues with ≥ 1 item, so `= 0` predicates never match empty queues (`approved = 0` means "has items, none approved"). If zero-comparisons-including-empty become a real ask, branch on the operator and add an inverse `NOT IN` query rather than UNION-ing the empty set in.
- Queue hotkeys (`components/queue/hotkeys.tsx`) are scoped **per shortcut** and all are gated on `!dialogOpen`. `⌘⏎` (approve/unapprove) sets `enableOnFormTags` + `enableOnContentEditable` so it fires inside CodeMirror and `<input>`s — it's the submit-and-advance key of the labelling loop. `⌘⌫` (discard), `⌘←`, `⌘→` deliberately use the DEFAULT scope so they do NOT fire from a focused editor; otherwise `⌘⌫` discards the item while the user is deleting a JSON line, and the arrows fight cursor-to-line-start/end. `Esc` blurs `document.activeElement` to escape the editor, and bails on `e.defaultPrevented` so it doesn't steal Escape from a Radix dialog or CodeMirror's search panel.
- `created_at` / `updated_at` are `DateTime64(3, 'UTC')`; model them in Rust as `u64` epoch millis.

## Rate Limiting (SQL + data ingestion)

- Two independent per-project limiters, gated by separate features: `Feature::RateLimiter` (`REDIS_URL` + `RATE_LIMIT` + `RATE_LIMIT_PERIOD_SECS`) covers the SQL surface; `Feature::IngestionRateLimiter` (`REDIS_URL` + `INGESTION_RATE_LIMIT` + `INGESTION_RATE_LIMIT_PERIOD_SECS`) covers trace ingestion on BOTH transports (gRPC + HTTP `/v1/traces`). Env names live in `app-server/src/env/rate_limit.rs`. The ingestion limit applies to every project by default (no per-project opt-in).
- **SQL** (`/v1/sql/query` + CLI twin `/v1/cli/sql/query`): `SqlRateLimiter` (`api/v1/sql.rs`) wraps a shared `actix_limitation::Limiter` (the env-default N/T) — counted inline in `handle_sql_query` with key `ratelimit:{project_id}`, not scope middleware, because `project_id` is only known after the auth extractor runs. A per-project N override read from cache on every request (`sql_rate_limit:{project_id}`, plain integer set out-of-band via `valkey-cli SET`, no app writer) swaps in an ad-hoc `Limiter` built with that N and the global period. Only N is overridable; T is global (`RATE_LIMIT_PERIOD_SECS`). Constant in `cache/keys.rs`. A changed N applies immediately; the window itself is actix-limitation's fixed window (counter key `ratelimit:{id}` with TTL set on window start — `DEL` it to reset early). Accepted trade-off shared with the ingestion limiter: the crate opens a fresh Redis connection per `count()`, outside `ResilientRedisConnection`; migrating to the shared-cache counter is planned.
- **Data ingestion:** `IngestionRateLimiter` (`traces/rate_limit.rs`, mirrors `SqlRateLimiter`) counts ONE shared quota key `ingestion_ratelimit:{project_id}` from both the gRPC path (`ProcessTracesService::export` in `traces/grpc_service.rs`, threaded as `Option<Arc<IngestionRateLimiter>>` through `::new` since tonic has no actix-style middleware; exceeded → `Status::resource_exhausted`) and the HTTP path (`api/v1/traces.rs::process_traces`, injected as `web::Data<Option<Arc<IngestionRateLimiter>>>`, checked before payload decode; exceeded → 429) — so neither transport can bypass the other. Per-project overrides in cache (plain integers via `valkey-cli SET`, no app writer, take precedence over the env defaults): `ingestion_project_rate_limit:{project_id}` for N AND `ingestion_project_rate_limit_period:{project_id}` for the window seconds — unlike the SQL limiter, the period is also overridable; either key can be set independently, the other falls back to the global default. Only `POST /v1/traces` is limited — `traces/metadata`, `/v1/spans`, `/v1/browser-sessions` etc. are not.
- Posture is fail-open on Redis/cache errors everywhere (logged, request allowed), so a Redis blip can't black-hole ingestion or SQL.
- **Rollout gotcha:** the unit is requests (OTLP export batches) per window, not spans/bytes — pick `INGESTION_RATE_LIMIT` high enough for the largest legitimate SDK batch cadence, then clamp offenders down via the per-project cache key.

## Ad-hoc SQL Endpoint Guards (`/v1/sql/query`)

- Per-query ClickHouse settings (`max_execution_time`, `max_result_bytes`, `max_memory_usage`) are applied in `app-server/src/sql/ch.rs` via `.with_setting(...)`, env-tunable through `app-server/src/env/sql.rs` (`SQL_QUERY_*`). They are tamper-proof: the query-engine validator strips any inline `SETTINGS` clause from user SQL, so a client can't override the server-applied caps.
- `max_memory_usage` (OOM protection — the lever that actually kills CH, not bytes scanned) is gated by `SqlQuerySource` (`sql/mod.rs`), threaded `execute_sql_query` → `route_and_run_query` → `ch::query`. It's applied ONLY for `SqlQuerySource::Public` (the internet-facing `/v1/sql/query`, CLI `/v1/cli/sql/query`, and the MCP query tool); the trusted frontend route (`routes/sql.rs`) and internal callers (`datasets/service.rs`, `sql/queries.rs`) pass `Frontend` and run uncapped. Default `SQL_QUERY_MAX_MEMORY_USAGE=0` means unlimited, so self-hosters are unrestricted unless they opt in. When adding a new caller of `sql::execute_sql_query`, pick the source deliberately.
- Settings only apply on the CLOUD deployment path; HYBRID forwards the raw query to a remote data plane (`sql/data_plane.rs`) which runs its own CH and is not covered by these caps.

## OTLP Trace Ingestion (`/v1/traces`)

- The HTTP handler dispatches on `Content-Type`: `application/json` decodes via `crate::opentelemetry_json` (serde shadow types → prost types), anything else falls through to `prost::Message::decode` (HTTP+protobuf, the default for every existing SDK). The gRPC server is unchanged. See `app-server/src/api/v1/traces.rs:decode_export_trace_request`.
- `build.rs` regenerates `src/opentelemetry_proto/mod.rs` from scratch every build via `tonic_prost_build::configure().include_file("mod.rs")`. Anything added inside `src/opentelemetry_proto/` will be clobbered on the next `cargo build`. Hand-written modules that work against the OTel proto types must live outside that directory (e.g. `src/opentelemetry_json.rs` declared from `main.rs`).
- The JSON decoder accepts the spec quirks browser SDKs actually emit: hex *or* base64 IDs, decimal-stringified `fixed64` *or* raw numbers, enum *names* (`SPAN_KIND_INTERNAL`) *or* ordinals for `kind` / `status.code`, and `intValue` as either string or number. Don't tighten any of these without checking real client output.
- When navigating to an ingested trace in the UI, the `traceId`/`spanId` query params must be dashed UUIDs, not raw OTLP hex — the API routes validate them as GUIDs (400/500 otherwise). A 16-byte trace id maps 1:1 (`5abe098dfc22bf38d4094b20c056a7dd` → `5abe098d-fc22-bf38-d409-4b20c056a7dd`); an 8-byte span id is left-padded with zeros to 16 bytes (`d2c361d0ea548a38` → `00000000-0000-0000-d2c3-61d0ea548a38`).

## Payload-too-large (413) responses

- **Actix's default 413 bodies are plain text and differ per extractor — there is no JSON error envelope anywhere in app-server** (`routes/error.rs::error_response` is `.body(format!("{}", self))`). Untouched, a `web::Json` handler returns `JSON payload (N bytes) is larger than allowed (limit: M bytes).` while a `Bytes` handler (`POST /v1/traces`, `/v1/logs`) returns just `payload reached size limit`, which SDKs log verbatim. An `ErrorHandlers` handler for `StatusCode::PAYLOAD_TOO_LARGE` in `main.rs` replaces the body with the static `PAYLOAD_TOO_LARGE_MESSAGE` for every route. Keep it a constant — the request size and limit are deliberately NOT parsed out of the headers.
- **`JsonConfig::error_handler` is NOT the right hook for this.** It only covers `web::Json` extraction, so the `Bytes`-based OTLP ingestion routes (the ones that actually 413 in production) would keep actix's terse default. An `ErrorHandlers` handler keyed on the status code catches every extractor at once.
- The handler is global, so the message stays route-agnostic — `/v1/datasets/datapoints`, `/v1/labeling_queues/*` and the SQL routes all 413 with no span involved.
- To reproduce a 413 locally, start app-server with a small `HTTP_PAYLOAD_LIMIT` (e.g. `PORT=8000 HTTP_PAYLOAD_LIMIT=10000 cargo run`) and POST an oversized body. Note the gRPC ingestion path uses the separate, much larger `GRPC_PAYLOAD_LIMIT` (25 MB), which is why a payload can 413 over HTTP and succeed over gRPC.

## App-server self-tracing (`src/instrumentation/`)

- This is **OTEL self-tracing infrastructure** — the app-server tracing ITSELF, distinct from the `traces` module which ingests client spans. Annotate a function with `#[tracing::instrument(target = "lmnr::internal")]` and its OTEL span is ingested via an in-process exporter into a Laminar project, instead of threading a tracer/queue handle through every call site. Set attributes via `tracing_opentelemetry::OpenTelemetrySpanExt::set_attribute`; add `parent = None` to root a fresh internal trace.
- `setup_tracing_and_logging` runs TWO independent `tracing-opentelemetry` layers, each with its own `SdkTracerProvider`, so Sentry tracing and Laminar's internal self-tracing never share a trace_id or corrupt each other's span context (a single-provider "routing processor" design produces mixed trees with torn parent-child links). The two layers carry **disjoint per-layer filters** (`!is_internal` vs `is_internal`, where `is_internal` = `target` starts with `"lmnr::internal"`); each span is admitted by exactly one layer so the stock bridge layers never double-write `OtelData`. Do NOT add a third unfiltered `tracing_opentelemetry::layer()`.
- The **`fmt` (stderr) logger also carries `!is_internal`**, so internal-target events never print as application logs. This matters because attaching an `exception` event to an internal span is done by emitting an internal `tracing::error!` with an `error` field (`spans::record_error`) — without the filter every such event would spam stderr. Same rule as `sentry_layer`: anything `lmnr::internal` stays out of the app logger AND out of Sentry.
- **`RUST_LOG` (`env_filter`) MUST be a per-layer filter on the `fmt`/Sentry layers, NOT `.with(env_filter)` on the registry.** A registry-level filter is GLOBAL: any layer whose `enabled` returns `false` short-circuits the span/event for the ENTIRE stack, so a module-scoped `RUST_LOG` like `app_server=debug` would silently starve the internal export layer. The default `EnvFilter::new("info")` masks the bug.
- The **Sentry provider stays the global tracer provider** (`global::set_tracer_provider`) and owns `SentrySpanProcessor`. The **internal provider is deliberately never set global** — that plus the disjoint filter keeps internal spans out of Sentry and Sentry spans from parenting internal spans.
- **Suppressing a known-noisy error from Sentry (while keeping it at `error` in logs) goes through `sentry_before_send`** (`instrumentation/mod.rs`, wired as `before_send` in `main.rs`'s `sentry::init`): add the message substring to `SENTRY_SUPPRESSED_MESSAGES`. The hook checks both `event.message` and exception values (substring match). Do NOT downgrade the log level to hide an error from Sentry — that loses it from pod logs too. For provider capacity errors we CAN'T act on (Bedrock 503, Gemini flex 429/503), the opposite convention applies: log at `warn`/`debug` instead of `error` (`log_bedrock_api_error` in `llm/bedrock/mod.rs`, `log_gemini_api_error` in `llm/gemini/client.rs`) since those aren't errors worth alerting on at all.
- **`sentry_layer` must carry `.span_filter(|_| false)`.** `sentry::integrations::tracing::layer()`'s DEFAULT span filter captures every INFO/WARN/ERROR tracing span as a Sentry span directly, duplicating the OTEL bridge (Provider A + `SentrySpanProcessor`) — each span arrives in Sentry twice with slightly different durations (the layer-created one is finished at `on_close`, the OTEL one at provider export). The OTEL bridge is the single owner of Sentry span export; the sentry_layer exists only for ERROR events. `event_filter` and `span_filter` are independent knobs — configuring one does not disable the other's default.
- **Sentry span sampling is plain probabilistic sampling via each SDK's own `traces_sample_rate` knob (LAM-2070).** Sentry bills by span volume while we use it for errors + latency, so only a fraction of transactions is sent: `EXTERNAL_TRACING_SAMPLE_RATE`, defaulting to **0.2 on app-server** (`env/sentry_sampling.rs`, an `f32` `NumEnv` read through `NumEnv::clamp(0.0, 1.0)` to match `ClientOptions::traces_sample_rate`) and **0.5 on the frontend** (`sentry.server.config.ts`, inline `Number` parse + clamp). The two are SEPARATE settings with deliberately different defaults and no parsing-parity requirement. **Both sides must treat an empty/whitespace value as UNSET, not as a number.** App-server's `NumEnv` already trims-then-filters-empty, but on the frontend `Number("")` is `0`, not `NaN` — so a k8s ConfigMap key present with no value silently resolved to a 0.0 rate and disabled Sentry transactions entirely (the `Number.isFinite` guard passes 0 happily). The frontend therefore checks the trimmed string for emptiness BEFORE calling `Number`. An explicit `0` is still honoured, so sampling can be deliberately turned off. Sampling is per-TRANSACTION, which is what keeps each sampled trace internally complete — sampling individual spans would leave orphaned children and broken timings in the Sentry UI.
- **Sampling does NOT affect error reporting.** `traces_sample_rate` gates transaction/span envelopes only; `capture_message`/`capture_event` errors are governed by the separate `sample_rate` and still arrive at rate 0 (verified end-to-end against a local collector: rate 0 → 0/40 transactions but the error event delivered; 0.2 → 8/40; 1.0 → 40/40). So dialing the rate down trades latency-trace granularity, never error visibility.
- **A duration/status-aware variant was built and then REMOVED as over-engineering — don't rebuild it without a concrete ask.** It kept every errored or slow (>N s) transaction and sampled only the fast successful remainder. That needs a hook that sees the FINISHED transaction: `traces_sampler` runs at transaction start (no duration/status yet) and the Rust SDK has no `before_send_transaction`, so app-server needed a custom `Transport` wrapper filtering `EnvelopeItem::Transaction`, plus a `beforeSendTransaction` twin on the frontend and a shared `lib/sentry/sampling.ts`. Two gotchas if it ever returns: `Envelope::filter`'s closure needs an explicit `|item: &EnvelopeItem|` annotation (sentry-types 0.48.5 turned that bound into a sealed `EnvelopeFilter` trait, so inference picks a by-value param and breaks on a patch bump), and an UNSET status must NOT count as an error (the OTEL bridge maps both `Unset` and `Ok` to `SpanStatus::Ok`, so treating unset as an error matches nearly every transaction and silently disables sampling).
- **There is NO `frontend/instrumentation-client.ts`** — browser-side Sentry is deliberately not initialised. The file existed but was DEAD CODE in production: its whole body was gated on `process.env.LAMINAR_CLOUD === "true"`, and `LAMINAR_CLOUD` reaches client code only by being inlined at BUILD time via `next.config.ts`'s `env` block, which the `frontend/Dockerfile` builder stage never sets (it only passes `NEXT_PUBLIC_APP_VERSION` / `NEXT_DEPLOYMENT_ID` / `NEXT_PUBLIC_BASE_PATH`). So the gate was always false in the shipped image. It was removed in LAM-2070; if browser Sentry is ever wanted, the env var must become a build ARG in the Dockerfile (or a `NEXT_PUBLIC_*` var) or it will silently no-op again.
- The two trees are gated INDEPENDENTLY: the Sentry tree on `Feature::Tracing` (`SENTRY_DSN` + `ENABLE_TRACING`), the internal self-tracing tree on `Feature::InternalTracing` (`ENABLE_TRACING` only — no Sentry DSN required). The internal tree deliberately does NOT depend on Sentry. When internal tracing is disabled the internal provider isn't built and internal spans drop ⇒ zero behaviour change. Each internal span carries its own destination project id via the `lmnr.internal.project_id` attribute (`INTERNAL_PROJECT_ID_ATTR`); the exporter routes per span and a `None` project id makes the span a no-op.
- **The internal exporter is in-process, NOT an OTLP loopback** (`internal_exporter.rs`, `InProcessInternalExporter`). It maps the SDK's `SpanData` onto the proto `ExportTraceServiceRequest` and calls `push_spans_to_queue` directly — same ingest path OTLP/gRPC feeds, minus the network hop. So there's no internal project API key and no auth header.
- **Threading / deferred deps:** the batch span processor drives `SpanExporter::export` on its own non-tokio thread, so the exporter holds a tokio `Handle` and `block_on`s the async ingest on it. But `setup_tracing_and_logging` runs in `main.rs` BEFORE the queue/DB/cache exist, while the provider must be built there so the subscriber initialises once. The bridge is `SharedIngestDeps = Arc<OnceLock<IngestDeps>>`: `setup_tracing_and_logging` returns it alongside the provider and `main` calls `.set(...)` once those services exist (right after the `queue` binding). Until set, the exporter drops spans.
- `setup_tracing_and_logging` takes `(enable_sentry_tracing, enable_internal_tracing, &tokio::runtime::Handle)` and RETURNS `(Option<SdkTracerProvider>, SharedIngestDeps)`. The returned provider (the internal tracer) is `#[must_use]` and main must hold it (`let _internal_tracer_provider = ...`) for the process lifetime so the batch exporter keeps flushing — drop it and internal spans stop exporting. Main must also populate the returned `SharedIngestDeps`.
- **Self-ingestion guardrail:** NEVER add `target = "lmnr::internal"` to the ingest path (`traces/grpc_service.rs`, `traces/producer.rs`/`push_spans_to_queue`, `db/spans.rs`, the span consumer). An internal span emitted from inside `push_spans_to_queue` would re-enter it and recurse.
- `instrumentation/spans.rs` is the generic internal-span builder (shared `lmnr.span.*` / `gen_ai.*` / `signal.*` / association-prop conventions, `lmnr.span.input`/`output` JSON-stringified via `json_attr`, `ai.prompt.tools` as an OTEL string array via `tools_attr`). It keeps `#[allow(dead_code)]` because OSS producers (`traces/system_extraction`) consume only part of the surface; the rest is used by `signals`-gated enterprise producers in `lmnr-private`.
- Span-creation pattern for producers: root via `info_span!(target: "lmnr::internal", parent: None, "<literal name>")` (tracing macros require literal span names) wrapped with `InternalSpan::wrap(...).parent(...).project(...).span_path_root(...)`; child spans created inside `.instrument()`-ed futures use plain `info_span!(target: "lmnr::internal", "name")` — contextual parenting nests them automatically, do NOT pass an explicit `parent:`. Attach the error AFTER the instrumented future resolves (`spans::record_error(&span, e.to_string())`), and note that a `let result = async { ... }` block whose error type is only used via `e.to_string()` needs an explicit `Result<T, E>` annotation (E0282).

## OTel GenAI Semantic Convention Ingestion

- **Backend (app-server)** preserves the native OTel GenAI message shape end-to-end — `gen_ai.input.messages` / `gen_ai.output.messages` are deserialised from JSON string to `Value` but NOT reshaped into Laminar's `ChatMessage` struct. This keeps the original instrumentation payload lossless; the frontend owns rendering. Do NOT add a backend ChatMessage conversion here.
- The same pass-through carries **verbatim AI SDK v7 payloads**: `{role, content}` messages with dash-typed parts (`tool-call`/`tool-result`/`reasoning`), LanguageModel `file` parts, `providerOptions`/`providerMetadata`. In `parse_and_enrich_attributes` the GenAI block runs AFTER the legacy `gen_ai.prompt.{i}.*` / `ai.prompt.messages` handlers and overwrites their `self.input`/`self.output`, so when a span carries both vintages the verbatim attrs win. `normalize_aisdk_attributes` never synthesizes or rewrites `gen_ai.input/output.messages` (it only copies `{prefix}.prompt.messages` → `ai.prompt.messages`). Pinned by `test_verbatim_ai_sdk_genai_messages_pass_through` / `test_verbatim_genai_messages_take_precedence_over_ai_prompt_messages` / `test_normalize_aisdk_does_not_touch_verbatim_genai_messages` in `traces/spans.rs`. Do NOT remove the legacy handlers — historical spans keep those attribute shapes in ClickHouse indefinitely.
- `gen_ai.system_instructions` is prepended to the input messages as a synthetic `{role: "system", parts: [...]}` entry so the system prompt threads into the same message array. Bare-string arrays (`["Be helpful"]`) are preserved verbatim inside `parts` — the frontend parser handles both shapes. Helper: `prepend_system_instructions` in `spans.rs`.
- **Frontend parser** lives at `frontend/lib/spans/types/gen-ai.ts` (`parseGenAIMessages`). It runs in `processMessages` (`frontend/lib/spans/process-messages.ts`) right after the signals-gated Anthropic check and BEFORE the OpenAI/AI-SDK/LangChain/Gemini detectors (the loose OpenAI assistant schema would otherwise claim `{role, parts}` payloads and render them empty), and decodes the GenAI parts (`text|thinking|tool_call|tool_call_response|uri|blob`) into `ModelMessage[]` for the existing generic renderer.
- Span-type inference from `gen_ai.operation.name`: `chat|text_completion|embeddings|generate_content` → LLM, `execute_tool` → Tool, `invoke_agent` → Default.
- **pydantic_ai tool-span quirk**: pydantic_ai emits `execute_tool <name>` spans WITHOUT `gen_ai.operation.name`; only `gen_ai.tool.call.arguments` / `gen_ai.tool.call.result` are set. `span_type()` has a fallback that classifies a span as Tool when either of those attributes is present. Do not remove this fallback when adding other GenAI emitters.
- The `gen_ai.tool.call.*` → `self.input`/`self.output` block in `parse_and_enrich_attributes` is gated on `self.span_type == SpanType::Tool` (not just the raw attribute keys) so it cannot clobber LLM-span input/output if a spec-violating emitter mixes LLM message attrs with tool-call attrs on the same span. The gate still works for pydantic_ai because `span_type()` already infers Tool from the `gen_ai.tool.call.*` fallback before this runs.

## Static System Prompt Extraction (`traces/system_extraction`)

- The extraction agent: given N example system prompts from one template family, an LLM tool-calling loop produces an ordered list of removal regexes that collapse all examples to the same static skeleton. Agent system prompt is `instructions.md` in the module, embedded via `include_str!`. (The span-ingest pipeline that drives it is documented under "Static System-Prompt Extraction" below.)
- Runnable on demand via `POST /api/v1/projects/{project_id}/system-extraction` (`routes/system_extraction.rs`, ungated — 503s when `LlmClient` is `None`). Body (camelCase): `examples`, optional `provider`/`modelSize`/`includeDiff`, plus `internalProjectId` (destination project for internal-tracing spans; omit = tracing off) and `parentTraceparent` (W3C, re-roots the run under an external eval's span).
- Internally traced via `instrumentation/spans.rs`: root `system_extraction` span → per-temperature `episode` spans → per-step `llm_call` LLM spans (input/tools/model/step pre-call; model_version/usage/output post-call) → `tool_call` Tool spans. Routing threads through `ExtractionTracing { project_id, parent }`; `project_id: None` (the `Default`) makes every span unroutable so the exporter drops them — tracing is effectively off with zero overhead concerns.
- The `regex` tool semantics (`tool.rs::run_regex_tool`) are a contract with the instruction doc: patterns run sequentially with flags `gm`, every match deleted, output feeds the next pattern. Uses `fancy-regex` because the model is instructed lookbehind works — don't swap to the `regex` crate. Diffs (`removed`, the Example-1-vs-2 user-message diff) use the `similar` crate.
- Retry ladder `[0, 0.4, 0.7]` re-runs the whole episode at the next temperature when the final answer parses to an empty regex list OR the episode errors (provider failure / per-LLM-call 180s timeout — errors are logged and swallowed, never propagated, so `extract_static_regexes` is infallible and returns `ExtractionResult { regexes, tool_calls }`); `max_steps` 12 caps LLM calls per episode.
- **Tool-verified fallback**: the loop tracks the LATEST tool-call input whose result had `isValid && isResultInAllIdenticalOutput`; if the model's parsed final answer doesn't collapse the shown examples (models "improve" patterns after their last test or typo them, e.g. `(??<=`), the tool-verified list is used instead. Keep this — trust the tool over the transcript.
- Tool output deliberately OMITS `residuals` / `residualLengths` / `offset` — echoing residuals blows the input budget, and `residualDivergences` `{a, b}` slices (80 chars before / 140 after the first differing byte, deduplicated) carry the only part that matters. Don't re-add them. `sharedRemoved` is substring-based (48-gram intersection, maximal runs, whitespace-collapsed, first 20 chunks), NOT line-based, so it fires on footers swept at different offsets per example.
- The `instructions.md` prompt, `build_user_message` hardening paragraph, and the `regex` tool description are VERBATIM from the reference spec (a ~3.5KB prompt outscored a 12KB one) — don't reword them for style.

## Billing and Tier Allowances

- **"Starter" is the DISPLAY name of the internal `hobby` tier.** The lowercase `hobby` key is structural and must NEVER be renamed: the TS `Tier` union / `TIERS` / `TIER_CONFIG` / `TIER_USAGE_HINTS` record keys, the Rust `WorkspaceTierName::Hobby` enum variant, Stripe lookup keys (`hobby_monthly_*`), webhook `["hobby","pro"]` comparisons, and `HOBBY_*` constants all stay as-is. Only user-facing strings say "Starter". Production `subscription_tiers.name` rows may carry EITHER "Hobby" (legacy) or "Starter" — every raw-DB-name consumption site normalizes both to the `hobby` key: `normalizeTier` + `tierDisplayName` in `frontend/lib/billing/tiers.ts`, `getTierUsageHint` in `components/workspace/usage/index.tsx`, `workspaceTierKey` in `components/workspace/billing/index.tsx`, `normalizeTierName` in `lib/actions/checkout/webhook.ts`, `getSubscriptionDetails`/`switchTier` in `lib/actions/checkout/index.ts` (the billing tab's `subscription.currentTier` comes from `getSubscriptionDetails`, so this site keeps the subscription arm of `currentTierKey` on the `hobby` key), `retentionCutoff` in `lib/billing/retention.ts`, and `getHasClusteringAccess` in `lib/features/clustering.ts`. The last two map/check `"starter"` INLINE rather than via `normalizeTier`, which would fold unknown tiers like self-hosted `unlimited` to `free` and impose a 7-day retention cutoff / clustering block on them. When rendering a raw `tierName` from the DB, route it through `tierDisplayName` (unknown names like `unlimited` pass through unchanged). The rename is frontend-display-only; if the `subscription_tiers.name` row is ever renamed to "Starter", Rust `WorkspaceTierName::from_str` in `app-server/src/db/projects.rs` must learn the `"starter"` alias or the tier falls to `Other`.
- **Signal cost is metered from three raw token counts, not a single number.** Per run we store `input_tokens`, `cache_read_tokens`, and `output_tokens` on `signal_runs` (CH); cost in micro-USD is derived at read time (`signal_token_cost_micro_usd` in `app-server/src/utils/mod.rs`, mirrored by `signalTokenCostMicroUsd` in `frontend/lib/billing/tiers.ts`) so a rate change re-prices history. **`cache_read_tokens` is a SUBSET of `input_tokens`** (the provider `prompt_token_count` already includes cached-read tokens across Bedrock/OpenAI/Gemini), so the cost fn bills `(input - cache_read)` at the input rate plus `cache_read` at a discounted cache rate — never additive, never double-charged. Rates are env-overridable: `SIGNAL_INPUT_TOKEN_PRICE_PER_MILLION` (default 0.5), `SIGNAL_OUTPUT_TOKEN_PRICE_PER_MILLION` (default 3.0), `SIGNAL_CACHE_READ_TOKEN_PRICE_PER_MILLION` (default 0.05 ≈ 0.1× input). The accumulator threads `cache_read_tokens` through the whole pipeline (`SignalMessage` → `SignalRun` → `response_processor` accumulate/rollback → `finalize_runs` metering → CH); the Failed-arm `saturating_sub` rollback covers all three counts so a re-enqueued retry doesn't double-count.
- **`signalTokenCostMicroUsd` only honours the `SIGNAL_*_TOKEN_PRICE_PER_MILLION` overrides server-side.** Those envs are not `NEXT_PUBLIC_`, so in the client bundle they resolve to `undefined` and `resolveRate` silently falls back to published defaults — a browser-side call would diverge from metered usage whenever an operator overrides a rate. So price runs server-side: `getSignalRuns` (`frontend/lib/actions/signal-runs/index.ts`) computes `costMicroUsd` per row and the runs-table Cost column (`components/signal/runs-table/columns.tsx`) only formats that precomputed value. Don't move the cost computation back into a client component / cell.
- **Workspace signal usage cache is THREE raw-token keys, not one cost key** (`workspace_signal_runs_usage_{input_tokens,cache_read_tokens,output_tokens}_v2`). Defined as Rust constants in `app-server/src/cache/keys.rs` and mirrored in `frontend/lib/cache.ts` — they MUST stay in sync (cross-service contract). Cost is derived at compare/read time from the three keys (`get_workspace_signal_tokens_cached`, `getWorkspaceUsage`, `checkSignalRunsLimit`), so a miss on ANY one key reseeds all three from ClickHouse.
- Tier included signal allowances (in micro-USD — signals are billed by token cost, never by step count) are pinned in FOUR places that MUST stay in sync: frontend `TIER_CONFIG.includedSignalCostMicroUsd` in `frontend/lib/actions/checkout/types.ts`, `TIERS[tier].includedSignalCostUsd` in `frontend/lib/billing/tiers.ts` (USD display form of the same number), Rust `WorkspaceTierName::included_signal_cost_micro_usd()` in `app-server/src/db/projects.rs`, and the DB column `subscription_tiers.signal_cost_included_micro_usd` (seeded $5 Free / $15 Hobby / $50 Pro by migration `0095`; the limit checks read it via the `db/projects.rs` join and `frontend/lib/actions/usage/limits.ts`). The backend uses these to detect whether a triggered usage warning corresponds to the tier's free allowance vs. a user-configured custom threshold — this drives tier-specific copy in the usage-warning email ("you've exhausted your included Hobby allowance, from now on usage is billed pay-as-you-go").
- **Pro signal token rates are discounted ($0.4 / 1M input, $2.5 / 1M output vs. the standard $0.5 / $3; cache-read $0.05 on both), and the metering path is tier-aware** so Pro accumulated cost matches what it's billed. `signal_token_cost_micro_usd` (`app-server/src/utils/mod.rs`) and `signalTokenCostMicroUsd` (`frontend/lib/billing/tiers.ts`) BOTH take a tier argument and pick the `PRO_SIGNAL_*_TOKEN_PRICE_PER_MILLION` envs when the workspace is Pro, else the standard `SIGNAL_*` envs. Defaults are pinned in `app-server/src/env/private/signals.rs` and the `frontend/lib/billing/tiers.ts` constants — keep the two in sync. Metering Pro at the standard rate over-counts cost and trips hard limits / soft warnings before the workspace reaches its dollar budget. Every caller must thread the workspace tier: app-server reads `project_info.tier_name`; frontend resolves it via `normalizeTier(...)` from a project→workspace→`subscription_tiers` join (`getWorkspaceUsage`, `checkSignalRunsLimit`, `getSignalRuns`). The `signalInputRate(tier)` / `signalOutputRate(tier)` display helpers feed the pricing calculator + `formatSignalsOverage*` and use the same per-tier numbers. The workspace usage-summary overage copy (`getUsageDescription` in `frontend/components/workspace/usage/index.tsx`) is also a consumer — it must thread `normalizeTier(tierName)` into `signalInputRate`/`signalOutputRate` rather than hardcoding the standard $0.5/$3. The per-GB data overage shown there comes from `TIER_USAGE_HINTS[tier].overageDataPrice` (Hobby $2, Pro $1.50), gated so it only renders for non-FREE tiers that have a `TIER_USAGE_HINTS` entry — `unlimited` (self-hosted / staging paid) has none, so hard-limit rows + overage copy never show there.
- Stripe invoice line items expose their lookup key in two places: legacy `line.price.lookup_key` and the newer `line.pricing.price_details.price.lookup_key`. Email-subject/body rendering must check BOTH before falling back to `line.description` or a generic "Subscription charge" string, otherwise the subject line silently becomes `Laminar: Payment for  is received.` (trailing empty label).
- Transactional-email "billing portal" CTAs link to `/checkout/portal?workspaceId=...` (`frontend/app/checkout/portal/page.tsx`), which mints a Stripe billing portal session via `getPaymentMethodPortalUrl` and 302s straight to Stripe. Unauthenticated clicks bounce through `/sign-in?callbackUrl=...`. `getPaymentMethodPortalUrl` requires owner/admin role on the workspace — non-admin recipients hit the catch and get redirected to the workspace billing tab as a graceful fallback. Don't link emails directly to the workspace settings page; that path requires the user to manually click "Billing portal" again.

## Workspace Usage Warnings vs Hard Limits

- Usage enforcement lives in two separate tables, both edited via Stripe webhook when a subscription is created or a tier is switched (`frontend/lib/actions/checkout/webhook.ts`):
  - `workspace_usage_warnings` — soft limits that fire a notification once per billing cycle. Checked in `check_soft_limits` in `app-server/src/utils/limits.rs`.
  - `workspace_usage_limits` — hard caps read by `get_project_and_workspace_billing_info` as `custom_bytes_limit` / `custom_signal_steps_limit` and enforced in `get_effective_*_limit` (app-server) and `checkSignalRunsLimit` (frontend). Only paid-tier custom limits + the Hobby default have rows here; free tier enforces the tier allowance with no row.
  - `workspace_hard_limit_notifications` — per-`(workspace_id, usage_item)` `last_notified_at` dedup for hard-limit emails (separate table so free-tier workspaces, which have no `workspace_usage_limits` row, can still dedup once per billing cycle). Stamped by `check_notify_hard_limit`.
- On tier transition into **Hobby**, we insert a soft warning row at the Hobby included allowance (15USD) AND a hard-limit row for `signal_cost` at `HOBBY_DEFAULT_HARD_LIMIT_SIGNAL_COST_MICRO_USD` (100,000,000). The hard cap is intentionally set to the same threshold as the overage email warning so ingestion is blocked at the same moment the user gets nudged. Pro and Free do NOT get a default hard limit.
- Hobby also gets two extra **overage warnings** above the included allowance ($100 signal cost / `HOBBY_OVERAGE_WARNING_SIGNAL_COST_MICRO_USD`, 40 GiB bytes / `HOBBY_OVERAGE_WARNING_BYTES`) so users accumulating a large overage bill are nudged before it grows further. These are Hobby-only rows; Pro does not get them. On transition OUT of Hobby they are cleared (matching exact value so user-adjusted thresholds are preserved) via `clearHobbyOverageWarnings`, which — like the hard-limit cleanup — runs on every transition including Hobby → Free.
- On tier transition OUT of Hobby, the default Hobby hard limit is deleted **only if it still equals a known Hobby default** — `HOBBY_DEFAULT_HARD_LIMIT_SIGNAL_COST_MICRO_USD` (100,000,000 micro-USD / $100). A user-set custom value is preserved across upgrades/downgrades. Same pattern for warnings.
- The hard-limit cleanup runs on **every** recognized tier transition — including Hobby → Free on cancellation; leaving the Hobby limit in place there would silently re-apply the Hobby cap the next time the workspace upgrades to any paid tier. Warnings, in contrast, are only written when the new tier is paid (Hobby/Pro) since Free has no warnings to carry.
- After inserting or deleting a `workspace_usage_limits` row, you MUST invalidate the per-project cache via `invalidateProjectCacheForWorkspace(workspaceId)` — the app-server caches `ProjectWithWorkspaceBillingInfo` keyed by project id and will otherwise keep enforcing stale limits until TTL.
- **Both soft warnings AND hard limits email the workspace owners.** Soft = `check_soft_limits` → `NotificationKind::UsageWarning`; hard = `check_notify_hard_limit` → `NotificationKind::UsageHardLimit`. Soft warnings fire only from the usage-update path (`update_workspace_bytes_ingested` / `update_workspace_signal_tokens` in `utils/limits.rs`), right after the cache total is bumped. Hard limits fire from BOTH the update path AND the enforcement gates (`get_workspace_bytes_limit_exceeded` / `get_workspace_signal_runs_limit_exceeded`): organic usage growth crosses the cap during an update, but a custom limit lowered BELOW current usage produces no crossing batch — the next ingestion batch is blocked at the API gate (403 `Forbidden` for bytes, silent skip for signals) and never re-enters the update path. So `check_notify_hard_limit` is also called from the enforcement read functions; the per-cycle DB dedup below makes the double call-site idempotent. The hard-limit email tells owners that data ingestion / signal runs are now stopped until the billing cycle resets.
- **Hard-limit notifications dedup via a dedicated DB table, mirroring soft warnings 1-to-1 — once per billing cycle.** `check_notify_hard_limit` reads `workspace_hard_limit_notifications.last_notified_at` for `(workspace_id, usage_item)`, skips when it is `>= current_billing_period_start(reset_time)`, and after a successful enqueue upserts the row to `NOW()` (`usage_warnings::{get_hard_limit_last_notified_at, mark_hard_limit_as_notified}`). It must be a SEPARATE table from `workspace_usage_limits`, not a column on it: free-tier workspaces enforce the tier's included allowance with NO limit row yet still need dedup, and adding a phantom limit row would surface as a fake "custom limit" in the settings UI and the billing query. `check_notify_hard_limit` takes `reset_time` (passed as `project_info.reset_time` at all four call sites) exactly like `check_soft_limits`. Because the enforcement gates run on EVERY blocked request, the Postgres read is fronted by a short cache (`HARD_LIMIT_NOTIFIED_CACHE_KEY:{workspace_id}:{usage_item}`, 5-min TTL): only the SUPPRESSING state (a `last_notified_at` within the current cycle) is cached — never "not notified", which would widen the duplicate-enqueue race to the TTL. The frontend's `deleteHardLimitNotification` evicts this cache key (shared Redis) right after deleting the DB dedup row, so a raised/removed limit can re-notify immediately; the short TTL is only a backstop for a failed eviction.
- **The dedup row has no FK cascade from `workspace_usage_limits` (free tiers have no limit row), so the frontend cleans it up explicitly whenever the underlying hard limit changes** (`lib/actions/usage/utils.ts`: `deleteHardLimitNotification`, `clearHardLimitNotificationOnIncrease`). Rules: removing a limit → delete the dedup row (a re-created limit must start fresh); lowering a limit → keep the row (the prior breach still stands); raising a limit → delete only if already notified this cycle AND the new limit sits above current usage, i.e. the workspace is back under its higher cap so a future breach is a genuinely new event. Current usage MUST come from `getWorkspaceUsage` (cache→ClickHouse, returns `totalSignalCostMicroUsd` matching the micro-USD `signal_cost` limit unit + `totalBytesIngested`), NOT the `workspace_usage` table — those columns are only written on checkout/reset, aren't synced with the enforcement caches, and `signal_cost` there isn't micro-USD. Wired from BOTH the user path (`custom-usage-limits.ts` `setUsageLimit`/`removeUsageLimit` — `setUsageLimit` reads the prior `limit_value` before its upsert to tell raise from reduction) AND the automatic path (`checkout/webhook.ts` `upsertDefaultTierUsageLimits` — both the Hobby-default delete on transition-out and the `.returning()`-guarded default insert on transition-in drop the `signal_cost` dedup row).
- `NotificationKind::UsageHardLimit` and `NotificationDefinitionType::UsageHardLimit` route targets through the SAME owner-email fan-out arm as `UsageWarning` in `notifications/mod.rs::fetch_targets`. Both also acquire a handler-side race-guard lock in `NotificationHandler::handle` (`usage_send_lock_key`): warnings key on `definition_id` (the warning row); hard limits share `definition_id` (= workspace_id) across usage items, so they key on `HARD_LIMIT_SEND_LOCK_KEY:{workspace_id}:{usage_item}` to avoid a bytes notification suppressing a concurrent signal-cost one. The lock is a 5-min race guard only; the durable per-cycle dedup is the DB `last_notified_at` above. On total fan-out failure the lock is freed with `release_lock` (NOT `remove`: the in-memory cache keeps locks in a separate map).
- **Warning thresholds are absolute totals measured from zero, NOT "on top of" the included allowance.** A `signal_cost` warning set to the tier's included allowance fires when that allowance is exhausted (i.e. when billable overage begins), not after spending that much again. `check_soft_limits` (`app-server/src/utils/limits.rs`) flags the case where the fired threshold exactly equals the tier's included allowance (`at_tier_included_allowance = tier_included == Some(limit_value)`) and whether overage is billable (`overage_billable` = Hobby/Pro), and threads both into the `UsageWarning` notification so the email can say "from now on, usage is billable" (`render_usage_warning_email` in `notifications/email.rs`). The UI copy in `frontend/components/workspace/usage/warnings/index.tsx` must keep describing thresholds as absolute totals counting the included allowance.
- **The Warnings + Hard-limits sections (`frontend/components/workspace/usage/{warnings,limits}`) only render for paid tiers AND workspace owners** (`isOwner && tierName !== FREE` in `usage/index.tsx`). To verify them in staging (where only `Free` / `unlimited` `subscription_tiers` rows exist), temporarily insert a `Hobby` row and point the workspace's `tier_id` at it, then revert — there is no billing tab to upgrade through (the `SUBSCRIPTION` feature flag / Stripe is not wired in staging).

## AI Features Model Setup

- All frontend AI features (chat-with-trace, SQL generation, span previews, session extraction regex, debugger-session naming) go through `getLanguageModel(tier)` in `frontend/lib/ai/model.ts`. Tiers are `small` / `medium` / `large` — never add new tier names without updating every call site.
- SQL "Ask AI" generation modes (`GenerationMode` in `frontend/lib/actions/sql/types.ts`: `query` / `eval-expression` / `trace-expression` / `dataset-expression`) are coupled across THREE places that must stay in sync: the `GenerationMode` type, `MODE_CONFIGS` in `frontend/lib/actions/sql/prompts.ts`, AND the `mode` zod enum in `frontend/lib/actions/sql/generate.ts`. The generate action's enum is the validation gate — a mode missing there throws `Invalid option: ... at mode` at request time even though the type and prompt config accept it. Each table's columns menu picks its mode (`traces-columns-menu` → `trace-expression`, eval → `eval-expression`, dataset → `dataset-expression` over the `dataset_datapoints` table).
- In OSS, these env vars are read by the frontend only (chat-with-trace / SQL-with-AI). Signals — which also reuses these vars — is not an OSS feature; it ships in `lmnr-private`. Don't document Signals as an OSS feature in the OSS README or docker-compose files.
- Provider selection: `LLM_PROVIDER` (=`openai` | `gemini` | `bedrock`) is the single switch. `openai` and `gemini` use `LLM_API_KEY` (+ optional `LLM_BASE_URL`; `openai` is OpenAI-compatible and works with LiteLLM proxy / OpenRouter / vLLM). `bedrock` uses AWS credentials (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_REGION`) instead of `LLM_API_KEY`. `LLM_MODEL_SMALL` / `LLM_MODEL_MEDIUM` / `LLM_MODEL_LARGE` are optional overrides; each provider has hard-coded defaults in `DEFAULT_MODELS`. Mirror the app-server's provider matching in `app-server/src/features/mod.rs` / `llm/mod.rs` when extending.
- `Feature.SIGNALS` requires `SIGNALS_ENABLED=true` AND `isAiProviderConfigured()`. `Feature.BATCH_SIGNALS` is currently disabled via the feature flag (`return false`) until the batch path is re-enabled; when re-enabling, gate on `LLM_PROVIDER === "gemini"` since the backend batch API is Gemini-specific.
- The Rust OpenAI client (`app-server/src/llm/openai/`, gated behind the `signals` feature — `allow(dead_code)` in OSS) is the path Signals hits. `provider_request_to_openai_body` (`conversions.rs`) must NOT forward `reasoning_effort` when **function tools are present**: gpt-5.x reasoning models 400 on `/v1/chat/completions` with "Function tools with reasoning_effort are not supported … use /v1/responses instead" — this fires on OpenAI direct AND on some OpenAI-compatible gateways (LiteLLM/OpenRouter) that forward to OpenAI, so endpoint-sniffing is unreliable. The guard is simply `if !has_tools` — forward `reasoning_effort` only when no tools are present, regardless of endpoint.
- The `signals` feature does NOT compile standalone in the OSS `lmnr` repo — it pulls in clustering worker variants (`BatchWorkerType::ClusteringBatching`, `WorkerType::Clustering`) that live in `lmnr-private`, so `cargo test --features signals` fails with E0599 in `main.rs`. Run `llm/openai` tests under default features (`cargo test --bin app-server llm::openai::conversions`); the test modules are not feature-gated.
- **Effort naming differs per provider for `ProviderThinkingLevel::XHigh`:** OpenAI's `reasoning_effort` tier above `high` is `"xhigh"`, but Bedrock's adaptive-thinking `output_config.effort` scale tops out at `"max"` (Anthropic naming; `"xhigh"` is a ValidationException, and `"max"` is Opus 4.6+-only). Gemini has no tier above HIGH — its `ThinkingLevel` accepts the provider enum's `X_HIGH` via a serde alias and collapses it to HIGH. Don't unify these strings across providers.

## Vercel AI SDK (v7)

- The frontend is on `ai` v7 (`@ai-sdk/*` providers at 4.x, `@ai-sdk/react` 4.x, `@ai-sdk/amazon-bedrock` 5.x). Playground chat and all server-side AI features go through it.
- **`LanguageModelUsage` is nested in v7** (was flat in v5). Shape: `{ inputTokens, inputTokenDetails: { noCacheTokens, cacheReadTokens, cacheWriteTokens }, outputTokens, outputTokenDetails: { textTokens, reasoningTokens }, totalTokens }`. Cached-input and reasoning tokens live UNDER `inputTokenDetails`/`outputTokenDetails` — there is no top-level `cachedInputTokens`/`reasoningTokens`. Any literal usage object (store initial state, fallbacks) must use this nested shape or it won't type-check.
- **`GenerateTextResult` takes THREE generics in v7**: `GenerateTextResult<TOOLS extends ToolSet, RUNTIME_CONTEXT extends Context, OUTPUT extends Output>`. We use `GenerateTextResult<ToolSet, Record<string, never>, never>`. `Context` is NOT re-exported from `ai` (it lives in `@ai-sdk/provider-utils`); use `Record<string, never>` for the runtime-context slot rather than importing it.
- `GenerateTextResult` has both `usage` and a deprecated `totalUsage` (both `LanguageModelUsage`). Prefer `result.usage` for display; `totalUsage` is only kept where the struct requires it.
- `result.reasoning` is `Array<ReasoningOutput | ReasoningFileOutput>` — `ReasoningFileOutput` has no `.text`, so guard with `("text" in r ? r.text : "")` before reading it.
- **Span attributes use v7 usage keys**: `result.usage.inputTokens` / `.outputTokens`, NOT v4's `.promptTokens` / `.completionTokens` (which are now `undefined`). `SpanData.result` is typed `any` in `lib/actions/chat/utils.ts`, so wrong keys silently emit `undefined` instead of failing to compile — verify against the nested shape.
- Telemetry is registered globally once via `registerTelemetry(new LaminarAiSdkTelemetry())` (`registerTelemetry` from `ai`, `LaminarAiSdkTelemetry` from `@lmnr-ai/lmnr`), called in `instrumentation.ts` right after `Laminar.initialize()`. With global telemetry registered, per-call `experimental_telemetry` / `tracer` options are NOT needed — `generateText`/`generateObject` calls are traced automatically. Do not add `experimental_telemetry: { isEnabled: true }` or a per-call `tracer: getTracer()` to call sites.
- `generateText` / `generateObject` use `maxOutputTokens` (not `maxTokens`) for the output cap; our form field is still named `maxTokens` and is mapped at the call site.
- The playground `ToolResultPart["output"]` shape is defined locally in `lib/playground/types.ts` (carries a `media` content variant), NOT imported from `ai` — v7's `ai` `ToolResultPart` is now generic over `ToolSet` and its `output` no longer matches the form's shape, so import the local type in `message-parts.tsx`.
- **Span-view rendering of native AI-SDK v7 prompts** (`lib/spans/types/ai-sdk.ts`, `parseAiSdkMessages`). The detector handles BOTH vintages the SDK has stored: (a) verbatim LanguageModel-level payloads from `gen_ai.input.messages` / `gen_ai.output.messages` — dash-typed parts (`tool-call`, `tool-result`, `reasoning`), `file` parts with top-level `data|url` + `mediaType`, `providerOptions`/`providerMetadata` intact; (b) the legacy server-reshaped `ai.prompt.messages` shape — snake_case `tool_call` parts, JSON-stringified assistant content, and tool results stored as `{type:"text"}` parts inside `role:"tool"` messages (historical ClickHouse rows keep this shape forever). It runs in `processMessages` BEFORE the OpenAI detectors (the loose OpenAI schemas would otherwise claim verbatim payloads and drop `reasoning` parts), gated by `hasAiSdkDiscriminator`: a message-level `providerOptions`/`providerMetadata`, a distinctive part type, or a LanguageModel `file` part (top-level `data|url` + string `mediaType` — OpenAI nests its file payload under a `file` key, so it never matches). Plain `[{role, content:"str"}]` chats are NOT claimed and fall through to OpenAI/generic. `parseAiSdkMessages` routes to the `type:"generic"` renderer; `matchAiSdkMessages` also drives the playground branch in `convertSpanToPlayground` (`lib/spans/utils.ts`). Detection ordering is pinned by `tests/test-process-messages-detection.test.ts`, including the `{role, parts}` (GenAI) vs `{role, content}` (AI SDK) mutual non-claim.
- **Do not add v7 part types to `convertToMessages`'s `processContentPart`** to fix this — that helper is shared with the playground; the span-view fix belongs in the dedicated `ai-sdk.ts` detector, which routes to the `type: "generic"` renderer (`components/traces/span-view/generic-parts.tsx`) that already handles `reasoning`/`tool-call`/`tool-result`.
- **The generic renderer's `default` switch case renders a labeled JSON block, not `undefined`.** v7 broadened `ModelMessage` with parts that have no dedicated UI (`custom`, `reasoning-file`, `tool-approval-request`, `tool-approval-response`); `parseAiSdkMessages` passes them through verbatim and `generic-parts.tsx` surfaces them as JSON so nothing is silently dropped. Add a dedicated `case` only when a part type warrants bespoke UI.

## Signals and Alerts

- Alerts reference signals via `alerts.source_id`. There is NO FK constraint from `source_id` to `signals.id` because `source_id` may reference other entity types in the future. When deleting signals, associated alerts must be deleted in application code within the same transaction (see `deleteSignal`/`deleteSignals` in `frontend/lib/actions/signals/index.ts`).
- The Signals sidebar item is behind a feature flag (`Feature.SIGNALS`) which requires `SIGNALS_ENABLED=true` AND a configured AI provider (`LLM_PROVIDER` set to `openai`/`gemini`/`bedrock` with matching credentials). See "AI Features Model Setup" above.
- Alert metadata is stored as JSONB in `alerts.metadata`. For `SIGNAL_EVENT` alerts, it contains `{severity: 0|1|2}` (info/warning/critical). The Rust backend reads this in `postprocess.rs` to filter events by severity threshold, defaulting to CRITICAL (2) when metadata is absent (historical alerts default to the most restrictive level). The frontend edit form also defaults to CRITICAL for alerts without metadata.
- Creating a signal auto-creates a CRITICAL-severity alert and subscribes all workspace member emails as alert targets.
- **`db/utils.rs::evaluate_array_contains_filter` is PURE SET SEMANTICS: `Eq` = contains, `Ne` = does not contain, and an EMPTY array legitimately satisfies `Ne`.** "State unknown / read failed" must be resolved by the CALLER before calling — an earlier version rejected an empty array under both operators to make one caller fail closed, which silently dropped every legitimate "field does not contain X" alert filter. The one guard that belongs here is on the TARGET (trimmed; blank rejects both operators), because the shared frontend `FilterSchema` accepts a whitespace-only value (`z.string().min(1)`) and `!= " "` would otherwise match every row. Contract pinned by tests in the same file — note they are `#[cfg(test)]`, NOT gated on the `signals` feature, since that feature doesn't compile in OSS and would make them dead here.
- **Signal FILTER columns are `total_token_count` / `status` / `span_names`, and `span_names` (plural, filter) is a DIFFERENT column from `span_name` (singular, trigger)** — the trigger matches only the firing span batch, the filter asks whether the name appears anywhere in the trace. The filter row renders word operators ("include" / "do not include") via a display-only override (`SPAN_NAMES_OPERATOR_LABELS` + `getFilterOperations` in `components/signals/trigger-filter-field.tsx`); `=`/`!=` read as a claim about one span and are actively misleading on a set. Persisted operators stay `eq`/`ne`, so no migration. Do NOT relabel the shared `OperatorLabelMap` — every table filter in the app renders from it. Evaluation itself is enterprise-only (see "Signal Triggers").
- New-cluster notifications render as a per-alert DIGEST: `NotificationKind::NewCluster` carries enrichment fields (`first_seen`/`last_seen: Option<String>`, `severity_counts: [u64; 3]`, `example_events: Vec<ClusterExampleEvent>`), all `#[serde(default)]` so already-queued legacy messages deserialize. The email/Slack renderers (`render_new_cluster_email` / `format_new_cluster_blocks`) take `&[&NotificationKind]` and render every `NewCluster` in a message's `notifications` vec as one digest. Slack caps at 50 blocks (2 per cluster), so `format_new_cluster_blocks` renders at most `MAX_CLUSTERS_PER_DIGEST` (20) clusters + an "…and N more" overflow section; per-cluster text goes through the 3000-char section budget. `Option<String>` fields are `None` when absent (never empty-string sentinels) — renderers gate with `if let Some`. OSS ships the enum and the renderers; the CH stat/sample helpers and the enriching producer are not part of OSS.
- The `NEW_CLUSTER` alert type and the `skipSimilar` metadata option depend on the clustering service. Gate both the auto-creation of `NEW_CLUSTER` alerts in `createSignal` and UI affordances in `manage-alert-sheet.tsx` behind `isFeatureEnabled(Feature.CLUSTERING)` / `useFeatureFlags()[Feature.CLUSTERING]`. When clustering is disabled, force `skipSimilar: false` on submit so the backend doesn't silently drop notifications.
- **Activate/deactivate.** Both signals and alerts carry an `enabled` flag in their JSONB metadata; **absence means enabled** (historical rows default to active). Signal sampling lives in the SAME `signals.metadata` jsonb as `metadata.sampleRate`. There is NO `enabled` boolean column on either table — it's purely a metadata key, only persisted when `false` (the UI omits it when active to keep metadata clean). Rust side: `SignalMetadata` (`db/signals.rs`) and `AlertMetadata` (`db/alert_targets.rs`) each expose an `enabled()` helper returning `self.enabled.unwrap_or(true)`. Disabled **signals** are skipped in `processor_hook.rs` (gate `!trigger.signal.metadata.enabled()` before evaluating triggers, and exclude them from the `any_has_sampling` sampling-factor fetch); disabled **alerts** are skipped in `postprocess.rs` (SIGNAL_EVENT loop) and `clustering/private/handler.rs` (both `notify_new_l0_clusters` skip-similar filter and the NEW_CLUSTER notification loop). Toggling a signal's enabled state MUST invalidate the `signal_triggers:{projectId}` cache (`updateSignal` already does); alert enabled needs no Rust cache invalidation because `get_alerts_for_signal` reads `alerts.metadata` fresh (only filter *rules* are cached, per-`(projectId, alertId)`). Frontend: the alert metadata Zod validators in `lib/actions/alerts/index.ts` must allow `enabled` — note `NewClusterMetadataSchema` is `.strict()`, so `enabled` had to be added there explicitly or NEW_CLUSTER toggles 400.
- In `manage-alert-sheet.tsx`, the `severities` Controller uses `shouldUnregister`. When its render condition (`selectedSignal && alertType === SIGNAL_EVENT`) flips to false — e.g. after a successful save resets `selectedSignal` — react-hook-form removes the field from form state and `watch("severities")` returns `undefined`. Any `useMemo` that reads `watch`ed values must null-check them (don't call `.length`/`.map` directly) or it will throw synchronously and break the whole page into the error boundary.
- Alert Slack targets persist a channel `id` in `alertTargets.channelId` and the display name in `alertTargets.channelName`. Both columns are populated for every row written by the form, so `resetFormFromSignals` in `manage-alert-sheet.tsx` filters to rows where both are present and uses them directly.
- `getSlackChannels` in `frontend/lib/actions/slack/index.ts` paginates through Slack `conversations.list` via `response_metadata.next_cursor` (limit=500/page) and returns `{ channels, rateLimited }`. On rate-limit (HTTP 429 OR a 200 OK with `{ok:false, error:"ratelimited"}`) it does NOT retry — it returns whatever was collected so far with `rateLimited: true`. The consumer (`manage-alert-sheet.tsx`) toasts when `rateLimited` is true so the user knows the list may be incomplete. We don't cache — each request fetches fresh so new/renamed channels appear immediately. ## Slack OAuth Broker

- Lets self-hosted instances use Laminar's official Slack app by setting ONE issued key instead of recreating the Slack app + 5 env vars. The broker runs both OAuth legs and hands the bot token back to the calling instance; message content never transits the broker ("direct-send").
- Instance auth is broker-owned (no license service exists). Each instance gets one key, validated by SHA3-256 hash lookup against the `slack_broker_instances` table (`key_hash` unique). `authenticateInstance` in `lib/actions/slack/broker.ts` returns the `instanceId` or null. Keys are minted with the same primitives as project API keys (`generateRandomKey` + `hashApiKey` in `lib/api-keys.ts`); the hash is one-way (no decoding).
- Three routes under `app/api/broker/slack/`: `/start` (POST, server-to-server) and `/redeem` (POST, server-to-server) both take the instance key in `Authorization: Bearer`; `/cb` (GET) is the ONLY browser-facing leg (Slack's registered redirect target). The bot token never appears in a browser-visible URL — `/cb` mints a one-time claim and redirects with only the claim + team name.
- Env vars: `SLACK_BROKER_STATE_SECRET` (HMAC-SHA256 key for the signed `state` blob), `SLACK_CLIENT_ID`/`SLACK_CLIENT_SECRET` (official app creds for `oauth.v2.access`, HTTP Basic auth), and `NEXT_PUBLIC_URL` (derives the registered `redirect_uri` `${NEXT_PUBLIC_URL}/api/broker/slack/cb` — must exactly match between authorize and token exchange).
- Security invariants: `state` is HMAC-signed and binds `returnUrl` so a claim can only redirect back to the originating instance; the claim is single-use, stored in Redis cache with a 5-min TTL, removed on redeem, and bound to `instanceId` (`/redeem` rejects claims whose `instanceId` ≠ authenticated caller).
- The claim ALSO binds `workspaceId` (carried in signed `state`, copied into `ClaimPayload` at `/cb` mint, echoed by `/redeem`). `instanceId` binding alone can't separate workspaces (one instance key for all), and the callback's `workspaceId` rides the public redirect as a mutable query param. Instance-side `redeemBrokeredSlackToken` rejects any claim whose echoed `workspaceId` ≠ URL `workspaceId` (cross-workspace claim substitution) — the broker-bound complement to the callback's `isUserMemberOfWorkspace` check.
- `state` is also single-use: `mintState` records the nonce server-side (`slack_broker_state:<nonce>` → `{instanceId, codeVerifier}`, 10-min TTL) and `/cb` calls `consumeState` (atomic `getAndRemoveIfMatch`, matched by `instanceId`) before code exchange — the HMAC alone is replayable. `mintState` is `async`; await it in `/start`.
- PKCE (S256) defends against OAuth token injection (single-use state alone doesn't stop an attacker who leaks a victim's `state`, wins the race to `/cb`, and completes it with their own Slack `code`; a session cookie can't bind the flow since `/start` is server-to-server). `mintState` generates the PKCE pair, stores the secret `verifier` in the server-side nonce record (NEVER in `state`), returns the public `challenge` for the authorize URL; `/cb` reads the verifier via `consumeState` and passes it to `oauth.v2.access`. The direct flow (`connectSlackIntegration`) passes no verifier — `exchangeSlackOauthCode`'s `codeVerifier` is optional.
- Single-use state/claim records live in `cache` (`lib/cache.ts`), which falls back to **per-process memory** when `REDIS_URL` is unset — a scaled broker without Redis routes `/start`/`/cb`/`/redeem` to different workers and never finds the record. `mintState` calls `assertSharedStore()` to fail loudly at `/start` when `REDIS_URL` is missing. Broker is Cloud-only (Redis always set); the guard catches misconfigured self-hosted deployments.

### Instance-side brokered consumer (self-hosted)
- The instance-side caller lives in the SAME OSS repo and is inert unless `SLACK_BROKER_URL` + `LMNR_LICENSE_KEY` are set. The broker routes and the consumer routes coexist in one codebase: broker routes activate where the official app creds + `slack_broker_instances` rows exist (Cloud); consumer routes activate where the two broker env vars are set (self-hosted). A given deployment is one or the other, decided purely by env. `LMNR_LICENSE_KEY` is the self-hoster's issued license key (sent to the broker as `Authorization: Bearer`) and is intended for reuse by other future paid-feature gates, not Slack-specific.
- Connect flow: `SlackConnectButton` is double-duty — **brokered mode takes precedence**: when `brokerEnabled` it links to `/api/integrations/slack/broker-start`; otherwise cloud mode links straight to `slack.com/oauth/v2/authorize` from `SLACK_CLIENT_ID`/`SLACK_REDIRECT_URL`. Broker must win because a broker-configured deployment has no usable Slack app of its own — leftover `SLACK_CLIENT_ID`/`SLACK_REDIRECT_URL` env vars must not divert it into the broken direct flow (the button is a client component and can't see `ENVIRONMENT`/secret vars to replicate the server-side `cloudEnabled` gate). On Laminar Cloud the broker vars are never set, so the direct flow still wins there. Wired ONLY through the workspace integration page chain (`page.tsx` → `WorkspaceComponent` → `WorkspaceIntegrations` → `SlackConnectionCard`), NOT onboarding (which builds its own cloud-only URL).
- `/api/integrations/slack/broker-start` (GET) POSTs the broker `/start` with the Bearer instance key (key never enters the browser) and 302s the browser to the returned `authorizeUrl`. The `returnUrl` it sends the broker points back at `/api/integrations/slack` with `workspaceId` (and optional `returnPath`) embedded — the broker echoes only claim + team on the way back, so the instance must carry its own workspace context in the returnUrl.
- `/api/integrations/slack` (the callback) has a brokered branch alongside the `code` branch, keyed on the `workspaceId` query param (the direct path never sets it — it carries context in `state`): it calls `redeemBrokeredSlackToken({claim, workspaceId})` (`lib/actions/slack/index.ts`), which POSTs the broker `/redeem` with the Bearer key, then persists via the shared `persistSlackIntegration` (same encrypt + upsert as the direct path). The stored `slack_integrations` row is identical regardless of path, so the Rust send path is path-agnostic. Both success (with `claim`) and broker-error (`slack=error`, no `claim`) route through this branch so the error lands on the workspace integrations card, not the `/projects` fallback.
- **Brokered `workspaceId` MUST be authorized against the caller's session.** The callback is a public OAuth redirect target and the broker echoes `workspaceId` back only via the URL (it's not bound to the single-use claim). The branch calls `getServerSession` + `isUserMemberOfWorkspace(workspaceId, userId)` before `redeemBrokeredSlackToken` — without it, a user who completed their own broker flow could rewrite `workspaceId` to any UUID and store their bot token into a workspace they don't belong to (cross-workspace claim substitution). The redirect runs in the user's browser, so the session cookie is present.
- Crypto: `getSlackKeyFromEnv` (frontend `lib/crypto.ts`) and `decode_slack_token` (`app-server/src/notifications/slack.rs`) both require `SLACK_ENCRYPTION_KEY`. Self-hosters don't set a second key — the Helm chart (`lmnr-ai/lmnr-helm`) maps the cluster's `AEAD_SECRET_KEY` secret onto `SLACK_ENCRYPTION_KEY`, so the env var is always populated without an in-code fallback. BOTH sides must stay in sync or encrypt/decrypt diverge.
- `Feature.SLACK` is enabled when EITHER all cloud vars OR `SLACK_BROKER_URL` + `LMNR_LICENSE_KEY` are set.

## Onboarding Wizard

Route groups: `(auth)/layout.tsx` requires a session (redirects to `/sign-in`); the nested `(auth)/(app)/layout.tsx` is the onboarding-cookie gate (redirects to `/onboarding` when the cookie is present). The wizard is `frontend/app/(auth)/onboarding/page.tsx` → `components/onboarding/`. There is NO `(authenticated)` route group — the app trees live under `(auth)/(app)/`.

- **The page is a Server Component and only READS the cookie** (`getOnboardingState`). Next.js 16 Server Components can't reliably write cookies — a silent fail/throw plus a same-request `redirect()` produces a redirect loop. All writes go through `app/api/projects/[projectId]/onboarding/state/route.ts` (project-scoped, so `proxy.ts`'s `/api/projects/*` gating enforces membership); `persistOnboardingStep` is the only write surface and `finishOnboarding` DELETEs. Writes only happen once workspace+project exist. The handler resets `startedAt` when the cookie's `userId` ≠ the session's, so a stale cross-user cookie is overwritten on first POST.
- **The gate belongs in the `(auth)/(app)/layout.tsx` route-group layout — do NOT move it into `proxy.ts`.** That needs the matcher expanded to every authenticated prefix, a callback hack to bypass the `/sign-in` short-circuit, and the cookie name leaked into the global pipeline. `proxy.ts` is scoped to API authz, the Strapi `/uploads/*` rewrite, and the unauthenticated sign-in redirect — it imports nothing from onboarding.
- **An other user's cookie must look ABSENT.** Narrow `saved` to `ownSaved = saved?.userId === user.id ? saved : null` before every gate (including the "already has workspaces" redirect to `/projects`, which fires only when `count > 0 AND no own cookie AND slack param undefined`). Otherwise the wizard renders and overwrites under user B, and the gate traps B in a loop until they create an unwanted workspace.
- **Every completion DELETE must gate the next navigation on `res.ok`** — `fetch` only throws on network errors, so a 401/500 still resolves and navigating into the app tree with a live cookie loops via the gate. `finishOnboarding` returns a boolean for exactly this; its sole call site (`ConnectStep.goToProject`) gates on it. Separately, the server-side stale-cookie clear (cookie references an inaccessible project) goes through `redirect("/api/onboarding?to=/projects")` — that is the ONLY non-project-scoped cookie write allowed, because at that point the cookie's project can't be authz'd.
- There is no mount-POST; step writes happen only after a successful save. If you add one, the completion DELETE must await its settle first or the POST's `Set-Cookie` resurrects the cookie and bounces back to `/onboarding`.
- Save handlers must return `false` + a destructive toast on failure — never advance optimistically; `track` / `persistOnboardingStep` are gated on success. `saveSignals` PUTs the full template selection and the server reconciles against existing template-named signals, so revisiting a step never duplicates (scope is limited to names in `components/signals/prompts.ts`, so custom-named signals are invisible to the diff).
- `workspaceName` MUST be re-derived from the DB on resume (`loadOnboardingResumeDefaults`): the plan step passes it to `/checkout` as Stripe metadata, so without it the `"${user.name}'s workspace"` fallback lands in Stripe. Keep the per-slice loaders composed with `Promise.all` so the queries parallelize.
- **Do NOT clear the cookie before redirecting to Stripe** — it must survive the round trip so the gate keeps the post-payment landing on `/onboarding`. `returnTo=onboarding` makes checkout set `success_url=/onboarding?upgraded=true`, which `WizardSteps` detects and renders as `<ConnectStep upgraded />`. In-app upgrades omit `returnTo` and keep `success_url=/workspace/<id>?tab=billing`.
- The Slack step's OAuth `state` is `"${workspaceId}:/onboarding"` with **no `slack=*` in the returnPath** — `buildRedirectUrl` appends `slack=success|error` itself, and embedding it in state yields `?slack=success&slack=error` where `URLSearchParams.get` reads the first and masks the error.
- Creating a workspace with `isFirstProject: true` auto-creates the **Failure Detector** signal + trigger + creator email targets in the same transaction, so the user is opted into report digests by step 1. There is no in-wizard email-subscription UI; opt-out lives in workspace settings.
- **The welcome email is sent from the completion DELETE handler**, gated on `Feature.SEND_EMAIL` — sending earlier would email users who bounce before creating a workspace. The OSS path (`OssWorkspaceOnly.onComplete`) keeps an inline fire-and-forget DELETE whose only side effect is that email.
- Step 0 is irreversible (`WizardSteps` passes no `onBack` to step 1); steps 2–4 get `onBack` and reconcile-on-save absorbs the oscillation. `ConnectStep` is the only place that calls `finishOnboarding`.
- Do NOT nest a Radix `Checkbox` (renders a `<button>`) inside a `<button>` card — hydration error. The signals step uses a plain `<span>` + `Check` icon.

## Static System-Prompt Extraction pipeline

- `app-server/src/traces/system_extraction/` (producer.rs + consumer.rs alongside the agent) derives, per naive signature (`lmnr.span.prompt_hash`), a regex list whose matches are the prompt's dynamic parts. Distinct from `checkpoints/system_prompt.rs`, which resolves a single stripping regex inline on the checkpoints path — this pipeline is span-ingest-wide and cache-first.
- Flow: the ingest producer (`traces/producer.rs::publish_span_messages`) collects `(prompt_hash, system_prompt)` from `preprocess_for_queue`, checks `static_prompt_regex:{project}:{hash}` and publishes misses to `static_prompt_queue` — best-effort, and only AFTER the span publish succeeded so rejected batches don't feed the accumulator. The consumer (`traces/system_extraction/consumer.rs`) appends the prompt to `static_prompt_accumulator:{project}:{hash}` (24h TTL, capped at 10 samples so a persistently failing agent can't grow the cache value unboundedly); at ≥ 5 samples it takes the per-signature lock `static_prompt_lock:{project}:{hash}` (30-min TTL — runs are normally under 10 min, but the per-step upper bounds are high just in case), runs the extraction agent, writes the regex cache (7-day TTL), clears the accumulator, and releases the lock.
- The lock is released on ALL exit paths — agent failure, post-agent regex-cache WRITE failure, and success — so a later message can retry immediately; the TTL is only a backstop for a crashed worker that never reaches the release. Trade-off: a persistently-failing agent is re-run on every incoming batch for the signature rather than throttled to once per TTL. Lock contention and cache-read errors both drop the message (no requeue); a later span with the same signature re-triggers.
- The consumer calls the real agent, `traces::system_extraction::extract_static_regexes`. It returns `ExtractionResult` (never errors); an EMPTY `regexes` list means every temperature episode failed and the consumer treats it as agent failure (no cache write, lock kept). The agent needs an `LlmClient` — `StaticPromptHandler` carries `Option<Arc<LlmClient>>` (built in main.rs only when `Feature::Signals` is enabled) and drains the queue without accumulating when it's `None`. Tests use the `#[cfg(test)] test_regexes` seam on the handler instead of a real client.
- The read-modify-write on the accumulator is NOT atomic across workers — concurrent appends to the same signature can lose samples. Acceptable: the threshold is a heuristic, and the stream of spans keeps feeding it.
- `tool.rs::compile_removal_regex` / `tool.rs::remove_all` and `consumer.rs::STATIC_REGEX_TTL_SECONDS` in `traces/static_sp_extraction/` are `pub` for the enterprise summarizer (`lmnr-private` `signals/private/summarize.rs`), which must apply the cached regex lists with EXACTLY the compile flags / removal semantics `run_regex_tool` tested them under. Don't re-privatize them based on OSS-only usage analysis; route any new applier through `compile_removal_regex` instead of compiling `(?m){pattern}` inline.

## System-prompt versioning (v2, `traces/sp_versioning`)

- **Two independent flags, and the split is the rollout mechanism.** `Feature::SystemPromptVersioning` (`SP_VERSIONING_ENABLED`, default off) routes ingest to this pipeline instead of the legacy skeleton-hash queue; `Feature::SignalsVersionedPrompts` (`SP_VERSIONING_SIGNALS_ENABLED`, requires BOTH) is what makes signals *consume* the versions. Keep them separate — versioning can mint and be inspected for a while before summarization depends on it, and collapsing them into one flag removes the observation window. With versioning off the legacy `static_prompt_queue` + `StaticPromptHandler` path runs unchanged; the queue/exchange declarations in `main.rs` are unconditional so a mixed-flag fleet can't lose messages.
- **Agent identity is the first-sentence hash (`lmnr.span.agent_hash`), NOT the skeleton hash.** Both are minted by `prompt_hash::prompt_hashes` in one pass and both must keep existing — the skeleton still feeds the legacy pipeline, checkpoints and signals. Keying on the first sentence means permuting/adding/removing the prompt's XML scaffolding does not fork the agent and re-trigger classification.
- **Classification is LLM-FREE.** Within an agent, a Redis window of the last N distinct prompts is clustered line-wise (top-K Jaccard → ordered LCS intersection) and the intersection hash IS the version. LLM spend is decoupled: **regex extraction is demand-driven**, not mint-driven. `static_sp_extraction::worker` runs the agent only when a consumer (today: the signals trace compressor) hits a version with no cached regexes, so cost is proportional to versions actually READ. An absent regex cache key means "not generated yet / generation failed" — readers fall back to the raw prompt rather than erroring.
- **The regex-extraction worker deliberately has NO retry topology.** A failure drops the message and the next demand retries; only the classifier queue parks. `sp_versioning_delay_queue` is a consumer-less park queue whose per-message TTL dead-letters back into `SP_VERSIONING_EXCHANGE` — **every park must use the SAME TTL** because RabbitMQ only expires at the queue HEAD, so a variable delay would reorder expiry relative to arrival and stall the head behind a longer-lived message.
- **Two ClickHouse tables with different engines and different reasons.** `system_prompt_versions` (plain MergeTree, partitioned by month) is one write-once row per resolved span. `system_prompt_version_defs` (ReplacingMergeTree, **deliberately unpartitioned**) is the append-only mint journal and the ONLY durable record of a version's static TEXT — the Redis registry keeps just 64-bit line hashes. It's unpartitioned because merges never cross partitions, so a re-mint months later still collapses onto its original row instead of leaving a duplicate. The versioning pipeline never reads it; Redis stays the runtime source of truth. Both must be added to `deleteProjectDataFromClickHouse` (they are).
- **`TraceCompressor::new` takes optional clickhouse + queue handles, and chat/MCP compression passes `None` for both.** Chat compression never summarizes, so it must never look up prompt versions or enqueue a regex-generation demand. Threading a real queue in there would make an interactive trace-context request trigger LLM spend.
- **Cheap-match hits are re-validated probabilistically** (`SP_VERSIONING_FULL_RUN_SAMPLING_N`, 1/20). This is the staleness bound for silent static ADDITIONS: an old, smaller static line set keeps subset-matching new prompts forever, so without sampling it would never notice. Removals self-detect on the first miss, which is why only one direction needs the sampling.

## Checkpoints / Agent Versioning

- **The whole pipeline is gated behind `CHECKPOINTS_ENABLED` (default off)** — `Feature::Checkpoints` in `features/mod.rs`, backed by `env::checkpoints::ENABLED` (`env/checkpoints.rs`). The gate sits at two points: the producer call in `traces/processor.rs` (no checkpoint messages published) and the worker spawn in `main.rs` (no `CheckpointsHandler` workers). The queue/exchange declarations in `main.rs` stay unconditional so a mixed-flag fleet can't lose messages (an enabled producer node can publish while a disabled node runs alongside).
- Checkpoint text fields (`name`, `system_prompt`, `tool_definitions`, `model`) originate from user span data and can contain a NUL byte (`0x00`), which Postgres `text` columns reject ("invalid byte sequence for encoding UTF8: 0x00"). The DB write helpers in `app-server/src/db/agents.rs` run every user-controlled string through `crate::utils::sanitize_string` (strips NUL + other control chars, keeps `\n`/`\t`) — the same helper used on the ClickHouse insert path. `version_hash` is hex so it's left untouched. Sanitize at the Postgres write boundary, not at hash time, so dedup hashing keeps the original bytes.

## Evaluations Page (groups + table)

- **Evaluation-level `name`/`group_id`/`metadata` live ONLY in Postgres `evaluations`** — ClickHouse `evaluation_datapoints` carries per-datapoint data (its `metadata` column is the datapoint's, not the evaluation's). So SDK-facing evaluation updates (`POST /v1/evals/{eval_id}`, `api/v1/evals.rs::update_eval`) are a pure Postgres UPDATE with no CH write. `group_id` is deliberately immutable there (ClickHouse datapoint rows denormalize `group_id` at insert time via `get_evaluation_group_id`, so changing it post-hoc would desync the two stores).
- **`evaluation_datapoints_v0` sources trace-level columns from `traces_agg` + `traces_static`** (migration `55`): costs/tokens/`start_time`/`end_time`/`duration` + `trace_status` (`has(statuses,'error')`) + `trace_tags` from a `traces_agg` GROUP BY, `trace_metadata` + `top_span_id` from `traces_static FINAL`. The view takes only `project_id` (no time params), so both joins carry a semi-join on `id IN (SELECT trace_id FROM evaluation_datapoints WHERE project_id = …)` to prune on the `(project_id, id)` PK instead of scanning every trace in the project.
- **Two type traps when recreating this view**, both caught by diffing `system.columns` against the previous definition: the `traces_agg` aggregates leak their `SimpleAggregateFunction(min|max, …)` wrapper into the exposed type (cast with `CAST(min(start_time) AS DateTime64(9,'UTC'))`), and `trace_status` must be `toLowCardinality(...)` to stay `LowCardinality(String)`.
- **`trace_spans.duration` must be an explicit expression** — the physical `spans` table has NO `duration` column, so a bare `duration` inside that subquery resolves against the OUTER `end_time - start_time AS duration` alias (which then rebinds the names to the spans columns — it only works by accident), and qualifying the outer alias (`t.end_time - t.start_time`) breaks that resolution with `Unknown expression identifier 'duration'` / `Correlated subqueries are not supported in JOINs`. Compute it inline: `(toUnixTimestamp64Nano(end_time) - toUnixTimestamp64Nano(start_time)) / 1000000000`.
- The evaluations list page (`frontend/components/evaluations/evaluations.tsx`) is split into the groups sidebar (`groups-list/`) and the table. The selected group is the `groupId` URL query param; the groups list defaults it to the first group via an effect on load. The table fetch is gated on `!isGroupDefaultPending` — without that gate the table fires one fetch with `groupId=null` (returns ALL groups' evals) BEFORE the default groupId is applied, then re-fetches filtered, briefly flashing the wrong (unfiltered) rows. `isGroupDefaultPending = isGroupsLoading || (!groupId && groups.length > 0)`; both components hit `/evaluation-groups` via SWR so the request dedupes.
- **InfiniteDataTable icon columns need `size` ≥ 60.** `cell.tsx` renders every cell with `px-4` (32px) padding and wraps content in an `overflow: hidden` truncate div, so a 28px (`h-7 w-7`) icon button in a `size: 40` column gets clipped — clicks land on the row instead of the button and trigger `getRowHref` navigation. Use `size: 64` for a single icon-button column and `e.stopPropagation()` in its `onClick` (same pattern as `createCheckboxColumn` in `utils.tsx`).
- `useDefaultLayout` from `react-resizable-panels` dereferences `localStorage` at call time in its default storage — throws during SSR. ## Trace Type Upsert

- The `traces.type` column uses a first-non-zero strategy in the ON CONFLICT upsert: `CASE WHEN traces.type = 0 THEN EXCLUDED.type ELSE traces.type END`. Once a trace is assigned a non-default type (e.g. EVALUATION=1), no subsequent batch can overwrite it. Do NOT revert to `COALESCE` (picks first non-null, lets `0` silently reset a previously set type) or `GREATEST` (picks highest numeric value, which conflates type ordering with type precedence).
- `TraceAggregation::from_spans` in `ch/traces.rs` applies the same rule within a single batch: `trace_type` is only written when `entry.trace_type == 0`, so a child span processed later in the loop cannot overwrite a non-default type already set by an earlier span.

## Trace token/cost aggregation (LLM spans only)

- **The gate is at the call site in `traces/processor.rs`.** The ingestion loop calls `get_llm_usage_for_span` (`traces/utils.rs`) ONLY when `m.span.is_llm_span()`, and uses `SpanUsage::default()` (all zeros) for non-LLM spans — the gate lives outside the function so no extra param is threaded through just for an instant quit. ## `traces_agg` AggregatingMergeTree

- **`traces_agg` + `traces_static` are the ONLY trace stores.** `db/trace.rs` keeps only `TraceType` (read by `ch/spans.rs`'s `Into<u8>` and the private signals hook) plus the unrelated `shared_traces` helpers. The physical `traces_replacing` table and the PG `traces` table still exist with historical rows — they are read-dead, not dropped, so `deleteProjectDataFromClickHouse` must keep purging `traces_replacing` (an `ALTER … DELETE` against a missing table throws and aborts the purge).
- **Every write to EITHER table is a per-batch DELTA and MUST NOT read a cumulative row first** (there is no cumulative source left to read). Nothing can double-count a `sum`, but the corollary dictates both schemas: **every column must fold correctly from partials alone.** Both are fed from the same three producers — `TraceAggregation` (span batches), the raw metadata patch, and the extracted agent io — written from one unconditional block in `traces/processor.rs`. There is no `from_trace(&Trace)` constructor on either; don't add one.
- **`start_time` is the partition key on both tables, so every writer must derive it from the same trace-level value** via `processor::resolve_static_start_times` (this batch's min span start) — never a span's end time. A trace whose spans arrived in an EARLIER flush isn't in that map and each table falls back differently: `traces_static` uses plain `now_ns`, while `traces_agg` uses `now_ns + PATCH_START_TIME_OFFSET_NS` (1h ahead — still a `min` no-op against any real past start, and close enough to stay in the same or an adjacent monthly partition so merges stay local). The fallback is exact whenever the trace started in the current partition period; one that started in a previous month lands a partition late, which `SELECT … FINAL` still coalesces but a tight `start_time` filter can clip.
- Metadata patches build their `traces_agg` partial via `CHTraceAgg::from_metadata_patch`: identity aggregates, `end_time = 0` (the `max` identity — a patch learns nothing about the trace's end, and `max` can never be lowered again), `num_spans = 1` for the virtual span, and the patched metadata map.
- `trace_exists` (the `POST /v1/traces/metadata` 404 gate) is a ClickHouse existence probe on `traces_agg` scoped by `(project_id, id)` — `ch/traces_agg.rs::trace_exists`. It's `SELECT 1 … LIMIT 1` + `fetch_optional`, NOT `count()`: no GROUP BY (a trace is present iff it has ≥1 partial) and the scan short-circuits on the first match rather than counting every partial. Note `LIMIT 1` is a no-op on an aggregate like `count()`, so that form always reads the whole matching range.
- `traces_agg` uses `SimpleAggregateFunction` columns; reads go through `traces_v0`, which re-aggregates with GROUP BY (never FINAL — FINAL can't use projections). Projections on AggregatingMergeTree require `deduplicate_merge_projection_mode = 'rebuild'` in table SETTINGS (default `throw` refuses the CREATE).
- **The view's `min_start_time`/`max_start_time` params are load-bearing for correctness, not just pruning.** An outer WHERE on aggregated `min(start_time)` cannot be pushed through the GROUP BY (measured: 122/122 granules read vs 4/80 with in-view params), and pushing it down would be unsound anyway — clipping some partials of a trace silently corrupts its sums. Callers must pad the bounds by more than the max trace duration and re-apply exact bounds in their own WHERE (same contract as `traces_v0`).
- Status/trace-type precedence lives ONLY in the view, so reordering precedence (e.g. playground over evaluation) is a view-only change with no data migration. Seen-values are **enum arrays**: `statuses SimpleAggregateFunction(groupUniqArrayArray, Array(Enum8('success'=1,'error'=2)))` and `trace_types` (same shape, `Enum8('DEFAULT'=0,'EVALUATION'=1,'EVENT'=2,'PLAYGROUND'=3)` mirroring `Into<u8> for TraceType`); the view reads `has(statuses, 'error')` / `multiIf(has(trace_types, 'PLAYGROUND'), …)`. Enum8 is Int8 on the wire — `CHTraceAgg` sends `Vec<i8>`, and CH accepts BOTH string names and ints on insert/read while JSON formats render names. **Gotcha: out-of-range ints are accepted at insert but poison every subsequent read of the part with `UNKNOWN_ELEMENT_OF_ENUM`** (string inserts validate, int inserts don't) — when extending `TraceType`, add the variant to the DDL enum via `ALTER … MODIFY COLUMN` (metadata-only, works inside the SimpleAggregateFunction wrapper) in the same PR as the Rust enum change.
- Metadata is stored as raw JSON values per key (`SimpleAggregateFunction(maxMap, Map(String, String))`) — no versioning. ClickHouse only ships min/max/sum-based per-key map-merge combinators (no arbitrary-per-key-wins one), so `maxMap` is used purely as an "any occurrence wins" merge: it picks each key's lexicographically-greatest raw JSON string, which is arbitrary from an application standpoint (NOT a guaranteed last-write-wins). The view re-emits a stringified JSON object via `arrayMap((k, v) -> concat(toJSONString(k), ':', v), mapKeys(...), mapValues(...))` (the existing consumer contract). `internal_metadata` is a second reserved `maxMap` column with the same encoding and no writer yet.
- **Agent IO read paths are SPLIT.** Both values are stored on `traces_static` (`input`, `output_hashes` — see that section), but only `agent_input` is exposed by `traces_v0`; `agent_output` lives in its own `trace_outputs_v0` view (project_id-parameterized only, NOT time-parameterized) which resolves `output_hashes` through `deduped_content_dict` into `agent_output Array(String)`, one raw message JSON per element. Keep them split: the dict-resolving join is too expensive inside the hot traces view. SQL surface: `trace_outputs` is a registered table in `validator.rs` `TableRegistry` + `schema.rs` + frontend `tableSchemas` + the MCP joins hint (`trace_outputs.trace_id = traces.id`). Frontend: `getAgentOutputsBatch` (`lib/actions/traces/outputs.ts`) reads the view via `executeQuery`, extracts display text with the shared `extractAgentOutput` (`lib/traces/agent-output.ts` — non-empty text/thinking/reasoning + tool calls as `Tool: <name>` (no arguments), unknown parts stringified, and a whole-array fallback that dumps the raw messages when nothing was extracted; pinned by `tests/test-agent-output-extraction.test.ts`), and falls back to the legacy last-main-agent-LLM-span preview for traces without a `trace_agent_output` row. Sole consumer: the session/debugger views' `POST /api/projects/:id/traces/output` batch route (store key `agentOutputs`) — the trace-view transcript deliberately does NOT render an output row (removed in review; `getTrace`/`getSharedTrace` return `agent_input` only).
- `traces_v0` omits `num_spans`; if a consumer needs it, add `sum(num_spans) AS num_spans` to the view (view-only change — the table column already folds correctly).

## `traces_static` CoalescingMergeTree

- The write-once / set-once trace columns (`input`, `output_hashes`, `user_id`, `session_id`, `metadata`, `root_span_*`, `has_browser_session`, reserved `internal_metadata`) live here (CH migration `54_traces_agg.sql`, `ch/traces_static.rs` → `CHTraceStatic`), separate from `traces_agg`'s aggregates. The per-batch-delta and `start_time` rules above apply to both tables.
- **Migration `54` also carries the READ side**: `traces_v0` joins `traces_static FINAL` via a subquery that repeats the view's `project_id` + `start_time` params as a **PREWHERE** — that pushdown is what makes the `FINAL` affordable (verified: prunes partition + MinMax + PK on the join side). `FINAL` is mandatory: it coalesces a trace's partials AND merges across partitions. The exposed column surface is deliberately IDENTICAL to the `validator.rs` registry, so only the source of the values moved. NULLs default back to the historical values, and `top_span_name` resolves `coalesce(root_span_name, root_span_name_from_path)` with NO `substring(_, 2)` — that prefix strip is a `traces_agg`-only hack.
- **`CoalescingMergeTree` has NO version parameter.** Its optional argument is a columns-to-coalesce LIST (SummingMergeTree-style), so `CoalescingMergeTree(start_time)` silently means "coalesce ONLY `start_time`" and leaves every other column un-coalesced (and is rejected outright when that column is in the partition key). Resolution is **last non-NULL write per column by INSERTION ORDER**, never by a timestamp — don't add one as an engine arg or reason about one as a version.
- **`start_time` is the trace start time AND the partition key** (`PARTITION BY toYYYYMM(start_time)`, mirroring `traces_agg`) so reads can push a PREWHERE down to it — verified pruning on partition + MinMax. There's a `PROJECTION p_start_time (SELECT * ORDER BY project_id, start_time, trace_id)`; projections on a CoalescingMergeTree require `deduplicate_merge_projection_mode = 'rebuild'` (default `throw` refuses the CREATE), same as `traces_agg`. Two consequences of partitioning a coalescing table, both accepted deliberately: **(1)** background merges never cross partitions, so a trace whose writes straddle a month keeps one part per partition — `SELECT ... FINAL` DOES merge across partitions, so reads still see one coalesced row, but readers MUST NOT set `do_not_merge_across_partitions_select_final=1` on this table. **(2)** a `start_time` predicate CLIPS partials (a window excluding one write's partition drops the columns only that write carried), so callers pad the bounds by more than the max trace duration and re-apply exact bounds in their own WHERE — the same contract `traces_v0` has.
- **A partition-key column is NOT aggregated or coalesced in a CoalescingMergeTree — it keeps the FIRST-ARRIVING value** (verified; this differs from AggregatingMergeTree, where `traces_agg`'s identical `min` + `PARTITION BY` pairing DOES fold to the true min). So `start_time` here can be a later batch's start when spans arrive out of order; it's deliberately a plain `DateTime64` rather than a `SimpleAggregateFunction(min, ...)` that would silently do nothing, reads treat it as a padded pruning bound, and the authoritative trace start lives in `traces_agg`.
- **A NULL means "no update" and never erases a prior value** — that's the whole point vs. `traces_agg`'s `max()`-based columns, which can't express set-once values. Corollary: every write must be a NULL hole for anything it didn't learn, so the coalescing columns are `Option` and each constructor returns `Option<Self>` (a batch that learned nothing static writes no row at all). Empty strings are normalized to `None` — writing `''` would clobber a value an earlier batch set.
- **`metadata` / `internal_metadata` have SET semantics, NOT patch semantics** — a plain `Nullable(String)` holding the whole stringified JSON object, written ONLY when the batch carries metadata. **Do NOT "fix" this into a `SimpleAggregateFunction(maxMap, Map(...))` like `traces_agg`**: per-key map merging is slow at scale, and escaping that cost is a main reason this table is split out. **KNOWN CAVEAT, deliberately accepted: a trace whose metadata is set more than once has UNDEFINED metadata** — the last write wins wholesale and the others' keys are lost, not merged. In practice metadata is set once per trace (the SDK sends it with the trace; `POST /v1/traces/metadata` is a set, not a patch), so treat multi-write metadata as unsupported. Empty objects encode to `None` so they can't clobber. **Extracted agent io must never be folded into a metadata key** — it flows to the `input` / `output_hashes` columns via `RawTraceIo`, and `encode_metadata` strips the reserved `lmnr_user_task` / `lmnr_trace_output` keys as a backstop, since a synthetic `{lmnr_user_task: …}` delta would REPLACE the customer's real keys (verified: a trace with real metadata came back holding only `lmnr_user_task`).
- **`status` / `trace_type` are deliberately NOT here — they stay in `traces_agg`** as its `statuses` / `trace_types` seen-value arrays, because their precedence can't be expressed by last-write-wins over deltas (sticky `error`: a later success-only batch must not downgrade a prior error; a `DEFAULT` must not pin a trace a later batch types as EVALUATION/PLAYGROUND). That needs the seen-value union, which `traces_agg` already stores and resolves in its view. So a batch carrying ONLY a status / trace type writes no `traces_static` row at all. **Net effect: `traces_static` has NO aggregate-function columns — it's purely coalescing**, which is the point of the split.
- Semantics that DON'T follow from "last write wins", verified against CH 26.2 and encoded in the writer:
  - **The root-span name is TWO columns: `root_span_name` (the real root's) and `root_span_name_from_path` (span-path-derived preview).** Readers resolve `coalesce(root_span_name, root_span_name_from_path)`. The fallback exists so in-progress traces — and traces whose root span never arrives — still render a preview. One column cannot carry both under last-write-wins: a later batch with no root span can't tell whether a real name was already written, so it would clobber it. This is why `traces_agg` needs its `'2'`/`'1'` priority-prefix hack to make `max(String)` prefer the root-derived name. Two nullable columns express the precedence directly, so it's order-independent with no sentinel encoding.
  - Provenance is knowable per batch, which is what makes the two-column split work on deltas: `top_span_id` set ⇒ the name is the real root's; unset ⇒ it came from the span path. A metadata patch learns nothing about the root span and writes no root columns at all.
- **`output_hashes` is concatenated lowercase hex (64 chars per 32-byte hash), not an Array**, because `Nullable(Array(FixedString(32)))` is rejected and a non-Nullable `Array` has no NULL hole (an omitted array arrives as `[]` and clobbers). Reconstruct at read with `arrayMap(i -> unhex(substring(output_hashes, i * 64 + 1, 64)), range(0, intDiv(length(output_hashes), 64)))`, which yields `Array(String)` that `dictGet` accepts for a `FixedString(32)` dictionary key (verified end-to-end against `deduped_content_dict`).
- The `root_span_type` DDL enum must list **`PIPELINE` = 2** even though no view surfaces it: `SpanType::Pipeline` is a reachable `Into<u8>` value, and an out-of-range `Enum8` int is accepted at INSERT but then poisons every later read of that part with `UNKNOWN_ELEMENT_OF_ENUM` (same trap as `traces_agg`'s enum arrays). Extend the DDL enum in the same PR as any `SpanType`/`TraceType` variant.

## Historical `traces_replacing` → `traces_agg`/`traces_static` backfill

One-shot migration script for self-hosters upgrading past the `traces_agg` cutover: `frontend/lib/clickhouse/scripts/backfill-traces-agg.ts` (+ `backfill-lock.ts`), fired and never awaited from `instrumentation.ts` after `initializeClickHouse()`. It walks backwards from the destination watermark in small batches and keeps NO persisted state — the resume point is `min(start_time)` of `traces_static`, so a restart re-derives it and an already-migrated deployment short-circuits.

**Both files are densely commented at each point of use — read them rather than this section before changing anything.** The reasoning that is expensive to rediscover (and was each found by reproducing a live corruption) is: `SELECT … FINAL` under a narrow `start_time` filter can resolve a STALE version, and padding + re-filtering in an outer WHERE does not help because the predicate is pushed back into the FINAL scan — resolve winners explicitly with `argMax` over the version column; the destination anti-join must run on EVERY window because `traces_agg` SUMS and self-hosted MergeTree has no insert dedup (staging's `Shared*` engines set `insert_deduplicate=1` and will MASK this — reproduce with `?insert_deduplicate=0` as a URL param, the `X-ClickHouse-Settings` header is ignored); the anti-join cannot substitute for the atomic `SET NX EX` claim, whose lease needs a fencing token because a stalled insert can outlive the TTL and a constant lock value lets a lapsed holder `DEL` its successor's lock; every `traces_static` column must be a NULL hole or it clobbers live ingest under CoalescingMergeTree; reserved metadata keys must be stripped; and a `toDateTime64('…', 9)` literal with **no** `'UTC'` argument is parsed in the SERVER's timezone even when every column is `DateTime64(9, 'UTC')`, which silently skews every window bound on a non-UTC server and is invisible on UTC staging.

Two traps worth carrying out of this script because they generalize:
- **`min()`/`max()` over an EMPTY ClickHouse table returns the type's ZERO value, not NULL** — for `DateTime64` that is the truthy string `"1970-01-01 00:00:00.000000000"`, which parses to a valid `Date` and sails through a `if (!value) return null` guard. `rows.length === 0` is NOT the empty-table signal for an aggregate, since an aggregate over zero rows still returns one row.
- **Never register a `SIGTERM`/`SIGINT` handler just to clean something up on shutdown.** Adding a listener SUPPRESSES Node's default terminate, so a handler that doesn't itself call `process.exit` leaves the process alive and ignoring the signal. Next installs its own handlers that exit 143/130, but only when `NEXT_MANUAL_SIG_HANDLE` is unset — so in the manual-handle configuration a stray listener strands the pod. Verifying this under `tsx`/`npm` wrappers gives a FALSE NEGATIVE: the parent dies and the run looks correctly terminated even when the child suppressed the signal.

## ClickHouse `spans` query scoping (latency)

- The `spans` table is `ORDER BY (project_id, trace_id, start_time, span_id)`. The frontend's `executeQuery` always injects `project_id` (via the `spans_v0(project_id=…)` view rewrite), but a query that filters by `span_id` WITHOUT a `trace_id` cannot prune on the primary key — ClickHouse falls back to a full-project granule scan ("generic exclusion search" over all granules) and decompresses the heavy `input`/`output`/`attributes`/`events` columns for the whole project. Under load this is the dominant cost on the trace/span read routes. **Always add `trace_id IN (…)` alongside `span_id` filters** when the trace id(s) are known (they always are on these routes); measured locally this dropped a single-span fetch from 67/67 granules to 27/67 and ~1.3s→0.4s even on a tiny dataset, and the gap widens with project size (see `fetchSpansByIds` in `lib/actions/sessions/trace-io.ts`).
- The `spans_no_io_by_start_time` PROJECTION is automatically chosen only when the SELECT omits the `input`/`output` columns; queries that need IO read the base table, so primary-key pruning via `trace_id` matters most there.

## Signal CRUD in app-server (`signals/service.rs`, `/v1/cli/signals`)

- **Signal CRUD is ungated by the `signals` cargo feature and lives in `signals/service.rs` + `db/signals.rs` + `db/signal_triggers.rs`.** Writing a signal row is a plain DB write; only signal *processing* is enterprise. `db/signals.rs` was previously `#[cfg(feature = "signals")]` — ungating it exposes `SignalMetadata` / `Signal` / `get_signal` as dead code in OSS, so those carry `#[cfg_attr(not(feature = "signals"), allow(dead_code))]`.
- **Every signal write path must lock the `signals` row (`SELECT … FOR UPDATE`) BEFORE touching `signal_triggers`.** With no FK there is nothing else serializing them, so a delete that went straight for the child rows would not block a concurrent trigger replace — the replace inserts rows the delete already scanned past and they survive as orphans (reproduced deterministically, 3/3 runs). `update_signal` and `delete_signal` both take that lock first; any new path that writes triggers must too.
- **`signal_triggers` has NO foreign key on `signal_id`** (verified against the live schema — `pg_constraint` returns zero FK rows for the table). Deleting a signal does NOT cascade to its triggers, so `db::signals::delete_signal` deletes them explicitly in the same transaction. `alerts.source_id` likewise has no FK (deliberate — it may reference other entity types), so alerts are deleted explicitly too; only `alert_targets` genuinely cascades (from `alerts`). **The frontend `deleteSignal`/`deleteSignals` path still has this gap** — staging holds orphan `signal_triggers` rows because of it. Fix that or add the FK before trusting "deleting a signal cleans up its triggers" anywhere.
- The service validates payloads the CLI/UI write: identifier field names, sampleRate 1..95, name trimmed-then-capped at 255 CHARACTERS, and `required` listing exactly the property names (the drawer marks every field required). Descriptions on payload fields are optional (the drawer does not require them). Extra JSON Schema keys (`additionalProperties`, `format`, …) are stored as-is — the drawer never emits them and ignores them on load. Numeric-string thresholds are TRIMMED before storage because the evaluator's `parse::<f64>()` does not trim, and non-finite values are rejected (Rust parses `"NaN"`/`"inf"`, which would make every comparison false).
- **The API models a signal's firing config as three sibling fields — `trigger` / `filters` / `mode` — while storage stays one `signal_triggers` row.** `Trigger` is a serde-tagged ENUM (`{"type":"rootSpanFinished"}` / `{"type":"spanName","spanNames":[…]}`), not a `{column,operator,value}` list, because those two shapes are the only ones `evaluate.rs` has an arm for: the old flat-list API accepted any column in either list, and a misplaced one was stored happily and then silently never fired. `Trigger::to_conditions` / `from_conditions` map to and from the legacy `value` column, so the evaluator, the browser drawer, and every existing row are untouched. `from_conditions` returns `None` for anything unfirable (empty list, a filter column, all-blank span names) so the API never reports a trigger that does nothing, and it does NOT trim surviving span names — the evaluator compares them literally, so a padded legacy name must read back as stored.
- **`mode` is `"batch"` / `"realtime"` on the wire, never the raw 0/1 discriminant** (`Mode::to_i16` / `from_i16` mirror `SignalMode::from_u8`, including "anything unknown is batch"). Rejecting the integer keeps a storage detail out of the contract.
- **One trigger row per signal is the API contract, but the table has no constraint enforcing it** — pre-split rows and the frontend's `syncTriggers` could create several. Reads take the newest (`ORDER BY created_at DESC, id DESC`) and `patch_signal_trigger` collapses the extras onto the row it locked. The `id` tiebreak is load-bearing: rows inserted in one transaction share a `created_at`, so without it the same signal can report a different trigger per request.
- **New filter column:** picker (`trigger-filter-field.tsx`) + evaluator (`evaluate.rs`) + `ch/private/trace_stats.rs` + one row on `FILTER_COLUMNS` in `signals/service.rs`. A new TRIGGER kind is a new `Trigger` variant plus an `evaluate_trigger_condition` arm.
- `PATCH /v1/cli/signals/{id}` is a true partial patch: an absent key leaves the stored value alone, so `sample_rate` and `trigger` are **double `Option`s** (`Option<Option<T>>`) via a generic `double_option` deserializer — plain serde `Option` collapses "absent" and explicit `null`, making "clear the sampling rate" / "stop firing on its own" indistinguishable from "don't touch it". `filters` needs only a single `Option` because `[]` already expresses "clear". Metadata merging preserves unknown keys, and clearing REMOVES the key rather than writing `null`/`false` (absence is the canonical "enabled / no sampling" state every reader assumes).
- Auto-created `NEW_CLUSTER` alert and `skipSimilar` follow `Feature::Clustering` (aliases Signals / `has_llm_provider`), same gate as clustering worker spawn. With clustering off `skipSimilar` MUST be false or the backend silently drops notifications. Frontend still keys the same affordances on `CLUSTERING_ENABLED`.

## Local `/v1/cli/*` testing in the sandbox

- **CLI-auth JWKS defaults to `https://laminar.sh`**, so every `/v1/cli/*` request 401s locally with an otherwise-valid token. Launch app-server with `NEXT_PUBLIC_URL=http://localhost:3000 NEXT_INTERNAL_URL=http://localhost:3000` (the JWKS URL is derived as `{base}/api/auth/jwks`). Mint a token with `POST /api/auth/sign-in/local-email` (`{"email":"agent@lmnr.ai"}`, `FORCE_EMAIL_AUTH=true` is set) then `GET /api/auth/token` with the session token as bearer.
- **The sandbox clock can run behind file mtimes**, so freshly-edited sources look OLDER than the built binary and `cargo build` reports "Finished" without recompiling — the running server then 404s routes that exist in the source. `touch` the changed files (or verify with `strings target/debug/app-server | grep -c '<a route literal>'`) before concluding a route is broken.
- **Never kill app-server with `pkill -f app-server` or a `ps | grep` loop** — the pattern matches the agent's own shell and terminates the turn. Match on `readlink /proc/<pid>/exe` against the binary path (including the `" (deleted)"` suffix a rebuild leaves behind, which is why a plain path equality check misses the old process) and skip anything sharing your own PGID.

- The frontend can be served under a sub-path (e.g. `app.company.com/lmnr`) for self-hosters who reverse-proxy Laminar onto an existing domain. The prefix is **baked at BUILD time** via `NEXT_PUBLIC_BASE_PATH` → `basePath` in `next.config.ts` — it is NOT a runtime flip, because `output: standalone` inlines absolute `/_next/static/...` asset URLs into the bundle. Empty/unset ⇒ root-served, so the regular `frontend-ee` image is unaffected; the EE side builds a separate `frontend-ee-basepath` image with `/lmnr` baked in (Dockerfile takes the prefix as a build-arg, same pattern as `NEXT_PUBLIC_APP_VERSION`). The `lmnr-private` CI matrix owns that second image target — it can't be done from the OSS repo.
- **What Next auto-prefixes (leave alone):** `<Link>`, `router.push`, `next/navigation` `redirect()` (Next 16 server redirect DOES prepend basePath), `next/image`, `/public` assets, fonts, API route mounting, and it STRIPS the prefix before middleware/rewrites run (so `proxy.ts` matchers and `req.nextUrl.pathname` stay prefix-free).
- **What is NOT auto-prefixed (must wrap with `withBasePath` from `lib/utils.ts`):** native `fetch("/api/...")`, `new EventSource("/...")`, `window.location.*`, Better Auth `callbackURL`/`errorCallbackURL` (redirected verbatim), and `NextResponse.redirect(new URL(path, base))` — `new URL(absolutePath, base)` DROPS the prefix, so prefix the path before constructing the URL. `redirect()` from `next/navigation` does NOT need wrapping.
- Native `fetch` / `EventSource` are handled globally by `components/common/base-path-fetch-shim.tsx` (mounted first in `app/layout.tsx`'s `<body>`), which monkey-patches `window.fetch`/`window.EventSource` to prefix root-relative requests once at client load. It prefixes both **string** paths (`fetch("/api/...")`) AND **same-origin `URL` objects** (`fetch(new URL("/api/foo", origin))` — re-prefixes the pathname; cross-origin URLs like PostHog/GitHub pass through). `Request` objects pass through (they carry an already-resolved absolute URL). It's gated on `BASE_PATH` non-empty (so root-served is a true no-op) and idempotent via a `__lmnrBasePathFetchPatched` window flag. This is why the ~140 native fetch call sites are NOT individually prefixed — don't start doing it by hand. `withBasePath` is still needed at the verbatim sites listed above (location/auth-callback/NextResponse.redirect) because those bypass `window.fetch`.
- `withBasePath(path)` is a no-op when `BASE_PATH` is empty, and skips absolute URLs (`http(s)://`, `//host`), non-root paths, and already-prefixed paths — so it's safe to wrap defensively. Its inverse `stripBasePath` removes the prefix off a browser-observed `window.location.pathname`.
- **`callbackUrl` in the sign-in query string is prefix-FREE by contract.** Both consumers re-prefix it (the sign-in page's `router.push` auto-adds basePath; OAuth's `errorCallbackURL` goes through `withBasePath`), so producers must NOT store a prefix-inclusive value or it double-stamps (`/lmnr/lmnr/...`). `proxy.ts` is naturally prefix-free (middleware sees the stripped pathname); `redirectToSignIn` (`lib/utils.ts`, fired on a 401 from `swrFetcher`) must `stripBasePath(window.location.pathname)` because the browser pathname carries the prefix.
- **Better Auth needs FOUR explicit base-path fixes — do NOT revert any, the shim does not cover them.**
  - **(1) Server** (`lib/auth.ts`): `betterAuth({ baseURL })` MUST be the `AUTH_URL` **origin only** (`AUTH_ORIGIN = new URL(AUTH_URL).origin`), never the full prefixed URL. Better Auth's router derives its mount/strip path from `new URL(baseURL).pathname` (`better-auth/dist/api/index.mjs`), but Next strips the base path before the route handler runs — so a prefixed `baseURL` (`https://host/lmnr`) makes the router try to strip `/lmnr` off an already-stripped `/api/auth/...` request and 404s EVERY auth route.
  - **(2) Client** (`lib/auth-client.ts`): `createAuthClient({ baseURL })` MUST be pinned to `` `${window.location.origin}${BASE_PATH}/api/auth` `` in the browser — client-side Better Auth resolves to the root-relative `/api/auth` default (prefix-free → 404), and it snapshots `customFetchImpl: fetch` by value at creation, so the global fetch shim can't reliably retro-prefix it if `auth-client.ts` imported before the shim patched `window.fetch`.
  - **(3) OAuth `redirect_uri` for ALL providers must be built as `${AUTH_ORIGIN}${BASE_PATH}/api/auth/callback/<id>` via `prefixedCallbackUri`, NOT `baseURL` and NOT raw `AUTH_URL`.** Better Auth computes social-provider (github/google) `redirect_uri` as `${context.baseURL}/callback/<id>` (`better-auth/dist/api/routes/sign-in.mjs` + `callback.mjs`) — and since `baseURL` is origin-only, that drops the prefix and the IdP redirect_uri match fails. So github/google MUST set `redirectURI: prefixedCallbackUri(<id>)` explicitly in `getSocialProviders` (azure/okta/keycloak already do via `getGenericOAuthConfig`). Both the authorize and token-exchange legs read `options.redirectURI || redirectURI`, so the explicit option covers both. **`prefixedCallbackUri` derives the prefix from the build-time-baked `BASE_PATH`, not from `AUTH_URL`** — the sub-path is the source of truth baked into the `frontend-ee-basepath` image, and a self-hoster naturally sets `BETTER_AUTH_URL` to their bare origin (no `/lmnr`), so building the callback off `AUTH_URL` emits an unprefixed `redirect_uri`, the IdP redirects to `/api/auth/callback/<id>`, and the reverse proxy 404s it. The final post-auth redirect uses the client-supplied `callbackURL`, already prefixed via `withBasePath`.
  - **(4) Device-flow `verificationUri` (CLI login) must be `` `${BASE_PATH}/device` ``, not bare `/device`.** Better Auth's `buildVerificationUris` (`better-auth/dist/plugins/device-authorization/routes.mjs`) resolves it via `new URL(verificationUri, baseURL)` — with origin-only `baseURL` a root-relative `/device` replaces the whole path and drops the prefix, so the RFC 8628 `verification_uri` the CLI opens becomes `https://host/device` (404 under a sub-path deploy). Prefixing with `BASE_PATH` keeps it relative so it resolves to `<origin><base>/device`; no-op when root-served.

## Authentication (Better Auth)

- Auth is **Better Auth** (`better-auth`), not NextAuth. Central config is `frontend/lib/auth.ts` (`auth = betterAuth({...})`); the route handler is `app/api/auth/[...all]/route.ts` via `toNextJsHandler(auth)`. Client helpers live in `frontend/lib/auth-client.ts`; the server-session wrapper is `frontend/lib/auth-session.ts` (`getServerSession()` → `auth.api.getSession({ headers: await headers() })`, shape `{ user: { id, name, email, image } } | null`). Env: `BETTER_AUTH_SECRET` / `BETTER_AUTH_URL`, falling back to `NEXTAUTH_SECRET` / `NEXTAUTH_URL` for compat.
- The drizzle adapter uses `usePlural: true`. Better Auth core appends `"s"` to each model name when `usePlural` is set (`@better-auth/core` `getModelName`), so the jwt plugin's already-plural `jwks` model becomes `jwkss` (no such table → `/api/auth/jwks` 500s). Fix is the jwt plugin's `schema: { jwks: { modelName: "jwk" } }` so pluralization yields `jwks`. Any future plugin whose default model name is already plural needs the same singular-base override.
- Better Auth's adapter writes JS `Date` objects for timestamp columns. The better-auth tables (`sessions`/`accounts`/`verifications`/`jwks`) and the `users.created_at`/`updated_at` columns MUST be declared `mode: "date"` (not `"string"`) in `lib/db/migrations/schema.ts` or user/session creation fails with `ERR_INVALID_ARG_TYPE` (Date passed where string expected). This is a TS-serialization-mode change only — the Postgres column type is unchanged, so switching mode needs no new migration.
- JWTs come from the `jwt` plugin: `definePayload` emits `{ userId, name, email }`; endpoints `/api/auth/token` (signed EdDSA JWT) and `/api/auth/jwks` (public key set). Workspace-invite tokens are still plain `jsonwebtoken` signed with `BETTER_AUTH_SECRET ?? NEXTAUTH_SECRET` (`lib/actions/workspace/invite.ts`), verified the same way in `app/(auth)/invitations/page.tsx`. The invitation expiry window (7 days) is pinned in THREE uncoordinated places that must stay in sync: the JWT `expiresIn` in `invite.ts`, `INVITATION_EXPIRY_MINUTES` in the invitations page (checked against the DB row's `createdAt`, independent of the JWT), and the human-readable copy in `lib/emails/workspace-invite.tsx`.
- Client sign-in is unified through `signInWithProvider(provider, callbackURL)` in `auth-client.ts`: github/google use `signIn.social(...)`, while azure/okta/keycloak use `signIn.oauth2({ providerId })` (genericOAuth plugin; provider ids are `microsoft-entra-id`/`okta`/`keycloak`). `signOut()` takes NO `callbackUrl` — callers MUST `window.location.href = "/"` (or equivalent) themselves after it resolves.
- Sign-in provider button icons (`components/auth/auth-provider-buttons.tsx`) MUST be inline `currentColor` SVG components from `components/ui/icons.tsx` (e.g. `IconGoogleMono`/`IconMicrosoft`/`IconOkta`/`IconKeycloak`/`IconGitHub`), NOT `next/image` of `@/assets/logo/*.svg`. `next/image` renders an `<img>`, which CSS `color`/`text-*` cannot tint — so on the dark `bg-surface-200` button a black/`currentColor` asset is invisible. The wrapper `<div>` in `provider-button.tsx` sets `text-foreground-100`, which only reaches inline SVGs. Use the monochrome `IconGoogleMono` for the button, not the multicolor `IconGoogle` (the latter is still used in `components/playground/utils.tsx`).
- `signInWithProvider` MUST pass `errorCallbackURL` (set to `/sign-in?callbackUrl=<original>`) to BOTH `signIn.social` and `signIn.oauth2`. The inline `{ error }` the client returns only covers failures BEFORE the browser redirects to the IdP; once the OAuth round-trip happens server-side, a callback failure (account-linking gate, missing-email rejection) is handled by Better Auth's `redirectOnError` (`oauth2/errors.mjs`), which redirects to the OAuth state's `errorURL`. That `errorURL` comes from the sign-in body's `errorCallbackURL` (`oauth2/state.mjs`) and DEFAULTS to `${baseURL}/error` (i.e. `/api/auth/error`) when unset — so without it, IdP failures never land back on `/sign-in?error=<code>` and the sign-in page's `searchParams.get("error")` UI never fires. Better Auth appends `?error=<code>` (separator-aware) itself, so the page reads it directly.
- Passwordless local-email sign-in (self-hosted only) is a custom plugin in `lib/auth-local-email.ts` (`POST /api/auth/sign-in/local-email`), mounted only when `Feature.EMAIL_AUTH`. Pending-invitation processing runs in a `databaseHooks` `session.create.after` hook in `lib/auth.ts`. The plugin creates users with `emailVerified: true` (NOT `false`): Better Auth's account-linking gate (`requireLocalEmailVerified`, defaults `true` — `node_modules/better-auth/dist/oauth2/link-account.mjs`) refuses to link an OAuth identity to a user whose local email is unverified, so a `false` here would brick a later GitHub/Google sign-in for the same address. Local-email is a no-password convenience with no verification state to protect. `EMAIL_AUTH` and OAuth providers are normally mutually exclusive (`features.ts` hides the dummy email input when any provider is configured), so this only bites when `FORCE_EMAIL_AUTH=true` runs both at once.
- **`callbackUrl` is attacker-controlled and must be sanitized to a same-origin relative path** before any client navigation. The local-email flow signs in via a `$fetch` POST (`signInLocalEmail`) that returns JSON and does NOT redirect — navigation is a pure client-side `router.push(callbackUrl)` (`components/auth/email-sign-in.tsx`), so Better Auth's `trustedOrigins` (which only guards its own server-side OAuth redirects) never sees it. The trust boundary is the query string entering `app/sign-in/page.tsx` and `app/sign-up/page.tsx`; both call `sanitizeCallbackUrl(searchParams?.callbackUrl)` (`lib/utils.ts`), which rejects anything not starting with a single `/` (absolute `https://evil.com/x`, protocol-relative `//evil.com`, backslash `/\evil.com`, and `\t\n\r`-obfuscated variants browsers normalise) and falls back to `/onboarding`. A `new URL(callbackUrl)`-style check is NOT sufficient — it lets absolute external URLs through (open redirect). The sanitized value also feeds `signInWithProvider`'s `errorCallbackURL`, so OAuth is covered by the same page-level guard.
- `proxy.ts` middleware calls `auth.api.getSession({ headers: req.headers })` directly (no `withAuth`). Next.js 16 middleware runs Better Auth on the Node runtime, so the Postgres session lookup works there. The unauthenticated-redirect-to-`/sign-in?callbackUrl=` behaviour for app trees is replicated inline.
- **Migration backfill for existing users** (`0089_lam_1720_better_auth.sql`): adding `users.email_verified boolean DEFAULT false` is NOT enough on its own. Pre-existing users have a `users` row but no `accounts` row, so their first OAuth sign-in hits Better Auth's account-*linking* path in `handleOAuthUserInfo`, which is gated on `requireLocalEmailVerified` (defaults to `true`). With every migrated row at `email_verified = false`, that gate returns `"account not linked"` and bricks every existing user. The migration therefore runs `UPDATE users SET email_verified = true` right after adding the column — these users were already IdP-authenticated, so they're effectively verified. The `trustedProviders` list does NOT save them (it only exempts the separate `!isTrustedProvider && !userInfo.emailVerified` term).
- **The personal `api_keys` table is obsolete and unused.** It is NOT the project-level `project_api_keys` table (which app-server auth reads on every request). The user-level `api_keys` table is referenced by **zero** code in either backend (`app-server`, `lmnr-private`) — nothing ever reads it as a credential, and no personal key is created on sign-up. The physical table still exists in the DB (kept, not dropped) with its original non-unique `api_keys_user_id_idx` index — do NOT introduce code that writes to it. If you need a per-user credential, use `project_api_keys` patterns or design a fresh table.

## CLI authentication (BetterAuth Device Flow → user-scoped tokens)

- The CLI stores **BetterAuth tokens** (user-scoped), NOT a project API key. `lmnr-cli login` walks BetterAuth's native `deviceAuthorization` flow end-to-end (no custom poll endpoint). `lmnr-cli setup` does the same login AND additionally mints a project API key that it writes ONLY to `./.env` (never into `credentials.json`) via our `POST /api/cli/api-key` endpoint.
- **Token model:**
  - **Access token** = a 15m EdDSA JWT minted by `GET /api/auth/token` (with the session token as bearer) → response `{ token }`. Verifiable via `/api/auth/jwks`. This is what app-server will eventually validate statelessly (JWKS). App-server JWT validation is a deliberate LATER phase — the CLI's JWT is NOT accepted by app-server yet, so `lmnr-cli sql`/ingestion against app-server with the JWT does not work this iteration.
  - **Refresh token** = the BetterAuth **session token**, returned as `access_token` from `POST /api/auth/device/token`. Durable (session `expiresIn` default 7 days, rolling). Refresh op = re-call `GET /api/auth/token` with the session token → fresh JWT, no browser.
- Endpoints, in `login` flow order:
  - `POST /api/auth/device/code` — BetterAuth RFC 8628 code mint. CLI sends `{client_id:"lmnr-cli", scope:"projects:rw"}`.
  - Browser → `/device?user_code=<code>` — server component at `app/(auth)/device/page.tsx`. The `(auth)` layout + `proxy.ts` matcher gate unauthenticated visitors to `/sign-in?callbackUrl=/device?user_code=...`. Server-side: claim the code via `auth.api.deviceVerify(...)`, then render **Approve / Deny only** (no project picker — the credential is user-scoped, nothing to scope at approval). Approve → `authClient.device.approve({userCode})`; Deny → `authClient.device.deny({userCode})`.
  - `POST /api/auth/device/token` — BetterAuth's NATIVE token endpoint (we own no custom poll endpoint). CLI polls here; on approval returns `{ access_token (=session token), expires_in, ... }`.
  - `GET /api/auth/token` (session bearer) → `{ token }` 15m JWT.
  - `GET /api/auth/get-session` (session bearer) → `{ user: { id, email } }` for profile metadata.
- **`POST /api/cli/api-key`** (`app/api/cli/api-key/route.ts`) — mints a project API key for the session user (the `setup` flow is the only caller today, but the endpoint is generic, not setup-bound). Auth via session bearer (`auth.api.getSession`). Body (zod `.strict()`): `{ projectId?, deviceName? }`. With `projectId` → membership-check + mint. Without → 1 project mints; >1 returns `400 {error:"project_ambiguous", projects:[{id,name,workspaceName}]}`; 0 returns `400 {error:"no_projects"}`. Returns `{apiKey, apiKeyId, projectId, projectName, workspaceId, workspaceName}`. The minted key goes to `./.env` only.
- **The `bearer()` plugin is required.** `auth.api.getSession({ headers })` only accepts cookie-borne sessions by default; without `bearer()` an `Authorization: Bearer <session-token>` header is ignored. The device-flow `access_token` IS a session token, so the bearer plugin is what lets it round-trip through `getSession()` (used by `/api/auth/token`, `/api/auth/get-session`, and `/api/cli/api-key`).
- **CLI credentials shape.** `~/.config/lmnr/credentials.json` (mode 0600, **keyed by `userId`**, version 1) stores tokens only: `sessionToken` (refresh), `accessToken` (the 15m JWT), `accessTokenExpiresAt` (from JWT `exp`), `sessionExpiresAt?` (from device token `expires_in`), `issuer`, `baseUrl`, `userEmail?`, `userId`, `createdAt`, `lastUsedAt?`. NO project API key, NO `apiKeyId`. `resolveAuth` refreshes the JWT when within ~30s of expiry (re-mint via `/api/auth/token`); a 401 means the session expired → "run `lmnr-cli login`". The returned JWT bearer is not yet accepted by app-server (later phase).
- **Logout** best-effort POSTs `/api/auth/sign-out` (session bearer) to revoke the session server-side, then deletes local creds; `--all` loops all profiles.
- **App-server later phase (two-flow validation):** the eventual design is JWT-via-JWKS for the CLI (user-scoped — so app-server must derive the project from the request path / an explicit `--project` arg, since the JWT carries no project) and project API key for the SDK. Not implemented here.
- **`validateClient: async (id) => id === "lmnr-cli"`** in `lib/auth.ts`. Multi-tenant client registration is intentionally out of scope.

## Project API Key Expiration

- `project_api_keys` carries two extra columns (migration `0094`): `user_id uuid` (FK→`users` `ON DELETE SET NULL`, records the creating user for audit — NOT cached, no UI) and `expires_at timestamptz` (null = never). The app-server `ProjectApiKey` struct (`app-server/src/db/project_api_keys.rs`) maps ONLY `expires_at` (with `#[serde(default)]` so pre-existing cache entries written before the column decode to `None`); `user_id` is frontend-only and never read by app-server.
- **Lazy expiry + cleanup** lives in `get_api_key_from_raw_value` (`app-server/src/api/utils.rs`): after resolving the key (cache-hit OR DB-read path), if `expires_at.is_some() && Utc::now() > expires_at` it removes the cache entry, `DELETE`s the DB row by hash (`delete_api_key_by_hash`), and returns an error. The expiry check is on the COMMON path (not per-validator) so both `project_auth` and `project_ingestion_auth` enforce it. A future pg_cron sweep is hygiene-only, out of scope.
- **`GET /v1/project` is project-key authed (`project_auth`), registered inside the broad `web::scope("/v1")`.** The handler (`api/v1/projects.rs::get_current_project`) carries `#[get("/project")]` (full path on the macro). It blocks ingest-only keys (that's `project_auth`'s job) — fine because `lmnr-cli setup` doesn't probe it; the CLI is logged in by setup time and resolves the project via the user-token endpoint below.
- **`POST /v1/cli/project` (`api/v1/cli/mod.rs::resolve_project`) resolves which project a project API key belongs to, for `lmnr-cli setup`.** User-token authed (`CliUserAuth`, mounted in the `/v1/cli` scope wrapped by `cli_auth`): the API key travels in the JSON body (`{ apiKey }`), NOT in `Authorization` (which carries the user JWT). It calls `get_api_key_from_raw_value` to verify the key, then `is_user_member_of_project` so a leaked key can't reveal a project the user isn't a member of (401 on bad key, 403 on non-member). Returns `{ projectId }`. The CLI side is `CliResource.resolveProjectByApiKey` in `lmnr-ts` (returns a tri-state `ProjectKeyProbe`: `ok`/`invalid` (401)/`unverifiable` (403/network/other)).
- **CLI-minted keys (`POST /api/cli/api-key`) have `expiresAt: null`** — both the explicit-`projectId` branch and the single-project fallback. A setup key that silently expired would break ingestion with no renew UI. The minting `userId` is always recorded.
- Frontend expiration UI is days-based: the dialog (`generate-key-dialog-content.tsx`) offers 1/7/30/365/Never; the route (`api-keys/route.ts`) converts `expiresDays` → absolute `expiresAt` ISO string. **The default-expiry preselection is frontend-only UX** (`handleKeyTypeChange` in `project-api-keys/index.tsx`): ingest-only keys preselect 1 day, default keys preselect 30 days. The backend has no per-key-type default; a CLI key explicitly passes `expiresAt: null`.
- The frontend `createApiKey` action caches the new key with `{ expireAt: new Date(expiresAt) }` (matching app-server's 1-day TTL ceiling) and deliberately omits `userId` from the cached payload.

## Analytics / PostHog

- Client-side analytics is centralized in `frontend/lib/posthog/`. Feature code should import `track` from `@/lib/posthog` — never import `posthog-js` directly.
- Server-side PostHog client lives at `@/lib/posthog/server` (separate import path to avoid bundling `posthog-node` into client bundles).
- The `AnalyticsProvider` (in `lib/posthog/provider.tsx`) handles both PostHog init and user identification. It wraps `PostHogProvider` from `posthog-js/react` so `usePostHog()` still works as an escape hatch.
- Custom events use `track(feature, action, properties?)` which emits `${feature}:${action}`. The `Feature` type is defined in `lib/posthog/client.ts` — add new categories there before using them. Use `'sessions'` for trace sessions and `'debugger_sessions'` for CLI debugger sessions — these are distinct features.
- All tracking is no-op when PostHog is disabled (`POSTHOG_TELEMETRY !== "true"`). No conditional checks needed in feature code.
- For page-view tracking on server-component pages, use the `PageViewTracker` client component at `components/common/page-view-tracker.tsx` — server components cannot call `track` directly (no hooks). For server-action buttons that need tracking, wrap them in a dedicated `"use client"` component that calls `track` before invoking the server action (see `components/invitations/invitation-actions.tsx`).
- `PageViewTracker` deliberately uses an empty `useEffect` dependency array so it fires exactly once on mount. Callers pass inline `properties` object literals (`{ slug }`, `{ traceId }`), which would otherwise create a new reference on every render and re-fire the event.
- Auth flows (sign-in/sign-up) track `*_attempted` before the provider redirect, not on success — the OAuth/email flows navigate away before any success callback runs, so the attempt is the last reliable hook. `EmailSignInButton` takes an `action` prop (`sign_in_attempted` | `sign_up_attempted`) because the same component is rendered on both `/sign-in` and `/sign-up`.
- Tracking calls must be guarded by success (`res.ok`). Firing `track(...)` after an unchecked `await res.text()` records events for failed requests and corrupts metrics.
- `track(...)` accepts a 4th arg `{ sendInstantly: true }` that maps to posthog-js's `send_instantly` and bypasses the batching queue. Use it whenever the very next line can tear down the page before the batch flushes: OAuth/email `signIn()` redirects (`components/auth/*`), `router.refresh()` after a mutation (`switch-tier-dialog.tsx`), or any `window.location.assign/href` navigation. Batched events are lost because the request is aborted when the page unloads.
- Server-side captures from Better Auth database hooks (e.g. `auth:user_created` in `lib/auth.ts`) are fire-and-forget: `posthog-node`'s default 10s `flushInterval` schedules a background flush from the active `setTimeout` (which keeps the per-request `PostHog` instance alive until the flush fires), so the Next.js container delivers the event without an explicit `shutdown`/`flush`. Do NOT `await client.shutdown(...)` on the request path — it adds up to the shutdown timeout to the login response if PostHog ingest is degraded. Wrap the block in try/catch so analytics failures cannot break login.
- `auth:user_created` fires exactly once per brand-new account, from the `databaseHooks.user.create.after` hook in `lib/auth.ts`.
- PostHog `distinctId` across the codebase is the user's **email**, not the DB user id. The single source of identification is the client-side `identify(email, { email })` call in `lib/posthog/provider.tsx` (mounted from the root `app/layout.tsx` so it runs on every authenticated page). Per PostHog's docs, server-side `posthog.identify(...)` only updates the person profile and CANNOT do the anonymous→identified linking the browser SDK does (the server has no anonymous session), so we deliberately don't call `identify` from `posthog-node` — it would just add redundant `$identify` events without contributing any new info. Any server-side `client.capture(...)` (e.g. from Better Auth database hooks) must still pass `distinctId: email` directly on each capture — passing the DB user id creates a separate PostHog person profile and detaches `$set_once` properties and funnel events from the real user.
- Workspace grouping uses the client-side `WorkspaceGroupTracker` (`components/common/workspace-group-tracker.tsx`), which calls `posthog.group("workspace", workspace.name, { name, id })` on mount. Per PostHog's web-SDK docs, `posthog.group(...)` does two things in one call: emits `$groupidentify` to register/update the group entity's properties AND associates every subsequent session event with `$groups: { workspace: <name> }`. We rely on this so client-side `track(...)` events are auto-tagged for workspace-level analytics — do not use server-side `posthog.groupIdentify(...)` instead, since that only updates the group entity and does NOT propagate group context to client events. The tracker is rendered in `app/workspace/[workspaceId]/page.tsx` (inside `WorkspaceMenuProvider`) and `app/project/[projectId]/layout.tsx` (inside `ProjectContextProvider`); render it in a component that already fetches the workspace so we don't add a duplicate query just to access `workspace.name`. Group key is `workspace.name` (readable in the PostHog UI) — do NOT key by id, PostHog group filters display the key directly. The tracker's `useEffect` is gated on `[workspaceName, workspaceId]` so it only re-fires on workspace switch, not every render.
- **The npm module build of `posthog-js` does NOT buffer pre-init calls** — `capture`/`identify`/`reset` called before `posthog.init()` are dropped with a console warning (only the snippet-injected `array.js` build has the `_execute_array` queue). React runs child effects before parent effects, so init must NOT live in a `PostHogProvider` `useEffect`: every child `track()` on first mount of a full page load (e.g. `auth:sign_in_page_viewed`) would fire pre-init and be lost. Init runs during the provider's render via a lazy `useState` initializer (`lib/posthog/provider.tsx`), guarded `typeof window !== "undefined"` for SSR and idempotent via `posthog.__loaded` so StrictMode double-invocation can't re-init.
- **`posthog.identify(newId)` on a browser that is still identified as a DIFFERENT user silently skips the `$identify` event** (posthog-js only takes the merge path when the persisted user_state is "anonymous") — it just switches `distinct_id` and sends a `$set`, so the pre-signup anonymous history (blog/landing pageviews) is never merged into the new user. The `identify()` wrapper in `lib/posthog/client.ts` therefore calls `posthog.reset()` first when `_isIdentified() && get_distinct_id() !== userId`, forcing the anonymous→identified merge path for the new account. Logout paths (`account-menu.tsx` `handleLogout`, `session-sync-provider.tsx` cross-tab listener) also call `reset()` per PostHog's recommended practice, so this wrapper guard is the backstop for sessions that ended via an expired session rather than an explicit logout.
- `AdvancedSearch` submit tracking lives in a single place: the store's `submit` function (`components/common/advanced-search/store/index.tsx`). `removeTag` and `applyRecentSearch` funnel through `submit`, so they are covered automatically; do not instrument them separately. `addCompleteTag` and `clearAll` do NOT funnel through `submit` — we intentionally accept under-counting there in exchange for one consistent metric definition (same `filterCount`/`hasSearch` logic everywhere). The `resource` prop is threaded into the store so the event can label its origin (`traces` / `spans` / `unknown`).
- `AdvancedSearch` autocomplete fetching is gated in `components/common/advanced-search/index.tsx`: SWR only hits `/api/projects/<id>/<resource>/autocomplete` when `resource === "traces" | "spans"` AND no `suggestions` map was passed. Omit the `resource` prop (or pass anything else) on pages that have no autocomplete endpoint (e.g. evaluations) to suppress the request. Tag-level suggestions in `components/common/advanced-search/components/tag.tsx` also silently degrade to `[]` when `AUTOCOMPLETE_FIELDS[resource]` is undefined, so no backend endpoint is required for non-traces/spans consumers.

## Self-hosted Telemetry (anonymous usage heartbeat)

- `frontend/lib/telemetry/` emits an anonymous `self_hosted_heartbeat` PostHog event for Helm/self-hosted deployments. Gated by `Feature.TELEMETRY` (`lib/features/features.ts`): on by default — only off when `LAMINAR_TELEMETRY_DISABLED === "true"` (operator opt-out) OR `LAMINAR_CLOUD === "true"` (cloud has first-party analytics). Deliberately does NOT gate on `ENVIRONMENT`, so the many self-hosted installs that don't set `ENVIRONMENT=FULL`/`PRODUCTION` are still observed; the `environment` property on every event lets dev/staging be filtered downstream instead of dropped at the source. Distinct from `Feature.POSTHOG` (that's cloud product analytics keyed on email) — telemetry keys on an opaque per-deployment UUID and never carries PII/customer content.
- Identity lives in a **separate `telemetry` Postgres schema** (NOT public), created via boot-time DDL in `lib/telemetry/instance.ts`, NOT a drizzle migration — so it can't break installs where the app role lacks CREATE on public, and the OSS migration set stays telemetry-free. The `telemetry.instance` table is a singleton (boolean PK `id` always true) holding `instance_id uuid` + `last_reported_at`.
- Cross-replica dedup is a CAS window-claim: `claimReportingWindow(intervalMs)` does an atomic `UPDATE ... WHERE last_reported_at IS NULL OR last_reported_at < now() - interval`, returning a row only to the winner. The job timer polls hourly but the 6h cadence is enforced by this DB claim, so multiple frontend pods + restarts can't over-report. Wired fire-and-forget from `instrumentation.ts::register()` (outside the `LOCAL_DB` gate, after Laminar init).
- **Counting the exposed `_v0` views directly is impossible** — every view in `4_views.sql` etc. is a project-parameterized view function (`WHERE project_id={project_id:UUID}`), so `count() FROM spans_v0` errors. `lib/telemetry/stats.ts` instead maps each exposed view to its physical backing table (`spans_v0`→`spans`, `traces_v0`→`traces_agg`, `clusters_v0`→`signal_event_clusters`, `event_clusters_all_v0`→`events_to_clusters`, etc.) and reads `system.tables.total_rows` — instant, no FINAL scans, no per-project iteration. Keep `VIEW_BACKING_TABLES` in sync with the query-engine `TableRegistry` (`validator.rs`). Counts are emitted as exact integers (`count_<view>_v0`); they are PRE-merge row counts, so folding tables (`traces_agg`'s per-batch partials, the RMTs) read above their logical entity count — fine for a usage-magnitude signal.
- Version comes from `NEXT_PUBLIC_APP_VERSION` (baked at Docker build, set as runtime ENV) — `npm_package_version` is empty in prod because the container starts via `node server.js`, not an npm script. Optional `LAMINAR_TELEMETRY_LABEL` lets an operator opt into being identifiable. The capture sets `$ip: null` (drops the source IP entirely, not just geoip enrichment) plus `disableGeoip: true`, so no IP is ever stored against the deployment.

## Render Templates (JSX iframe renderer)

- User-authored render templates run inside a sandboxed iframe (`frontend/components/ui/template-renderer/jsx-renderer.tsx`) via Preact + twind. The iframe's initial `<script>` overwrites `window.fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, and `navigator.sendBeacon` with throwing stubs so template code cannot exfiltrate project data. Do NOT loosen the CSP `connect-src` or restore these globals — any new capability the template needs must be piped in through the parent-to-iframe `postMessage` channel instead.
- AI generation lives outside the app: the dialog exposes a "Copy prompt" button that copies `RENDER_TEMPLATE_AI_PROMPT` from `lib/actions/render-template/prompts.ts` to the clipboard. Users paste it into their own AI tool with their data and request, then drop the returned JSX into the editor. There is no `/render-templates/generate` route and no in-dialog AI panel.
- The iframe's twind config (`jsx-renderer.tsx`) is wired up to Laminar's design tokens via `LAMINAR_IFRAME_THEME` in `frontend/components/ui/template-renderer/theme.ts`. This means semantic classes like `bg-background`, `text-foreground`, `bg-card`, `text-primary`, `border-border`, `text-destructive`, `text-success`, `text-llm`, `text-tool`, `text-subagent` all resolve inside generated templates. The prompt's style guide and example use these semantic classes — do NOT use raw palette names (`text-sky-400`, `bg-neutral-900`, etc.), which drift from the rest of the platform and won't follow theme changes. When you change a token in `globals.css` (the `:root` block), mirror it as a hex literal in `theme.ts` — the iframe runs twind from a CDN and has no access to our CSS variables.
- Span and trace templates live in ONE Postgres table, `render_templates`, with a `type` text column (`'span'` default | `'trace'`) and a nullable `where_clause` text column — behind ONE endpoint family (`/api/projects/[projectId]/render-templates`, GET takes an optional `?type=` filter; actions in `lib/actions/render-template/index.ts`). `type` is set at create and immutable on update. The frontend `TemplateScope` ("span" | "trace") maps 1:1 onto the `type` column (`TemplatePickerProvider`'s `scope` prop drives the `?type=` list filter and the POST body's `type`). Trace templates carry an optional `where_clause` SQL fragment; `getTraceRenderData` (`frontend/lib/actions/trace/render-data.ts`) composes it as `SELECT ... FROM spans WHERE trace_id = {traceId: UUID} AND (<fragment>) ORDER BY start_time` through `executeQuery`, so the app-server query-engine validator is the security boundary — same trust model as the SQL editor. Do NOT sanitize or parse the fragment in the frontend. Results are capped at `MAX_TRACE_RENDER_SPANS` (256) and delivered as `{ spans, truncated }`. The trace view's "Custom" tab (`components/traces/trace-view/custom-view/`) fetches this via POST `/api/projects/[projectId]/traces/[traceId]/render-data`.
- Trace-scoped "Copy prompt" embeds a live trace outline: GET `/api/projects/[projectId]/traces/[traceId]/span-outline` (`lib/actions/trace/span-outline.ts`) returns one representative span per distinct `(name, span_type)` (`argMin(col, start_time)` so all sample columns come from the same row — not `any()`), with `occurrences` counts, `input`/`output`/`attributes` JSON-parsed FIRST and then leaf-truncated (64-char strings / 10-item arrays / depth 8) — truncating the raw JSON string would cut mid-token. `buildTraceRenderTemplatePrompt` (`lib/actions/render-template/prompts.ts`) embeds the outline + the WHERE-fragment contract and asks the LLM for TWO fenced blocks: ```sql (fragment, empty = all spans) then ```jsx. The outline deliberately ignores the template's current whereClause (the LLM must see the whole trace to choose a filter). From settings (no traceId) the prompt falls back to a placeholder outline.
- `ManageTemplateDialog` lives at `frontend/components/ui/template-renderer/manage-template-dialog/` (folder with `index.tsx`, `code-editor.tsx`, `data-panel.tsx`). Layout: left column is a Preview/Data tab pair (Preview = live `JsxRenderer`, Data = the `testData` JSON editor in `DataPanel`); right column has the name input + save button, the "Copy prompt" affordance, and `CodeEditor` for the JSX. `DataPanel` pretty-prints `testData` once on mount with `shouldDirty: false` and again on CodeMirror `onBlur` with `shouldDirty: true` — there is no Format button. The dialog is a shared form UI consumed both from the inline template picker (`components/ui/template-renderer/index.tsx`) and from project settings (`components/settings/render-templates/`). Both callers must wrap it in a `FormProvider` whose form shape matches `ManageTemplateForm` — the dialog uses `useFormContext` and will crash without a provider. The settings wrapper in `render-template-dialog.tsx` fetches the full template on open and resets the form; the inline picker already has the template loaded via SWR + `fetchTemplate`. The Span-filter input is the shared `SQLEditor` (`components/sql/sql-editor.tsx`, CodeMirror) scoped via `schema={{ tables: ["spans"] }}` so autocomplete only offers spans columns; it's multiline, so Enter inserts a newline — only the "Test" button (shown when traceId is present) POSTs the draft `whereClause` to the render-data endpoint and pipes the response into the form's `testData` — safe because `custom-view`'s own fetch is `isManaging`-gated, so the provider's testData-sync effect won't clobber it while the dialog is open. Note: `fetcherJSON` throws with the RAW backend response body as the message, so for query-engine rejections that's a JSON string like `{"error":"..."}` — routes that surface these to users must unwrap it (see `unwrapErrorMessage` in the render-data route) or the UI shows raw JSON.

## Project Settings (`projects.settings` JSONB)

- Per-project knobs live in `projects.settings JSONB DEFAULT '{}'` — one row per project, one column for ALL settings, NOT one column per setting. Adding a new setting means adding a typed field on each side, no migration. The column travels on the same row as `ProjectWithWorkspaceBillingInfo` (Rust), which is cached in Redis under `project:{project_id}`, so the read lookup is free after the first batch.
- **Writes are Next.js-only.** The Rust app-server is read-only — `db::projects::ProjectSettings` (Rust struct) deserializes via `serde_json` with `#[serde(default)]` on every field so older rows / unknown keys don't break. Malformed JSON falls back to defaults and logs a warning rather than poisoning the cache.
- Writes go through `updateProjectSettings` in `lib/actions/project/settings.ts`. The Zod schema is `.strict()` (unknown keys → 400, not silent drop into the JSONB). Tier gates per key live in `PRO_TIER_KEYS` — `removePii` is the only entry today; gates are applied server-side regardless of UI state. Update SQL uses Postgres `||` JSONB merge so partial updates preserve unspecified keys without a read-modify-write race.
- After every successful update, the action removes `project:{id}` from the Redis cache so the next ingest batch reads the new value. Both sides of `ProjectSettings` (TS Zod, Rust `serde`) MUST stay in sync — drift surfaces as one-sided defaults, not crashes, so it can be silent.
- API: `PATCH /api/projects/:projectId/settings` with body `{ settings: <Partial<ProjectSettings>> }`. Auth + project-membership gate at the top of the route via `getServerSession` + `isUserMemberOfProject` returning 401 / 403 JSON; do not use `requireProjectAccess` here, it `redirect()`s / `notFound()`s which is the page-tree pattern, not an API-route shape.

### PII redaction (`settings.removePii`)

- Setting `removePii=true` on a project routes every span ingested for that project through the `pii-redactor` gRPC service before storage.
- Frontend toggle: `components/settings/pii-redaction.tsx`, mounted in the General tab. Pro-tier gated in BOTH the UI (greyed `Switch` + "Pro plan required" badge) AND the server action (rejects non-Pro/Enterprise with 403). The server gate is the source of truth; the UI gate is purely UX.
- **The Pro-tier gate only applies on Laminar Cloud.** Self-hosted installs aren't on tiered billing — their only seeded `subscription_tiers` row is `unlimited` (`frontend/lib/db/initial-data.json`), which would never satisfy `PRO_LIKE_TIERS`. Both gates (`PRO_TIER_KEYS` check in `updateProjectSettings`, `isProTier` in `pii-redaction.tsx`) short-circuit to allowed when `Feature.LAMINAR_CLOUD` is off, so self-hosters can freely toggle `removePii`. The two sides must stay in sync; the server side is authoritative.
- Redaction runs in the consumer (`process_span_messages`) AFTER `build_dedup_batch` and BEFORE the `llm_messages` ClickHouse insert. For dedup'd LLM spans (most LLM spans — root spans excepted) `span.input` is `None` on the wire, so redaction targets `dedup.messages[k].content` directly: this single buffer is what the `llm_messages` insert reads AND what Quickwit indexing reads via the `*_new_message_indices` columns, so one update covers both storage tiers. Already-seen messages are NOT in `dedup.messages` and ride the wire as hashes only — they were redacted on first emit. Root LLM spans (which keep `span.input` populated for the trace-list preview) plus non-LLM spans get whole-`input` redaction. `span.output` is always whole-redacted.
- The redactor is best-effort: gRPC failures, response-length mismatches, and parse errors all log and return without mutating the batch. Redaction failures must NEVER block trace ingestion.
- After redaction mutates `dedup.messages[k].content` in place, the `redact_spans_in_place` write-back loop also patches `dedup.span_content_bytes[dedup_idx]` so the post-dedup input-bytes loop bills the redacted size, matching the "size reflects redacted content" invariant on `estimate_size_bytes`.

## App-server env vars (`src/env/`)

- Every env var the app-server reads is registered in `app-server/src/env/` (one submodule per domain: `server`, `workers`, `batching`, `clickhouse`, `database`, `mq`, `quickwit`, `llm`, `secrets`, `connections`, `rate_limit`, `observability`, `notifications`, `storage`, `sql`, `debugger`, `mock`). Do NOT inline a string literal env name or hand-roll a `std::env::var(...).parse().unwrap_or(...)` chain at a call site — add/look up the entry here.
- **`mod env` shadows `std::env`.** Inside any file that does `use crate::env;`, you MUST write `std::env::var(...)` (fully-qualified) for bare reads — a plain `env::var` resolves to this module and won't compile.
- Two kinds of entry:
  - **Typed descriptors** `NumEnv<T>` / `StringEnv` / `BoolEnv` for vars with a static default — `pub const FOO: NumEnv<u32> = NumEnv::new("FOO", 4);`, read via `env::workers::FOO.get()`. `.get()` trims, treats empty string as unset, parses, and falls back to the default (empty-string-as-unset matters for k8s ConfigMap keys). `BoolEnv` accepts `true/1/yes/on` + `false/0/no/off` case-insensitively. Float types work too (`NumEnv<f32>` for `EXTERNAL_TRACING_SAMPLE_RATE`), since `.get()` is generic over `FromStr`.
  - **`NumEnv::clamp(min, max)`** for a var whose valid range is narrower than its type (a 0.0-1.0 probability, a bounded worker count) — `SAMPLE_RATE.clamp(0.0, 1.0)`. Use it instead of `f64::clamp` / `Ord::clamp` at the call site: those PANIC when `min > max` and `f64::clamp` propagates NaN, and an env descriptor must never be able to take the process down. A non-finite parse (`NaN`, `inf`, or an overflowing literal like `1e999` — `f64::from_str` returns `inf` for that, it does NOT error) falls back to the DEFAULT rather than clamping to a bound, because clamping would silently promote a typo to the most extreme legal setting (for a sample rate: "keep everything", the exact cost blowup the clamp exists to prevent). Note the Sentry SDK's own `sample_should_send` already clamps internally, so for `EXTERNAL_TRACING_SAMPLE_RATE` the clamp is defence-in-depth rather than panic-prevention. The generic bound needs the local `FiniteNum` trait (impl'd true for every int, real check for `f32`/`f64`) because `is_finite` lives on the float types, not on a shared numeric trait in std.
  - **Bare-name `&str` constants** (`pub const URL: &str = "CLICKHOUSE_URL";`) for required secrets/connection strings that `expect()` at boot and for vars consumed only inside multi-var feature detection — forcing a default onto those would be misleading, so they keep their read logic at the call site and only borrow the name.
  - `env::num_with_default(name, default)` free fn for the rare var whose default is a runtime value (a crate const) and so can't be a `NumEnv` const.
- **`cargo fmt` and `cargo check --features signals` both fail in OSS** because the `signals` feature gates modules whose files live only in `lmnr-private`. `cargo fmt` walks the module tree and errors on the missing `mod agent`. To format `main.rs` (or anything that triggers the tree walk), `touch` empty stubs and run `rustfmt --edition 2024 <file>`, then delete the stubs. Current stub set: `src/agent.rs`, `src/clustering/private.rs`, `src/signals/private.rs`, `src/traces/previews.rs`, `src/traces/sampling.rs`, `src/api/v1/cli/agent.rs`, `src/ch/private.rs`, `src/db/private.rs`, `src/env/private.rs` (rustfmt names each missing mod one at a time, so just iterate). Note `rustfmt --check` on `main.rs` with stubs also reports diffs in OTHER files it pulls in (including the empty stubs themselves) — filter the output to `Diff in .*main.rs` before concluding main.rs needs changes. Per-file `rustfmt` on leaf files works without stubs. Default-feature `cargo check`/`cargo fmt` is the real gate.

## Debugger Replay Cache

- Server-side cache that lets the SDK replay recorded LLM responses during a debugger re-run. Orchestration lives in `app-server/src/debugger/mod.rs::lookup`; the HTTP surface is `POST /v1/rollouts/{session_id}/cache` (`api/v1/rollouts.rs::lookup_cache`). Cache identity is `(project_id, replay_trace_id, normalize_needle(cache_until))` — the `cache_until` window is part of the key so the same trace can be replayed at different cache points within or across sessions; a wider/narrower window is a distinct namespace that warms cold rather than reusing a stale window's entries (and a warm-but-absent hash stays a true terminal MISS *for that window*). `session_id` is in the path for route consistency only and is NEVER part of the cache key — warmed content is session-independent, so cross-session sharing of the same trace+window is always safe and is what scoping the lock + ready marker by the needle (not just `(project, trace)`) preserves.
- **Three wire outcomes** (`CacheLookupResponse`, `#[serde(rename_all="camelCase", tag="outcome")]`): `hit` (replay this response), `miss` (warm cache, hash absent → SDK runs live forever), `live` (warmup timed out → run live this call, retry next). MISS ≠ COLD ≠ Live: `Live` is ONLY the warmup-timeout path, never an absent hash in a warm cache. COLD never surfaces directly — the block-and-warm path turns it into hit/miss/live.
- **Input hash** = `hex(blake3(canonical_json(messages_without_system)))`, computed by `debug_input_hash` in `traces/input_dedup.rs`. This hashes the WHOLE message array (system messages removed) as one blob — distinct from the per-message dedup hashing in the same file. **EVERY** `role=="system"` message is stripped regardless of content or position (leading, trailing, repeated) — a deliberate `role`-only filter that does NOT reuse `prompt_hash::extract_system_message` (which strips a single system message and only when it has extractable text). The contract is "drop all system messages" because the coding agent edits its own system prompt between iterations; the SDK mirrors this exactly. Keys are sorted recursively, array order preserved, NO number canonicalization in v1. Cross-language parity vectors live at `app-server/test/data/debug/input_hash_vectors.json` — the SDKs MUST copy this fixture and produce identical hashes; the app-server impl is the reference.
- **Warmup reads through `spans_v0`**, which is a **parameterized view** (`WHERE project_id = {project_id:UUID}` baked into the view body). Pass project scope via `.param("project_id", project_id)` on the query builder, NOT as a SQL `WHERE` clause — see `ch/spans.rs::query_debug_cache_spans_page`. Warmup query selects `LLM` + `CACHED` spans (string `span_type` from the view), `ORDER BY start_time ASC`, paged. Output attributes (`lmnr.sdk.raw.response`, `gen_ai.output.messages`, `gen_ai.response.finish_reason`) are pulled via `JSONExtractRaw(attributes, ...)` (empty string when absent).
- **Tagged response envelope** (the SDK must match this): stored `response` is `{ "type": "raw", "response": <lmnr.sdk.raw.response> }` when the raw attribute is present, else `{ "type": "genAi", "messages": <gen_ai.output.messages>, "finishReason": <reason|null> }`. Raw is preferred; a span with neither output source is skipped (its input hash becomes a MISS).
- **`cache_until`** is a span-id needle: hyphen-stripped + lowercased, suffix-matched against `span_id.simple()`, INCLUSIVE of the matched span. Needle genuinely absent (full scan, no match, no ceiling) → empty warm (every lookup a clean MISS, the safe degrade). Ceiling hit before the needle → keep the bounded prefix. A single span whose response alone exceeds `MAX_BYTES` is skipped (like an output-less span) and the scan continues toward the needle — only a *cumulative* overflow trips the byte ceiling, so one oversized span can't abort the whole warmup. Dedupe is earliest-by-`start_time` wins, and the earliest occurrence claims its input hash in `seen` *even when its response is uncacheable* (oversized) — otherwise a later span with the same input would be cached and a lookup would replay that later call's output instead of degrading to a clean MISS. So an uncacheable-earliest input is a MISS, never a wrong-response HIT. Two size knobs: query page size (strict, 8) vs cache ceiling (`MAX_SPANS` 256 / `MAX_BYTES` 64 MiB).
- **Spawn-and-wait warmup**: one winner takes a Redis lock (`try_acquire_lock`), `tokio::spawn`s `warm` (which writes entry keys + a ready marker, all with TTL — even an empty warm sets the marker so COLD can't persist), then releases the lock. Winner AND waiters both poll the ready marker up to `WARMUP_TIMEOUT_SECONDS`; on timeout they return `Live`. The warm runs a sibling heartbeat task that `renew_lock`s the lock every ~`LOCK_TTL_SECONDS/3` so a warm that paginates a large trace can outlive a single `LOCK_TTL_SECONDS` without the lock expiring and a second lookup double-warming; the heartbeat is `abort()`ed before the lock is released. `renew_lock` is a `CacheTrait` method (Redis `EXPIRE`, returns false when the key is already gone; in-memory updates the `locks` map and reports false for an expired entry) — note `set_ttl` does NOT touch the in-memory `locks` map, which is why a dedicated renew primitive exists. Six env knobs, all `DEBUGGER_CACHE_*` (`QUERY_PAGE_SIZE`, `MAX_SPANS`, `MAX_BYTES`, `TTL_SECONDS`, `LOCK_TTL_SECONDS`, `WARMUP_TIMEOUT_SECONDS`), read once via `LazyLock`. Key-name constants are in `cache/keys.rs` (`DEBUGGER_CACHE_KEY` / `_READY_KEY` / `_LOCK_KEY`); concrete keys are `{KEY}:{project_id}:{trace_id}:{needle}[:{input_hash}]` where `needle = normalize_needle(cache_until)` — all three keys (entry, ready, lock) carry the needle, so lock granularity matches content granularity (same trace+window → one shared warmup; different windows → independent, non-contending warmups).
- The pure selection logic (`select_entries`) takes explicit `max_spans` / `max_bytes` params so dedupe / ceiling / needle-boundary behaviour is unit-testable without a live ClickHouse. Edition-2024 let-chains (`if … && let Ok(x) = …`) are used throughout — this crate is on Rust edition 2024.

## Debugger Session Blocks

- Debugger sessions render as a list of **blocks** (cells) stored in Postgres `debugger_session_blocks` (`type` = `trace` | `evaluation` | `text`, `content` jsonb: `{traceId, note?}` / `{evaluationId, note?}` / `{text}`). App-server writes blocks at ingest (`db/debugger_session_blocks.rs`): trace blocks in `traces/processor.rs::trace_branch` for traces carrying the `rollout.session_id` metadata key, evaluation blocks in `api/v1/evals.rs::init_eval`. Block ids are deterministic (`Uuid::new_v5(session_id, "{type}:{entity_id}")`) so ingest retries collapse via `ON CONFLICT (id) DO UPDATE SET content` — note that ON CONFLICT updates **only `content`**, never `created_at`: a block's `created_at` is frozen at first insert to the source entity's time (trace `start_time` / eval `created_at`), which is the timeline's stable ordering key. The insert is gated on the session existing in the same project (sessions are registered explicitly — an unregistered/cross-project session id is a silent no-op, never an FK error).
- **Blocks index is LIGHTWEIGHT; trace rows load lazily client-side.** `getSessionBlocks` (`frontend/lib/actions/debugger-sessions/index.ts`) resolves only `evaluation` blocks server-side (one PG + one CH-scores query); `trace` blocks carry just `{id, createdAt, traceId, note?}` — NO CH trace query at index time. The blocks route splits by method: `GET …/blocks` → `{ blocks }` (index); `POST …/blocks` with body `{ traceIds: string[] }` → `{ traces: TraceRow[] }` via `getSessionTraceRows` (zod-capped at `MAX_TRACE_ROWS_PER_REQUEST` = 100 ids per call). The window fetch is POST (not a `?traceIds=` query string) so a full window of ids can't overflow the URL length limit. Trace blocks are never dropped for a missing row — the client shows a skeleton while loading and renders nothing when the row is confirmed `missing` (deleted / not yet in CH; realtime fills the latter in). The legacy fallback (`getLegacySessionBlocks`) is slimmed the same way (id-only trace refs).
- **Store owns lazy row fetch** (`debugger-session-view/store`): `traceRowStates: Record<traceId, "loading"|"loaded"|"missing">` + `ensureTraceRows(ids)`, which the virtualized list calls for blocks in the virtual window. Fetches are debounced (150ms), deduped against in-flight ids, and chunked (100/request) via closure-scoped state; the merge preserves realtime-bumped `endTime`s and error paths delete the "loading" marks so retry is possible. Realtime unchanged: `span_update` streams into `traceSpans`; `trace_update` appends/updates blocks and marks the row `loaded`.
- **Timeline is virtualized with @tanstack/react-virtual — outer block virtualizer + inner per-trace span virtualizers, ALL bound to one shared scroll element via `scrollMargin`** (`debugger-list/index.tsx` / `trace-segment.tsx`). Outer cells are NORMAL-FLOW with padding spacer divs, NOT absolute+transform — TraceSegment's `sticky top-0` header breaks inside a transformed ancestor. Each virtualizer's `scrollMargin` (its offset within the shared scroll content) is kept fresh by the `useScrollMargin` hook, which re-measures via a ResizeObserver on the shared scroll content (fires on block expand/collapse/lazy-load but NOT on scroll) with a ±1px convergence guard. Overscan is generous (8 blocks / 10 spans) by request.
- **CRITICAL virtual-core gotcha: every `useVirtualizer` on a SHARED scroll element MUST set `initialOffset: () => scrollEl?.scrollTop ?? 0`.** On attach, virtual-core calls `_scrollToOffset(getScrollOffset())`, which falls back to `initialOffset` (default 0) — so an inner segment virtualizer mounting mid-scroll yanks the whole shared container back to the top. This presented as outline navigation "landing at the top" with no error.
- **Outline scroll-to-block is a store-subscription-driven rAF loop, not an effect and not `scrollToIndex`** (`debugger-list/index.tsx`): TanStack's `scrollToIndex` retry loop gives up after 10 attempts under dynamic measurement, and an effect keyed on `scrollToBlockId` self-cancels (consuming the request re-runs the effect, whose cleanup kills the loop it just started). The loop jumps to `getOffsetForIndex`, then corrects by the target cell's real bounding-rect delta each frame until stable — stability doesn't count while any trace row is `"loading"` (the debounced batch lands late and swaps skeletons for taller cards). It scopes cell lookup with `:scope > [data-index]` (inner virtualizers stamp `data-index` too), forces `style.scrollBehavior = "auto"` (the container has `scroll-smooth`), treats bottom-clamp as at-target, and aborts on wheel/touchmove. Active-outline highlight reads `virtualizer.measurementsCache` on scroll (virtualized-out rows unmount, so IntersectionObserver can't work).
- **`command` blocks** render CLI commands agents ran (`content`: `{command, args?, exitCode?, output?, raw?}` — only `command` guaranteed). Validation lives in `lib/actions/debugger-sessions/command-content.ts` (`parseCommandBlockContent`), a client-safe module deliberately shared by BOTH the server block index (`getSessionBlocks`) and the realtime `applyBlockUpdate` path in the session store — realtime payloads are raw `JSON.parse` output, so storing them unvalidated poisons the store and crashes rendering on a malformed `command`/`args`. `args` validation is all-or-nothing (any non-string element → `args` absent); compacting would shift positional meaning (`args[0]` is rendered as SQL for `sql query`). The component (`debugger-list/command-block/`) dispatches on `content.command` via a literal switch; `SQLEditor` is `next/dynamic`-imported at the leaf so the CodeMirror SQL schema/autocomplete payload defers to first expand.
- **Expandable virtualized rows must keep expand state in the session store** (like `expandedTraceIds` / `expandedCommandBlockIds`), never local `useState` — rows unmount when scrolled past overscan, so local state silently collapses and the stale measurement cache under the row's stable key causes a layout jump on remount. Expand/collapse height changes need no extra virtualizer code: `measureElement`'s ResizeObserver + `useScrollMargin` handle re-measurement. Untrusted large text (command output) must be length-capped in the DOM (`OUTPUT_CHAR_BUDGET` + explicit "Show full output"), not just visually clipped with `max-h` — a multi-MB text node stalls layout, and `whitespace-pre` on one long line creates a million-px scroll width (use `pre-wrap` + `break-words`).
- **No backend emitter exists yet for realtime `command` block_updates** — `api/v1/debugger.rs::handle_add_block` only broadcasts text-shaped content. Command blocks written to Postgres appear on reload but do not stream live; the frontend realtime arm is ready and validated for when the emitter ships (CLI-side work).

## Project-scoped shared content dedup (`shared_content` / `spans_v0`)

- **`shared_content` table** (`46_shared_content_project_scope.sql`) is `(project_id, content_hash) → content` — project-scoped, not trace-scoped. Same content shared across traces collapses to one row. Backs three paths: input messages, output messages, and tool-definition blobs (hash space is shared; the table doesn't know which path produced a row).
- **Forward-only migration**: `llm_messages` (trace-scoped) is NOT dropped; `spans_v0` reads with `coalesce(dictGetOrNull('shared_content_dict', ...), dictGetOrNull('llm_messages_dict', ...))` so legacy spans keep resolving via the trace-scoped dict. New writes only go to `shared_content`. Backfill is optional / future work; dropping `llm_messages` is a separate later migration.
- **`shared_content_dict`** is created at frontend boot (`ensureSharedContentDict` in `frontend/instrumentation.ts`), same `CREATE OR REPLACE` env-driven pattern as `llm_messages_dict` and for the same reason (clickhouse-migrations checksum guard rules out baking creds into a migration). Recreating both on boot is cheap (DDL only); both are `COMPLEX_KEY_CACHE(SIZE_IN_CELLS 131072)` with `LIFETIME(MIN 30 MAX 60)`.
- **Two Redis scopes, two semantics**: `s:{project}:{hash}` is project-scoped storage presence (drives wire content + `shared_content` insert). `tn:{project}:{trace}:{hash}` is trace-scoped first-occurrence (drives `*_new_message_indices` for search). They are independent: a message can be storage-hit + trace-miss (don't ship content, but DO mark trace-new) — that's the cross-trace case that keeps span search returning the right span per trace under project-scoped storage.
- **Stamping invariant**: producer never writes Redis. `mark_seen` is the sole writer and runs on the consumer **only after BOTH the `shared_content` AND the `spans` inserts succeed** (last step of the span branch). The two key axes have different backing tables: `s:` (storage) keys are backed by `shared_content`, but `tn:` (trace-new) keys are backed by `spans.*_new_message_indices`. Stamping `tn:` before the spans insert leaves a window where a permanently-dropped spans insert orphans the trace-new marker — later spans in the same trace see the `tn:` key and ship empty `*_new_message_indices`, so no span records the first occurrence. Insert failure → return transient → Rabbit redelivers → no phantom keys for data that didn't land in CH.
- **Output dedup uses the same `shared_content` table**. CHSpan gets `output_message_hashes Array(FixedString(32))` + `output_new_message_indices Array(UInt16)`. The `seen_storage_in_batch` HashSet is shared across input + output + tools so a hash that appears as input in span A, output in span B, and inside a tool blob in span C emits exactly one row, billed to the first referrer in batch order.
- **Tool definitions** are normalized into a single canonical JSON array per span by `traces/tool_dedup.rs::extract_tool_definitions` from `ai.prompt.tools` (Vercel AI SDK), `gen_ai.tool.definitions` (OTel GenAI), or `llm.request.functions.{N}.*` (OpenLLMetry/LangChain). The producer hashes the array as one blob and stores it on `CHSpan.tool_definitions_hash FixedString(32)`. Empty/zero hash = no tools. Attributes-tab does NOT show tool definitions anymore; `spans_v0` exposes a virtual `tool_definitions` column reconstructed via `dictGet('shared_content_dict', 'content', (project_id, tool_definitions_hash))`.
- **`should_keep_attribute`** strips `ai.prompt.tools`, `gen_ai.tool.definitions`, and any key starting with `llm.request.functions.` so that legacy spans reaching the consumer without a producer-built `tool_dedup` verdict don't surface tool defs in `CHSpan.attributes` (avoids double-counting bytes AND prevents stale tool data in the attributes tab). Producer also strips them at extraction time so they don't ride the wire.
- **`lmnr.span.input` / `lmnr.span.output` are `remove`d from `raw_attributes` by `parse_and_enrich_attributes`, not just read** (LAM-2116). They used to be copied into `span.input` / `span.output` and left in place, so the whole payload rode the queue twice; `should_keep_attribute` dropped them at the consumer anyway, so nothing downstream could ever read them. **This attribute shape is NOT LLM-only** — it's the manual/SDK path for every span type (`observe`, `cua`, `kernel`, `skyvern`, `browser_use`, `openai_agents`), so the saving applies to Default/Tool spans too. The `remove` is safe because the ONLY reader of either key is that one block in `spans.rs`: everything between it and the consumer-side drop reads `span.input`/`span.output` instead (provider conversion, dedup, PII redaction, Quickwit, previews, `traces_agg`/`traces_static`, input-extraction, signals triggers, which only see `span.name` + aggregations). `should_keep_attribute` still lists both keys — that's the fallback for legacy spans reaching the consumer with `pre_processed = false`, so don't delete it as now-dead. Same reasoning applies to any future attribute whose value is copied into a struct field: strip at the producer, keep the `should_keep_attribute` entry as the legacy backstop.
- **Frontend**: `Span.tools?: string` from `spans_v0`. `extractToolsFromColumn(tools)` is the primary path; `extractToolsFromAttributes(attrs)` is the legacy fallback. `resolveTools(span)` (in `tool-list.tsx`) prefers the column and falls back to attribute extraction; call sites use `resolveTools(span)`.
- **Wire shape**: `RabbitMqSpanMessage` carries three `Option<...>` fields with `serde(default)`: `input_dedup: Option<MessageDedup>`, `output_dedup: Option<MessageDedup>`, `tool_dedup: Option<ToolDedup>`. Legacy producers (no dedup fields) still work — the consumer's per-span resolution treats `None` as "no dedup applies", so `CHSpan` falls through to raw `input` / `output` / no `tool_definitions_hash`.
- **Search snippets** (`search/snippets.rs::build_snippet_query`) tries `shared_content_dict` first then falls back to `llm_messages_dict` for input. Output snippets read only `shared_content_dict` (no legacy data exists). Both still scope to `*_new_message_indices` so search semantics are "first occurrence per trace" — preserved across project-scoped storage exactly because trace-new is its own Redis scope.
- **Billing accounting** in `process_span_messages`: input bytes follow the existing model (32B/hash + first-referrer content_bytes for dedup'd, raw JSON otherwise). Output bytes added on top — only counted when there's an output dedup verdict; non-dedup output is already in `estimate_size_bytes` via `span.output`. Tool bytes: 32B for the hash + first-referrer content if any; `should_keep_attribute` removed the source attribute bytes from `attributes` accounting so this isn't double-counted.

## LLM span input deduplication (`llm_messages` / `spans_v0`)

- LLM span `input` is structurally deduplicated: each message in the JSON array is BLAKE3-256 hashed over **sorted-key canonical JSON** (so field-order-only diffs collapse), emitted as a row in `llm_messages` (ReplacingMergeTree, `ORDER BY (project_id, trace_id, message_hash)`, **trace-scoped** — same content in two traces = two rows), and referenced via `spans.input_message_hashes Array(FixedString(32))` while `spans.input` is stored empty. Stored `content` is the message's **original-order** `serde_json::to_string` run through `sanitize_string` (serde built with `preserve_order`), so reconstruction is byte-identical to the non-dedup path; the hash is over canonical JSON for stable dedup identity. Non-LLM / tool-span `input` is never touched.
- `spans_v0` reconstructs via `arrayMap(h -> dictGetOrDefault('llm_messages_dict', 'content', (project_id, trace_id, h), 'null'), input_message_hashes)`, falling through to raw `input` when `input_message_hashes` is empty. The `llm_messages_dict` is a COMPLEX_KEY_CACHE dictionary **created at frontend boot** (`ensureLlmMessagesDict` in `frontend/instrumentation.ts`, `CREATE OR REPLACE` with `CLICKHOUSE_USER/PASSWORD/DB` interpolated into `SOURCE`), NOT by migration — `clickhouse-migrations` MD5-checksums `.sql` files and would break on credential rotation. Boot recreate is cheap (lazy cache, `LIFETIME(MIN 30 MAX 60)` refreshes within ~1min) and runs before Next.js serves traffic. Use `dictGetOrDefault` keyed on `(project_id, trace_id, message_hash)`, not a LEFT JOIN + `groupArray` (CH can't push the outer `trace_id` predicate through `GROUP BY`, so it aggregates all project messages). Dict attrs can't be `FixedString(N)` on CH 25.12 (`UNKNOWN_TYPE`) — `message_hash` is `String` and CH coerces the `FixedString(32)` transparently.
- `spans_v0` exposes `multiIf(...) AS span_type` which collides with `spans.span_type UInt8` under CH 25.x's analyzer. Migration 43 sidesteps this without a rename via `ALTER TABLE spans ADD COLUMN span_kind UInt8 DEFAULT span_type`; the view reads `span_kind`, ingestion keeps writing `span_type` (`CHSpan.span_type` in `app-server/src/ch/spans.rs`). Do NOT drop `span_type` — ingestion depends on it; `span_kind` is the DEFAULT-derived shadow column.
- **Billing / size attribution:** `span.estimate_size_bytes()` does NOT count `input`; the post-dedup input-bytes loop in `process_span_messages` (`app-server/src/traces/processor.rs`) owns it for every span (runs before both `CHSpan::from_db_span` and `update_workspace_bytes_ingested`, covers non-recorded spans too). Branches: dedup'd LLM spans pay `32 * num_hashes + span_content_bytes` (`span_content_bytes` = newly-inserted `llm_messages.content` only, so a shared message is billed once to the first referrer; `build_dedup_batch` returns it aligned with `span_hashes`); non-recordable LLM spans (e.g. CC Bash `anthropic.messages` via `is_skip_cc_span`, excluded from `recordable_indices` so no `dedup_lookup` entry) are charged from their own `dedups[span_idx]` (`hashes.len()*32 + sum(new_contents lens)`) — a naïve `estimate_json_size(span.input)` fall-through would charge 0; everything else pays `estimate_json_size(span.input)`. `estimate_size_bytes` filters `raw_attributes` via `should_keep_attribute` (matching `CHSpan.attributes`) because parsers COPY input-bearing attributes into `span.input` without removing them from `raw_attributes` — without the filter every OTel LLM/tool span double-bills. The loop MUST run AFTER `convert_span_to_provider_format` (LangChain conversion rewrites `span.input` to a differently-sized `Value::Array`).
- CH 25.x views do NOT support correlated scalar subqueries (both `SELECT (SELECT content FROM llm_messages WHERE message_hash = h)` and `WITH (SELECT ... WHERE trace_id = s.trace_id)` fail `NOT_IMPLEMENTED: can't find correlated column` at SELECT time though `CREATE VIEW` succeeds) — use the dictionary lookup.
- Redis key `m:{project_id_simple}:{trace_id_simple}:{hex(hash)}` TTL 1h, hot-path "seen recently" filter. MUST include `trace_id` (table is trace-scoped; a project-scoped key would suppress an insert for a message seen in another trace, leaving dangling `input_message_hashes`). Best-effort: on `exists()` error always insert, RMT merges. `mark_seen` is the only Redis writer, runs AFTER a successful `llm_messages` insert; never stamp before insert (a transient failure would leak `m:` keys whose rows don't exist, surfacing as literal `null` in reconstructed input).
- Ingest order in `process_span_messages`: build dedup batch synchronously, then `tokio::join!` two branches — (a) trace upsert (PG `traces` → CH `traces` → realtime) and (b) the **sequential** span path `shared_content → spans → mark_seen`. Span path stays sequential because `spans` is plain MergeTree (NOT RMT): inserting `spans` before `shared_content` and having `shared_content` fail would double-store every span on retry. `mark_seen` is LAST so `tn:` keys aren't stamped until backing rows are durable. `build_dedup_batch` dedupes `(project_id, trace_id, hash)` triples via HashSet (key MUST match table ORDER BY; a batch can mix projects). Do NOT collapse into a 3-way join.

### Producer-side dedup

- Hashing + Redis-existence checks ALSO run on the producer (HTTP / gRPC ingest in `publish_span_messages`) BEFORE the message hits Rabbit. Already-seen LLM input messages are stripped from `span.input`; the wire payload carries a `MessageDedup` (see `traces/input_dedup.rs`) instead. Wire savings grow linearly with conversation history depth, which is the point.
- `RabbitMqSpanMessage` carries two new fields with serde defaults: `pre_processed: bool` (consumer skips `parse_and_enrich_attributes` + `convert_span_to_provider_format` when true) and `input_dedup: Option<MessageDedup>` (the producer's hash + Redis-status verdict).
- Consumer ordering invariant: `prepare_span_for_recording` runs unconditionally (handles usage / span path / status), `convert_span_to_provider_format` runs ONLY when `pre_processed=false` — running it twice would double-apply the LangChain rewrite (which replaces `span.input` with a fresh `Value::Array`) and the producer's hashes would no longer match the consumer's view of the input.
- `span.input = None` on the wire when a plan was produced — EXCEPT for spans the consumer would render as the trace's root, because `TraceAggregation::from_spans` reads it for `root_span_input` (truncated preview rendered in the trace list). The producer carve-out matches the consumer's promotion logic, not just OTel parentage: keep `input` if `parent_span_id.is_none()` (natural OTel root) OR `is_top_span(span, &span.attributes)` (Laminar SDK top span — `span_id == ids_path[0]` AND `name == path[0]`; `prepare_span_for_recording` will later null its `parent_span_id`). A naïve `parent_span_id.is_some()` check lets an OTel-parented top span ride the wire with `input = None` and then get promoted to root on the consumer, silently erasing `root_span_input`. `is_top_span` is `pub(crate)` in `traces::utils` for this reason; do not duplicate the heuristic. Root spans are 1 per trace; dedup savings come from the long tail of nested LLM spans either way.
- **Producer is the only dedup site.** `preprocess_for_queue` in `producer.rs` is the one place that runs `build_dedup`; the consumer never re-mints. A `None`-dedup span reaching `build_dedup_batch` is treated as "no dedup applies": empty hashes, `CHSpan.input` keeps the raw JSON written by `from_db_span`, and `spans_v0` falls through to raw `input` via its `if(notEmpty(input_message_hashes), <reconstruct>, input)` branch. This means any ingest path that bypasses `publish_span_messages` (currently only `routes/spans.rs::create_span`, which always writes `input: None` anyway) is stored the old way without dedup — correct, just uncompressed. Adding a new bypass path that ships populated array input would silently miss dedup compression; if that becomes a concern, gate it with an `assert!` / `log::warn!` at the consumer rather than re-introducing the mint loop.
- `build_dedup_batch` is hardened against malformed dedups: `dedup.hashes.get(pos as usize)` and `dedup.new_contents.get(i)` are bounds-checked with `else continue`, so a corrupt-on-deserialise dedup or a future producer bug skips the bad entries instead of panicking and looping the entire flush on requeue.
- Quickwit indexing reads pre-built `dedup.span_new_message_values` (a `Vec<Vec<Value>>` aligned with the spans batch) instead of projecting indices back onto `span.input` — required because `span.input` is `None` on the producer path.
- Producer NEVER writes Redis. `mark_seen` is the only writer, runs only on the consumer, AFTER a successful `llm_messages` insert. The "stamp only after success" invariant is preserved exactly — the producer's Redis check is read-only and best-effort (errors fall through to "treat as new", same as the consumer's prior behaviour).
- `preprocess_for_queue` in `app-server/src/traces/producer.rs` runs sequentially per-span (NOT parallel via rayon) — Redis `exists()` calls are cheap and we don't want to thunder-herd Redis on large batches. Most ingest calls carry 1-N spans; per-span async loop is the right granularity.

## Quickwit indexing of LLM spans

- Quickwit only indexes the **new** subset of an LLM span's input — the messages this span was first to introduce in its trace. Older repeated history is searchable via the earlier span that introduced it. Implementation: `build_dedup_batch` in `app-server/src/traces/input_dedup.rs` returns `span_new_indices: Vec<Vec<u16>>` (0-based positions inside `span_hashes[i]`); `process_span_messages` projects those indices back onto `span.input` (`build_new_messages_subset`) and `QuickwitIndexedSpan::from_span` indexes the resulting array. Non-LLM spans / non-array input fall through to raw `span.input`.
- The same indices land in ClickHouse as `spans.input_new_message_indices Array(UInt16) CODEC(ZSTD(3))` (migration `44_spans_input_new_message_indices.sql`). `CHSpan` only populates them when `input_message_hashes` is non-empty; legacy rows have an empty array, which the search snippet query handles gracefully (empty `arrayMap` → empty input snippet, output / attributes still match).
- Search snippets read directly from the raw `spans` table (NOT `spans_v0`): for spans with `notEmpty(input_message_hashes)` the input snippet is built by `arrayMap(i -> dictGetOrDefault('llm_messages_dict', 'content', (project_id, trace_id, input_message_hashes[i + 1]), 'null'), input_new_message_indices)` joined with `,`; non-LLM spans (empty `input_message_hashes`) fall back to `extract(input, ...)` so their raw `spans.input` is still searchable. Output / attributes use `extract(...)` unconditionally. Single CH query, no parallel split. CH arrays are 1-indexed, hence `[i + 1]`. See `build_snippet_query` in `app-server/src/search/snippets.rs`.
- Cleaning runs at `from_span` build time, not in the consumer. `clean_for_indexing(s, strip_roles)` in `app-server/src/quickwit/preprocess.rs` chains `ANSI strip → strip_noise (base64 images, signature / thought_signature values) → optional strip_role_keys → clean_whitespace (collapse real + literal `\n\t\r`, drop other backslashes) → unicode whitespace classes → NFC`. LLM spans pass `strip_roles=true` for input/output; attributes always pass `false`. The chain only removes / collapses chars (never adds), so the snippet `extract()` regex with `[\s\S]{0,50}` context and `[^a-zA-Z0-9]+` token gaps still matches the reconstructed-and-cleaned text.
- Events keep their own `preprocess_text` path (`PreprocessForIndexing` impl on `QuickwitIndexedEvent`); spans' `PreprocessForIndexing` is a no-op because cleaning already happened upstream.

## Quickwit indexing of signal events

- Signal events get their own Quickwit index `signal_events` (`frontend/lib/quickwit/indexes/signal_events.yaml`, applied at boot by `initializeQuickwitIndexes`). `mode: dynamic` (like `spans_v2.yaml`); the free-text content field is `payload`, declared `type: json`. `default_search_fields` is `[]` because the json field type **rejects bare root queries** — every search addresses subfields (`payload.foo:"…"`), built by the search route. Structural ids (`project_id`, `signal_id`, `trace_id`, `id`) are tokenizer:raw + fast; `severity` is `u64` (Quickwit rejects `u8`).
- **`payload` ships as a raw JSON object**, not flattened/filtered: `QuickwitIndexedSignalEvent.payload` is `serde_json::from_str(&event.payload).unwrap_or(Value::Null)`. The json field type is used instead of flatten-with-allow-list because: (1) **per-subfield position streams** — each key gets its own positions so phrase queries (all user queries are phrases via `escape_quickwit_query`) can't span field boundaries (a space-join produces cross-field adjacency false positives); (2) **type inference** — numeric/boolean subfields indexed under inferred types, so a string-path `OR` can't match a numeric column; (3) **keys are field paths, not tokens** — searching `"prompt"` doesn't false-match every event with a `prompt` column.
- Producer hook `publish_signal_events_for_indexing(events, queue)` in `app-server/src/quickwit/producer.rs` mirrors the span/event indexer (`IndexerQueuePayload::SignalEvents` in `quickwit/mod.rs`, routed by `QuickwitIndexerHandler` in `consumer.rs`). Called in the private signals handler (`app-server/src/signals/private/response_processor.rs`, after `insert_signal_events` succeeds, before clustering). Errors logged + swallowed (a Quickwit hiccup never blocks signal-event creation).
- `flatten_json` is a no-op (ships `Value` as-is for per-subfield indexing); `preprocess_for_indexing` walks the `Value` and applies `preprocess_text` (ANSI strip + whitespace collapse + NFC) to every string LEAF via `preprocess_json_strings` (`quickwit/utils.rs`). Leaf-aware because collapsing the whole JSON to a string would break per-subfield indexing.
- **`payloadFields` is load-bearing for search, not just snippets.** Used for (1) building the Quickwit query `payload.f1:"…" OR payload.f2:"…"` (json field has no searchable root) and (2) per-field CH `extract()` for snippet offsets. Frontend filters to `f.type === "string"` before sending. `search_signal_events` short-circuits to empty hits when `payload_fields.is_empty()` (a query with no clauses is rejected by Quickwit) — there is NO all-fields fallback; new callers MUST send a non-empty list.
- **Field-name injection is blocked at query construction:** `search_signal_events` filters every `payload_fields` entry against `PAYLOAD_FIELD_NAME_RE` (`^[a-zA-Z_][a-zA-Z0-9_]*$`) before interpolating into `payload.{name}:{escaped_query}`. The form rule in `schema-field-row.tsx` is the only prior validation (server zod is `z.record(z.string(), z.unknown())`), so without the Rust filter a name like `f1:"x") OR (payload.f1` would escape the parenthesised tenant scope and search the whole index cross-tenant. Failing names are silently dropped (unsearchable but still render). Mirror this filter anywhere user-derived field names hit Quickwit syntax.
- `CHSignalEvent.timestamp` is `i64` nanos-since-epoch (CH `DateTime64(9,'UTC')`); `from_event` reconstructs via the infallible `DateTime::<Utc>::from_timestamp_nanos`, and Quickwit's `timestamp` field accepts the RFC3339 serialisation natively.
- Search route `POST /api/v1/projects/{projectId}/signal-events/search` (`app-server/src/routes/signal_events.rs`) wraps `crate::search::signal_events::search_signal_events`. Returns `{ hits: SignalEventSearchHit[] }`, each `{ id, fieldSnippets: Record<fieldName, SnippetInfo> }`. With `payloadFields: string[]` it runs a CH `extract()` per field over the real `signal_events.payload` for highlight offsets; empty `payloadFields` returns ids only. No `snippetsCount`/`+N` badge (every matching field renders in its own column).
- Snippet fetch `fetch_signal_event_snippets` (`app-server/src/search/snippets.rs`): `SELECT id, array(extract(coalesce(nullIf(JSONExtractString(payload,'<f>'),''), toString(JSONExtractRaw(payload,'<f>'))), '<regex>'), …) AS field_snippets ... WHERE project_id=? AND signal_id=? AND id IN (…)`. Positional `Array(String)` zipped against the field-name list. `JSONExtractString` unescapes so offsets land on glyphs; `JSONExtractRaw` fallback covers non-string fields. `signal_events` is plain MergeTree scoped by `(project_id, signal_id)` — no FINAL. `build_search_regexes` / `post_process_snippet` / `escape_quickwit_query` (pub(crate) re-export from `search/mod.rs`) are shared with the spans path — don't fork. Quickwit query: `project_id:{pid} AND signal_id:{sid} AND (payload.f1:"…" OR …)`; `search_field` not set (each clause carries its path).
- **Filter vs highlight can disagree on tokenisation edge cases** (unicode whitespace, hyphenation — Quickwit `default` tokenizer ≠ CH regex byte-for-byte) → a row with no highlighted cell. Do NOT re-filter hits against snippet emptiness — it drops valid matches.
- Time bounds attached to the Quickwit body only when supplied; the events CH query is unbounded with no params, so a default window in search would drop older matches. Backfill NOT included — pre-existing events show in the table but aren't searchable until re-indexed.
- **Frontend flow:** `searchSignalEvents` (`frontend/lib/actions/events/search.ts`) returns `SignalEventSearchHit[]`; `getEventsPaginated` / `getEventsByEmergingClusterPaginated` build `idFilter` from hit ids, retain the list, then `attachSnippets` merges `fieldSnippets` onto each `EventRow` by id. The events route accepts repeated `payloadField=<name>` params (only when `search` active). `createPayloadColumnDef` (`frontend/components/signal/events-table/columns.tsx`) renders `<HighlightedSnippet>` (UTF-16 `<mark>` slices) when `fieldSnippets?.[field.name]` is set, else the normal cell. Table UI uses `AdvancedSearch` (`events-table/index.tsx`); `resource` widened to include `"signal-events"` (`advanced-search/types.ts`), which disables autocomplete (no endpoint; `autocompleteResource` gate restricts to `"traces"|"spans"`). Recent searches persist via Zustand keyed `signal-events-${signal.id}`.

Sort state lives in the views layer (`effective.sortBy`/`sortDirection` via `useTableView().setSort`), persisted to URL + DB like filters/search.

When adding a new events fetch path, thread all three (`sortBy`, `sortDirection`, `sortType`).

## Traces Table Filters and `traces_v0`

- **The `filter` URL param has TWO incompatible encodings — pick by who reads it.** A **browser URL** (anything you `window.open` / `router.push` / link to) is read by nuqs `parseAsArrayOf(parseAsString)`, which joins/splits the array on `,` and percent-escapes literal commas inside each item. So `URLSearchParams.append("filter", JSON.stringify(f))` is WRONG for a browser URL: the standard `%2C` encoding of the commas *inside* the filter JSON is decoded before nuqs splits, so one filter shreds into 4 fragments (`{"column":"user_id"`, `"value":"alice"`, …), each fails `FilterSchemaRelaxed`, and all are dropped — the page silently renders UNFILTERED with no chip and no console error. Build these with nuqs `createSerializer({ filter: parseAsArrayOf(parseAsString), … })` so the writer's escaping matches the reader (see `handleOpenUserTraces` in `components/traces/trace-view/header/index.tsx`). An **API-route URL** (`fetch("/api/projects/:id/traces?…")`) is read by `parseUrlParams` → `searchParams.getAll("filter")`, which expects genuinely repeated params — there `append` + plain `URLSearchParams` is correct and nuqs must NOT be used. Same param name, opposite conventions; converting a `fetch` call into a navigation (or vice versa) requires re-encoding.
- Filters written into a browser URL should carry `dataType` (e.g. `"string"`) alongside `column`/`operator`/`value`. It's optional in `FilterSchemaRelaxed`, but the filter-chip UI and `FilterPopover` set it, so including it keeps a link-generated filter byte-identical to a hand-added one and avoids a spurious "not equal" when the two are compared with `isEqual`.
- The traces table queries the `traces_v0` ClickHouse view. Older migration files (e.g. `6_trace-summary-views.sql`, `10_trace_browser_session.sql`) reference columns the view no longer exposes; they are historical and must not be edited — later migrations supersede them.
- When removing a column from `traces_v0`, it must ALSO be removed from (1) `tracesColumnFilterConfig.processors` in `frontend/lib/actions/traces/utils.ts`, (2) the `filters` array in `frontend/components/traces/traces-table/columns.tsx`, and (3) the `TraceRow` type in `frontend/lib/traces/types.ts`. A stale filter processor is the mechanism by which selecting the filter in the UI injects SQL referencing a missing column and 500s the traces API route.
- **`traces_v0` is a PARAMETERIZED view with THREE params — `project_id`, `min_start_time`, `max_start_time`** (migration `53_traces_v0_start_time_params.sql`). It keeps the `trace_tags` LEFT JOIN inline. The two `start_time` params are pushed into a `PREWHERE project_id = … AND start_time BETWEEN min AND max` on the `traces_replacing FINAL` scan, so the range narrows the granules read BEFORE FINAL dedups/merges (running FINAL over the whole project first and filtering after is far slower). ClickHouse parameterized views FORBID default arg values, so the query engine (the only entrypoint) MUST always supply all three; a bare `SELECT … FROM traces_v0` fails.
- **The `min_start_time` / `max_start_time` defaults are computed in the Rust validator, NOT the view** (`app-server/src/query_engine/validator.rs`, `traces_time_bound_args` and helpers). The `ViewRewriter` inspects the enclosing SELECT's WHERE (`where_stack`) when rewriting `traces` → `traces_v0(...)`: no `start_time`/`end_time` filter → broad epoch defaults (`1970-01-01` / `2099-12-31`); filter present → derived bounds padded ±`INTERVAL 3 HOUR` (safety pad because PREWHERE runs before FINAL and a newer row version could shift `start_time` out of a too-tight range — always prefer underfiltering/slow over overfiltering/wrong data). The original user WHERE is left intact; the PREWHERE is purely additive pruning.
- **Bound-extraction rules** (`extract_bounds` / `analyze_comparison` / `analyze_between`): only `start_time` and `end_time` (bare or qualified by THIS relation's alias — a joined table's `start_time` is ignored via the alias check) contribute. Because `end_time >= start_time` always holds, an UPPER bound on `end_time` is also an upper bound on `start_time`, but a LOWER bound on `end_time` says nothing and is dropped. Single-arg date-trunc functions (`toDate`/`toStartOfDay`/`toStartOfHour`/`toStartOf{Five,Ten,Fifteen}Minutes`/`toStartOfMinute`/`toStartOfMonth`/`toStartOfQuarter`/`toStartOfYear`/`toMonday`/`toStartOfWeek`) are supported: `f(start_time) = X` widens the upper bound by the bucket width (`bucket_width_interval`). Boolean algebra: `AND` = tightest (`greatest` of lowers, `least` of uppers); `OR` = loosest AND only when BOTH branches bound that side (an unbounded OR branch drops the whole bound so `start_time > X OR unrelated = 1` stays broad). A comparison whose value side references a column, `NOT BETWEEN`, and multi-arg functions (`toStartOfInterval`, `addDays`, etc.) all fall back to the broad default. Column-on-right comparisons flip the operator. Bounds are emitted as `toDateTime64(…, 9)` strings so `least`/`greatest` share a comparable type. GOTCHA: a `{name:Type}` bind placeholder parses as an `Expr::Dictionary` whose inner `Type` is an `Expr::Identifier` — so `expr_references_column` must skip identifiers nested inside a Dictionary or it wrongly classifies `start_time >= {startTime:String}` / `now() - INTERVAL {pastHours:UInt32} HOUR` as column-referencing and drops the bound (silently reverting to broad epoch defaults). Placeholders are scalar binds evaluated once at the call site, so the whole value expr round-trips verbatim into `toDateTime64(<value>, 9)`.
- Adding another consumer of `traces_v0` outside the query engine (i.e. a caller that doesn't go through the validator's rewrite) MUST supply all three params by hand — there is no default-arg fallback in the view.

## Removed standalone `events` / `tags` tables (migration 50)

- The standalone `events` and `tags` ClickHouse tables (plus their `events_v0` / `tags_v0` views) are **dropped** in `50_drop_events_tags.sql` — they were write-dead (only read/deleted) and were never in the query-engine validator allowlist, so they were never SQL-queryable. Do NOT add new reads/writes/deletes against them. Tags now live on the `traces`/`trace_tags` path; events on `signal_events`.
- **Project deletion (`deleteProjectDataFromClickHouse` in `lib/actions/project/index.ts`) must list EVERY project-scoped physical ClickHouse table.** It issues `ALTER TABLE <t> DELETE WHERE project_id = ...` per table. `deleteProject` is idempotent: a missing Postgres row is treated as "PG delete already committed on a prior attempt" and re-runs the CH purge instead of throwing `Project not found`, so a first delete that crashed mid-purge can be retried. A CH purge failure still throws (there is no background reconciliation for retained rows, so the user's retry is the retry path). Two coupled rules: (1) the list must be **complete** — to enumerate it, query the live schema for tables (not views/dictionaries) carrying a `project_id` column (`system.tables` ⋈ `system.columns`), then cross-reference the migrations so you only include tables a freshly-migrated DB actually has; (2) it must contain **no dropped or staging-only tables** — an `ALTER ... DELETE` against a non-existent table throws. Exclude legacy/superseded tables that survive only in staging (e.g. `old_spans` whose drop in migration 33 is commented out, `span_tags`, `evaluator_scores`) and never-canonical intermediates. When a migration adds or drops a project-scoped table, update this list in the same PR.
- **Tag autocomplete has two distinct paths**, and both must source **span-level** tags because the `tags` autocomplete `field` feeds the `tags` array-column filter in BOTH spans search (`spans_v0.tags` = physical `tags_array`) and traces search (`traces_v0.tags` = `arrayDistinct` of aggregated span tags) — sourcing from `trace_tags` (the separate trace-level filter) would surface suggestions that match nothing in the `tags` filter. (1) app-server cache (`cache/autocomplete.rs`) queries ClickHouse directly with no validator, so it uses the physical column name `FROM spans ARRAY JOIN tags_array AS tag` (filter on `start_time`, scope by `project_id` param); this also matches the realtime `insert_current_span_values` path in the same file, which populates the `tags` key from `span.attributes.tags()`. (2) frontend (`lib/actions/autocomplete/index.ts`) goes through the validator (rewrites `FROM spans` → `spans_v0(project_id=...)`), so it uses the view alias `FROM spans ARRAY JOIN tags AS tag`. The standalone `tags` table is gone — never write a `FROM tags` query, and do NOT source tag autocomplete from `trace_tags`.
- **Deleting a signal purges its full ClickHouse footprint** by `signal_id` across three tables, in order: `events_to_clusters` (link rows, resolved via a subquery on `signal_events.id` — must run BEFORE deleting `signal_events`), then `signal_event_clusters`, then `signal_events`. `purgeSignalsFromClickhouse` in `frontend/lib/actions/signals/index.ts` is called by `deleteSignal` / `deleteSignals` / `setTemplateSignals` (template removals). It is signal_id-based (not name-based) since the ids are in hand at delete time and avoids name collisions; failures are logged and swallowed so a CH hiccup never blocks the Postgres delete.

## Post-factum Trace Metadata (`POST /v1/traces/metadata`)

- Customers patch trace metadata after ingestion via `POST /v1/traces/metadata` `{ traceId, metadata }`. The handler (`api/v1/traces_metadata.rs`) verifies the trace exists via `ch::traces_agg::trace_exists` (a `count()` probe on `traces_agg`; returns 404 otherwise) and pushes a virtual span carrying the metadata as `lmnr.association.properties.metadata.<key>` attributes plus the `lmnr.internal.metadata_only` marker (`SPAN_METADATA_ONLY`), reusing the regular `observations_queue` via `publish_span_messages`.
- Consumer split (`process_span_messages`): metadata-only spans are pulled out of `messages` BEFORE the regular pipeline (after `parse_and_enrich_attributes`, before usage lookup) into a `TraceMetadataPatch`, then written as one `traces_agg` identity partial plus one `traces_static` delta. No Postgres, no stub row, no version games — a patch that beats the trace's span batch is just another partial.
- Because `traces_static.metadata` is a whole-object SET column (see that section), a trace whose metadata is written by BOTH a span batch and a patch has undefined metadata — last write wins wholesale, verified end-to-end. In practice metadata is set once per trace, and `traces_agg`'s `maxMap` retains the per-key history if it's ever needed.
- The existence check is best-effort, not a guarantee: a trace deleted between request and consumption still leaves its patch behind as a metadata-only row.
- `should_record_to_clickhouse` returns `false` for metadata-only spans, but the actual filter happens earlier (the `messages.retain` in the processor) so they never reach `recordable_indices`, `CHSpan` build, dedup, Quickwit indexing, autocomplete, realtime span updates, or workspace-bytes billing. They contribute nothing to `TraceAggregation` either.
- **Internal (server-side) metadata patches go through `publish_trace_metadata_patch` in `traces/metadata.rs`** — it builds the same virtual metadata-only span (marker + `{ASSOCIATION_PROPERTIES_PREFIX}.metadata.{key}` attrs, name `"lmnr.trace.metadata"`, zero-duration) and publishes via `publish_span_messages`, skipping the HTTP route's existence pre-check. **It is deliberately a non-async `fn` returning `Pin<Box<dyn Future<Output = Result<()>> + Send>>`** wrapping `Box::pin(async move { ... })`: any caller reachable FROM `publish_span_messages` (e.g. the ingestion user-task hook) creates the async cycle `publish_span_messages → caller → publish_trace_metadata_patch → publish_span_messages`, which a plain `async fn` can't express (E0733 recursion-in-async + an unprovable-`Send` cycle). Type-erasing at the DEFINITION breaks both. Runtime recursion is bounded because the virtual span is non-LLM with no input, so the user-task hook early-returns on it. (The boxed-future erasure now lives on the shared `publish_metadata_only_span` helper that both `publish_trace_metadata_patch` and the trace-io façades `publish_trace_input_update` / `publish_trace_output_update` build on.)

## Ingestion-time trace input/output extraction

- Extracts, **at ingestion**, the trace-level "user task" (LLM-generated regex over the winning span's input) and the trace "output" (the latest output messages on that winner's path). Code in `app-server/src/traces/input_extraction/`; each file carries a `//!` header describing its own role, so read those rather than expecting an inventory here. Compile-time ungated; the producer hook early-returns unless `Feature::InputExtraction` is on.
- **Backend `Feature` flags must be fine-grained: one flag per feature, even when two flags share the same condition.** Never gate a new feature on another feature's flag. The shared `LlmClient` in `main.rs` is built when ANY LLM-backed flag is on (union of `Feature::Signals` and `Feature::InputExtraction`) — gating it on one feature's flag would silently disable the others if the conditions ever diverge.
- **Storage — raw values on the wire, into `traces_static`'s own io columns.** The values ride a virtual metadata-only span on dedicated attributes `SPAN_TRACE_INPUT` / `SPAN_TRACE_OUTPUT_HASHES`, carrying the RAW JSON value / hex per-message hashes with NO metadata key. `processor.rs` routes them to a neutral `RawTraceIo` (not a `TraceMetadataPatch`) and `collect_static_agent_io_rows` writes `traces_static.input` / `.output_hashes`.
- **Never fold io into a metadata key.** `traces_static.metadata` has whole-object SET semantics, so a synthetic `{lmnr_user_task: …}` delta would REPLACE the customer's real keys. `encode_metadata` strips reserved keys as a backstop — note the two sides differ: `ch/traces_static.rs` strips both `lmnr_user_task` and `lmnr_trace_output`, `ch/traces_agg.rs` strips only `USER_TASK_METADATA_KEY`.
- `from_agent_io`'s `start_time` must be the **trace's** start time, not the span's — it's `traces_static`'s partition key.
- **Input winner heuristic (`lock.rs`).** Per-trace lock keyed `{USER_TASK_LOCK_CACHE_KEY}:{project_id}:{trace_id}`. The winner is the span at the **shallowest observed depth**, within the first `ROSTER_CAP` spans by `start_time` at that depth (the roster closes the arbitration window), with the **most TOTAL input tokens — cached + uncached, NOT uncached-only**: the true first span's system prompt is often cache-read from prior conversations while helper spans are too small to cache at all, so subtracting cache-read ranks the helper higher. Ties keep the first published. The effect is best-effort (errors logged and swallowed) with no recovery path, which is what keeps arbitration simple: a shallower span ALWAYS wins by resetting `lock.depth`, so once a legit span is seen at some depth no deeper span can own the task. `write_lock_merged` is a re-read-merge-write with no mutex — a stale roster is harmless under RMT versioning.
- **Output arbitration is INHERITED from the input winner, not independently computed.** Pass 1 caches the winner's path minus its last segment at `main_agent_path:{project}:{trace}` (`lock.rs::main_agent_path_cache_key`); Pass 2 treats any LLM span whose `path[..len-1]` equals that prefix as an output candidate. Both sides must strip the last segment identically. **This is why Pass 1's arbitration + path write run UNCONDITIONALLY** — only the extraction *effect* is gated on `llm_client_available()`. Gating the whole pass would leave Pass 2 matching a stale deeper path. With no cached prefix (no winner yet, or a cache miss) **every** LLM span is a candidate, so output is visible before arbitration converges. Among a batch's matches only the latest `end_time_ns` publishes; "latest wins" beyond the batch is enforced by the `trace_agent_output` RMT version (`updated_at` = the span's end time), NOT a lock. `end_time_ns` degrades to `i64::MAX` when unknown ("unknown beats real"). Output capture deliberately does NOT filter to "the last toolless assistant message" — tool-call-only turns are captured too, since always writing the latest is cheaper than predicting a model-specific "I'm done" signal.
- Capture ordering in `traces/producer.rs::preprocess_for_queue`: the input candidate is taken BEFORE the dedup strip nulls `span.input`; the output candidate is built AFTER `build_message_dedup` because it needs the dedup's `hashes`. Both are processed AFTER the wire publish so the hook can never mutate or delay the payload.
- **Separator pipeline (order is binding):** extract last-turn user parts → canonicalize (sort, so part arrival order is irrelevant) → join with the signpost `\n\n== lmnr_part_separator ==\n\n` → generate AND apply the regex against the signposted text → re-join captured parts with the user-facing whitespace separator. Never conflate the signpost (LLM-facing) with the user-facing separator. **The signposted text is USER-ONLY — including system content was tried and reverted; do not re-add it.** The generation prompt is framed around a TEMPLATE model (every piece STATIC or VARIABLE) and classifies markers by FUNCTION, never syntax (XML tags, delimiter lines, markdown headings, ALL-CAPS labels, JSON envelopes all equivalent) — keep it syntax-agnostic.
- Regexes run on **`fancy-regex`** (NOT the RE2-only `regex` crate) with a backtrack limit so catastrophic patterns degrade to `NoMatch` instead of hanging — the `Err` arm of `captures` IS a non-match.
- **The `prompt_hash` half of the regex cache key is the system prompt's FIRST-SENTENCE hash, NOT the skeleton hash stamped on `lmnr.span.prompt_hash`.** `prompt_hash::prompt_hashes` returns both from one pass; the skeleton (first sentence + sorted XML tag names) still feeds the span attribute, static-SP extraction, checkpoints and signals, so both must keep existing. Using `first_sentence` means permuting/adding/removing the prompt's XML scaffolding does NOT fork the cache key and re-trigger an LLM generation. Pinned by `regex_cache_key_survives_system_prompt_tag_permutations` (`regex.rs`); don't "simplify" it to reading `SPAN_PROMPT_HASH` off the span.
- **Accepted trade-off of that wider key:** two prompt templates sharing an opening sentence but differing in TAG SET now collide. That is only unsafe if they also disagree on the USER message's extraction layout — and the user fingerprint is deliberately ORDER-INSENSITIVE, so `<ctx>…</ctx>\n\n<task>` and the reverse share a fingerprint and a regex. A regex anchored to one layout then yields `NoUserRequest` (empty user task) on the other, and **that does NOT self-heal: only `ApplyRegexResult::NoMatch` evicts the cache entry; `NoUserRequest` refreshes its TTL.** If empty `lmnr_user_task` values show up in the wild, make the USER fingerprint layout-sensitive (or treat a cached `NoUserRequest` as stale) — do NOT re-narrow the key to the skeleton, which restores a scaffolding-permutation cardinality blowup.
- The regex cache is deliberately **separate from the frontend's** extraction cache — signposted samples are incompatible with plain-joined ones, and `generate.rs` has its own prompt rather than reusing the frontend's `SYSTEM_PROMPT`.
- `fingerprint_user_message` (`fingerprint.rs`) sorts + dedups tag NAMES globally (not just consecutive repeats) and captures only TOP-LEVEL tags. Its **TypeScript twin `fingerprintUserMessage` in `frontend/lib/actions/sessions/extract-input.ts` does NEITHER**, so the two produce different strings for the same input. Harmless today (the TS function has zero callers, the caches are separate) — but do not assume parity if you wire it up.
- **The pipeline is infallible: an LLM failure or budget exhaustion can never requeue the message.** Both resolve to the uncached passthrough regex (the full reconstructed input beats a wrong empty value), each stamping its own flag (`budget_exhausted` / `llm_failed`) on the self-tracing root. The only transient error left in the consumer is a publish failure, and it **acks only after `publish_trace_input_update` succeeds**. If flapping providers hurt throughput, raise `NUM_INPUT_EXTRACTION_WORKERS` — custom retry loops and pipeline deadlines were both tried and reverted.
- Before publishing, the consumer re-reads the winner lock and drops the message if the published winner `supersedes` the `winner_state` snapshot it carried; after a successful publish it re-asserts that snapshot via `write_lock_merged` (healing a possibly-failed producer write). Absent lock / cache error fails open.
- **Self-tracing is emitted ONLY from the queue consumer** — the producer hook sits on the ingest path and an internal span there would recurse through `push_spans_to_queue`. **Cache-hit runs emit no self-tracing at all**; an internal trace exists only when a real LLM generation runs. Spans route to `USER_TASK_INTERNAL_PROJECT_ID` (its own env var, distinct from other features' internal project ids); unset ⇒ `project_id = None` ⇒ the exporter drops them. `SpanScope` carries BOTH the internal routing project and `source_project_id` (the extracted trace's owner).
- **The Sentry span per regex APPLICATION uses the DEFAULT target, deliberately.** `apply_regex_externally_traced` (`regex.rs`) emits `user_task.apply_regex` for every authoritative application (cached and freshly generated); the disjoint per-layer filters in `instrumentation/mod.rs` route a default-target span to Sentry only, never the `lmnr::internal` tree — which is what makes it safe on the ingest path, since Sentry spans never re-enter `push_spans_to_queue`. Generation-loop PROBES are deliberately not Sentry-traced (model experiments, not applications).

## Trace-view Span Attributes

- The trace-view (transcript/tree) and shared-trace endpoints do NOT fetch the full `attributes` JSON blob from ClickHouse. LLM spans' `attributes` can be tens of kB each, so we extract only the keys listed in `TRACE_VIEW_ATTRIBUTE_KEYS` via `buildTraceViewAttributesExpression()` in `frontend/lib/actions/spans/utils.ts`. Downstream `tryParseJson` + key access keeps working unchanged because missing keys are omitted from the synthesized JSON.
- The single-span endpoint (`getSpan` in `frontend/lib/actions/span/index.ts`) still selects the full `attributes` — span-view renders the complete attribute table. Do not trim it there.
- When adding a new consumer of `attributes` inside trace-view components (transcript/tree/store/search/lang-graph), add the key to `TRACE_VIEW_ATTRIBUTE_KEYS` or the access will silently return undefined.
- Use full `JSONHas` + `JSONExtractRaw` (not `simpleJSON*` variants) in the expression — array/nested values like `lmnr.span.ids_path` contain embedded commas that the simple variants mishandle.
- **Per-trace `cacheReadInputTokens` / `cacheCreationInputTokens` / `reasoningTokens` are denormalized onto the trace row** — `getTrace`/`getSharedTrace` read `cache_read_input_tokens`/`cache_creation_input_tokens`/`reasoning_tokens` straight from `traces_v0`, NOT a separate `SUM(simpleJSONExtractUInt(attributes, …)) FROM spans WHERE span_type='LLM'` scan (which reads the full `attributes` column for every LLM span). The values are summed at ingestion: `SpanUsage` carries them (cache-read = `InputTokens.cache_read_tokens`, cache-creation = `InputTokens.cache_write_tokens` — Anthropic prompt-cache writes, reasoning = `int_attr(gen_ai.usage.reasoning_tokens)`) and `TraceAggregation::from_spans` sums per batch; `traces_agg`'s `SimpleAggregateFunction(sum, …)` columns accumulate across batches. Adding another per-trace aggregate now touches four places: a CH migration (ALTER `traces_agg` + recreate `traces_v0`), `SpanUsage` + `TraceAggregation` + `CHTraceAgg` in Rust, the `traces_columns` allowlist in `query_engine/validator.rs`, and the frontend reader (`getTrace`/`getSharedTrace` SELECT + `TraceViewTrace` type) — plus the realtime mirror below. Keep `TraceAggregation`'s counters `i64` and cast to `u64` at the `CHTraceAgg` boundary (the CH columns are `UInt64`, defaulting to 0 implicitly like `num_spans`).
- **The realtime `trace_update` SSE payload is a SIXTH touch-point for per-trace aggregates:** `RealtimeTrace` in `app-server/src/traces/realtime.rs` is a hand-mirrored camelCase projection of the trace stats — a new trace column doesn't reach live table rows until it's added there AND to the frontend `RealtimeTracePayload` type (`frontend/lib/traces/types.ts`, which documents the mirror) plus the consumers that rebuild rows from it (`realtimeTraceToRow`/`mergeTraceDelta` in `components/traces/traces-table/realtime.ts`, `mergeTraceUpdateIntoRows` in `components/evaluation/utils.ts`). Also add the column to `tracesSelectColumns` (`lib/actions/traces/utils.ts`) so fetched rows carry it too.
- **The `trace_update` payload is per-batch DELTAS:** `RealtimeTrace::from_aggregation` ships one `TraceAggregation` per batch and the frontend ACCUMULATES (`mergeTraceDelta`: `+=` tokens/costs, min/max times, error-wins status, tag union). `dispatch_trace_realtime_updates` is the only dispatch path. It carries no `root_span_input`/`root_span_output` — the real `agent_input` can't ride the delta (extraction is async), so it ships on its own `trace_agent_input_update` event (`send_agent_input_update`, published from the `raw_trace_io` choke point under the same flag, covering both the extraction consumer and public `POST /v1/traces/metadata`). The event is routed to ALL of the trace's channels (project / evaluation / debugger) via `channels_for_trace_id` — a CACHE-ONLY resolver (the extraction span carries no routing keys): eval id from `lookup_trace_evaluation_id`, rollout session from `lookup_trace_rollout_session_id`, a `(project,trace)→rollout.session_id` cache (`TRACE_ROLLOUT_SESSION_ID_CACHE_KEY`) populated on span ingest in `send_span_updates` (PG-free, survives the planned PG-trace removal). Frontend consumers: traces table (`applyTracePartial` + `pendingFragmentsRef` buffer for the event beating the row) and the debugger store (`applyAgentInput`, which patches the loaded row or buffers by traceId and flushes in `applyTraceUpdate`'s create/lazy-row branch — the branch that would otherwise drop it). The eval table has no `agent_input` column, so the eval-channel event currently has no frontend consumer (harmless).

## ClickHouse async-insert tuning

- The global CH client in `app-server/src/main.rs` sets `async_insert=1, wait_for_async_insert=1` on every insert. With CH's adaptive busy-timeout (`async_insert_use_adaptive_busy_timeout=1`), the server raises the per-buffer wait toward `async_insert_busy_timeout_max_ms` (default 1000 ms) whenever flushes are time-triggered rather than size-triggered. Our consumer-side batchers already coalesce rows upstream, so CH's per-flush byte size is far below `async_insert_max_data_size` and every flush is time-triggered — the adaptive loop parks at `max_ms` and `wait_for_async_insert=1` makes the client block for that full duration.
- The hot ingest tables (`spans`, `traces_replacing`, `llm_messages`) override `configure_insert` to pass `async_insert_busy_timeout_max_ms`. The value is read once at boot from `SPANS_CH_WAIT_FOR_ASYNC_INSERT_MS` (default 400) into `SPANS_CH_ASYNC_INSERT_BUSY_TIMEOUT_MAX_MS` in `app-server/src/ch/mod.rs` — single env var covers all three tables since they share the same hot ingest path. Capping the max ceiling without touching durability (`wait_for_async_insert=1` still acks after disk flush). p50 client-observed wait drops from ~1 s to ~400 ms. Trade-off: ~2.5× the parts/sec on these tables — monitor `system.parts` active count for `spans` after rolling out and watch for `parts_to_delay_insert`/`parts_to_throw_insert` proximity (CH stock defaults are 1000 / 3000; `spans` has no `PARTITION BY` so it's all one virtual partition). Steady-state was ~179 active parts on `spans` pre-change, so the 2.5× headroom still leaves >2× margin to the delay threshold.
- Do NOT set this option on the global client — it would also apply to non-batched, low-volume inserts (notifications, signal_events) where the larger coalescing window is harmless and the extra parts churn is wasted.

## RabbitMQ Connections

- Reconnect is delegated to lapin 4.x via `ConnectionProperties::enable_auto_recover()` (called in `app-server/src/main.rs`; the `mq` module is `mod.rs` + `rabbit.rs` + `tokio_mpsc.rs` + `utils.rs`). The same `Connection` handle stays alive across broker blips — lapin redials TCP, re-opens channels, and re-establishes consumers in place. The `MessageQueue` trait exposes `is_healthy()` as a readiness probe.
- `get_receiver` in `app-server/src/mq/rabbit.rs` and the publisher channel pool's `create_channel()` are both wrapped in `tokio::time::timeout` (15s and 10s respectively). lapin can hang inside a setup call against a half-dead connection; the per-attempt timeout makes the outer backoff retry actually fire. Worker connect backoff caps at 5s `max_interval` (`worker/mod.rs`, `batch_worker/worker.rs`) so a transient pod-init failure resolves within seconds.
- Liveness (`/health`) is process-only and always returns 200 (`app-server/src/routes/probes.rs`). Readiness (`/ready`) gates on `MessageQueue::is_healthy()` AND `Cache::is_healthy()` and returns 503 when either is mid-reconnect — so k8s steers traffic away during a blip but does NOT kill the pod. Do not re-couple `/health` to dependency state: a 3-replica cluster losing one node would otherwise crashloop the entire app-server fleet while the resilient connections are doing their job.
- Quorum queues are already declared (`x-queue-type=quorum` in `main.rs`) so message data survives node loss; the resilience work is purely about client-side reconnect, not durability.

## RabbitMQ Streams transport (LAM-2024)

- **Second, additive transport for the two highest-volume ingest paths** (spans + Quickwit indexing), gated behind `RABBITMQ_STREAMS_ENABLED` (default off) AND `Feature::FullBuild`. Lives in `app-server/src/mq/stream/` (`mod.rs` registry + `topology.rs` + `publisher.rs` + `reader.rs`); env in `env/streams.rs`. The AMQP `MessageQueue` enum is untouched — streams are NOT a `MessageQueue` variant, because the trait's ack/reject/requeue surface has no meaning on a log (see below). **Both consumers run simultaneously by design during the transition**: the quorum-queue workers drain their backlog while streams take new traffic; removing `SpanHandler` / `QuickwitIndexerHandler` is a later release.
- **Why streams at all**: a quorum queue replicates every message through the Raft WAL with fsync-before-confirm, so a 4 GB/min burst of 50–200 KB spans piles up in broker MEMORY, trips `vm_memory_high_watermark` (0.6 of the 12 Gi limit in the prod configmap), and RabbitMQ then **blocks every publisher** — a total ingest outage. A stream is an append-only disk log, so the same burst becomes consumer lag on disk. Retention also buys a replay window a queue can't.
- **Uses the dedicated stream protocol (port 5552), not AMQP.** `RABBITMQ_STREAM_*` env vars are separate from `RABBITMQ_URL` because the `rabbitmq-stream-client` crate takes host/port/credentials, not a URL, and broker-side offset tracking only exists on the stream protocol. Requires the `rabbitmq_stream` plugin enabled and 5552 exposed — the prod configmap's `enabled_plugins` and the statefulset ports do NOT include it yet.
- **Ack → offset. There is no requeue.** The record never leaves the log, so "retry" = don't advance the offset, and `store_offset` runs only AFTER a successful flush (the analogue of the existing flush-then-ack in `SpanHandler`). Consequences to preserve: (1) a transient flush failure retries IN PLACE **forever** and never advances the offset — head-of-line blocking on that partition, which is correct because the failure mode is "ClickHouse/PG is down", which blocks everything on the queue path too; (2) a permanent failure is LOGGED and DROPPED, then the offset advances past it.
- **`with_max_elapsed_time` on the flush retry MUST stay `None`.** A bounded transient budget drops the batch and advances the offset, which silently loses spans the quorum queue would have kept — the queue path requeues transient failures indefinitely (`batch_worker/worker.rs` `to_requeue` has no give-up arm), and a >budget ClickHouse outage is exactly when losing data is worst. `Permanent` is the only arm that discards, so handlers must classify infrastructure failures as `transient` (they do: `processor.rs` CH inserts, `quickwit/client.rs` `Unavailable`/`DeadlineExceeded`). Pinned by `transient_retry_budget_is_unbounded`.
- **Reader teardown never drains — every exit path (including a delivery error) aborts the batchers and drops what they hold.** Held records were never flushed, so the replay from the last stored offset writes them exactly once; a drain-flush would double-write them whenever the offset store behind it failed, and teardown usually means the connection is already dead, so that store WAS going to fail (the broker-sent deactivation callback also never arrives on a dead connection, so the revocation gate can't cover this case). The residual duplicate window is a flush already in flight at abort time (insert landed, store didn't) — irreducible without an idempotent sink. Abort, don't drop: merely DROPPING a `JoinHandle` detaches the task, so the old batcher would survive every reconnect — still retrying (unbounded transient retries), still able to `store_offset` for partitions the fresh batchers now own, one leaked task per reconnect for the length of an outage. Pinned by `teardown_aborts_a_stuck_batcher`.
- **On SAC activation, only `ResponseCode::OffsetNotFound` means "no stored offset".** Treating every `query_offset` error as absent resumes at `First` and replays the whole retained partition (hours of duplicate spans) on a mere connection blip. The activation callback matches `OffsetNotFound` explicitly, and any other error goes through `retry_query_offset` (bounded by `OFFSET_QUERY_RETRY_BUDGET` — the broker is waiting on the activation response). If that also fails, the reader NEVER guesses a start position: it revokes the partition (so the flush/store gates discard anything delivered), fires an `offset_unresolved` `Notify` that the delivery loop selects on to tear down and reconnect, and returns `Next` to the broker (inert — the revocation blocks both ingest and stores until the fresh activation re-queries the offset). `retry_query_offset` cannot use `backoff::future::retry` (the client's `consumer_update` future must be `Sync`, which the combinator's closure isn't), so it steps `ExponentialBackoff` manually via `Backoff::next_backoff` — the crate still owns jitter and the `max_elapsed_time` budget rather than a hand-rolled sleep-and-double loop. Note `next_backoff` measures `max_elapsed_time` on the REAL clock (`Instant::now()`), NOT tokio's virtual clock, so it only terminates because the loop actually sleeps; a test that polls it under `start_paused = true` never ends, and the jitter ceiling is `max_interval * 1.5`, not `max_interval`.
- **`store_offsets` has TWO guards, and the cross-pod one is the important one.** (1) **Partition revocation** (`revoke_partition` / `is_partition_revoked`, populated from `consumer_update(active = 0)`): once the broker deactivates this consumer for a partition, the successor — typically in ANOTHER POD, e.g. mid rolling deploy — owns it, and a still-running batcher must store nothing for it however far ahead its own offsets look. This is the only sound answer because the successor's committed position lives in a different process; the held records are simply replayed. Re-activation clears the flag. **`REVOKED_PARTITIONS` is an async `tokio::sync::RwLock`, not a `std::sync::Mutex`, and that is the guard itself:** `store_offsets` holds a READ guard ACROSS the `store_offset` await while `revoke_partition` needs the WRITE guard, so a revocation cannot be recorded while a store that already passed the check is still in flight. A mutex could only make the *check* atomic — the write would escape the fence. **Residual window, unfixable client-side:** `StoreOffset` carries only `(reference, stream, offset)` (no epoch/generation/fencing token) and the protocol marks it "expects response: No", so the broker can neither distinguish nor reject a stale store under a shared reference; the spec also doesn't promise the broker waits for our `ConsumerUpdateResponse` before promoting the successor. If it promotes first, a store we believe is legitimate can still land late — degrading to a REWIND (duplicate reprocessing), never a skip-forward, i.e. the same at-least-once outcome a handover already has for unflushed records. (2) **A process-wide monotonic high-water mark** per `(consumer_name, partition)` — this only orders the two batchers INSIDE one process (outgoing reader's vs incoming one's), so it is NOT a handover guard on its own; don't rely on it for that. The mark advances ONLY after a confirmed `store_offset` (`offset_advances_high_water_mark` reads, `commit_offset_high_water_mark` writes) — advancing before the broker call would make a failed store poison the offset locally, so its retry would look stale and be skipped, leaving the group behind until a higher offset happened to land. The pre-store check is only a fast filter, NOT mutual exclusion: `store_offset` awaits, so another batcher or a whole new `run_once` generation can commit further ahead in between. `commit_offset_high_water_mark` is therefore **max-wins and returns whether it advanced** — a late confirmation from an aborted/superseded batcher can never lower the mark, and the `false` return logs the reorder instead of hiding it. Relatedly, the teardown **awaits the cancellation** (`handle.abort()` then `handle.await`): abort only *requests* cancellation, so a task inside `store_offset` keeps running to its next await point and could confirm after generation N+1 has started. Pinned by `late_confirmation_cannot_lower_the_mark` / `awaiting_the_abort_means_the_task_is_finished`. Offsets are committed under the SHARED consumer name, so during a single-active-consumer handover the deactivated owner's batcher can still be mid-flush and issue a store AFTER the successor has committed further ahead — rewinding the group's restart position and re-processing the successor's work. A stale store can only ever be BEHIND (a batcher commits only offsets for records it received itself, and per-partition delivery is offset-ordered), so dropping any non-advancing store is sufficient and never loses progress. It cannot mask a genuine skip-forward. **Severity framing for future reviews of this pattern: a stale store is a REWIND (duplicate reprocessing), never a skip-forward (loss)** — skip-forward would require the stale writer to hold a HIGHER offset than the live one, which the data flow prevents. The mark is a process `static` rather than reader/batcher state specifically so it also survives `run_once` reconnects, which respawn every batcher; holding it per-reader would let a fresh generation's first commit rewind the previous one's position via that second path. Pinned by `stale_offset_store_cannot_rewind_the_committed_position` / `offset_high_water_marks_are_per_partition`.
- **Revocation also gates the FLUSH, not just the store.** `flush_and_commit` snapshots `REVOKED_PARTITIONS` (read guard NOT held across the insert — that would block `consumer_update`'s write for the length of a ClickHouse insert) and discards batched records for deactivated partitions TOGETHER with their pending offsets via `discard_revoked_entries` — the pairing is the invariant (storing offsets for dropped records = loss; flushing records whose stores are refused = the deterministic double-write every SAC handover used to produce). Batch entries carry their partition name (`Vec<(String, H::Message)>`) purely to make this filter possible. The store-side read-guard fence remains the backstop for a revocation landing mid-flush, so the residual duplicate window is at most one in-flight batch per batcher. Pinned by `discard_revoked_drops_records_and_offsets_together`.
- **Unprocessable records are logged and DROPPED — deliberately lossy for now (accepted trade, follow-up work).** Empty records, undecodable records (`serde_json` failure — same verdict as the queue path's reject-on-deserialize), and permanently-failing batches are logged at `error` via `log_skipped_record` / the `Permanent` arm of `flush_and_commit`, and the offset advances past them. There is NO dead-letter sink: reaching these cases needs malformed data from our own producer or a genuinely unprocessable batch, so it should not happen in practice, and a durable sink needs a substrate that retains until CONSUMED — a stream expires under retention, so a stream is the wrong substrate (an unconsumed quorum queue would be the right one, but reusing `observations_queue` is NOT viable: its live `SpanHandler` workers would immediately re-reject the poison and destroy the evidence, so it needs its own consumer-less queue). Until then the drop is visible in logs. **A skipped record STILL forwards its offset** to the batcher as `StreamDelivery { message: None }` — skipping the offset too would pin the partition whenever its tail is poison (nothing later stores a higher offset, so every reconnect re-reads and re-logs the same records). That's also why the batcher flushes on "empty batch but pending offsets", not just on a full batch: an all-skipped stretch never reaches the size threshold. Pinned by `skipped_records_still_record_their_offset` / `flush_triggers_on_pending_offsets_with_an_empty_batch`.
- **`publish` AWAITS the broker confirmation — do not "optimize" it back to fire-and-forget.** Every caller treats `Ok` as durable and skips the quorum-queue fallback, so returning `Ok` on enqueue alone means a nack or a mid-flight disconnect drops the payload with an HTTP 200 and no queue copy — strictly worse than not using streams. The AMQP path awaits its publisher confirm (`mq/rabbit.rs` awaits the `basic_publish` promise), so awaiting here is what keeps the two transports' durability equivalent. The wait is bounded by `RABBITMQ_STREAM_CONFIRM_TIMEOUT_MS` (10s) because the client does NOT invoke the confirm callback for messages still in `waiting_confirmations` when the connection drops — it hands them to an `on_closed` handler we deliberately don't set — so an unbounded wait would hang the ingest path. A timeout returns `Err`, so the caller falls back to the queue; the record may still land later, which makes that a DUPLICATE rather than a loss (the stream consumer is already at-least-once, so duplicates are the safe direction). Hash routing resolves to exactly one partition, hence exactly one confirmation per publish.
- **A publish can outlive the producer it was sent on, so `mark_unhealthy` is GENERATION-SCOPED.** The confirm wait runs up to `CONFIRM_TIMEOUT_MS`, during which another caller may rebuild the producer; the old producer's in-flight confirms then fail (its connection is dead, or the rebuild closed it). Unguarded, that late failure flips the BRAND-NEW producer unhealthy — and since a rebuild stamps the cooldown, the next publish can't rebuild either, so every publish falls back to the quorum queue for a full `REBUILD_COOLDOWN` window against a perfectly good connection (self-inflicted, and it looks exactly like a broker outage). Each publish reads `generation` BEFORE sending; `condemn_if_current` (extracted as a free fn so it's testable without a broker) ignores failures whose generation has moved on, and `try_rebuild` bumps the generation BEFORE re-arming `healthy`. Pinned by `a_stale_generation_failure_cannot_condemn_a_rebuilt_producer`.
- **The DECLARE list is gated by the same flags as the publishers/readers.** `RABBITMQ_STREAM_SPANS_INDEXER_ENABLED=false` means neither the indexer publisher nor its reader is built, so declaring `spans_indexer_stream` anyway would (a) create a 32-partition super stream nothing ever touches and (b) — because a declare failure `return (None, None, None)`s the whole block — let an error on that unused stream disable the observations transport too and force a full queue fallback. `main`'s streams block therefore builds the declare list conditionally (observations always, indexer only when its flag is on). A new stream must be added to the list under the same flag that gates its publisher and reader.
- **General rule — never register a stream publisher whose reader might not start.** An unread stream silently expires under retention, whereas an unconsumed quorum queue retains until drained, so "publisher without reader" is strictly worse than "no streams at all". Concretely: `set_spans_indexer_publisher` (producer pods) and the indexer reader spawn (consumer pods) are BOTH gated on the same config flag `RABBITMQ_STREAM_SPANS_INDEXER_ENABLED`. **It must NOT be gated on `quickwit_client.is_some()`** — that was the original shape and it's cross-pod unsafe: `QuickwitClient::connect` is a per-pod TCP dial at boot (`QUICKWIT_INGEST_URL` has a `localhost` default, and `app-server.yaml` / `app-server-consumer.yaml` are separate Deployments), so a producer pod that connects while a consumer pod's dial fails registers the publisher with NO reader anywhere — and unlike the quorum queue, an unread stream is silently deleted by retention. A config flag is read identically by both roles, so the gate is symmetric by construction. **The READER must not be gated on this pod's own `quickwit_client` either** — that handle comes from an eager boot-time dial (`QuickwitClient::connect` → `Endpoint::connect()`), so a Quickwit blip during THIS pod's startup left the stream with no reader for the pod's whole lifetime while producer pods (gated only on the flag) kept publishing, and retention then deleted those jobs. So when the flag is on and the boot dial failed, the reader is built with `QuickwitClient::connect_lazy` (tonic `connect_lazy`, no dial — errors only on a MALFORMED endpoint, which is a config problem worth surfacing). That's safe because `StreamQuickwitIndexerHandler` classifies `Unavailable`/`DeadlineExceeded` as `Transient`: the batch retries in place without advancing the offset and calls `reconnect()`, so the backlog waits on broker disk and drains once Quickwit returns. Pinned by `quickwit::client::tests::connect_lazy_succeeds_against_an_unreachable_endpoint`. Note the QUEUE-path indexer workers keep their `quickwit_client.is_some()` gate — an undrained quorum queue retains its messages, so skipping those workers loses nothing. Leaving the publisher unset keeps `publish_for_indexing` on its queue fallback; note that fallback only triggers when the publisher is absent or `publish` errors — a successful publish to an unread stream returns `Ok` and never falls back. (`OPERATION_MODE=producer` is NOT an instance of this: readers live in the consumer pods, exactly as the quorum-queue workers already do.)
- **A stream flush can mix payloads for DIFFERENT destinations, so a handler must never early-return on the first failure.** `StreamQuickwitIndexerHandler::flush` groups payloads by index id and attempts EVERY index before returning, then prefers a `Transient` error over a `Permanent` one. Returning on first failure would let a bad events/signal-events payload fail the whole batch (the reader logs, drops, and advances offsets on `Permanent`) and silently discard sibling spans payloads that never got attempted — `HashMap` iteration order is nondeterministic, so which siblings die would vary run to run. The queue path doesn't have this hazard because it handles one payload per delivery. Any future stream handler that fans out over sub-groups needs the same accumulate-then-prioritise shape; pinned by the `quickwit::stream_consumer::tests` precedence tests.
- **Two invariants in `reader.rs` that are silent-data-loss bugs if broken.** (1) **Partition affinity** — `BatcherAssignment` pins each partition stream to one batcher for the life of the connection. Round-robin fan-out would let batcher A store partition P's offset past records still unflushed in batcher B. Assignment is by first-sight order, deliberately NOT by parsing the `-N` suffix off the partition name (that's a client-side naming convention; an unparseable name would collapse every partition onto batcher 0). (2) **`PendingOffsets` stores the MAX offset per partition per batch**, not the last-seen — an out-of-order record must never lower a stored offset. Both are unit-tested in `reader.rs::tests`.
- **Partition count is effectively immutable.** Hash routing is `murmur3(key) % partitions` (client-side, `superstream.rs`), so changing `RABBITMQ_STREAM_PARTITIONS` re-maps in-flight traces to different partitions and breaks per-trace ordering mid-flight. There is no resize operation. Treat a change as a v2 super stream + producer flip + drain migration. Size it ≥ the max consumer pod count you'd ever scale to (more pods than partitions = idle pods); partitions are cheap.
- **Routing key is `trace_id`, and that choice is load-bearing.** It spreads one customer's burst across all partitions while keeping a trace's spans on ONE partition, which gives per-trace ordering AND a single writer for the Postgres `traces` upsert (removing the `(project_id, id)` row-lock contention between concurrent workers). Routing by `project_id` would funnel a bursting customer's whole eval run into one partition and rebuild the hotspot. `producer.rs` keys on the FIRST span's trace_id — an export batch is overwhelmingly single-trace, and splitting per-trace would multiply small records. Quickwit indexing has no ordering requirement, so it keys on a fresh `Uuid::now_v7()` purely to spread (keying on the index id would pin every span doc to one partition).
- **Retention ignores consumer offsets — this is the data-loss trap.** `max-age` / `max-length-bytes` are evaluated per CLOSED SEGMENT and delete segments a lagging group never read, with no error raised; the consumer silently resumes at the oldest surviving offset. So retention must exceed worst-case (burst + ClickHouse outage + drain), and the alarm that matters shifts from queue depth to **per-partition consumer lag vs retention headroom** — page at ~50% of the byte cap, which gives hours of runway instead of firing when the broker is already blocking publishers.
- **Prod disk math (3 × 400 Gi local-NVMe, `lmnr-ai/k8s` `rabbitmq/statefulset.yaml`):** at the default RF=3 EVERY node holds EVERY partition, so cluster stream capacity is ONE node's free disk, not the sum. Minus the `disk_free_limit.relative = 2.0` floor (~24–32 GB) and quorum-queue headroom, that's ~250 GB usable ⇒ 128 partitions × 1.75 GiB ≈ 224 GiB, about **60 minutes of 4 GB/min peak**. **`max-length-bytes` is PER PARTITION** — `create_super_stream` passes one option map to every partition — so the disk the super stream can occupy is the PRODUCT `PARTITIONS × MAX_LENGTH_BYTES`, and raising EITHER multiplies the total. Retention is creation-only, so an oversized default can't be fixed by a redeploy (it needs `rabbitmqctl set_policy`), which is why `topology.rs::default_retention_budget_fits_one_prod_node` asserts the product fits one node — bumping the partition count without dividing the per-partition cap is exactly the mistake it catches. `RABBITMQ_STREAM_REPLICATION_FACTOR` is applied at creation via the raw `initial-cluster-size` arg (the crate has no typed setter). RF=2 ≈ 1.5× capacity and still survives one node; RF=1 makes capacity the SUM of node disks but a destroyed disk loses that partition's un-flushed backlog — a durability DOWNGRADE vs the quorum queue being replaced, so it needs an explicit decision, never a default. **`declare` sets `initial-cluster-size` explicitly** — omitting the arg does NOT mean one replica, it means the broker's default of a replica on EVERY configured node, so a stream that skipped it would silently ignore an operator's RF=1/2 capacity choice. The creation log prints the applied `initial-cluster-size` — it's creation-only and otherwise invisible afterwards.
- **Retention/segment args apply only at CREATION.** The broker ignores them for an existing stream, so changing `RABBITMQ_STREAM_MAX_LENGTH_BYTES` needs `rabbitmqctl set_policy`, not a redeploy. `stream-max-segment-size-bytes` is set to 100 MB (vs the 500 MB broker default) because retention only ever drops whole closed segments — 500 MB segments against a 7 GiB per-partition cap make expiry granularity 1/14th of the budget.
- **Publishers are built in BOTH pod roles — do NOT wrap the boot-block build in `enable_producer()`.** Ingest (`api/v1/spans.rs`) is producer-side, but the CONSUMER publishes too: `publish_for_indexing` runs inside `process_span_messages`, and the metadata façades (`publish_trace_{input,output}_update` via input-extraction, `publish_trace_metadata_patch` via the checkpoints consumer) all call `publish_span_messages` from consumer-side handlers. Gating the build on `enable_producer()` left both publishers `None` under `OPERATION_MODE=consumer`, so every one of those paths silently fell back to the quorum queue — the exact path this transport exists to unload, and invisible because the fallback is the normal, non-error branch. Role-scoping belongs on the READER spawn (which is already inside `enable_consumer()`), not on publisher construction.
- **Publishers are threaded explicitly as `Option<Arc<StreamPublisher>>` parameters, NOT a global registry.** Only two payloads ride streams — span export batches (`spans_stream_publisher`, into `push_spans_to_queue`/`publish_span_messages` and the metadata façades) and Quickwit indexing (`indexer_stream_publisher`, into `publish_for_indexing`, carried as a field on `SpanHandler`/`StreamSpanHandler`/`DataPlaneSpanHandler`) — so both are built once in `main`'s streams boot block and passed to their publish sites like `queue`/`db`/`cache`: actix `web::Data<Option<Arc<StreamPublisher>>>` for HTTP routes, a constructor arg on `ProcessTracesService`, a field on `IngestDeps` (set AFTER the streams block so the internal exporter gets it), and fields on `InputExtractionHandler`/`CheckpointsHandler` for the metadata-patch paths. `publish_signal_events_for_indexing` passes `None` internally — signal events deliberately stay on the quorum queue (low-volume; avoids an `lmnr-private` cross-repo change). The earlier boot-time `OnceLock` registry (`set_observations_publisher` etc.) was removed. `None` (tests, LITE, streams disabled, **or a failed connect at boot**) ⇒ every producer takes the AMQP path, so a broker outage degrades instead of dropping data. Pinned by `topology.rs::tests::connect_to_dead_endpoint_errors_rather_than_panicking`; verified by booting with `RABBITMQ_STREAM_PORT=1` (logs the fallback, zero panics, HTTP/SSE bind normally).
- **Stream readers have their OWN flush interval** (`STREAM_SPANS_BATCH_FLUSH_INTERVAL_MS`, default 1000 vs the queue path's 500) so the two transports tune independently. Lengthening is safe because a stream backlog waits on broker disk. (An earlier "reader sees only a slice of partitions so it needs a longer window" rationale was wrong — the queue path also split traffic across multiple workers.) Batcher counts are per-stream env vars: `RABBITMQ_STREAM_SPANS_BATCHERS` / `RABBITMQ_STREAM_SPANS_INDEXER_BATCHERS` (both default 4), threaded through `StreamReader::new` rather than read globally in the reader.
- **Stream record bodies are plain JSON — body compression was REMOVED (LAM-2024 prod OOM).** The first release zstd-compressed bodies via a per-record `lmnr.encoding` property (`mq/stream/encoding.rs`, since deleted) and producer/consumer pods leaked RSS until OOMKill; a first fix (thread-local `bulk::Compressor`/`Decompressor` context reuse + the jemalloc `unprefixed_malloc_on_supported_platforms` feature, targeting glibc-arena fragmentation from per-call multi-MB C-side zstd contexts) did not stop the growth, so compression was pulled entirely to eliminate the class. macOS does NOT reproduce the leak (its allocator returns large frees to the OS), so a local leak probe passing proves nothing — that's exactly how it shipped. Before re-adding compression: soak a canary on Linux watching RSS over hours, and keep the decode-by-property design (absent property = plain JSON) so mixed records stay readable during rollout. The jemalloc `unprefixed_malloc_on_supported_platforms` feature is KEPT — routing C deps' allocations through jemalloc is correct hardening regardless. Broker "memory growth" under streams is page cache from segment I/O charged to the container by cgroups (`anon` stays flat; check `/sys/fs/cgroup/memory.stat`), reclaimable and harmless — alert on `anon`, not working-set, for the broker.
- **`StreamBatchHandler::batch_size` is counted in `message_weight` units, NOT records.** One stream record carries a whole `Vec<RabbitMqSpanMessage>` export, while `SPANS_BATCH_SIZE` is a SPAN count (the queue `SpanHandler` sums `message.len()` across deliveries). `StreamSpanHandler` therefore overrides `message_weight` to `message.len()`; counting records would flush ~N× more spans per ClickHouse insert under multi-span exports — exactly the parts/sec problem the interval tuning above exists to avoid. The trait default is 1, which is right for handlers whose record IS one unit (Quickwit payloads). Pinned by `message_weight_*` tests in `reader.rs`.
- **`consumer_update`'s `active` flag is a `u8`, not a bool** (0 = deactivated) — the single-active-consumer handover callback. On activation it re-queries the stored offset and resumes at `offset + 1` (the stored value is the last PROCESSED record); with no stored offset it starts at `First`. On deactivation the successor replays anything our batcher still held unflushed — at-least-once, matching the queue path's redelivery.
- `cargo fmt` on `main.rs` walks the whole module tree and reformats unrelated files even with the signals stubs in place. Format the leaf files individually with `rustfmt --edition 2024 <file>`, and after formatting `main.rs` revert the collateral churn (`git checkout --` the files you didn't touch) before committing.

## Redis Connections

- `redis::aio::MultiplexedConnection` does NOT auto-reconnect — once the TCP socket drops, every command on that handle errors out forever. Wrap it in `ResilientRedisConnection` (`app-server/src/cache/connection.rs`), which tracks `is_connected` via an `AtomicBool`, runs a 30s `PING` health-check loop, listens for `notify_error()` from callers, and on real failure redials with uncapped exponential backoff and atomically swaps the new `MultiplexedConnection` in via `ArcSwap`. The supervisor PINGs first to coalesce transient hiccups before declaring the connection dead.
- Three timeouts bound every network call so a silent socket can't wedge the supervisor or hang command call sites: `DIAL_TIMEOUT` (10s) on `get_multiplexed_async_connection`, `PING_TIMEOUT` (5s) on the supervisor's coalesce check and the periodic health PING, and `COMMAND_RESPONSE_TIMEOUT` (10s) applied via `set_response_timeout` to the returned `MultiplexedConnection` so every cache get/set inherits the bound. Without these, a half-dead TCP connection could (a) hang process startup forever at pod init, (b) wedge the supervisor's `ping` before it reached the redial branch, or (c) hang the request that triggered any cache operation.
- One `ResilientRedisConnection` is shared by `RedisCache` and `RedisPubSub`'s publish path. Both call `connection.current_clone()` per operation (the `MultiplexedConnection` itself is a cheap-to-clone handle) and call `connection.notify_error()` on every command error. Pub/Sub's *subscribe* path still uses a dedicated `redis::aio::PubSub` connection from `client.get_async_pubsub()` — Redis pins subscription state per socket, so the multiplexed connection can't be reused there. Subscribe is kept simple: when the stream ends, the loop exits and the caller decides whether to re-subscribe.
- Startup degrades gracefully: if the initial `ResilientRedisConnection::connect` fails, app-server falls back to `Cache::InMemory` and `PubSub::InMemory` (logged as a warning). Once connected, the supervisor keeps trying forever — Redis flapping does not crashloop the pod.
- `Cache::is_healthy()` is the trait gate read by `/ready`. The Redis variant returns `connection.is_connected()` (the AtomicBool flipped by the health-check loop and the supervisor); the InMemory variant returns `true`.

## SSE proxy routes and Next's `failed to pipe response`

- Any App Router route that returns a `ReadableStream` must NOT call `controller.error(err)` for an upstream/transport failure. Next's `pipeToNodeResponse` (`next/dist/server/pipe-readable.js`) only swallows `AbortError` / `ResponseAborted`; every other stream error is rethrown as `Error: failed to pipe response` (`__NEXT_ERROR_CODE: "E180"`), which reaches `onRequestError` → `Sentry.captureRequestError` and is reported as an unhandled 500. This was the source of `GET /api/projects/[projectId]/realtime` Sentry noise: when the app-server-consumer pod goes away mid-stream (rollout, scale-down, LB idle cutoff), `reader.read()` on the proxied body rejects with `TypeError: terminated` / `UND_ERR_SOCKET: other side closed`.
- The fix is `controller.close()` on EVERY exit path (wrap it in try/catch — closing an already-cancelled controller throws) and a `console.warn` instead of an unhandled throw. Losing the upstream is a normal lifecycle event, and closing the response lets the browser's `EventSource` do its own reconnect; erroring the stream just costs a Sentry event and the client reconnects anyway. Suppress the log when `abortController.signal.aborted` — that's our own client disconnecting, not a fault.
- `sentry.server.config.ts` only drops realtime **transactions** (`beforeSendTransaction`), NOT error events, so an `E180` from this route was still reported. Don't reach for a `beforeSend` message filter to hide a streaming error — fix the stream's error path so the exception is never raised.
- To reproduce locally: point `BACKEND_RT_URL` at a throwaway `http.createServer` that writes SSE headers + one event then calls `res.socket.destroy()`. Because `/api/projects/*` is auth-gated by `proxy.ts`, either sign in first (`POST /api/auth/sign-in/local-email` with `{"email":"agent@lmnr.ai"}` and a cookie jar, `FORCE_EMAIL_AUTH=true` is set in the sandbox `.env.local`) or temporarily copy the handler to an unguarded path. Note an `app/api/_name/` folder is a **private** App Router directory and 404s — don't name a scratch route with a leading underscore.

## CSP and rrweb Browser Session Replay

- The site-wide CSP in `frontend/next.config.ts` deliberately omits `base-uri`. rrweb-player rebuilds captured DOM by injecting `<base href="<recorded-origin>">` so relative URLs in the snapshot resolve against the original site. `base-uri 'self'` blocks that and the replay loses every relative asset. Do NOT add `base-uri` without first moving the player into a CSP-relaxed iframe.
- The `Blocked script execution ... 'allow-scripts' is not set` console warnings during replay are NOT a bug — rrweb-player intentionally creates its replay iframe with a sandbox that omits `allow-scripts` so captured `<script>` tags can't execute inside lmnr.ai. They render as warnings in dev tools but the replay itself is unaffected.

## Frontend Best Practices

### One component per file

Related components should be in a folder named by the parent component (`my-list/`) and the parent component should follow the index.tsx pattern (`my-list/index.tsx`) and all related components should be in the folder (`my-list/my-list-item.tsx`).

Please do your best to keep components <150 lines.

### Writing a new data table (rendering-perf pattern)

New tables built on `InfiniteDataTable` MUST follow the split established for traces/sessions/spans/queues/etc. (`components/traces/traces-table/`, `sessions-table/`, `spans-table/`, `signal/events-table/`, `datasets/`, `evaluations/`, `playgrounds/`, …). Do NOT put fetching + controls + `<InfiniteDataTable>` in one component — the virtualized body then re-renders on every filter/search/URL keystroke. Structure:

- **`constants.ts`** — `FETCH_SIZE`, `RESOURCE`, chart-bar counts, and any other magic values (no inline literals in the components).
- **`index.tsx`** — a thin `default export` that mounts `<InfiniteDataTableProvider>` and renders an inner `*TableContent` component. `*TableContent` owns all the **volatile** state (URL params via `useSearchParams`, `useTableView()` effective filters/search/sort, custom columns) and the memoized handlers (`useCallback`/`useMemo` for `onSort`, `onRefresh`, column defs, filter arrays). It passes those down as **stable props** to `*TableContents` and renders `*TableControls` as its **`children`**.
- **`table-contents.tsx`** — `export const XTableContents = memo(function …)`. Owns data fetching (`useInfiniteScroll`, `useRealtime`) and renders `<InfiniteDataTable>`, forwarding `{children}` through to it. This is the component whose re-renders are expensive, so every prop it takes must be memoized upstream and it is wrapped in `memo`.
- **`table-controls.tsx`** — the toolbar/filter/search/chart JSX (`DataTableFilter`, `AdvancedSearch`, `ViewsToolbar`, `DateRangeFilter`, `RefreshButton`, columns menu, charts). It re-renders freely on filter/search changes; because it's rendered as `children` inside a separate `<div>` in `InfiniteDataTable`, its churn doesn't touch the virtualized rows.

Row/cell memoization lives inside `InfiniteDataTable` (row + cell are `memo`'d with custom comparators) — you get it for free. Your job is only to (a) keep the props you pass into `*TableContents` referentially stable, and (b) keep cell components cheap (see the tooltip rule below). For a heavy custom virtualized list outside the datatable (e.g. the trace-view transcript), apply the same idea: a `memo`'d row component with a hand-written comparator that checks only the fields that row actually reads.

### Tooltips in table cells / hot render paths

There is ONE app-wide `<TooltipProvider>` in `app/layout.tsx`. Cell components (and anything rendered per-row) MUST NOT wrap their tooltip in a local `<TooltipProvider>` — that mounts a provider per cell and is a measurable render cost at 50 rows × N columns. Use a bare `<Tooltip delayDuration={…}>` (delay goes on the `Tooltip`, not a provider) with `<TooltipTrigger>` + `<TooltipPortal><TooltipContent/></TooltipPortal>`. Same rule for shared cell-level components (`CopyTooltip`, `JsonTooltip`, `ClientTimestampFormatter`, tag/cost/tokens/duration cells).

### Bias towards complex logic and state in the Zustand store

When you anticipate lots of complex state management with useState and useEffects, this would be a good time to rethink or refactor and move state into a shared store and expose derived state via selectors.

### Avoid syncing URL params with Zustand store antipattern

Use the nuqs library to handle url param state when possible. Avoid using a useEffect to sync URL param state with the Zustand store. Prefer keeping source of truth as the useQueryState and passing in necessary state as function params to the store when needed.

### Use Zustand shallow to avoid unnecessary rerenders

Pass shallow as the equality function to useStore when applicable. That way even with a new selector reference each render, Zustand compares the result shallowly and won't re-render if the contents are the same.

### AbortController

Use an `AbortController` to cancel in-flight `fetch` requests when a newer request supersedes them, or when the component/store state they would update has moved on. Pass the controller's `signal` to `fetch`; the browser rejects with an `AbortError`, so bail in the catch without touching state. Prefer this over hand-rolled "snapshot state at start, compare at resolve, discard if drifted" patterns — it's the standard primitive and it cancels the actual request, not just its effect on state.

Use it for: an older response overwriting newer state (user paginates, then changes the filter — page 1 resolves after page 0 and splices stale rows onto fresh data), wasted network/server work, and rapid user actions (repeated scrolls, debounce-escaped clicks, search typing) where only the latest result should land.

**The reference implementation is `fetchNextTablePage` / `executeQuery` in `frontend/components/dashboards/editor/dashboard-editor-store.tsx`** — a per-store-instance controller ref in closure scope (not module scope, so instances can't cancel each other). Four non-obvious rules it encodes:

- Do NOT reset loading flags in the abort branch of the catch. Whoever aborted you owns the next state, and resetting races with it.
- Conversely, when one action aborts another, the ABORTING action must clear any loading flag the aborted one left behind.
- In the `finally`, only null out the shared controller ref if it still points at your own controller — otherwise a newer operation has already replaced it and you'd clobber its handle.
- On the success path use functional `set((state) => ...)` rather than closing over `state.data`, so you merge with the latest value rather than a snapshot.

### Error handling

**Client-side fetch calls** (in `"use client"` components): Always wrap `fetch` calls in `try/catch`. Check `res.ok` before using the response. On error, show a toast notification to the user via `useToast()`. Extract the error message from the response JSON when available, falling back to a generic message.

```typescript
try {
  const res = await fetch(`/api/projects/${projectId}/resource`, { method: "POST", body: JSON.stringify(data) });
  if (!res.ok) {
    const errMessage = await res.json().then((d) => d?.error).catch(() => null);
    toast({ variant: "destructive", title: errMessage ?? "Something went wrong" });
    return;
  }
  // handle success
} catch {
  toast({ variant: "destructive", title: "Something went wrong" });
}
```

**API route handlers** (`app/api/**/route.ts`): Wrap the handler body in `try/catch`. Distinguish `ZodError` (return 400 with `prettifyError()`) from other errors (return 500). Always return a JSON response with an `error` field.

```typescript
try {
  const result = await someAction(input);
  return Response.json(result);
} catch (error) {
  if (error instanceof ZodError) {
    return Response.json({ error: prettifyError(error) }, { status: 400 });
  }
  return Response.json({ error: error instanceof Error ? error.message : "Internal server error" }, { status: 500 });
}
```

**Server components** (`page.tsx`): Let database/fetch errors propagate to the nearest `error.tsx` error boundary — do **not** catch them and convert to `notFound()`. Only use `try/catch` or `.catch()` when you need a specific fallback value for optional data. Use `notFound()` only for genuinely missing resources (i.e. when a query returns `null`/`undefined`).
