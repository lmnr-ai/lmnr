## OTLP Trace Ingestion (`/v1/traces`)

- The HTTP handler dispatches on `Content-Type`: `application/json` decodes via `crate::opentelemetry_json` (serde shadow types → prost types), anything else falls through to `prost::Message::decode` (HTTP+protobuf, the default for every existing SDK). The gRPC server is unchanged. See `app-server/src/api/v1/traces.rs:decode_export_trace_request`.
- `build.rs` regenerates `src/opentelemetry_proto/mod.rs` from scratch every build via `tonic_prost_build::configure().include_file("mod.rs")`. Anything added inside `src/opentelemetry_proto/` will be clobbered on the next `cargo build`. Hand-written modules that work against the OTel proto types must live outside that directory (e.g. `src/opentelemetry_json.rs` declared from `main.rs`).
- The JSON decoder accepts the spec quirks browser SDKs actually emit: hex *or* base64 IDs, decimal-stringified `fixed64` *or* raw numbers, enum *names* (`SPAN_KIND_INTERNAL`) *or* ordinals for `kind` / `status.code`, and `intValue` as either string or number. Don't tighten any of these without checking real client output.
- When navigating to an ingested trace in the UI, the `traceId`/`spanId` query params must be dashed UUIDs, not raw OTLP hex — the API routes validate them as GUIDs (400/500 otherwise). A 16-byte trace id maps 1:1 (`5abe098dfc22bf38d4094b20c056a7dd` → `5abe098d-fc22-bf38-d409-4b20c056a7dd`); an 8-byte span id is left-padded with zeros to 16 bytes (`d2c361d0ea548a38` → `00000000-0000-0000-d2c3-61d0ea548a38`).

## Payload-too-large (413) responses

- **Actix's default 413 bodies are plain text and differ per extractor — there is no JSON error envelope anywhere in app-server** (`routes/error.rs::error_response` is `.body(format!("{}", self))`). Untouched, a `web::Json` handler returns `JSON payload (N bytes) is larger than allowed (limit: M bytes).` while a `Bytes` handler (`POST /v1/traces`, `/v1/logs`) returns just `payload reached size limit`, which SDKs log verbatim. An `ErrorHandlers` handler for `StatusCode::PAYLOAD_TOO_LARGE` in `main.rs` replaces the body with the static `PAYLOAD_TOO_LARGE_MESSAGE` for every route. Keep it a constant — the request size and limit are deliberately NOT parsed out of the headers.
- **`JsonConfig::error_handler` is NOT the right hook for this.** It only covers `web::Json` extraction, so the `Bytes`-based OTLP ingestion routes (the ones that actually 413 in production) would keep actix's terse default. An `ErrorHandlers` handler keyed on the status code catches every extractor at once.
- The handler is global, so the message stays route-agnostic — `/v1/datasets/datapoints`, `/v1/labeling_queues/*` and the SQL routes all 413 with no span involved.
- To reproduce a 413 locally, start app-server with a small `HTTP_PAYLOAD_LIMIT` (e.g. `PORT=8000 HTTP_PAYLOAD_LIMIT=10000 cargo run`) and POST an oversized body. Note the gRPC ingestion path uses the separate, much larger `GRPC_PAYLOAD_LIMIT` (25 MB), which is why a payload can 413 over HTTP and succeed over gRPC.

## OTel GenAI Semantic Convention Ingestion

- **Backend (app-server)** preserves the native OTel GenAI message shape end-to-end — `gen_ai.input.messages` / `gen_ai.output.messages` are deserialised from JSON string to `Value` but NOT reshaped into Laminar's `ChatMessage` struct. This keeps the original instrumentation payload lossless; the frontend owns rendering. Do NOT add a backend ChatMessage conversion here.
- The same pass-through carries **verbatim AI SDK v7 payloads**: `{role, content}` messages with dash-typed parts (`tool-call`/`tool-result`/`reasoning`), LanguageModel `file` parts, `providerOptions`/`providerMetadata`. In `parse_and_enrich_attributes` the GenAI block runs AFTER the legacy `gen_ai.prompt.{i}.*` / `ai.prompt.messages` handlers and overwrites their `self.input`/`self.output`, so when a span carries both vintages the verbatim attrs win. `normalize_aisdk_attributes` never synthesizes or rewrites `gen_ai.input/output.messages` (it only copies `{prefix}.prompt.messages` → `ai.prompt.messages`). Pinned by `test_verbatim_ai_sdk_genai_messages_pass_through` / `test_verbatim_genai_messages_take_precedence_over_ai_prompt_messages` / `test_normalize_aisdk_does_not_touch_verbatim_genai_messages` in `traces/spans.rs`. Do NOT remove the legacy handlers — historical spans keep those attribute shapes in ClickHouse indefinitely.
- `gen_ai.system_instructions` is prepended to the input messages as a synthetic `{role: "system", parts: [...]}` entry so the system prompt threads into the same message array. Bare-string arrays (`["Be helpful"]`) are preserved verbatim inside `parts` — the frontend parser handles both shapes. Helper: `prepend_system_instructions` in `spans.rs`.
- **Frontend parser** lives at `frontend/lib/spans/types/gen-ai.ts` (`parseGenAIMessages`). It runs in `processMessages` (`frontend/lib/spans/process-messages.ts`) right after the signals-gated Anthropic check and BEFORE the OpenAI/AI-SDK/LangChain/Gemini detectors (the loose OpenAI assistant schema would otherwise claim `{role, parts}` payloads and render them empty), and decodes the GenAI parts (`text|thinking|tool_call|tool_call_response|uri|blob`) into `ModelMessage[]` for the existing generic renderer.
- Span-type inference from `gen_ai.operation.name`: `chat|text_completion|embeddings|generate_content` → LLM, `execute_tool` → Tool, `invoke_agent` → Default.
- **pydantic_ai tool-span quirk**: pydantic_ai emits `execute_tool <name>` spans WITHOUT `gen_ai.operation.name`; only `gen_ai.tool.call.arguments` / `gen_ai.tool.call.result` are set. `span_type()` has a fallback that classifies a span as Tool when either of those attributes is present. Do not remove this fallback when adding other GenAI emitters.
- The `gen_ai.tool.call.*` → `self.input`/`self.output` block in `parse_and_enrich_attributes` is gated on `self.span_type == SpanType::Tool` (not just the raw attribute keys) so it cannot clobber LLM-span input/output if a spec-violating emitter mixes LLM message attrs with tool-call attrs on the same span. The gate still works for pydantic_ai because `span_type()` already infers Tool from the `gen_ai.tool.call.*` fallback before this runs.

## Static System Prompt Extraction (`traces/static_sp_extraction`)

- The extraction agent: given N example system prompts from one template family, an LLM tool-calling loop produces an ordered list of removal regexes that collapse all examples to the same static skeleton. Agent system prompt is `instructions.md` in the module, embedded via `include_str!`. (The span-ingest pipeline that drives it is documented under "Static System-Prompt Extraction" below.)
- Runnable on demand via `POST /api/v1/projects/{project_id}/system-extraction` (`routes/static_sp.rs`, ungated — 503s when `LlmClient` is `None`). Body (camelCase): `examples`, optional `provider`/`modelSize`/`includeDiff`, plus `internalProjectId` (destination project for internal-tracing spans; omit = tracing off) and `parentTraceparent` (W3C, re-roots the run under an external eval's span).
- Internally traced via `instrumentation/spans.rs`: root `system_extraction` span → per-step `llm_call` LLM spans (input/tools/model/step pre-call; model_version/usage/output post-call) → `tool_call` Tool spans, the children parenting contextually. Routing threads through `ExtractionTracing { project_id, source_project_id, parent, prompt_hash }` — `project_id` is the internal DESTINATION project while `source_project_id` is where the prompts came from (stamped as trace metadata, not used for routing); `project_id: None` (the `Default`) makes every span unroutable so the exporter drops them, i.e. tracing is off with zero overhead concerns.
- The `regex` tool semantics (`tool.rs::run_regex_tool`) are a contract with the instruction doc: patterns run sequentially with flags `gm`, every match deleted, output feeds the next pattern. Uses `fancy-regex` because the model is instructed lookbehind works — don't swap to the `regex` crate. Diffs (`removed`, the Example-1-vs-2 user-message diff) use the `similar` crate.
- One agent loop, no temperature ladder (the old `[0, 0.4, 0.7]` re-run-the-episode retry and its `episode` span layer are GONE). `MAX_STEPS` = **20** caps LLM calls — raised from 12 because large example families were hitting the cap mid-tool-call and falling back to the last tool-verified list instead of a converged one. Transient LLM failures retry with exponential backoff (`LLM_RETRY_INITIAL_BACKOFF` 2s, `LLM_RETRY_MAX_ELAPSED` 600s). Errors are logged and swallowed, never propagated, so `extract_static_regexes` is infallible and returns `ExtractionResult { regexes, tool_calls }` with an empty `regexes` on failure.
- **`MAX_OUTPUT_TOKENS` = 32,000 per LLM call, and the provider default is not survivable here.** At the default 4096 a reasoning model (Claude Sonnet-5 adaptive thinking) spent the whole budget thinking on large inputs and never emitted a `tool_use` block, so the agent saw zero function calls and every retry produced an empty answer.
- **Tool-verified fallback**: the loop tracks the LATEST tool-call input whose result had `isValid && isResultInAllIdenticalOutput`; if the model's parsed final answer doesn't collapse the shown examples (models "improve" patterns after their last test or typo them, e.g. `(??<=`), the tool-verified list is used instead. Keep this — trust the tool over the transcript.
- Tool output deliberately OMITS `residuals` / `residualLengths` / `offset` — echoing residuals blows the input budget, and `residualDivergences` `{a, b}` slices (80 chars before / 140 after the first differing byte, deduplicated) carry the only part that matters. Don't re-add them. `sharedRemoved` is substring-based (48-gram intersection, maximal runs, whitespace-collapsed, first 20 chunks), NOT line-based, so it fires on footers swept at different offsets per example.
- The `instructions.md` prompt, `build_user_message` hardening paragraph, and the `regex` tool description are VERBATIM from the reference spec (a ~3.5KB prompt outscored a 12KB one) — don't reword them for style.

## Static System-Prompt Extraction pipeline

- **This is the LEGACY pipeline, live only when `SP_VERSIONING_ENABLED` is off** — the producer dispatches on that flag (see "System-prompt versioning" below). Its agent and regex-application helpers are still shared by the v2 path.
- `app-server/src/traces/static_sp_extraction/` (producer.rs + consumer.rs alongside the agent) derives, per naive signature (`lmnr.span.prompt_hash`), a regex list whose matches are the prompt's dynamic parts. Distinct from `checkpoints/system_prompt.rs`, which resolves a single stripping regex inline on the checkpoints path — this pipeline is span-ingest-wide and cache-first.
- Flow: the ingest producer (`traces/producer.rs::publish_span_messages`) collects `(prompt_hash, system_prompt)` from `preprocess_for_queue`, checks `static_prompt_regex:{project}:{hash}` and publishes misses to `static_prompt_queue` — best-effort, and only AFTER the span publish succeeded so rejected batches don't feed the accumulator. The consumer (`traces/static_sp_extraction/consumer.rs`) appends the prompt to `static_prompt_accumulator:{project}:{hash}` (`SP_EXTRACTION_ACCUMULATOR_TTL_SECONDS`, 1h); on trigger it takes the per-signature lock `static_prompt_lock:{project}:{hash}` (`EXTRACTION_LOCK_TTL_SECONDS`, 1h — runs are normally under 10 min, but the per-step upper bounds are high just in case), runs the extraction agent, writes the regex cache (`STATIC_REGEX_TTL_SECONDS`, 7 days), clears the accumulator, and releases the lock.
- **TWO trigger conditions, and the second one is load-bearing.** `samples.len() >= SP_EXTRACTION_PROMPT_SAMPLES` (5) is the normal path; `occurrences >= SP_EXTRACTION_OCCURRENCE_THRESHOLD` (100) is the fallback, because a **fully-static prompt collapses to one unique sample forever** and would otherwise never resolve — the producer would re-enqueue it on every trace, indefinitely.
- **The samples blob is self-bounding, not capped by a constant:** `accumulate` early-returns once `samples.len() >= PROMPT_SAMPLES`, so it stops growing at the threshold; same-trace resamples and byte-identical prompts are dropped before the push (they add no variance, so the blob isn't rewritten for them). The occurrence counter is a **separate** key using atomic `increment` — `INCR` leaves no expiry, so its TTL is refreshed on every message to keep it sliding with the samples blob.
- The lock is released on ALL exit paths — agent failure, post-agent regex-cache WRITE failure, and success — so a later message can retry immediately; the TTL is only a backstop for a crashed worker that never reaches the release. Trade-off: a persistently-failing agent is re-run on every incoming batch for the signature rather than throttled to once per TTL. Lock contention and cache-read errors both drop the message (no requeue); a later span with the same signature re-triggers.
- The consumer calls the real agent, `traces::static_sp_extraction::extract_static_regexes`. It returns `ExtractionResult` (never errors); an EMPTY `regexes` list means the agent loop produced no usable answer and the consumer treats it as agent failure (no cache write, lock kept). The agent needs an `LlmClient` — `StaticPromptHandler` carries `Option<Arc<LlmClient>>` (built in main.rs when ANY LLM-backed flag is on: the union of `Feature::Signals` and `Feature::InputExtraction`) and drains the queue without accumulating when it's `None`. Tests use the `#[cfg(test)] test_regexes` seam on the handler instead of a real client.
- The read-modify-write on the samples blob is NOT atomic across workers — concurrent appends to the same signature can lose samples. Acceptable: the threshold is a heuristic, and the stream of spans keeps feeding it. (The occurrence counter is exempt — `increment` is atomic, so the fallback trigger can't be starved by racing workers.)
- `tool.rs::compile_removal_regex` / `tool.rs::remove_all` and `consumer.rs::STATIC_REGEX_TTL_SECONDS` in `traces/static_sp_extraction/` are `pub` for the enterprise summarizer (`lmnr-private` `signals/private/summarize.rs`), which must apply the cached regex lists with EXACTLY the compile flags / removal semantics `run_regex_tool` tested them under. Don't re-privatize them based on OSS-only usage analysis; route any new applier through `compile_removal_regex` instead of compiling `(?m){pattern}` inline.

## System-prompt versioning (v2, `traces/sp_versioning`)

**`app-server/src/traces/sp_versioning/README.md` is the narrative walkthrough** (algorithm, window mechanics, measured results, debugging playbook). This section is the invariant list.

- **THREE flags, stacked, and the split is the rollout mechanism.** `Feature::SystemPromptVersioning` (`SP_VERSIONING_ENABLED`, default off) routes ingest to this pipeline instead of the legacy skeleton-hash queue; `Feature::SignalsVersionedPrompts` (`SP_VERSIONING_SIGNALS_ENABLED`, requires BOTH) makes signals *consume* the versions; `Feature::VersionedInputExtraction` (`SP_VERSIONING_INPUT_EXTRACTION_ENABLED`, also requires the master flag) keys user-task regexes on them (see "Ingestion-time trace input/output extraction" below). Keep them separate — versioning can mint and be inspected for a while before anything depends on it, and collapsing them removes the observation window. With versioning off the legacy `static_prompt_queue` + `StaticPromptHandler` path runs unchanged; the queue/exchange declarations in `main.rs` are unconditional so a mixed-flag fleet can't lose messages.
- **Agent identity is the first-sentence hash (`lmnr.span.agent_hash`), NOT the skeleton hash.** Both are minted by `prompt_hash::prompt_hashes` in one pass and both must keep existing — the skeleton still feeds the legacy pipeline, checkpoints and signals. Keying on the first sentence means permuting/adding/removing the prompt's XML scaffolding does not fork the agent and re-trigger classification.
- **Classification is LLM-FREE.** Within an agent, a Redis window of recent distinct prompts is clustered line-wise (top-K% Jaccard → ordered LCS intersection) and the intersection hash IS the version. LLM spend is decoupled: **regex extraction is demand-driven**, not mint-driven. `static_sp_extraction::worker` runs the agent only when a consumer (today `signals/private/system_prompts.rs`, the summarizer's static resolution) hits a version with no cached regexes, so cost is proportional to versions actually READ. An absent regex cache key means "not generated yet / generation failed" — readers fall back to the raw prompt rather than erroring.
- **The window is bounded by AGE, not count** (`SP_VERSIONING_WINDOW_MAX_AGE_SECONDS`, 1h; `SP_VERSIONING_WINDOW_SIZE`, 200, is only a burst cap) — so a slow agent's window can't span days and dilute a genuine prompt change with pre-change prompts. Age eviction stops at `SP_VERSIONING_WINDOW_MIN_ENTRIES` (10): without that floor a slow agent's window empties between prompts and every mint intersects a cluster of ONE, which is the triggering prompt verbatim, matches only itself, and forces a fresh mint on the next prompt (measured: half of all mints came from agents in this state).
- **The cluster is a PERCENTAGE of the window** (`SP_VERSIONING_TOP_K_PERCENT`, 50), not a fixed K. A fixed K at or below one cohort's size makes the cluster *be* that cohort, and its dynamic values (a user id repeated across a session's prompts) then read as static and mint a version per cohort.
- **Presence thresholds are a dead end — measured twice, monotonically worse.** Relaxing the all-must-agree LCS veto admits cohort-shared *dynamic* content, because the cluster is Jaccard-*selected*: over the cluster 100% → 145 versions vs 50% → 958; over the full window 100% → 49 vs 70% → 571.
- **The regex-extraction worker deliberately has NO retry topology.** A failure drops the message and the next demand retries; only the classifier queue parks. `sp_versioning_delay_queue` is a consumer-less park queue whose per-message TTL dead-letters back into `SP_VERSIONING_EXCHANGE` — **every park must use the SAME TTL** because RabbitMQ only expires at the queue HEAD, so a variable delay would reorder expiry relative to arrival and stall the head behind a longer-lived message.
- **Two ClickHouse tables with different engines and different reasons.** `system_prompt_versions` (plain MergeTree, partitioned by month) is one write-once row per resolved span. `system_prompt_version_defs` (ReplacingMergeTree, **deliberately unpartitioned**) is the append-only mint journal and the ONLY durable record of a version's static TEXT — the Redis registry keeps just 64-bit line hashes. It's unpartitioned because merges never cross partitions, so a re-mint months later still collapses onto its original row instead of leaving a duplicate. The versioning pipeline never reads it; Redis stays the runtime source of truth. Both must be added to `deleteProjectDataFromClickHouse` (they are).
- **`TraceCompressor::new` takes optional clickhouse + queue handles, and chat/MCP compression passes `None` for both.** Chat compression never summarizes, so it must never look up prompt versions or enqueue a regex-generation demand. Threading a real queue in there would make an interactive trace-context request trigger LLM spend.
- **Cheap-match hits are re-validated at most once per agent per `SP_VERSIONING_FULL_RUN_INTERVAL_SECONDS`** (300). This is the staleness bound for silent static ADDITIONS: an old, smaller static line set keeps subset-matching new prompts forever, so without the probe it would never notice. Removals self-detect on the first miss, which is why only one direction needs it. The bound is **wall-clock, not the 1-in-N sampling it replaced** (`SP_VERSIONING_FULL_RUN_SAMPLING_N` is GONE): the quantity being bounded is detection latency after a prompt change, and under 1-in-N that latency scaled inversely with traffic — measured across one project's agents, the same N gave a 5-minute bound on the busiest agent and a 4-day bound on the quietest. Deliberately no minimum-message companion bound. The marker is a **shared** cache key (`SYSTEM_PROMPT_PROBE_CACHE_KEY`, `{project}:{agent}`) whose TTL is the interval and whose presence is the marker; shared rather than process-local so the interval means the same thing however many ingest pods run. Claiming is a plain check-then-set with NO lock (a race costs one extra clustering run). **Cache errors don't probe** — the full algorithm reads window+registry from the same cache so it couldn't run usefully anyway, and probing puts the raw prompt body on the wire.
- **A probe mint requires the new intersection to be a STRICT SUPERSET of the matched version's line set** (`similarity::is_strict_superset`, gate in `consumer.rs::full_algorithm` behind `probe_of`). On the probe path `cheap_match` already proved the matched version describes this prompt and the span is already labeled, so a non-superset intersection is not evidence about the prompt — it is the intersection estimator disagreeing with itself across two samples of the window, and minting on it forks the version on resampling noise (measured: the dominant source of churn, since the probe re-runs the estimator far more often than cheap-match misses do). Nothing is lost, because the probe's job is ADDITIONS and a removal breaks the subset match by construction, arriving through the miss path where the gate doesn't apply. A lapsed line-set key also skips the mint (premise unverifiable) and self-heals, since `cheap_match` skips that version from then on.
- **Redis here is working storage, not a cache.** The in-memory fallback (`DEFAULT_CACHE_SIZE = 100` entries, process-wide moka) silently destroys it: the cold-by-design per-entry line-set keys are evicted first, every cluster collapses to a handful of entries, and version counts explode with no error anywhere. If version counts look absurd, check Redis is up before reading the algorithm.
- **The window blob RMW is not atomic** (`load_window` → `upsert_entry` → `save_window`, `NUM_SP_VERSIONING_WORKERS` defaults to 2). Lost appends / `seen_count` bumps / `labeled` flags are all benign and self-heal. The one asymmetric case: worker A evicts entry P and deletes its line-hash key while worker B's blob write keeps P, leaving the blob referencing a deleted key. `available` (usable entries, not `win.len()`) absorbs it, so it dents intersection quality rather than correctness — but for a *recurring* prompt it does not self-heal, because `touch_entry_lines` is a Redis `EXPIRE` that returns 0 on a missing key without erroring, so P stays a permanent dead slot while it keeps arriving. Symptom is `cluster_size` well below `TOP_K_PERCENT` of `window_len` in the journal.

## Checkpoints / Agent Versioning

- **The whole pipeline is gated behind `CHECKPOINTS_ENABLED` (default off)** — `Feature::Checkpoints` in `features/mod.rs`, backed by `env::checkpoints::ENABLED` (`env/checkpoints.rs`). The gate sits at two points: the producer call in `traces/processor.rs` (no checkpoint messages published) and the worker spawn in `main.rs` (no `CheckpointsHandler` workers). The queue/exchange declarations in `main.rs` stay unconditional so a mixed-flag fleet can't lose messages (an enabled producer node can publish while a disabled node runs alongside).
- Checkpoint text fields (`name`, `system_prompt`, `tool_definitions`, `model`) originate from user span data and can contain a NUL byte (`0x00`), which Postgres `text` columns reject ("invalid byte sequence for encoding UTF8: 0x00"). The DB write helpers in `app-server/src/db/agents.rs` run every user-controlled string through `crate::utils::sanitize_string` (strips NUL + other control chars, keeps `\n`/`\t`) — the same helper used on the ClickHouse insert path. `version_hash` is hex so it's left untouched. Sanitize at the Postgres write boundary, not at hash time, so dedup hashing keeps the original bytes.

## Post-factum Trace Metadata (`POST /v1/traces/metadata`)

- Customers patch trace metadata after ingestion via `POST /v1/traces/metadata` `{ traceId, metadata }`. The handler (`api/v1/traces_metadata.rs`) verifies the trace exists via `ch::traces_agg::trace_exists` (a `count()` probe on `traces_agg`; returns 404 otherwise) and pushes a virtual span carrying the metadata as `lmnr.association.properties.metadata.<key>` attributes plus the `lmnr.internal.metadata_only` marker (`SPAN_METADATA_ONLY`), reusing the regular `observations_queue` via `publish_span_messages`.
- Consumer split (`process_span_messages`): metadata-only spans are pulled out of `messages` BEFORE the regular pipeline (after `parse_and_enrich_attributes`, before usage lookup) into a `TraceMetadataPatch`, then written as one `traces_agg` identity partial plus one `traces_static` delta. No Postgres, no stub row, no version games — a patch that beats the trace's span batch is just another partial.
- Because `traces_static.metadata` is a whole-object SET column (see "`traces_static` CoalescingMergeTree" in `docs/internal/clickhouse-traces.md`), a trace whose metadata is written by BOTH a span batch and a patch has undefined metadata — last write wins wholesale, verified end-to-end. In practice metadata is set once per trace, and `traces_agg`'s `maxMap` retains the per-key history if it's ever needed.
- The existence check is best-effort, not a guarantee: a trace deleted between request and consumption still leaves its patch behind as a metadata-only row.
- `should_record_to_clickhouse` returns `false` for metadata-only spans, but the actual filter happens earlier (the `messages.retain` in the processor) so they never reach `recordable_indices`, `CHSpan` build, dedup, Quickwit indexing, autocomplete, realtime span updates, or workspace-bytes billing. They contribute nothing to `TraceAggregation` either.
- **Internal (server-side) metadata patches go through `publish_trace_metadata_patch` in `traces/metadata.rs`** — it builds the same virtual metadata-only span (marker + `{ASSOCIATION_PROPERTIES_PREFIX}.metadata.{key}` attrs, name `"lmnr.trace.metadata"`, zero-duration) and publishes via `publish_span_messages`, skipping the HTTP route's existence pre-check. **It is deliberately a non-async `fn` returning `Pin<Box<dyn Future<Output = Result<()>> + Send>>`** wrapping `Box::pin(async move { ... })`: any caller reachable FROM `publish_span_messages` (e.g. the ingestion user-task hook) creates the async cycle `publish_span_messages → caller → publish_trace_metadata_patch → publish_span_messages`, which a plain `async fn` can't express (E0733 recursion-in-async + an unprovable-`Send` cycle). Type-erasing at the DEFINITION breaks both. Runtime recursion is bounded because the virtual span is non-LLM with no input, so the user-task hook early-returns on it. (The boxed-future erasure now lives on the shared `publish_metadata_only_span` helper that both `publish_trace_metadata_patch` and the trace-io façades `publish_trace_input_update` / `publish_trace_output_update` build on.)

## Ingestion-time trace input/output extraction

- Extracts, **at ingestion**, the trace-level "user task" (the instruction the agent was asked to carry out, pulled out of the scaffolded LLM input) and the trace "output" (the latest output messages on the winner's path). Code in `app-server/src/traces/input_extraction/`; each file carries a `//!` header describing its own role, and `docs/internal/user-task-extraction.md` is the narrative walkthrough — this section is the invariant list. Compile-time ungated; the producer hook early-returns unless `Feature::InputExtraction` is on.
- **Three execution paths, one per candidate.** (1) A cached regex for the prompt's VERSION — zero LLM calls, applied inline on the producer. (2) A **direct** one-shot LLM extraction (`extract.rs`, `ModelSize::Small`, no tools, nothing cached) when the version resolves but has no regex yet, or the prompt has no version at all. (3) The **legacy** single-sample regex generation keyed by user-message shape, which is the permanent path for LLM spans with no system message and the whole pipeline while `VersionedInputExtraction` is off.
- **Backend `Feature` flags must be fine-grained: one flag per feature, even when two flags share the same condition.** Never gate a new feature on another feature's flag. The shared `LlmClient` in `main.rs` is built when ANY LLM-backed flag is on (union of `Feature::Signals` and `Feature::InputExtraction`) — gating it on one feature's flag would silently disable the others if the conditions ever diverge.
- **Storage — raw values on the wire, into `traces_static`'s own io columns.** The values ride a virtual metadata-only span on dedicated attributes `SPAN_TRACE_INPUT` / `SPAN_TRACE_OUTPUT_HASHES`, carrying the RAW JSON value / hex per-message hashes with NO metadata key. `processor.rs` routes them to a neutral `RawTraceIo` (not a `TraceMetadataPatch`) and `collect_static_agent_io_rows` writes `traces_static.input` / `.output_hashes`.
- **Never fold io into a metadata key.** `traces_static.metadata` has whole-object SET semantics, so a synthetic `{lmnr_user_task: …}` delta would REPLACE the customer's real keys. `encode_metadata` strips reserved keys as a backstop — note the two sides differ: `ch/traces_static.rs` strips both `lmnr_user_task` and `lmnr_trace_output`, `ch/traces_agg.rs` strips only `USER_TASK_METADATA_KEY`.
- `from_agent_io`'s `start_time` must be the **trace's** start time, not the span's — it's `traces_static`'s partition key.
- **Input winner heuristic (`lock.rs`) is a TWO-STEP reduction, and fusing the steps is a correctness bug.** Per-trace lock keyed `{USER_TASK_LOCK_CACHE_KEY}:{project_id}:{trace_id}`. (1) Per `agent_hash`, the **earliest-starting** candidate represents that agent — a trace's task lives in the FIRST step of its agent, while later loop steps grow monotonically in tokens and their last turn is tool output, not the task. (2) Across agents, the representative with the **most TOTAL input tokens — cached + uncached, NOT uncached-only**: the true first span's system prompt is often cache-read from prior conversations while helper spans are too small to cache at all, so subtracting cache-read ranks the helper higher. **Do NOT collapse the two into one comparison** — "earlier inside an agent, more tokens across agents" as a single relation is not transitive (`{X,t=1,10tok}` beats `{X,t=2,100tok}` beats `{Y,t=0,50tok}` beats the first), so a fold over it depends on iteration order and the stored task flip-flops for as long as spans keep arriving; pinned by `winner_is_independent_of_registration_order`. `min(start_time)` is monotone, so a late-arriving earlier step just corrects its agent's representative — which is why there is no arbitration window (a `ROSTER_CAP` "first N by start time" roster used to serve that purpose). Spans with no system message share the empty-`agent_hash` bucket; the map is capped at `MAX_AGENTS`, evicting the lowest-token representative. `write_lock_merged` is a re-read-merge-write with no mutex — safe because earliest-per-agent is commutative, so concurrent writers converge instead of clobbering.
- **Span-path depth is deliberately NOT part of arbitration (LAM-2137).** A depth gate reads like a clean main-agent-vs-subagent signal, and it was one until prod data showed the opposite shape: traces routinely run a small helper agent ("summarize the task", title generation) at a SHALLOWER depth than the main agent. The gate then keeps only the helper, and no later comparison can recover — the main agent never enters the agent map at all, and tokens are only compared among survivors. Token mass across agents handles helpers at any depth. The accepted trade-off is a subagent whose FIRST call out-tokens the main agent's first call; in practice the main agent carries the larger context. The span path is still computed, but only to seed the main-agent path cache Pass 2 matches against.
- **The publish gate compares TEXT, not strength.** `should_run_effect` runs the effect when the derived winner's `content_hash` differs from `lock.published`. It deliberately is NOT "the challenger must beat the published winner": under the per-agent model the winner legitimately moves DOWN in tokens when a genuinely earlier step for the winning agent arrives late, and that correction must publish. `published` moves only after the effect lands, so a swallowed failure doesn't gate retries for the whole lock TTL. `supersedes` (the queued-extraction drop check) likewise compares text: drop only when the derived winner now carries DIFFERENT text, since a winner change to the same text is a no-op either way.
- **The producer MUST persist the agent map before dispatching the effect, and `published` is set on ENQUEUE not on publish.** Those two facts interact: without the pre-write the ordering is enqueue-then-write, so a consumer picking the message up inside that window reads the pre-batch representative, `supersedes` compares the snapshot against that stale winner and DROPS the correcting extraction — and because `published` was already advanced optimistically, every later batch skips via `should_run_effect` and the superseded text stays stored for good (it also lands on the cache-hit path, where the drop check runs before the result is used). The extra `write_lock_merged` inside the `should_run_effect` branch makes the order write → enqueue → consumer-read; effects only run when the winner's text changes, so it is a rare round-trip, and `merge_from` being commutative means it composes with a concurrent batch's write.
- **`supersedes` exempts a same-agent winner that starts LATER than the snapshot** — that means the state is BEHIND, not ahead, and the snapshot is that agent's earlier representative, i.e. exactly the correction to publish. Defence in depth for the pre-write above, which is best-effort. Cross-agent supersession is unchanged: a different agent outranking us legitimately owns the task. Pinned by `a_stale_same_agent_winner_does_not_supersede_an_earlier_snapshot`.
- **KNOWN GAP: a winner whose representative is not in the current batch can't be published**, because the lock stores hashes while the effect needs the prepared text, which only this batch's contenders carry. Usually moot (an unchanged winner was already published; a new agent or an earlier step for the winner arrives in the batch), but a **demotion reorders without changing the promoted agent's representative**: an earlier — hence lower-token — step for the current winner drops its rank and can promote an already-stored agent whose representative came from a previous batch, leaving `published` on the superseded value with no later batch to heal it. Reaching it needs one agent's steps to arrive out of order (export reordering or concurrent batches), so it is measured rather than assumed — `process_trace_inputs` logs at ERROR when the winner isn't in the batch **and `should_run_effect` says its text is owed**. That second condition is not optional: an out-of-batch winner is the STEADY STATE of any multi-batch loop (the representative stays the first step while later batches carry later steps), so logging on the first condition alone fires once per batch per trace, floods prod, and makes the real rate unmeasurable. The log carries the winner's `content_hash` alongside `published` so a hit is directly checkable. **Do NOT "fix" it by ranking agents on max(tokens) seen:** that removes demotion but makes the out-of-batch case COMMON in the mirror direction (a helper outranking the main agent's first step at cold start, then the main agent's loop growing in a later batch and promoting it while its representative sits in the earlier one). The real fix is resolving a winner's text by span id in the worker — it already holds the ClickHouse client and the span id — transient-erroring while the span isn't inserted yet so redelivery heals it. Per-agent text in Redis was rejected: at trace volume, up to `MAX_AGENTS` × the 200k-char `signposted_text` cap per live trace is too much memory.
- **Output arbitration is INHERITED from the input winner, not independently computed.** Pass 1 caches the winner's path minus its last segment at `main_agent_path:{project}:{trace}` (`lock.rs::main_agent_path_cache_key`); Pass 2 treats any LLM span whose `path[..len-1]` equals that prefix as an output candidate. Both sides must strip the last segment identically. **This is why Pass 1's arbitration + path write run UNCONDITIONALLY** — only the extraction *effect* is gated on `llm_client_available()`. Gating the whole pass would leave Pass 2 matching a stale deeper path. With no cached prefix (no winner yet, or a cache miss) **every** LLM span is a candidate, so output is visible before arbitration converges. Among a batch's matches only the latest `end_time_ns` publishes, and `end_time_ns` degrades to `i64::MAX` when unknown ("unknown beats real"). **Across batches there is no "latest wins" guarantee any more:** that was the `trace_agent_output` RMT version, and migration 54 moved the value onto `traces_static`, a CoalescingMergeTree with NO version parameter that resolves by INSERTION ORDER. `SPAN_TRACE_OUTPUT_END_TIME` is still stamped by `publish_trace_output_update` but is read by nothing — `RawTraceIo` has no end-time field. Batches normally arrive chronologically so the outcome usually agrees; a redelivered earlier batch or two concurrent flushes of one trace can regress the output to an earlier turn, self-healing on the next batch. Several comments (`traces/metadata.rs`, `span_attributes.rs`, `input_extraction/output.rs`, `query_engine/validator.rs`) still describe the retired RMT. Output capture deliberately does NOT filter to "the last toolless assistant message" — tool-call-only turns are captured too, since always writing the latest is cheaper than predicting a model-specific "I'm done" signal.
- Capture ordering in `traces/producer.rs::preprocess_for_queue`: the input candidate is taken BEFORE the dedup strip nulls `span.input`; the output candidate is built AFTER `build_message_dedup` because it needs the dedup's `hashes`. Both are processed AFTER the wire publish so the hook can never mutate or delay the payload.
- **Separator pipeline (order is binding):** extract last-turn user parts → canonicalize (sort, so part arrival order is irrelevant) → join with the signpost `\n\n== lmnr_part_separator ==\n\n` → generate AND apply the regex against the signposted text → re-join captured parts with the user-facing whitespace separator. Never conflate the signpost (LLM-facing) with the user-facing separator. **The signposted text is USER-ONLY — including system content was tried and reverted; do not re-add it.** The generation prompt is framed around a TEMPLATE model (every piece STATIC or VARIABLE) and classifies markers by FUNCTION, never syntax (XML tags, delimiter lines, markdown headings, ALL-CAPS labels, JSON envelopes all equivalent) — keep it syntax-agnostic.
- Regexes run on **`fancy-regex`** (NOT the RE2-only `regex` crate) with a backtrack limit so catastrophic patterns degrade to `NoMatch` instead of hanging — the `Err` arm of `captures` IS a non-match.
- **Two regex keyings, and they must NEVER read each other's entries** — they hold regexes generated under different cohort definitions. `regex_target` (`regex.rs`) returns one of three things per candidate, and the middle case is why it's an enum: agent hash + version ⇒ the VERSIONED key `{USER_TASK_VERSION_REGEX_CACHE_KEY}:{project}:{agent_hash}:{version_hash}:{h|n}`; **no agent hash ⇒ the LEGACY key permanently** (an LLM span with no system message can never have a version, so keying it versioned would cost an LLM call every trace forever); agent hash but no minted version yet ⇒ `Unversioned`, i.e. NO key at all and no legacy fallback. `agent_hash` stays in the versioned key because `version_hash` is only 32 bits (`sp_versioning::similarity::version_hash` truncates to 8 hex chars); `has_history` stays because a first turn and a follow-up carry different layouts.
- **`Feature::VersionedInputExtraction` (`SP_VERSIONING_INPUT_EXTRACTION_ENABLED`, requires `SystemPromptVersioning`) is the switch.** Off ⇒ every candidate takes the legacy key, byte for byte as before. Flipping it ORPHANS every existing regex cache entry (the key shape changes), so each cohort pays one warm-up cycle of direct-extraction fallbacks — roll out per project.
- **`agent_hash` is the system prompt's FIRST-SENTENCE hash, NOT the skeleton hash stamped on `lmnr.span.prompt_hash`.** `prompt_hash::prompt_hashes` returns both from one pass; the skeleton (first sentence + sorted XML tag names) still feeds the span attribute, static-SP extraction, checkpoints and signals, so both must keep existing. Using `first_sentence` means permuting/adding/removing the prompt's XML scaffolding does NOT fork the cache key and re-trigger an LLM generation. Pinned by `regex_cache_key_survives_system_prompt_tag_permutations` (`regex.rs`); don't "simplify" it to reading `SPAN_PROMPT_HASH` off the span.
- **Accepted trade-off of that wider key — LEGACY keying only:** two prompt templates sharing an opening sentence but differing in TAG SET collide. That is only unsafe if they also disagree on the USER message's extraction layout — and the user fingerprint is deliberately ORDER-INSENSITIVE, so `<ctx>…</ctx>\n\n<task>` and the reverse share a fingerprint and a regex. A regex anchored to one layout then yields `NoUserRequest` (empty user task) on the other, and **that does NOT self-heal: only `ApplyRegexResult::NoMatch` evicts the cache entry; `NoUserRequest` refreshes its TTL.** If empty `lmnr_user_task` values show up in the wild, make the USER fingerprint layout-sensitive (or treat a cached `NoUserRequest` as stale) — do NOT re-narrow the key to the skeleton, which restores a scaffolding-permutation cardinality blowup.
- **Accepted trade-off of the VERSIONED key:** it narrows on the system-prompt axis and widens on the user-message axis at once — the tag fingerprint is gone from the key entirely, because user messages carry dynamic tag sets (HTML in a quoted PR body, per-run injected blocks) that churned it constantly. Two templates sharing a version but disagreeing on user-message layout therefore share a regex, with the same non-self-healing `NoUserRequest` outcome as above. `has_history` splits the commonest instance of that (first turn vs follow-up); the rest is accepted.
- **Version resolution ladder.** The sp-versioning producer resolves each distinct prompt inline (memo, then subset match) and `publish_static_prompt_candidates` returns a `VersionVerdicts` map keyed by `full_prompt_hash` — that is why the subset match runs on the ingest path at all. On a `None` the worker re-resolves: memo (the classifier consumes a message published one line earlier, so it has usually landed), then the `system_prompt_versions` ClickHouse row for the winning span (`span_id` rides `InputExtractionMessage` for exactly this).
- **Samples accumulate on the WORKER, never the producer** (`accumulator.rs`), under the same `(project, agent_hash, version_hash, has_history)` cohort tuple the regex is cached under. The worker appends the text it was about to extract directly, so samples cost nothing beyond the fallback already happening and are exactly the winner-span texts the regex gets applied to; the ingest path stays free of the write. Per-sample head+tail cap (`SAMPLE_MAX_CHARS`) because `signposted_text` is capped at 200k chars and five uncapped samples would be a megabyte.
- **`last_attempt_at` is load-bearing, not hygiene.** The accumulator is capped at the sample target and never deleted, so without it a full cohort would publish an agent request on every subsequent trace forever. It is stamped in the SAME write that reports readiness (one round-trip); the duplicate-publish window that leaves is closed by the agent worker's per-cohort run lock.
- **The multi-sample regex agent runs on its OWN queue** (`user_task_regex_queue`, `regex_agent.rs` + `generate_multi.rs`) because a run takes minutes while a per-trace extraction takes seconds — sharing one queue would block the fast path behind the slow one. Failures DROP rather than requeue: the accumulator's retry interval is the spacing, which self-proportions retries to real traffic.
- **The agent's acceptance check is match-only, and the passthrough `(?s)(.*)` is a legitimate submission — do not regrow a clause forbidding it.** Every probe runs against ALL samples and a submit is accepted when it extracts non-empty text from every one; a pattern anchored on one sample's own words fails the others, so the multi-sample match IS the generalization test. Acceptance briefly also demanded that a submit discard something somewhere, to reject whole-message captures: that made UNSCAFFOLDED cohorts (a bare chat message under a system prompt, where the whole text genuinely IS the instruction) unsatisfiable — the agent burned its full 8-call budget arguing with a validator it could not satisfy, cached nothing, every trace then paid a `Small` direct-extraction call forever, and because the cache stayed empty `record_sample` re-triggered the same doomed run once per `SP_VERSIONING_INPUT_REGEX_RETRY_INTERVAL_SECONDS`, indefinitely. Pinned by `passthrough_is_accepted` / `empty_capture_is_still_rejected`. Note this is NOT the "removed text is identical" dual of the static-prompt extractor — that doesn't transfer, since here the regex KEEPS the dynamic part (the task) and discards scaffolding that is itself part static and part injected dynamic state, so the removed text differs per sample by construction.
- **`GenerationVerdict::Exhausted` caches NOTHING, and the asymmetry with the point above is deliberate:** a passthrough the model CHOSE is a verdict; one the server invents after the model failed is a guess, and where scaffolding IS present but no anchor was found it would pin every future trace's task to the full scaffolded text, worse than the direct extraction it displaces. The tool-verified-fallback trick from the static-prompt agent is kept (models routinely "improve" a pattern after their last successful probe).
- **No backfill.** Nothing re-extracts a trace once a real regex lands, so the direct extraction is the PERMANENT value for the early traces of every version — and versions churn during an agent's cold start. Check the `fallback` resolution rate before assuming `ModelSize::Small` is cheap enough.
- The regex cache is deliberately **separate from the frontend's** extraction cache — signposted samples are incompatible with plain-joined ones, and `generate.rs` has its own prompt rather than reusing the frontend's `SYSTEM_PROMPT`.
- `fingerprint_user_message` (`fingerprint.rs`) sorts + dedups tag NAMES globally (not just consecutive repeats) and captures only TOP-LEVEL tags. Its **TypeScript twin `fingerprintUserMessage` in `frontend/lib/actions/sessions/extract-input.ts` does NEITHER**, so the two produce different strings for the same input. Harmless today (the TS function has zero callers, the caches are separate) — but do not assume parity if you wire it up.
- **An LLM failure or budget exhaustion can never requeue the message, but the two paths resolve it OPPOSITELY.** The LEGACY generation is infallible: both endings fall back to the uncached passthrough regex (the full reconstructed input beats a wrong empty value), each stamping its own flag (`budget_exhausted` / `llm_failed`) on the self-tracing root. A **failed DIRECT extraction publishes NOTHING** — `extract_user_task_directly` returns `None` and the worker returns early, because an absent `lmnr_user_task` means "never ran" whereas the empty string `extraction_outcome_value` writes for `NoUserRequest`/`NoMatch` would claim the message carried no user request. The only transient error left in the consumer is a publish failure, and it **acks only after `publish_trace_input_update` succeeds**. If flapping providers hurt throughput, raise `NUM_INPUT_EXTRACTION_WORKERS` — custom retry loops and pipeline deadlines were both tried and reverted.
- **Ordering inside `resolve_uncached` differs by path, deliberately.** The accumulator append comes FIRST (cohort-level — valid even for a candidate this trace drops as superseded, and it needs no LLM call). Then a **direct extraction** checks supersession BEFORE the call, because nothing is cached so a superseded candidate's call is pure waste; a **legacy generation** keeps its check AFTER, because its work populates a shape-keyed entry a later trace reuses.
- Before publishing, the consumer re-reads the winner lock and drops the message if the published winner `supersedes` the `winner_state` snapshot it carried; after a successful publish it re-asserts that snapshot via `write_lock_merged` (healing a possibly-failed producer write). Absent lock / cache error fails open.
- **Self-tracing is emitted ONLY from the queue consumer** — the producer hook sits on the ingest path and an internal span there would recurse through `push_spans_to_queue`. **Cache-hit runs emit no self-tracing at all**; an internal trace exists only when a real LLM generation runs. Spans route to `USER_TASK_INTERNAL_PROJECT_ID` (its own env var, distinct from other features' internal project ids); unset ⇒ `project_id = None` ⇒ the exporter drops them. `SpanScope` carries BOTH the internal routing project and `source_project_id` (the extracted trace's owner), plus a `RunKind` picking one of THREE deliberately distinct root names — `user_task.version_regex` (the cohort-scoped agent run), `user_task.extract_direct`, `user_task.extract_legacy` — with the LLM and tool spans named apart too (`generate_extraction_regex_multi` / `try_extraction_regex_multi` vs the single-sample pair). Sharing names made the three paths indistinguishable in the trace UI. The root name is also the `lmnr.span.path[0]` every descendant is stamped with, so the two must never drift. The agent run's `trace_id` is **nil**: it belongs to a cohort, not to whichever trace tripped the trigger.
- **The Sentry span per regex APPLICATION uses the DEFAULT target, deliberately.** `apply_regex_externally_traced` (`regex.rs`) emits `user_task.apply_regex` for every authoritative application (cached and freshly generated); the disjoint per-layer filters in `instrumentation/mod.rs` route a default-target span to Sentry only, never the `lmnr::internal` tree — which is what makes it safe on the ingest path, since Sentry spans never re-enter `push_spans_to_queue`. Generation-loop PROBES are deliberately not Sentry-traced (model experiments, not applications). The same default target carries `user_task.resolve`, one span per candidate with `resolution` ∈ `cached` | `fallback` | `no_version` — **the fallback rate is the health metric for the versioned pipeline** — emitted ONLY for the versioned path, since counting legacy-key hits would inflate the denominator with prompts that can never have a version. There is deliberately no `stale` variant: a cached regex that stopped matching already shows as `regex_from_cache=true` with `success=false` on the application span.
