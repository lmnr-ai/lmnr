## AI Features Model Setup

- All frontend AI features (chat-with-trace, SQL generation, span previews, session extraction regex, debugger-session naming) go through `getLanguageModel(tier)` in `frontend/lib/ai/model.ts`. Tiers are `small` / `medium` / `large` — never add new tier names without updating every call site.
- SQL "Ask AI" generation modes (`GenerationMode` in `frontend/lib/actions/sql/types.ts`: `query` / `eval-expression` / `trace-expression` / `dataset-expression`) are coupled across THREE places that must stay in sync: the `GenerationMode` type, `MODE_CONFIGS` in `frontend/lib/actions/sql/prompts.ts`, AND the `mode` zod enum in `frontend/lib/actions/sql/generate.ts`. The generate action's enum is the validation gate — a mode missing there throws `Invalid option: ... at mode` at request time even though the type and prompt config accept it. Each table's columns menu picks its mode (`traces-columns-menu` → `trace-expression`, eval → `eval-expression`, dataset → `dataset-expression` over the `dataset_datapoints` table).
- In OSS, these env vars are read by the frontend only (chat-with-trace / SQL-with-AI). Signals — which also reuses these vars — is not an OSS feature; it ships in `lmnr-private`. Don't document Signals as an OSS feature in the OSS README or docker-compose files.
- Provider selection: `LLM_PROVIDER` (=`openai` | `gemini` | `bedrock`) is the single switch. `openai` and `gemini` use `LLM_API_KEY` (+ optional `LLM_BASE_URL`; `openai` is OpenAI-compatible and works with LiteLLM proxy / OpenRouter / vLLM). `bedrock` uses AWS credentials (`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_REGION`) instead of `LLM_API_KEY`. `LLM_MODEL_SMALL` / `LLM_MODEL_MEDIUM` / `LLM_MODEL_LARGE` are optional overrides; each provider has hard-coded defaults in `DEFAULT_MODELS`. Mirror the app-server's provider matching in `app-server/src/features/mod.rs` / `llm/mod.rs` when extending.
- `Feature.SIGNALS` requires `SIGNALS_ENABLED=true` AND `isAiProviderConfigured()`. `Feature.BATCH_SIGNALS` is currently disabled via the feature flag (`return false`) until the batch path is re-enabled; when re-enabling, gate on `LLM_PROVIDER === "gemini"` since the backend batch API is Gemini-specific.
- The Rust OpenAI client (`app-server/src/llm/openai/`, gated behind the `signals` feature — `allow(dead_code)` in OSS) is the path Signals hits. `provider_request_to_openai_body` (`conversions.rs`) must NOT forward `reasoning_effort` when **function tools are present**: gpt-5.x reasoning models 400 on `/v1/chat/completions` with "Function tools with reasoning_effort are not supported … use /v1/responses instead" — this fires on OpenAI direct AND on some OpenAI-compatible gateways (LiteLLM/OpenRouter) that forward to OpenAI, so endpoint-sniffing is unreliable. The guard is simply `if !has_tools` — forward `reasoning_effort` only when no tools are present, regardless of endpoint.
- The `signals` feature does NOT compile standalone in the OSS `lmnr` repo — it pulls in clustering worker variants (`BatchWorkerType::ClusteringBatching`, `WorkerType::Clustering`) that live in `lmnr-private`, so `cargo test --features signals` fails with E0599 in `main.rs`. Run `llm/openai` tests under default features (`cargo test --bin app-server llm::openai::conversions`); the test modules are not feature-gated.
- **Effort naming differs per provider for `ProviderThinkingLevel::XHigh`:** OpenAI's `reasoning_effort` tier above `high` is `"xhigh"`, but Bedrock's adaptive-thinking `output_config.effort` scale tops out at `"max"` (Anthropic naming; `"xhigh"` is a ValidationException, and `"max"` is Opus 4.6+-only). Gemini has no tier above HIGH — its `ThinkingLevel` accepts the provider enum's `X_HIGH` via a serde alias and collapses it to HIGH. Don't unify these strings across providers.

## Vercel AI SDK (v7)

- The frontend is on `ai` v7 (`@ai-sdk/*` providers at 4.x, `@ai-sdk/react` 4.x, `@ai-sdk/amazon-bedrock` 5.x). Playground chat and all server-side AI features go through it.
- **`LanguageModelUsage` is nested in v7** (was flat in v5). Shape: `{ inputTokens, inputTokenDetails: { noCacheTokens, cacheReadTokens, cacheWriteTokens }, outputTokens, outputTokenDetails: { textTokens, reasoningTokens }, totalTokens }`. Cached-input and reasoning tokens live UNDER `inputTokenDetails`/`outputTokenDetails` — there is no top-level `cachedInputTokens`/`reasoningTokens`. Any literal usage object (store initial state, fallbacks) must use this nested shape or it won't type-check.
- **`GenerateTextResult` takes THREE generics in v7**: `GenerateTextResult<TOOLS extends ToolSet, RUNTIME_CONTEXT extends Context, OUTPUT extends Output>`. We use `GenerateTextResult<ToolSet, Record<string, never>, never>`. `Context` is NOT re-exported from `ai` (it lives in `@ai-sdk/provider-utils`); use `Record<string, never>` for the runtime-context slot rather than importing it.
- `GenerateTextResult` has both `usage` and a deprecated `totalUsage` (both `LanguageModelUsage`). Prefer `result.usage` for display; `totalUsage` is only kept where the struct requires it.
- `result.reasoning` is `Array<ReasoningOutput | ReasoningFileOutput>` — `ReasoningFileOutput` has no `.text`, so guard with `("text" in r ? r.text : "")` before reading it.
- **Span attributes use v7 usage keys**: `result.usage.inputTokens` / `.outputTokens`, NOT v4's `.promptTokens` / `.completionTokens` (which are now `undefined`). `SpanData.result` is typed `any` in `lib/actions/chat/utils.ts`, so wrong keys silently emit `undefined` instead of failing to compile — verify against the nested shape.
- Telemetry is registered globally once via `registerTelemetry(new LaminarAiSdkTelemetry())` (`registerTelemetry` from `ai`, `LaminarAiSdkTelemetry` from `@lmnr-ai/lmnr`), called in `instrumentation.ts` right after `Laminar.initialize()`. With global telemetry registered, per-call `experimental_telemetry` / `tracer` options are NOT needed — `generateText`/`generateObject` calls are traced automatically. Do not add `experimental_telemetry: { isEnabled: true }` or a per-call `tracer: getTracer()` to call sites.
- `generateText` / `generateObject` use `maxOutputTokens` (not `maxTokens`) for the output cap; our form field is still named `maxTokens` and is mapped at the call site.
- The playground `ToolResultPart["output"]` shape is defined locally in `lib/playground/types.ts` (carries a `media` content variant), NOT imported from `ai` — v7's `ai` `ToolResultPart` is now generic over `ToolSet` and its `output` no longer matches the form's shape, so import the local type in `message-parts.tsx`.
- **Span-view rendering of native AI-SDK v7 prompts** (`lib/spans/types/ai-sdk.ts`, `parseAiSdkMessages`). The detector handles BOTH vintages the SDK has stored: (a) verbatim LanguageModel-level payloads from `gen_ai.input.messages` / `gen_ai.output.messages` — dash-typed parts (`tool-call`, `tool-result`, `reasoning`), `file` parts with top-level `data|url` + `mediaType`, `providerOptions`/`providerMetadata` intact; (b) the legacy server-reshaped `ai.prompt.messages` shape — snake_case `tool_call` parts, JSON-stringified assistant content, and tool results stored as `{type:"text"}` parts inside `role:"tool"` messages (historical ClickHouse rows keep this shape forever). It runs in `processMessages` BEFORE the OpenAI detectors (the loose OpenAI schemas would otherwise claim verbatim payloads and drop `reasoning` parts), gated by `hasAiSdkDiscriminator`: a message-level `providerOptions`/`providerMetadata`, a distinctive part type, or a LanguageModel `file` part (top-level `data|url` + string `mediaType` — OpenAI nests its file payload under a `file` key, so it never matches). Plain `[{role, content:"str"}]` chats are NOT claimed and fall through to OpenAI/generic. `parseAiSdkMessages` routes to the `type:"generic"` renderer; `matchAiSdkMessages` also drives the playground branch in `convertSpanToPlayground` (`lib/spans/utils.ts`). Detection ordering is pinned by `tests/test-process-messages-detection.test.ts`, including the `{role, parts}` (GenAI) vs `{role, content}` (AI SDK) mutual non-claim.
- **Do not add v7 part types to `convertToMessages`'s `processContentPart`** to fix this — that helper is shared with the playground; the span-view fix belongs in the dedicated `ai-sdk.ts` detector, which routes to the `type: "generic"` renderer (`components/traces/span-view/generic-parts.tsx`) that already handles `reasoning`/`tool-call`/`tool-result`.
- **The generic renderer's `default` switch case renders a labeled JSON block, not `undefined`.** v7 broadened `ModelMessage` with parts that have no dedicated UI (`custom`, `reasoning-file`, `tool-approval-request`, `tool-approval-response`); `parseAiSdkMessages` passes them through verbatim and `generic-parts.tsx` surfaces them as JSON so nothing is silently dropped. Add a dedicated `case` only when a part type warrants bespoke UI.
