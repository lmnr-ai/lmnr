**Status: PR1 shipped behind `PII_DUAL_MODE_ENABLED` (default off).** PR1 covers the main pipeline — ClickHouse storage, ingestion, the access policy, and the spans/traces read path. The "Known gaps" section lists what a project in `dual` mode still leaks until the follow-ups land; that is why the flag stays off in production.

## Goal and scope

- v0 has exactly one permission, `view_pii`. The model, storage, and read path are built so further permissions and custom roles are data changes, not redesigns: the policy already carries a trace-level scope (`traceFilters`) that the views enforce, even though no role produces one yet.
- Roles are workspace-level (`member | admin | owner`); the PII mode is project-level (`projects.settings.piiMode`). A user's effective policy combines both.
- Out of scope for v0: `attributes`, `events`, `metadata`, `user_id`/`session_id` (stay raw); scoped API keys; per-member permissions.

## Permission model

- Built-in defaults only, no `workspace_roles` table yet: `permissions_for_role` in `app-server/src/access_policy/mod.rs` gives owner/admin `{view_pii: true}` and member `{view_pii: false}`. Unknown role strings get member permissions (fail-closed).
- **Invariant: no data-read path branches on the role name.** Membership/management checks may keep using the enum; anything deciding *what data a user sees* reads `RolePermissions`. Custom roles later = a `workspace_roles(workspace_id, name, permissions jsonb)` table feeding the same struct.
- Only owner/admin may change `piiMode`. Enforced in `frontend/app/api/projects/[projectId]/settings/route.ts` (`PRIVILEGED_KEYS`) via the uncached `getWorkspaceRole`; the UI disables the control for members.

## Access policy

- `AccessPolicy { mask_pii, trace_filters }` (`access_policy/mod.rs`) is the only type that serializes to the JSON the views consume (`to_view_arg()` → `{"maskPii":true}`; `UNRESTRICTED` → `{}`). Absent keys mean "no restriction", so adding a field never invalidates callers passing `'{}'`.
- **`traceFilters`** is a row-level scope: a span or trace is visible only if its trace satisfies every filter (AND). Each filter is `{"column": "user_id" | "metadata", "key"?: string, "operator": "eq" | "ne", "value": string}` — the same `column`/`operator`/`value` shape as the UI's `Filter` (`lib/actions/common/filter-schemas.ts`, `db::utils::Filter`) so a stored filter converts one-to-one, with the metadata key lifted into its own field instead of a `metadata.key` column string. Only `eq`/`ne` exist; a filter with any other operator or column hides every row. Missing trace data — no `traces_static` row, NULL `user_id`, absent metadata key — compares as `''`, so `eq` hides such traces and `ne` shows them. Non-string metadata values compare against their raw JSON (`false`, `42`). The Rust side is the `TraceFilter` struct (`TraceFilter::user_id(..)` / `TraceFilter::metadata(key, ..)`); **no caller produces filters yet** — `for_actor` still emits `maskPii` alone. Wiring role → filters is a data change on `permissions_for_role`, plus a `TryFrom<Filter>` bridge when the UI gets a trace-filter editor.
- Derivation: `AccessPolicy::for_actor(actor, project_id, db, cache)`. `mask_pii = effective_pii_mode == Dual && !permissions.view_pii`. `Off`/`Redact` projects are unrestricted for everyone (there is nothing to mask). Inputs are cached — `project:{id}` (settings) and `member_role:{workspace_id}:{user_id}` (1h TTL, positive-only) — the policy itself is not, so a mode flip or role change needs no cross-user invalidation. The frontend removes the `member_role` key on role update, ownership transfer, and member removal (`lib/actions/workspace/index.ts`); the key format is duplicated in `lib/cache.ts` and `cache/keys.rs` and must stay in sync.
- **Actor contract.** The internal `/sql/query` and `/sql/validate` routes require an `actor`: `{"type":"user","userId":"…"}` or `{"type":"shared"}`. A missing actor is a 400; a derivation error masks (`routes/sql.rs::policy_for`). `shared` and non-members always mask in `dual`. The frontend resolves it in `lib/actions/sql/actor.ts` (explicit → session user → `SHARED_ACTOR`) and passes it as a separate `options.actor` argument — **never from a request body**; `app/api/projects/[projectId]/sql/route.ts` spreads the body into `executeQuery`, so an actor in the input schema would be user-controlled.
- Unrestricted callers, each marked with a comment: public API keys (`api/v1/sql.rs`, `api/v1/mcp.rs`, CLI), saved-query and dataset internals (`sql/queries.rs`, `datasets/service.rs`), and every backend pipeline (system-prompt versioning, debugger, private signals). They need raw data for correctness; API keys get the admin-equivalent policy until `project_api_keys.permissions` exists.

## Storage: raw text + masks

- `piiMode: off | redact | dual` replaces the `removePii` boolean (Drizzle migration `0111_pii_mode.sql` rewrites the JSONB; both readers still translate a stray `removePii: true` to `redact`). Rust: `PiiMode` in `db/projects.rs`; an unknown string deserializes as `Redact` with a warning. `effective_pii_mode()` maps `Dual` → `Redact` while `Feature::PiiDualMode` is off, so a stale `dual` setting never stores raw text on a deployment that cannot mask it. The read policy uses the *configured* `pii_mode()` instead: rows written while the flag was on still hold raw text, so turning the flag off must keep masking them (redact-mode rows are checked with no masks and render their already-redacted text). The frontend rejects writing `dual` when its `Feature.PII_DUAL_MODE` is off; both read the same `PII_DUAL_MODE_ENABLED`.
- **Redactor contract** (`pii-redactor/proto/pii_redactor.proto`, mirrored in `app-server/proto/`): `Redact` returns, per text, `RedactedText { text, masks }` — `text` is the redactor's canonical compact re-serialization of the input (it parses JSON, recursively expands stringified-JSON leaves, and writes the tree back with `serde_json` semantics, key order preserved), `masks` are sorted non-overlapping `(start, end, label)` **byte** ranges into exactly that string, on char boundaries. A mask over an entity containing `"` or `\n` covers the escaped bytes; a mask inside a stringified-JSON leaf covers the doubly-escaped bytes, so splicing at any level yields valid JSON. The service never renders placeholders; `[REDACTED_<LABEL>]` (label uppercased) is fixed on both readers. app-server and pii-redactor deploy in lockstep on this change — the response shape is not backwards compatible.
- **Canonical-text invariant.** Masks only hold against the exact bytes the redactor returned. In `dual` mode app-server therefore stores `RedactedText.text` verbatim as `spans.input`/`output` and `unique_content.content` (replacing the row's own serialization) and `masks` as `input_masks`/`output_masks`/`content_masks` (`Array(Tuple(start UInt32, end UInt32, label String))`) — no `sanitize_string`, no re-serialization. Inputs are sanitized *before* the RPC instead (`redact_spans_in_place` for whole values; dedup rows arrive pre-sanitized), so the redactor may still emit characters `sanitize_string` would strip (it unescapes `\u0085`), and re-sanitizing its output would shift every later offset. Anything that rewrites a stored `dual` text must recompute or drop its masks.
- `redact` is the destructive path: app-server splices the masks itself (`pii_redactor::masks::apply_masks`) and stores the result; nothing about masks is persisted. Quickwit gets the spliced text in both modes. `MaskedText::has_pii()` (`!masks.is_empty()`) is the "changed" signal; there is no marker-string heuristic.
- `pii_checked Bool` on `spans` and `unique_content`: the redactor screened the row. Checked + no masks ⇒ raw is safe, checked + masks ⇒ splice, unchecked ⇒ unavailable. `false` for every pre-existing row, every `off` row, and every failure (RPC error, oversize, unparsable, malformed mask) — indistinguishable in storage and need not be, since both fail closed. `apply_masks` errors on a malformed mask (out of order, past the end, off a char boundary) rather than emit partially redacted text, and the caller treats that like an RPC failure; `dual` mode runs the same check (`MaskedText::validate`) before storing masks, because the ClickHouse splice has no guard of its own. `SpanPii`/`PiiOutcome` live in `pii_redactor/mod.rs`; `redact_spans_in_place` is generic over `RedactTexts` so tests use a fake client.
- Dedup'd LLM messages (`unique_content`, group-scoped — `dedup-search.md`) get the same treatment per message; the span's own `input`/`input_masks` are cleared when message hashes are present, since the view resolves those through the dict. `unique_content_dict` (recreated at frontend boot, `instrumentation.ts`) carries `content, content_masks, pii_checked`. The legacy `deduped_content` table has no writer and no PII columns, so the masked branch skips its dict entirely: pre-migration rows are unavailable under mask.
- **Dedup self-heal**: the `s:` storage-presence key is skipped for rows whose redaction failed (`PiiOutcome::shared_row_failed`, in-process only — `off` rows are unchecked but not failed, and are stamped normally), so a failed `unique_content` row is re-inserted by the next occurrence instead of needing a retry queue. `SharedContentBatch::storage_marks` takes the skip predicate.
- Quickwit indexes spliced text in both modes; in `dual`, a `failed` span contributes no `input`/`output` to its document (`PiiOutcome::is_indexable`). A raw index would be a yes/no oracle for members.
- Why masks and not a redacted copy: the model's native output already is a span list; a copy doubles storage on every PII row while masks cost a few bytes per entity, and they enable PII highlighting in the UI later. The earlier objection — the redactor re-serializes nested stringified JSON, so offsets into the *original* bytes would drift — is answered by computing masks against the redactor's own canonical output and storing that output (the invariant above).

## Read path

- ClickHouse parameterized views have no default arguments, so adding `policy` to `spans_v0`/`traces_v0` would break every bare caller. Migration `65_pii_dual_storage.sql` adds **`spans_v1(project_id, policy)`** and **`traces_v1(project_id, policy, min_start_time, max_start_time)`**; the `_v0` views are unchanged. `policy` is a JSON string; the views read `JSONExtractBool({policy:String}, 'maskPii')` and `trace_visible(.., {policy:String})`, both of which ClickHouse constant-folds, so `'{}'` compiles to the v0 plan (verified with EXPLAIN: no `pii_checked`/`*_masks` reads, no `trace_access_policy_dict` call).
- **SQL UDFs** (`CREATE FUNCTION`, migration 65; macro-expanded into the query, replicated by ClickHouse Cloud): `apply_pii_masks(text, masks)` is the read-time twin of Rust `apply_masks` and must produce identical output (checked by a fixture run against local CH when either changes); `trace_visible(user_id, metadata, policy)` evaluates `traceFilters` via `pii_str_op`/`pii_json_scalar`. Lambda parameters carry a `pii_` prefix because UDF expansion does not rename them, so a caller column of the same name would be captured.
- Masked shape for whole values: `if(pii_checked, apply_pii_masks(raw, masks), '"[PII_MASKED_UNAVAILABLE]"')`. The sentinel is a JSON string literal so `input`/`output` stay parseable; unchecked rows render it — **fail-closed, including history ingested before a project flipped to `dual`**. Per dedup'd message the same choice runs inside the reconstruction lambda over `('content', 'content_masks', 'pii_checked')` from `unique_content_dict` and yields the sentinel as the array element (distinct from the `null` a dict miss yields in the unrestricted branch); `tool_definitions` (also a `unique_content` row) resolves the same way. `traces_v1.agent_input` is masked entirely under `maskPii` (`traces_static` has no masks yet).
- **Trace scope in `spans_v1`**: `WITH dictGetOrDefault('trace_access_policy_dict', ('user_id', 'metadata'), (project_id, trace_id), ('', '')) AS trace_scope … WHERE project_id = {project_id} AND trace_visible(trace_scope.1, trace_scope.2, {policy})`. The dictionary (`instrumentation.ts`, `COMPLEX_KEY_DIRECT`, `QUERY 'SELECT … FROM traces_static FINAL'`, no cache so a new trace is filterable as soon as its `traces_static` row exists) turns the trace join into a row-local predicate, which lands in PREWHERE and keeps projections and lazy materialization usable; an `IN`/`JOIN` on `traces_static` would not. Cost is one `traces_static` PK lookup per block, paid only when the policy carries filters. `traces_v1` evaluates the same UDF on its already-joined `ts` row.
- The query-engine `ViewRewriter` (`query_engine/validator.rs`) rewrites `spans`/`traces` to the `_v1` views and injects `policy = '<json>'` next to `project_id`; a user-supplied `policy` argument is rejected like `project_id`. Other tables (`evaluation_datapoints`, `signal_*`, `trace_outputs`, …) still target `_v0` without a policy (`takes_policy()`). `validate_and_secure_query(sql, project_id, policy)` is the entry; tests in `validator/tests.rs` assert every spans/traces reference receives the policy.
- Direct `_v1` callers outside the rewriter pass `policy='{}'`: `ch/spans.rs` (debugger page), `ch/system_prompt_versions.rs`, private `signals/private/spans.rs`.
- Adding a `spans` column now means updating **both** `spans_v0` and `spans_v1` (plus the allowlists listed in `clickhouse-traces.md`).

## Known gaps (why the flag is off)

Each of these lets a member of a `dual` project see raw text and is a follow-up PR:

- Realtime SSE (`realtime/`, `send_span_updates`) publishes the raw span once to every subscriber; needs dual publish with per-connection policy.
- `trace_outputs_v0` (agent output) and `signal_events_v0` take no policy; Signals stores its produced event raw (`handle_create_event`, private repo).
- Search snippets (`search/snippets.rs`) extract from the raw `spans` columns; under `maskPii` they must splice `*_masks`.
- `traces_static.input` (extracted task) has no masks or `pii_checked`, hence the blanket mask on `agent_input`; `traceFilters` are enforced on it already.
- `traceFilters` are honoured by `spans_v1`/`traces_v1` only; `trace_outputs_v0`, `signal_events_v0`, search and realtime do not scope by trace.
- The Laminar Agent (private repo) reads trace context and runs its `query_sql` tool unrestricted, and its replies are not masked per user.
- Backfill for unchecked history, per-role notification rendering, and a `pii_terms` search field for admin raw search.
