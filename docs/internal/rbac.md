# Role-based PII masking and trace access policy

<!-- Detailed working notes for coding agents and developers. -->
<!-- Referenced from the index in the repo-root CLAUDE.md; read when working in this area. -->
<!-- Sibling files in docs/internal/ may be cross-referenced by section name. -->

Projects choose how span input/output is treated for PII (`projects.settings.piiMode`); workspace roles decide who sees it. In `dual` mode the raw text is stored once with byte-range masks next to it, and ClickHouse splices `[REDACTED_<LABEL>]` over the masks at read time for readers whose policy says `maskPii`. The same policy carries an optional trace-level scope (`traceFilters`) that the views enforce. `dual` is selectable by any Pro workspace; the "Known gaps" section lists the read paths that still bypass the policy.

## Permission model

- Roles are workspace-level (`member | admin | owner`); the PII mode is project-level. A user's effective policy combines both.
- There is one permission, `view_pii`, with built-in defaults and no `workspace_roles` table: `permissions_for_role` in `app-server/src/access_policy/mod.rs` gives owner/admin `{view_pii: true}` and member `{view_pii: false}`. Unknown role strings get member permissions (fail-closed).
- **Invariant: no data-read path branches on the role name.** Membership/management checks may keep using the enum; anything deciding *what data a user sees* reads `RolePermissions`. Custom roles would be a `workspace_roles(workspace_id, name, permissions jsonb)` table feeding the same struct.
- Only owner/admin may change `piiMode`. Enforced in `frontend/app/api/projects/[projectId]/settings/route.ts` (`PRIVILEGED_KEYS`) via the uncached `getWorkspaceRole`; the UI disables the control for members.
- Not covered by the policy: `attributes`, `events`, `metadata`, `user_id`/`session_id` stay raw; there are no per-member or per-API-key permissions.

## Access policy

- `AccessPolicy { mask_pii, trace_filters }` (`access_policy/mod.rs`) is the only type that serializes to the JSON the views consume (`to_view_arg()` → `{"maskPii":true}`; `UNRESTRICTED` → `{}`). Absent keys mean "no restriction", so adding a field never invalidates callers passing `'{}'`.
- **`traceFilters`** is a row-level scope: a span or trace is visible only if its trace satisfies every filter (AND). Each filter is `{"column": "user_id" | "metadata", "key"?: string, "operator": "eq" | "ne", "value": string}` — the same `column`/`operator`/`value` shape as the UI's `Filter` (`lib/actions/common/filter-schemas.ts`, `db::utils::Filter`) so a stored filter converts one-to-one, with the metadata key lifted into its own field instead of a `metadata.key` column string. Only `eq`/`ne` exist; a filter with any other operator or column hides every row. Missing trace data — no `traces_static` row, NULL `user_id`, absent metadata key — compares as `''`, so `eq` hides such traces and `ne` shows them. Non-string metadata values compare against their raw JSON (`false`, `42`). The Rust side is the `TraceFilter` struct (`TraceFilter::user_id(..)` / `TraceFilter::metadata(key, ..)`). **No caller produces filters yet** — `for_actor` emits `maskPii` alone; wiring role → filters is a data change on `permissions_for_role`, plus a `TryFrom<Filter>` bridge once the UI has a trace-filter editor.
- Derivation: `AccessPolicy::for_actor(actor, project_id, db, cache)`. `mask_pii = pii_mode == Dual && !permissions.view_pii`. `Off`/`Redact` projects are unrestricted for everyone (there is nothing to mask). Inputs are cached — `project:{id}` (settings) and `member_role:{workspace_id}:{user_id}` (1h TTL, positive-only) — the policy itself is not, so a mode flip or role change needs no cross-user invalidation. The frontend removes the `member_role` key on role update, ownership transfer, and member removal (`lib/actions/workspace/index.ts`); the key format is duplicated in `lib/cache.ts` and `cache/keys.rs` and must stay in sync.
- **Actor contract.** The internal `/sql/query` and `/sql/validate` routes require an `actor`: `{"type":"user","userId":"…"}` or `{"type":"shared"}`. A missing actor is a 400; a derivation error masks (`for_actor_or_masked`, the fail-closed wrapper every route uses). `shared` and non-members always mask in `dual`. The frontend resolves it in `lib/actions/sql/actor.ts` (explicit → session user → `SHARED_ACTOR`) and passes it as a separate `options.actor` argument — **never from a request body**; `app/api/projects/[projectId]/sql/route.ts` spreads the body into `executeQuery`, so an actor in the input schema would be user-controlled.
- **Credential actors.** `Actor::ApiKey` (project API key: `/v1/sql/query`, every MCP tool including the private `get_trace_context`/`ask_agent`) and `Actor::Cli` (CLI user token: `/v1/cli/sql/query`, private `/v1/cli/agent/chat`) are built by the route from its auth extractor and get member permissions, i.e. they mask in `dual`. Keys mask because `project_api_keys` carry no permissions yet, so the owner's own SDK key reads masked too; per-key permissions are the extension point. The CLI masks *despite* knowing the user: a CLI session may be driven by an AI agent rather than the person and the two are indistinguishable, so the stricter policy applies until a session can declare which it is. `off`/`redact` projects are unaffected (nothing to mask).
- Unrestricted callers, each marked with a comment: saved-query and dataset internals (`sql/queries.rs`, `datasets/service.rs`) and every backend pipeline (system-prompt versioning, debugger, private signals). They need raw data for correctness.

## Storage: raw text + masks

- `piiMode: off | redact | dual`. The legacy `removePii` boolean is not migrated: both readers translate `removePii: true` to `redact` when `piiMode` is absent, and `updateProjectSettings` mirrors `piiMode` into it (`mode !== "off"`) so app-server pods on the previous binary, which read only that boolean, follow changes made during a rollout. Rust: `PiiMode` in `db/projects.rs`; an unknown string deserializes as `Redact` with a warning. Ingest and the read policy both use `pii_mode()`; there is no deployment-level switch (redact-mode rows are checked with no masks and render their already-redacted text under any policy).
- **Redactor contract** (`pii-redactor/proto/pii_redactor.proto`, mirrored in `app-server/proto/`): `Redact` returns, per text, `RedactedText { text, masks }` — `text` is the redactor's canonical compact re-serialization of the input (it parses JSON, recursively expands stringified-JSON leaves, and writes the tree back with `serde_json` semantics, key order preserved), `masks` are sorted non-overlapping `(start, end, label)` **byte** ranges into exactly that string, on char boundaries. A mask over an entity containing `"` or `\n` covers the escaped bytes; a mask inside a stringified-JSON leaf covers the doubly-escaped bytes, so splicing at any level yields valid JSON. The service never renders placeholders; `[REDACTED_<LABEL>]` (label uppercased) is fixed on both readers. app-server and pii-redactor deploy in lockstep — the response shape has no compatibility path.
- **Canonical-text invariant.** Masks only hold against the exact bytes the redactor returned. In `dual` mode app-server therefore stores `RedactedText.text` verbatim as `spans.input`/`output` and `unique_content.content` (replacing the row's own serialization) and `masks` as `input_masks`/`output_masks`/`content_masks` (`Array(Tuple(start UInt32, end UInt32, label String))`) — no `sanitize_string`, no re-serialization. Inputs are sanitized *before* the RPC instead (`redact_spans_in_place` for whole values; dedup rows arrive pre-sanitized), so the redactor may still emit characters `sanitize_string` would strip (it unescapes `\u0085`), and re-sanitizing its output would shift every later offset. Anything that rewrites a stored `dual` text must recompute or drop its masks.
- `redact` is the destructive path: app-server splices the masks itself (`pii_redactor::masks::apply_masks`) and stores the result; nothing about masks is persisted. Quickwit gets the spliced text in both modes. `MaskedText::has_pii()` (`!masks.is_empty()`) is the "changed" signal; there is no marker-string heuristic.
- `pii_checked Bool` on `spans` and `unique_content`: the redactor screened the row. Checked + no masks ⇒ raw is safe, checked + masks ⇒ splice, unchecked ⇒ unavailable. `false` for every pre-existing row, every `off` row, and every failure (RPC error, oversize, unparsable, malformed mask) — indistinguishable in storage and need not be, since both fail closed. `apply_masks` errors on a malformed mask (out of order, past the end, off a char boundary) rather than emit partially redacted text, and the caller treats that like an RPC failure; `dual` mode runs the same check plus a JSON parse (`MaskedText::validate_for_storage`) before storing a text verbatim, because the ClickHouse splice has no guard of its own and a `unique_content` row is spliced into a message array, so a non-JSON row would break the whole value. Spliced shared rows in `redact` mode get the same JSON check. `SpanVerdict`/`PiiOutcome` live in `pii_redactor/mod.rs`; `redact_spans_in_place` is generic over `RedactTexts` so tests use a fake client.
- Dedup'd LLM messages (`unique_content`, group-scoped — `dedup-search.md`) get the same treatment per message; the span's own `input`/`input_masks` are cleared when message hashes are present, since the view resolves those through the dict. `unique_content_dict` (recreated at frontend boot, `instrumentation.ts`) carries `content, content_masks, pii_checked`. The legacy `deduped_content` table has no writer and no PII columns, so the masked branch skips its dict entirely: pre-migration rows are unavailable under mask.
- **Dedup self-heal**: the `s:` storage-presence key is skipped for rows whose redaction failed (`PiiOutcome::shared_row_failed`, in-process only — `off` rows are unchecked but not failed, and are stamped normally), so a failed `unique_content` row is re-inserted by the next occurrence instead of needing a retry queue. The `tn:` trace-new key is skipped the same way for spans whose text was kept out of the index (`!PiiOutcome::is_indexable`), so the messages first seen on such a span are trace-new again on the next span and reach Quickwit then; the cost is that two `spans` rows may list the same message in `*_new_message_indices`. `SharedContentBatch::storage_marks` and `MessageBatch::trace_new_marks` take the skip predicate. The failed span's own row does not heal (stays unchecked).
- Realtime (SSE) never carries `dual` span text: `span_update`/`trace_update` payloads have no input/output columns, and the `trace_agent_input_update` event (extracted agent input, raw stored value) is skipped for `dual` projects, where readers differ; on `off`/`redact` every reader is unrestricted so it rides the event as before. Live agent input for `dual` (role-keyed channels, or masks on `traces_static`) is a follow-up.
- Quickwit indexes spliced text in both modes; in `dual`, a `failed` span contributes no `input`/`output` to its document (`PiiOutcome::is_indexable`). A raw index would be a yes/no oracle for members. The same holds when no redactor is configured at all (`PiiOutcome::without_redactor`): modes are resolved on every batch, redactor or not. A mode lookup that fails (Postgres unreachable) fails the batch as a transient error so RabbitMQ redelivers it (`resolve_project_pii_modes`); rows are never stored on a guessed mode.
- Masks rather than a redacted copy because the model's native output already is a span list, a copy doubles storage on every PII row while masks cost a few bytes per entity, and masks allow PII highlighting in the UI. Computing them against the redactor's own canonical output (and storing that output) is what makes byte offsets stable across nested stringified JSON.

## Read path

- ClickHouse parameterized views have no default arguments, so adding `policy` to `spans_v0`/`traces_v0` would break every bare caller. Migration `66_pii_dual_storage.sql` adds **`spans_v1(project_id, policy)`** and **`traces_v1(project_id, policy, min_start_time, max_start_time)`**; the `_v0` views are unchanged. `policy` is a JSON string; the views read `JSONExtractBool({policy:String}, 'maskPii')` and `trace_visible(.., {policy:String})`, both of which ClickHouse constant-folds, so `'{}'` compiles to the v0 plan (verified with EXPLAIN: no `pii_checked`/`*_masks` reads, no `trace_access_policy_dict` call).
- **SQL UDFs** (`CREATE FUNCTION`, migration 66; macro-expanded into the query, replicated by ClickHouse Cloud): `apply_pii_masks(text, masks)` is the read-time twin of Rust `apply_masks` and must produce identical output (checked by a fixture run against local CH when either changes); `trace_visible(user_id, metadata, policy)` evaluates `traceFilters` via `pii_str_op`/`pii_json_scalar`. Lambda parameters carry a `pii_` prefix because UDF expansion does not rename them, so a caller column of the same name would be captured.
- Masked shape for whole values: `if(pii_checked, apply_pii_masks(raw, masks), '"[PII_MASKED_UNAVAILABLE]"')`. The sentinel is a JSON string literal so `input`/`output` stay parseable; unchecked rows render it — **fail-closed, including history ingested before a project flipped to `dual`**. Per dedup'd message the same choice runs inside the reconstruction lambda over `('content', 'content_masks', 'pii_checked')` from `unique_content_dict` and yields the sentinel as the array element (distinct from the `null` a dict miss yields in the unrestricted branch); `tool_definitions` (also a `unique_content` row) resolves the same way. `traces_v1.agent_input` is masked entirely under `maskPii` (`traces_static` has no masks).
- **Trace scope in `spans_v1`**: `WITH dictGetOrDefault('trace_access_policy_dict', ('user_id', 'metadata'), (project_id, trace_id), ('', '')) AS trace_scope … WHERE project_id = {project_id} AND trace_visible(trace_scope.1, trace_scope.2, {policy})`. The dictionary (`instrumentation.ts`, `COMPLEX_KEY_DIRECT`, `QUERY 'SELECT … FROM traces_static FINAL'`, no cache so a new trace is filterable as soon as its `traces_static` row exists) turns the trace join into a row-local predicate, which lands in PREWHERE and keeps projections and lazy materialization usable; an `IN`/`JOIN` on `traces_static` would not. Cost is one `traces_static` PK lookup per block, paid only when the policy carries filters. `traces_v1` evaluates the same UDF on its already-joined `ts` row.
- The query-engine `ViewRewriter` (`query_engine/validator.rs`) rewrites `spans`/`traces` to the `_v1` views and injects `policy = '<json>'` next to `project_id`; a user-supplied `policy` argument is rejected like `project_id`. Other tables (`evaluation_datapoints`, `signal_*`, `trace_outputs`, …) still target `_v0` without a policy (`takes_policy()`). `validate_and_secure_query(sql, project_id, policy)` is the entry; tests in `validator/tests.rs` assert every spans/traces reference receives the policy.
- **Search** (`/spans/search`, `routes/spans.rs`) takes the same mandatory `actor` as `/sql/query` (`lib/actions/traces/search.ts` resolves it from the server session; every frontend search path goes through that helper). Hits come from the Quickwit index, which holds spliced text, so a masked reader cannot find a span by its PII value. Snippets are cut from raw `spans`/`unique_content` rows by `search/snippets.rs`, so under `maskPii` the route withholds them (`get_snippets` forced off) instead of masking; masked snippets (`apply_pii_masks` over the same rows, as `spans_v1` does) are a follow-up.
- Direct `_v1` callers outside the rewriter pass `policy='{}'`: `ch/spans.rs` (debugger page), `ch/system_prompt_versions.rs`, private `signals/private/spans.rs`.
- Adding a `spans` column means updating **both** `spans_v0` and `spans_v1` (plus the allowlists listed in `clickhouse-traces.md`).

## Known gaps

Each of these lets a member of a `dual` project see raw text:

- Realtime SSE (`realtime/`, `send_span_updates`) publishes the raw span once to every subscriber; needs dual publish with per-connection policy.
- `trace_outputs_v0` (agent output) and `signal_events_v0` take no policy; Signals stores its produced event raw (`handle_create_event`, private repo).
- `traces_static.input` (extracted task) has no masks or `pii_checked`, hence the blanket mask on `agent_input`; `traceFilters` are enforced on it already.
- `traceFilters` are honoured by `spans_v1`/`traces_v1` only; `trace_outputs_v0`, `signal_events_v0`, search (hit existence) and realtime do not scope by trace.
- The Laminar Agent (private repo) runs under the caller's policy (`AgentSource::actor`: UI → the user's role, CLI → `Actor::Cli`, MCP → `Actor::ApiKey`, Slack → `Shared`), but its replies are not re-masked per user, and conversation history persists whatever the first caller saw.
- Unchecked history is never backfilled; notifications are not rendered per role; there is no `pii_terms` search field for admin raw search.
