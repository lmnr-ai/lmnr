## Onboarding Wizard

Route groups: `(auth)/layout.tsx` requires a session (redirects to `/sign-in`); the nested `(auth)/(app)/layout.tsx` is the onboarding-cookie gate (redirects to `/onboarding` when the cookie is present). The wizard is `frontend/app/(auth)/onboarding/page.tsx` → `components/onboarding/`. There is NO `(authenticated)` route group — the app trees live under `(auth)/(app)/`.

- **The page is a Server Component and only READS the cookie** (`getOnboardingState`). Next.js 16 Server Components can't reliably write cookies — a silent fail/throw plus a same-request `redirect()` produces a redirect loop. All writes go through `app/api/projects/[projectId]/onboarding/state/route.ts` (project-scoped, so `proxy.ts`'s `/api/projects/*` gating enforces membership); `persistOnboardingStep` is the only write surface and `finishOnboarding` DELETEs. Writes only happen once workspace+project exist. The handler resets `startedAt` when the cookie's `userId` ≠ the session's, so a stale cross-user cookie is overwritten on first POST.
- **The gate belongs in the `(auth)/(app)/layout.tsx` route-group layout — do NOT move it into `proxy.ts`.** That needs the matcher expanded to every authenticated prefix, a callback hack to bypass the `/sign-in` short-circuit, and the cookie name leaked into the global pipeline. `proxy.ts` is scoped to API authz, the Strapi `/uploads/*` rewrite, and the unauthenticated sign-in redirect — it imports nothing from onboarding.
- **An other user's cookie must look ABSENT.** Narrow `saved` to `ownSaved = saved?.userId === user.id ? saved : null` before every gate (including the "already has workspaces" redirect to `/projects`, which fires only when `count > 0 AND no own cookie AND slack param undefined`). Otherwise the wizard renders and overwrites under user B, and the gate traps B in a loop until they create an unwanted workspace.
- **Every completion DELETE must gate the next navigation on `res.ok`** — `fetch` only throws on network errors, so a 401/500 still resolves and navigating into the app tree with a live cookie loops via the gate. `finishOnboarding` returns a boolean for exactly this; its sole call site (`ConnectStep.goToProject`) gates on it. Separately, the server-side stale-cookie clear (cookie references an inaccessible project) goes through `redirect("/api/onboarding?to=/projects")` — that is the ONLY non-project-scoped cookie write allowed, because at that point the cookie's project can't be authz'd.
- There is no mount-POST; step writes happen only after a successful save. If you add one, the completion DELETE must await its settle first or the POST's `Set-Cookie` resurrects the cookie and bounces back to `/onboarding`.
- Save handlers must return `false` + a destructive toast on failure — never advance optimistically; `track` / `persistOnboardingStep` are gated on success. `saveSignals` PUTs the full template selection and the server reconciles against existing template-named signals, so revisiting a step never duplicates (scope is limited to names in `components/signals/prompts.ts`, so custom-named signals are invisible to the diff).
- `workspaceName` MUST be re-derived from the DB on resume (`loadOnboardingResumeDefaults`): the plan step passes it to `/checkout` as Stripe metadata, so without it the `"${user.name}'s workspace"` fallback lands in Stripe. Keep the per-slice loaders composed with `Promise.all` so the queries parallelize.
- **Do NOT clear the cookie before redirecting to Stripe** — it must survive the round trip so the gate keeps the post-payment landing on `/onboarding`. `returnTo=onboarding` makes checkout set `success_url=/onboarding?upgraded=true`, which `WizardSteps` detects and renders as `<ConnectStep upgraded />`. In-app upgrades omit `returnTo` and keep `success_url=/workspace/<id>?tab=billing`.
- The Slack step's OAuth `state` is `"${workspaceId}:/onboarding"` with **no `slack=*` in the returnPath** — `buildRedirectUrl` appends `slack=success|error` itself, and embedding it in state yields `?slack=success&slack=error` where `URLSearchParams.get` reads the first and masks the error.
- Creating a workspace with `isFirstProject: true` auto-creates the **Failure Detector** signal + trigger + creator email targets in the same transaction, so the user is opted into report digests by step 1. There is no in-wizard email-subscription UI; opt-out lives in workspace settings.
- **The welcome email is sent from the completion DELETE handler**, gated on `Feature.SEND_EMAIL` — sending earlier would email users who bounce before creating a workspace. The OSS path (`OssWorkspaceOnly.onComplete`) keeps an inline fire-and-forget DELETE whose only side effect is that email.
- Step 0 is irreversible (`WizardSteps` passes no `onBack` to step 1); steps 2–4 get `onBack` and reconcile-on-save absorbs the oscillation. `ConnectStep` is the only place that calls `finishOnboarding`.
- Do NOT nest a Radix `Checkbox` (renders a `<button>`) inside a `<button>` card — hydration error. The signals step uses a plain `<span>` + `Check` icon.

## Serving under a base path (sub-path / reverse proxy)

- The frontend can be served under a sub-path (e.g. `app.company.com/lmnr`) for self-hosters who reverse-proxy Laminar onto an existing domain. The prefix is **baked at BUILD time** via `NEXT_PUBLIC_BASE_PATH` → `basePath` in `next.config.ts` — it is NOT a runtime flip, because `output: standalone` inlines absolute `/_next/static/...` asset URLs into the bundle. Empty/unset ⇒ root-served, so the regular `frontend-ee` image is unaffected; the EE side builds a separate `frontend-ee-basepath` image with `/lmnr` baked in (Dockerfile takes the prefix as a build-arg, same pattern as `NEXT_PUBLIC_APP_VERSION`). The `lmnr-private` CI matrix owns that second image target — it can't be done from the OSS repo.
- **What Next auto-prefixes (leave alone):** `<Link>`, `router.push`, `next/navigation` `redirect()` (Next 16 server redirect DOES prepend basePath), `next/image`, `/public` assets, fonts, API route mounting, and it STRIPS the prefix before middleware/rewrites run (so `proxy.ts` matchers and `req.nextUrl.pathname` stay prefix-free).
- **What is NOT auto-prefixed (must wrap with `withBasePath` from `lib/utils.ts`):** native `fetch("/api/...")`, `new EventSource("/...")`, `window.location.*`, Better Auth `callbackURL`/`errorCallbackURL` (redirected verbatim), and `NextResponse.redirect(new URL(path, base))` — `new URL(absolutePath, base)` DROPS the prefix, so prefix the path before constructing the URL. `redirect()` from `next/navigation` does NOT need wrapping.
- Native `fetch` / `EventSource` are handled globally by `components/common/base-path-fetch-shim.tsx` (mounted first in `app/layout.tsx`'s `<body>`), which monkey-patches `window.fetch`/`window.EventSource` to prefix root-relative requests once at client load. It prefixes both **string** paths (`fetch("/api/...")`) AND **same-origin `URL` objects** (`fetch(new URL("/api/foo", origin))` — re-prefixes the pathname; cross-origin URLs like PostHog/GitHub pass through). `Request` objects pass through (they carry an already-resolved absolute URL). It's gated on `BASE_PATH` non-empty (so root-served is a true no-op) and idempotent via a `__lmnrBasePathFetchPatched` window flag. This is why the ~140 native fetch call sites are NOT individually prefixed — don't start doing it by hand. `withBasePath` is still needed at the verbatim sites listed above (location/auth-callback/NextResponse.redirect) because those bypass `window.fetch`.
- `withBasePath(path)` is a no-op when `BASE_PATH` is empty, and skips absolute URLs (`http(s)://`, `//host`), non-root paths, and already-prefixed paths — so it's safe to wrap defensively. Its inverse `stripBasePath` removes the prefix off a browser-observed `window.location.pathname`.
- **`callbackUrl` in the sign-in query string is prefix-FREE by contract.** Both consumers re-prefix it (the sign-in page's `router.push` auto-adds basePath; OAuth's `errorCallbackURL` goes through `withBasePath`), so producers must NOT store a prefix-inclusive value or it double-stamps (`/lmnr/lmnr/...`). `proxy.ts` is naturally prefix-free (middleware sees the stripped pathname); `redirectToSignIn` (`lib/utils.ts`, fired on a 401 from `swrFetcher`) must `stripBasePath(window.location.pathname)` because the browser pathname carries the prefix.
- **Better Auth needs FOUR explicit base-path fixes — do NOT revert any, the shim does not cover them.**
  - **(1) Server** (`lib/auth.ts`): `betterAuth({ baseURL })` MUST be the `AUTH_URL` **origin only** (`AUTH_ORIGIN = new URL(AUTH_URL).origin`), never the full prefixed URL. Better Auth's router derives its mount/strip path from `new URL(baseURL).pathname` (`better-auth/dist/api/index.mjs`), but Next strips the base path before the route handler runs — so a prefixed `baseURL` (`https://host/lmnr`) makes the router try to strip `/lmnr` off an already-stripped `/api/auth/...` request and 404s EVERY auth route.
  - **(2) Client** (`lib/auth-client.ts`): `createAuthClient({ baseURL })` MUST be pinned to `` `${window.location.origin}${BASE_PATH}/api/auth` `` in the browser — client-side Better Auth resolves to the root-relative `/api/auth` default (prefix-free → 404), and it snapshots `customFetchImpl: fetch` by value at creation, so the global fetch shim can't reliably retro-prefix it if `auth-client.ts` imported before the shim patched `window.fetch`.
  - **(3) OAuth `redirect_uri` for ALL providers must be built as `${AUTH_ORIGIN}${BASE_PATH}/api/auth/callback/<id>` via `prefixedCallbackUri`, NOT `baseURL` and NOT raw `AUTH_URL`.** Better Auth computes social-provider (github/google) `redirect_uri` as `${context.baseURL}/callback/<id>` (`better-auth/dist/api/routes/sign-in.mjs` + `callback.mjs`) — and since `baseURL` is origin-only, that drops the prefix and the IdP redirect_uri match fails. So github/google MUST set `redirectURI: prefixedCallbackUri(<id>)` explicitly in `getSocialProviders` (azure/okta/keycloak already do via `getGenericOAuthConfig`). Both the authorize and token-exchange legs read `options.redirectURI || redirectURI`, so the explicit option covers both. **`prefixedCallbackUri` derives the prefix from the build-time-baked `BASE_PATH`, not from `AUTH_URL`** — the sub-path is the source of truth baked into the `frontend-ee-basepath` image, and a self-hoster naturally sets `BETTER_AUTH_URL` to their bare origin (no `/lmnr`), so building the callback off `AUTH_URL` emits an unprefixed `redirect_uri`, the IdP redirects to `/api/auth/callback/<id>`, and the reverse proxy 404s it. The final post-auth redirect uses the client-supplied `callbackURL`, already prefixed via `withBasePath`.
  - **(4) Device-flow `verificationUri` (CLI login) must be `` `${BASE_PATH}/device` ``, not bare `/device`.** Better Auth's `buildVerificationUris` (`better-auth/dist/plugins/device-authorization/routes.mjs`) resolves it via `new URL(verificationUri, baseURL)` — with origin-only `baseURL` a root-relative `/device` replaces the whole path and drops the prefix, so the RFC 8628 `verification_uri` the CLI opens becomes `https://host/device` (404 under a sub-path deploy). Prefixing with `BASE_PATH` keeps it relative so it resolves to `<origin><base>/device`; no-op when root-served.

## Render Templates (JSX iframe renderer)

- User-authored render templates run inside a sandboxed iframe (`frontend/components/ui/template-renderer/jsx-renderer.tsx`) via Preact + twind. The iframe's initial `<script>` overwrites `window.fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, and `navigator.sendBeacon` with throwing stubs so template code cannot exfiltrate project data. Do NOT loosen the CSP `connect-src` or restore these globals — any new capability the template needs must be piped in through the parent-to-iframe `postMessage` channel instead.
- AI generation lives outside the app: the dialog exposes a "Copy prompt" button that copies `RENDER_TEMPLATE_AI_PROMPT` from `lib/actions/render-template/prompts.ts` to the clipboard. Users paste it into their own AI tool with their data and request, then drop the returned JSX into the editor. There is no `/render-templates/generate` route and no in-dialog AI panel.
- The iframe's twind config (`jsx-renderer.tsx`) is wired up to Laminar's design tokens via `LAMINAR_IFRAME_THEME` in `frontend/components/ui/template-renderer/theme.ts`. This means semantic classes like `bg-background`, `text-foreground`, `bg-card`, `text-primary`, `border-border`, `text-destructive`, `text-success`, `text-llm`, `text-tool`, `text-subagent` all resolve inside generated templates. The prompt's style guide and example use these semantic classes — do NOT use raw palette names (`text-sky-400`, `bg-neutral-900`, etc.), which drift from the rest of the platform and won't follow theme changes. When you change a token in `globals.css` (the `:root` block), mirror it as a hex literal in `theme.ts` — the iframe runs twind from a CDN and has no access to our CSS variables.
- Span and trace templates live in ONE Postgres table, `render_templates`, with a `type` text column (`'span'` default | `'trace'`) and a nullable `where_clause` text column — behind ONE endpoint family (`/api/projects/[projectId]/render-templates`, GET takes an optional `?type=` filter; actions in `lib/actions/render-template/index.ts`). `type` is set at create and immutable on update. The frontend `TemplateScope` ("span" | "trace") maps 1:1 onto the `type` column (`TemplatePickerProvider`'s `scope` prop drives the `?type=` list filter and the POST body's `type`). Trace templates carry an optional `where_clause` SQL fragment; `getTraceRenderData` (`frontend/lib/actions/trace/render-data.ts`) composes it as `SELECT ... FROM spans WHERE trace_id = {traceId: UUID} AND (<fragment>) ORDER BY start_time` through `executeQuery`, so the app-server query-engine validator is the security boundary — same trust model as the SQL editor. Do NOT sanitize or parse the fragment in the frontend. Results are capped at `MAX_TRACE_RENDER_SPANS` (256) and delivered as `{ spans, truncated }`. The trace view's "Custom" tab (`components/traces/trace-view/custom-view/`) fetches this via POST `/api/projects/[projectId]/traces/[traceId]/render-data`.
- Trace-scoped "Copy prompt" embeds a live trace outline: GET `/api/projects/[projectId]/traces/[traceId]/span-outline` (`lib/actions/trace/span-outline.ts`) returns one representative span per distinct `(name, span_type)` (`argMin(col, start_time)` so all sample columns come from the same row — not `any()`), with `occurrences` counts, `input`/`output`/`attributes` JSON-parsed FIRST and then leaf-truncated (64-char strings / 10-item arrays / depth 8) — truncating the raw JSON string would cut mid-token. `buildTraceRenderTemplatePrompt` (`lib/actions/render-template/prompts.ts`) embeds the outline + the WHERE-fragment contract and asks the LLM for TWO fenced blocks: ```sql (fragment, empty = all spans) then ```jsx. The outline deliberately ignores the template's current whereClause (the LLM must see the whole trace to choose a filter). From settings (no traceId) the prompt falls back to a placeholder outline.
- `ManageTemplateDialog` lives at `frontend/components/ui/template-renderer/manage-template-dialog/` (folder with `index.tsx`, `code-editor.tsx`, `data-panel.tsx`). Layout: left column is a Preview/Data tab pair (Preview = live `JsxRenderer`, Data = the `testData` JSON editor in `DataPanel`); right column has the name input + save button, the "Copy prompt" affordance, and `CodeEditor` for the JSX. `DataPanel` pretty-prints `testData` once on mount with `shouldDirty: false` and again on CodeMirror `onBlur` with `shouldDirty: true` — there is no Format button. The dialog is a shared form UI consumed both from the inline template picker (`components/ui/template-renderer/index.tsx`) and from project settings (`components/settings/render-templates/`). Both callers must wrap it in a `FormProvider` whose form shape matches `ManageTemplateForm` — the dialog uses `useFormContext` and will crash without a provider. The settings wrapper in `render-template-dialog.tsx` fetches the full template on open and resets the form; the inline picker already has the template loaded via SWR + `fetchTemplate`. The Span-filter input is the shared `SQLEditor` (`components/sql/sql-editor.tsx`, CodeMirror) scoped via `schema={{ tables: ["spans"] }}` so autocomplete only offers spans columns; it's multiline, so Enter inserts a newline — only the "Test" button (shown when traceId is present) POSTs the draft `whereClause` to the render-data endpoint and pipes the response into the form's `testData` — safe because `custom-view`'s own fetch is `isManaging`-gated, so the provider's testData-sync effect won't clobber it while the dialog is open. Note: `fetcherJSON` throws with the RAW backend response body as the message, so for query-engine rejections that's a JSON string like `{"error":"..."}` — routes that surface these to users must unwrap it (see `unwrapErrorMessage` in the render-data route) or the UI shows raw JSON.

## Shared Settings page (`/project/[projectId]/settings`)

- Workspace settings AND project settings render on ONE page: `frontend/app/(auth)/(app)/project/[projectId]/settings/page.tsx` → `components/shared-settings/index.tsx`, **nested inside the project layout** so the main project sidebar stays visible. Section is chosen by `?tab=<name>` (matches the app-server email/Slack `?tab=alerts` links); `activeSection` defaults to `general`. There is **no** standalone `/settings` or `/settings/[workspaceId]` route, and **no project/workspace picker** — settings implicitly target the current project (from the URL) and its workspace.
- Because the page lives under `/project/[projectId]/`, it inherits `ProjectContextProvider` from the project layout (the page does NOT mount its own providers). Project-settings section components (`components/settings/*`: RenameProject, DeleteProject, PiiRedaction, ProjectApiKeys, ProviderApiKeys, CustomModelCosts, RenderTemplates, AgentVersions, AlertsSettings) read `useParams().projectId` + `useProjectContext()`. Workspace section components (`components/workspace/*`) receive `workspace` as a **prop** — they must NOT read `useParams().workspaceId`, which is undefined under this route.
- **Nav order** (left settings sidebar, top→bottom): "Project settings" group FIRST — General / Project API Keys / Model providers / Model costs / Render templates / Agent versions / Security / Alerts; then "Workspace settings" group — workspace General (`workspace-general`, owner-only) first, then Usage / Team / [Data residency if `Feature.DEPLOYMENT`] / Integrations / Reports / [Billing if `Feature.SUBSCRIPTION`]. Billing / Data residency are feature-gated (absent on OSS/self-hosted). Project-first is a deliberate product decision — do not flip it to workspace-first.
- **Settings-link source:** in-app links use `useProjectContext().settingsHref(tab?)` (project-scoped, single source of truth). Server/external callers that know only a workspace id (Stripe return URLs, Slack callbacks, checkout, invite-accept) use `getWorkspaceSettingsPath(workspaceId, section?)` in `lib/actions/projects`, which resolves the workspace's newest project via `getNewestProjectId` and falls back to `/projects` when it has none (acceptable — every real caller targets a workspace with ≥1 project). The settings-tab union (`SettingsSection`) is single-sourced in `contexts/project-context.tsx`.
- **The Settings entry is a project sidebar nav item** (`getSidebarMenus()` in `components/project/utils.ts`, href `/project/[id]/settings`), NOT in the sidebar footer. The footer (`components/projects/sidebar-footer.tsx`, shared by project/workspace sidebars) holds `SidebarUserMenu` (account + log out + tier-gated upgrade).
- **Legacy `/workspace/[workspaceId]` is a redirect-only shim** (`app/(auth)/(app)/workspace/[workspaceId]/page.tsx`): maps `?tab=` (remapping the legacy workspace `settings` tab → `workspace-general`) and redirects to the workspace's project settings via `getWorkspaceSettingsPath`. Two consumers: (1) already-sent app-server emails (`/workspace/{id}?tab=usage|reports`); (2) in-app links that know only a workspace id and may render without project context — the create-project dialog in the project-less `/projects` surface links `/workspace/{id}?tab=billing`. App-server `email.rs`/`slack.rs` emit `/project/{id}/settings?tab=alerts` directly.
- **A workspace must always retain ≥1 project:** `DeleteProject` disables its button (with an inline note) when `useProjectContext().projects.length <= 1`; the `deleteProject` action (`lib/actions/project`) also throws `"Cannot delete the only project in a workspace"` before any side effect, so the rule holds even via a direct `DELETE /api/projects/:id` call.

## Workspace Settings (`workspaces.settings` JSONB) — Privacy Mode

- Workspace-level knobs live in `workspaces.settings JSONB DEFAULT '{}'` (migration `0106`), the workspace twin of `projects.settings`. Typed view + write path: `lib/actions/workspace/settings.ts` (`WorkspaceSettingsSchema`, `.strict()`, Postgres `||` merge); client-safe interface mirror in `lib/workspaces/types.ts`. Writes are owner-only via `checkUserWorkspaceRole` and go through `PATCH /api/workspaces/:id/settings` (membership pre-gated by `proxy.ts`'s `/api/workspaces/:path+` matcher). No Rust reader today — nothing to keep in sync app-server-side yet.
- **Privacy Mode is TRI-STATE and CLOUD-ONLY.** The stored `privacyMode` key is the owner's EXPLICIT choice; absence = unset. NEVER read the raw JSONB — resolve through `resolvePrivacyMode(settings, tierName)` (`lib/actions/workspace/settings.ts`), which applies precedence: `dpaEnforcedPrivacyMode` (locked ON, ops-set out-of-band, overrides even an explicit off; NOT writable via the PATCH route — `UpdatableWorkspaceSettingsSchema` picks `privacyMode` only) > explicit choice > `privacyModeProtected` (floor stamped by `preservePrivacyModeOnDowngrade` from the Stripe webhook so a Pro→Free downgrade of an unset workspace doesn't flip it to the free default) > per-plan default (Free/Hobby OFF, Pro+ ON — but ONLY once `PRIVACY_MODE_TIER_DEFAULTS_EFFECTIVE_DATE` is set and passed; while it's `null` every unset workspace resolves ON). `Workspace.privacyMode` (`PrivacyModeState {enabled, locked}`) is the resolved value the UI consumes. The toggle (`components/workspace/privacy-mode.tsx`) returns null unless `Feature.LAMINAR_CLOUD`, the settings route 404s off-cloud; turning OFF requires a confirmation dialog, turning ON is instant, DPA-locked shows disabled-ON (never hidden). Open rollout items live in `docs/internal/counsel-handoff.md`.
- Policy pages are MARKDOWN, not JSX: content lives in `lib/policies/content/*.md` (gray-matter frontmatter `title`/`description`), rendered by the single route `app/policies/[slug]/page.tsx` via the same `next-mdx-remote/rsc` + `remark-gfm` + `rehype-slug` pipeline as the blog; typography comes from the `prose prose-invert` wrapper in `app/policies/layout.tsx` (landing header/footer chrome). Slug allowlist is `POLICY_SLUGS` in `lib/policies/utils.ts` — adding a policy = drop a `.md` file + add the slug there. Three traps: (1) the `.md` files are read with `fs` at request time, so `outputFileTracingIncludes` in `next.config.ts` must keep including them or the standalone image 500s on `/policies/*`; (2) MDXRemote parses MDX, so raw `<`/`{` in the markdown are syntax errors — escape or rephrase; (3) prettier's markdown parser rewrites `{/* */}` MDX comments into invalid `{/_ _/}` (the pre-commit hook runs it on staged `.md`), which 500s the page — `lib/policies/content/` is in `.prettierignore` for exactly this reason, keep it there. Intra-doc anchors must be rehype-slug ids (github-slugger of the heading text), not the legacy Termly `#services`-style ids. Legal drafts carry a "DRAFT — NOT REVIEWED BY COUNSEL" note and `NEEDS CONFIRMATION`/`NEEDS-CONFIRMATION` markers for facts not verifiable from code; keep both until counsel signs off.

## Project Settings (`projects.settings` JSONB)

- Per-project knobs live in `projects.settings JSONB DEFAULT '{}'` — one row per project, one column for ALL settings, NOT one column per setting. Adding a new setting means adding a typed field on each side, no migration. The column travels on the same row as `ProjectWithWorkspaceBillingInfo` (Rust), which is cached in Redis under `project:{project_id}`, so the read lookup is free after the first batch.
- **Writes are Next.js-only.** The Rust app-server is read-only — `db::projects::ProjectSettings` (Rust struct) deserializes via `serde_json` with `#[serde(default)]` on every field so older rows / unknown keys don't break. Malformed JSON falls back to defaults and logs a warning rather than poisoning the cache.
- Writes go through `updateProjectSettings` in `lib/actions/project/settings.ts`. The Zod schema is `.strict()` (unknown keys → 400, not silent drop into the JSONB). Tier gates per key live in `PRO_TIER_KEYS` — `removePii` is the only entry today; gates are applied server-side regardless of UI state. Update SQL uses Postgres `||` JSONB merge so partial updates preserve unspecified keys without a read-modify-write race.
- After every successful update, the action removes `project:{id}` from the Redis cache so the next ingest batch reads the new value. Both sides of `ProjectSettings` (TS Zod, Rust `serde`) MUST stay in sync — drift surfaces as one-sided defaults, not crashes, so it can be silent.
- API: `PATCH /api/projects/:projectId/settings` with body `{ settings: <Partial<ProjectSettings>> }`. Auth + project-membership gate at the top of the route via `getServerSession` + `isUserMemberOfProject` returning 401 / 403 JSON; do not use `requireProjectAccess` here, it `redirect()`s / `notFound()`s which is the page-tree pattern, not an API-route shape.

### PII redaction (`settings.removePii`)

- Setting `removePii=true` on a project routes every span ingested for that project through the `pii-redactor` gRPC service before storage.
- Frontend toggle: `components/settings/pii-redaction.tsx`, mounted in the General tab. Pro-tier gated in BOTH the UI (greyed `Switch` + "Pro plan required" badge) AND the server action (rejects non-Pro/Enterprise with 403). The server gate is the source of truth; the UI gate is purely UX.
- **The Pro-tier gate only applies on Laminar Cloud.** Self-hosted installs aren't on tiered billing — their only seeded `subscription_tiers` row is `unlimited` (`frontend/lib/db/initial-data.json`), which would never satisfy `PRO_LIKE_TIERS`. Both gates (`PRO_TIER_KEYS` check in `updateProjectSettings`, `isProTier` in `pii-redaction.tsx`) short-circuit to allowed when `Feature.LAMINAR_CLOUD` is off, so self-hosters can freely toggle `removePii`. The two sides must stay in sync; the server side is authoritative.
- Redaction runs in the consumer (`process_span_messages`) AFTER `build_dedup_batch` and BEFORE the `llm_messages` ClickHouse insert. For dedup'd LLM spans (most LLM spans — root spans excepted) `span.input` is `None` on the wire, so redaction targets `dedup.messages[k].content` directly: this single buffer is what the `llm_messages` insert reads AND what Quickwit indexing reads via the `*_new_message_indices` columns, so one update covers both storage tiers. Already-seen messages are NOT in `dedup.messages` and ride the wire as hashes only — they were redacted on first emit. Root LLM spans (which keep `span.input` populated for the trace-list preview) plus non-LLM spans get whole-`input` redaction. `span.output` is always whole-redacted.
- The redactor is best-effort: gRPC failures, response-length mismatches, and parse errors all log and return without mutating the batch. Redaction failures must NEVER block trace ingestion.
- After redaction mutates `dedup.messages[k].content` in place, the `redact_spans_in_place` write-back loop also patches `dedup.span_content_bytes[dedup_idx]` so the post-dedup input-bytes loop bills the redacted size, matching the "size reflects redacted content" invariant on `estimate_size_bytes`.

## Next.js Catch-all Route Params

- In Next.js 16 App Router, **catch-all** (`[...slug]`) dynamic params are NOT auto-decoded — `await props.params` returns the raw URL-encoded segments. Single-segment dynamic params (`[slug]`) ARE auto-decoded. If a caller uses `encodeURIComponent` on an id containing URL-unsafe chars (e.g. Slack ids `slack:C0ATXMVNUH1:...`) and the target route is catch-all, the page must `decodeURIComponent` each segment or the encoded `%3A`s flow into downstream filters and the API double-encodes them (`%253A`) yielding zero results. See `app/project/[projectId]/sessions/[...sessionId]/page.tsx`.

## SSE proxy routes and Next's `failed to pipe response`

- Any App Router route that returns a `ReadableStream` must NOT call `controller.error(err)` for an upstream/transport failure. Next's `pipeToNodeResponse` (`next/dist/server/pipe-readable.js`) only swallows `AbortError` / `ResponseAborted`; every other stream error is rethrown as `Error: failed to pipe response` (`__NEXT_ERROR_CODE: "E180"`), which reaches `onRequestError` → `Sentry.captureRequestError` and is reported as an unhandled 500. This was the source of `GET /api/projects/[projectId]/realtime` Sentry noise: when the app-server-consumer pod goes away mid-stream (rollout, scale-down, LB idle cutoff), `reader.read()` on the proxied body rejects with `TypeError: terminated` / `UND_ERR_SOCKET: other side closed`.
- The fix is `controller.close()` on EVERY exit path (wrap it in try/catch — closing an already-cancelled controller throws) and a `console.warn` instead of an unhandled throw. Losing the upstream is a normal lifecycle event, and closing the response lets the browser's `EventSource` do its own reconnect; erroring the stream just costs a Sentry event and the client reconnects anyway. Suppress the log when `abortController.signal.aborted` — that's our own client disconnecting, not a fault.
- `sentry.server.config.ts` only drops realtime **transactions** (`beforeSendTransaction`), NOT error events, so an `E180` from this route was still reported. Don't reach for a `beforeSend` message filter to hide a streaming error — fix the stream's error path so the exception is never raised.
- To reproduce locally: point `BACKEND_RT_URL` at a throwaway `http.createServer` that writes SSE headers + one event then calls `res.socket.destroy()`. Because `/api/projects/*` is auth-gated by `proxy.ts`, either sign in first (`POST /api/auth/sign-in/local-email` with `{"email":"agent@lmnr.ai"}` and a cookie jar, `FORCE_EMAIL_AUTH=true` is set in the sandbox `.env.local`) or temporarily copy the handler to an unguarded path. Note an `app/api/_name/` folder is a **private** App Router directory and 404s — don't name a scratch route with a leading underscore.
