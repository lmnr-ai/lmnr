# Hosted evals (Harbor trials in provider sandboxes, proxied through the app-server)

<!-- Detailed working notes for coding agents and developers. -->
<!-- Referenced from the index in the repo-root CLAUDE.md; read when working in this area. -->
<!-- Sibling files in docs/internal/ may be cross-referenced by section name. -->

`app-server/src/hosted_evals/` lets `lmnr-cli eval run --remote` run a project's Harbor suites with every trial in a sandbox (Daytona today; LAM-2427, LAM-2434). The client side lives in lmnr-ts: `packages/lmnr-cli/src/commands/eval/` and the Harbor environment class `packages/lmnr-cli/assets/lmnr_hosted_env.py`. v0 has no run status API: results arrive as regular evaluations through the Laminar Harbor plugin.

## Shape

- **Module layout** (`app-server/src/hosted_evals/`):
  - `provider/mod.rs`: `SandboxProviderTrait` (`enum_dispatch` over `SandboxProvider`, like `Storage`) and the provider-neutral types (`SandboxSpec`, `SandboxHandle {id, route}`, `SandboxState`, `ImageState`, `PushedImage`, `Resources`, `CommandResult`).
  - `provider/daytona/`: the only implementation. `client.rs` is the raw REST client (own reqwest client with connect/read timeouts); `mod.rs` maps the trait onto it: snapshots, private-registry entries, labels, sessions, state mapping.
  - `sandboxes.rs`: provider-agnostic project logic: ownership check + route cache, the capacity cap, `prepare_image` / `create_trial`, `wait_until_started`.
  - `registry.rs`: our image registry (ECR or generic) and per-project `Repository`. `images.rs`: layer and image push logic on top of it.
  - `mod.rs`: `HostedEvals {provider, registry}`, built once in `main.rs` from the shared AWS config and registered as `web::Data<Option<HostedEvals>>` (`None` = disabled; routes answer 404 "not enabled"). Also remote runs (`start_run`).
  - A second provider is a new `SandboxProvider` variant: nothing above `provider/` names Daytona. Providers own how a pushed image becomes startable (`prepare_image`), how project ownership is recorded (`SandboxInfo.project_id`) and what a command id looks like.

- **Harbor always runs where `lmnr-cli` runs**: on the user's machine locally, in the orchestrator sandbox for `--remote`. Remote trials use a custom Harbor environment (`environment.import_path = "lmnr_hosted_env:LaminarEnvironment"`) whose methods call the app-server's sandbox routes with a project API key. The app-server forwards to Daytona. **The Daytona key never leaves the app-server.**
- **Remote runs** (`--remote`; streaming results back to the CLI is the follow-up): the CLI uploads the evals folder and `POST /runs` starts one orchestrator sandbox (Daytona default snapshot) that downloads the archive from the app-server and runs `npx lmnr-cli@<requesting CLI version> eval orchestrate` (Harbor plus `LaminarEnvironment`) with a short-lived project key. The run spec (`LMNR_EVAL_RUN`) is opaque to the server: the CLI writes it and the same CLI version reads it.

## Routes (`api/v1/hosted_evals.rs`)

All under `/v1/hosted-evals`, project API key. The CLI twins (`api/v1/cli/hosted_evals.rs`, `CliProjectAuth`) exist only for what the CLI itself calls: `images/layers/*`, `POST images`, `POST uploads`, `POST runs`.

| Route | What |
|---|---|
| `POST /images/layers/missing` | `{diffIds}` → `{missing}`: layers (by uncompressed digest) the project still has to upload. |
| `PUT /images/layers/{diffId}` | Gzip layer body (8 GiB cap), streamed into our image registry → `{digest, size}`. |
| `POST /images` | `{config}` (the image config JSON, verbatim) → `{image}` (manifest digest); `409 {missing}` if a layer isn't uploaded. Rejects non-`amd64` configs. |
| `POST /images/snapshots` | `{image, cpus?, memoryGb?, diskGb?}` → `{state: "ready"}` \| `{state: "pending"}` \| `{state: "failed", errorReason}`. Prepares the image for those resources on first call (Daytona: creates its snapshot); Harbor's class polls it. Key only. |
| `POST /sandboxes` | `{image, cpus?, memoryGb?, diskGb?}` (the image's snapshot for those resources must be ready, else `409`) → `201 {sandboxId}`. Returns before the sandbox starts; clients poll `GET`. |
| `GET/DELETE /sandboxes/{id}` | `{state: pending \| started \| error \| destroyed, errorReason?}` (provider states are mapped onto these four; a stopped Daytona sandbox counts as `destroyed`) / delete. |
| `POST /sandboxes/{id}/commands` | `{command}` → `{commandId}` (async). |
| `GET /sandboxes/{id}/commands/{commandId}` | `{exitCode: null}` while running, then `{exitCode, stdout, stderr}`. |
| `PUT/GET /sandboxes/{id}/files?path=/abs` | Raw file body (512 MiB cap). Directories are tarred by the Python class. |
| `POST /uploads`, `GET /uploads/{id}` | Remote-run archive (`.tar.gz`, 1 GiB), in `S3_EXPORTS_BUCKET`. The orchestrator downloads with its run key; no presigned URL, so it also works for self-hosted S3 that Daytona can't reach. |
| `POST /runs` | `{uploadId, cliVersion, spec}` → `202 {sandboxId}`. |

Provider, registry and S3 failures answer a generic `502 {error: "Hosted evals <operation> failed upstream. Retry shortly."}` and log the cause (`upstream_error`): their errors can carry upstream response bodies. A missing S3 object is told apart from a transient error (`StorageTrait::exists`).

## Invariants and gotchas

- **Project scoping is a sandbox label** on Daytona. Every sandbox gets `lmnr-project-id` (+ `lmnr-role` = `trial` / `orchestrator`), surfaced as `SandboxInfo.project_id`. `sandboxes::resolve` checks it before any toolbox call and caches `hosted_evals_sandbox:{project}:{sandbox}` → the handle's route (toolbox proxy URL) only after a match. Another project's id answers 404, never 403.
- **One image path: the CLI builds or pulls every image with local Docker and pushes it** (`hosted_evals/images.rs`, next bullets): `lmnr.yaml` images, per-task `environment/Dockerfile`s and public `docker_image`s alike. Trial sandboxes only ever start from a snapshot of a pushed image. Daytona's own Dockerfile builds (`buildInfo` + uploaded contexts) are not used: they cache only by exact Dockerfile + context, so changing one file reran a 30 s `RUN` before the `COPY` every time (4/4 runs).
- **Pushed images go to our own registry:** the AWS account's ECR (`AWS_REGION`, default credential chain), or any registry set with `HOSTED_EVALS_REGISTRY_URL` + `_USERNAME` / `_PASSWORD`. The credentials never leave the app-server, and every byte goes through it. Each project pushes to `<HOSTED_EVALS_REGISTRY_REPOSITORY_PREFIX, default lmnr-hosted-evals>/<project_id>`, and only the app-server builds image names, so a digest from another project isn't in the caller's repository and its snapshot simply fails.
  - **ECR:** `GetAuthorizationToken` returns a 12 h basic-auth token (`AWS:<password>`) for the whole registry, with the app-server role's permissions; it is reused for 6 h per process. `ensure_exists` runs `CreateRepository` once per repository per process (an existing one answers `RepositoryAlreadyExistsException`) and, on creation, a lifecycle policy that expires images 30 days after push. A generic registry configured without username/password panics at boot. The role needs `ecr:GetAuthorizationToken` plus, on `repository/lmnr-hosted-evals/*`: `CreateRepository`, `PutLifecyclePolicy`, `BatchCheckLayerAvailability`, `InitiateLayerUpload`, `UploadLayerPart`, `CompleteLayerUpload`, `PutImage`, `BatchGetImage`, `GetDownloadUrlForLayer`. Registry requests use a client that doesn't follow redirects, and a `3xx` on a blob `HEAD` counts as present (ECR may redirect blobs to S3).
  - **Daytona pulls with the same credentials:** before creating a snapshot, `DaytonaProvider::grant_pull` updates the Daytona private-registry entry (`/docker-registry`) for the host, or creates one named `lmnr-hosted-evals`. The first snapshots of a burst each find no entry and create one (4 concurrent images left 4 entries), so it keeps one and deletes the rest. Daytona copies the image into its own registry while building the snapshot (the snapshot's `ref` is `cr.app.daytona.io/sbox/...`). Measured: with the source registry gone, a sandbox still started from the snapshot in 0.1 s. So the token only has to be fresh at snapshot creation, and ECR's lifecycle can expire images that active snapshots still use. The entry holds a token with the app-server's ECR permissions (push included) for up to 12 h; a pull-only role for that token would narrow it.
  - **Testing without AWS:** `crane registry serve` behind a cloudflared quick tunnel, as `HOSTED_EVALS_REGISTRY_URL=https://<tunnel>` with any username/password, exercises the whole push → snapshot → sandbox path. The ECR control plane runs against moto (`AWS_ENDPOINT_URL`, fake keys): token, repository and lifecycle calls succeed, then the push hits the real `123456789012.dkr.ecr…` host and gets `DENIED`.
- **Layers are keyed by `diff_id`** (uncompressed digest, known from the config without compressing) → `hosted_evals_layer:{project}:{diff_id}` = `{digest, size}` of the gzip blob, 7-day TTL. `missing_layers` also `HEAD`s the blob, so a blob the registry dropped is re-uploaded. Losing the cache (in-memory in LITE, Redis eviction) means one full re-upload, and since the CLI re-gzips, new blob digests, a new manifest and a new snapshot. The `diff_id` isn't verified server-side: a wrong one only breaks the uploader's own image.
- **Tags are `sha256-<manifest digest>`**, so a tag never moves: ECR repositories are created `MUTABLE` (re-putting a manifest is then a no-op), and `put_manifest` skips a tag that exists (`HEAD`). It also treats a `412` on the `PUT` as success, for registries with immutable tags (Daytona's answered `412` to a `PUT` after 12 concurrent ones had committed with `201`).
- **Snapshots fix resources** (sandbox + `snapshot` + `cpu` → 400), so there is one per image and resource shape: `lmnr-<project_id as 32 hex>-<image[..16]>-<c>c<m>g<d>d` (55+ characters, accepted). Unset disk defaults to the cap (the image must fit). Creating an existing name answers `409`; `get_snapshot` works by name. A snapshot whose image is missing becomes `error` but keeps its name, so `prepare_image` deletes failed ones for the next run to retry. `inactive` ones get `POST /snapshots/{id}/activate`. On each new snapshot, the project's snapshots idle for 7 days (`lastUsedAt`, else `createdAt`) are deleted. Timings: ~15 s from push to active for a 45 MB image; sandbox from an active snapshot 0.6–3.5 s.
- **Daytona REST session logs merge stdout and stderr** (the SDK splits only the websocket stream). `start_command` wraps the command as `sh -c '<cmd>' 2>/tmp/.lmnr-exec/<session>` and `command_result` reads that file back. One session per command, as Harbor's Daytona environment does. The command id is `<session hex>.<Daytona cmd id>`; both halves are checked to be id characters before they go into toolbox URL paths.
- **`DELETE` on a sandbox that is being destroyed (or still transitioning) answers `409 "Sandbox state change in progress"`.** `client::Daytona::delete_sandbox` treats gone/destroying as deleted and retries other 409s for up to a minute.
- **Limits:** `HOSTED_EVALS_MAX_SANDBOXES_PER_PROJECT` (default 50, `429` past it), per-sandbox `HOSTED_EVALS_MAX_SANDBOX_{CPUS,MEMORY_GB,DISK_GB}` clamps, and `ttlMinutes = HOSTED_EVALS_MAX_RUN_MINUTES` on every sandbox, so a crashed client can't leak one past the cap. `autoStopInterval` stays 0: a running command doesn't count as activity.
- **The sandbox cap needs two things, because Harbor creates trials concurrently.** Every create (trial and orchestrator) goes through `sandboxes::create`:
  - **A per-project lock** (`hosted_evals_capacity_lock:{project}`) is held across the count and the create. Without it, a burst of 8 creates with a cap of 3 got 8× `201`.
  - **A recent-creates record** (`hosted_evals_recent_sandboxes:{project}`). Daytona's `GET /sandbox` is eventually consistent: a new sandbox shows up about 1 s after the create returns, so the lock alone still let all 8 through. Creates from the last 15 s that the list doesn't show yet are added to the count.
  - Deleted sandboxes drop out of the list, so a recent create missing from it may already be gone; counting it errs on the safe side.
  - Daytona answers a create in about 100 ms, so a burst queues for seconds. The lock's 90 s TTL outlives one list plus one create (30 s client timeouts each). Past 60 s of waiting the request gets a `429` (`CapacityBusy`), which `lmnr_hosted_env.py` retries.
  - If the cache errors, creates proceed unlocked (the cap is best-effort) rather than failing.
- **Remote runs mint their own key**: `lmnr-internal-evals-<UTC timestamp>` (`RUN_KEY_NAME_PREFIX`), full (the plugin needs `/v1/evals`), expiring with the TTL, deleted if the launch fails. The frontend's `getApiKeys` hides the prefix: keep the two constants in sync. The key is visible to user code in the orchestrator, which is fine: it only reaches the project that started the run.
- **The orchestrator command** (`ORCHESTRATOR_COMMAND`) goes through the provider's generic `start_command`, so it runs under `sh` (no bash-only syntax) with `exec 2>&1` folding stderr into the command log. The npm spec goes through env (`LMNR_CLI_PACKAGE`) rather than being spliced into the command; `cliVersion` must be plain semver characters. It self-deletes through `DELETE /v1/hosted-evals/sandboxes/$LMNR_SANDBOX_ID` (exported, shell-quoted, in front of the command) with the run key, however the run ended. The default snapshot (`daytonaio/sandbox:0.8.0`) ships node 25, npx and uv; 1 vCPU / 1 GB.
- **Harbor semantics to remember when debugging trials:** a task with its own `environment/Dockerfile` (and no `docker_image`) does NOT get `environment/` uploaded after start; its Dockerfile must `COPY` the case data. The Laminar plugin exports spans over gRPC (port 8443 unless `--pk grpc_port=`; the CLI forwards `LMNR_GRPC_PORT`), datapoints over HTTP.

## Testing locally

- Uploads need S3: `uvx --from 'moto[server]' moto_server -p 9100`, create the bucket, and start the app-server with `AWS_ACCESS_KEY_ID=test AWS_SECRET_ACCESS_KEY=test AWS_ENDPOINT_URL=http://127.0.0.1:9100 S3_EXPORTS_BUCKET=<bucket>`. moto's `list-objects-v2` omits `KeyCount`.
- Point the scratch project's `.env` at the local server (`LMNR_BASE_URL=<server or its tunnel>`; `LMNR_GRPC_PORT=8001` for local-mode traces). Without a CLI login `--remote` falls back to `LMNR_PROJECT_API_KEY`, which exercises the key routes.
- Remote runs need the app-server reachable from Daytona: a cloudflared quick tunnel (`cloudflared tunnel --url http://localhost:8000`, binary from GitHub releases) as `HOSTED_EVALS_LMNR_BASE_URL`, and an unreleased CLI via `HOSTED_EVALS_CLI_PACKAGE=<url of a pnpm-packed tgz>` (serve it through a second tunnel). This host caches the DNS miss for a brand-new trycloudflare hostname for a while; Daytona resolves it fine. Traces from remote runs don't reach a tunnelled local server (gRPC), datapoints do.
- Cross-project checks need a key for a second project: insert an expiring `lmnr-internal-evals-*` row for another project and delete it afterwards.
- The Daytona org is shared with other workloads: delete only sandboxes you created (filter by `lmnr-project-id`) and snapshots named `lmnr-<project hex>-<16 hex>-…` you created. A test with `HOSTED_EVALS_REGISTRY_URL` also leaves a `lmnr-hosted-evals` private-registry entry pointing at the tunnel. Delete it by matching the tunnel URL, never the name: deployments sharing the org have their own `lmnr-hosted-evals` entries for their ECR host (deleting one costs that deployment nothing but a re-create on its next snapshot).
- **Real Docker for the push path:** this sandbox has none, but Docker-in-Docker works in a Daytona sandbox (`FROM docker:27-dind` + `apk add nodejs npm` + uv; start `dockerd` in a command). The app-server no longer creates sandboxes from a Dockerfile, so create it with Daytona's own `POST /sandbox {buildInfo: {dockerfileContent, contextHashes: []}, labels: {lmnr-project-id: <project>, lmnr-role: trial}}`: the labels let the local app-server's toolbox routes drive it. Daytona's build of that image took over 15 minutes once. Then upload the `pnpm pack`ed CLI and a scratch project through the files route, point the project's `LMNR_BASE_URL` at the tunnel, and run `lmnr-cli eval run` there, local mode included. `crane pull --format=tarball` writes a `docker save`-style archive for server-only checks without Docker.
- Never `pkill -f <pattern>` with a pattern that also appears in your own command line: it kills the shell running it. Stop test processes by PID.
