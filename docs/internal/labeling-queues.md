## Labeling Queue Items (ClickHouse)

- Queue metadata (`labeling_queues`) lives in Postgres; per-item rows (`labeling_queue_items`) live in ClickHouse as a `ReplacingMergeTree(updated_at)` keyed `(project_id, queue_id, id)` — see `frontend/lib/clickhouse/migrations/42_labeling_queue_items.sql`, which also creates the `labeling_queue_items_v0` SQL view. Registering a column for ad-hoc SQL takes TWO app-server files: the allowlist in `query_engine/validator.rs` AND the column/type/description metadata in `query_engine/schema.rs` (editing only the validator silently desyncs autocomplete + AI generation).
- **`edit` is the canonical current target; `payload` is the insert-time snapshot.** `edit String DEFAULT ''` is seeded equal to `payload.target` on insert by BOTH write paths (Rust `create_labeling_queues_items`, TS `pushQueueItems`) and overwritten by every UI PATCH, so readers never branch on "is `edit` empty?" and `dirty` is a value compare rather than a write-detector — which is what makes reverting an edit correctly drop the dirty flag. The public ingest API does not accept `edit`. Note the two frontend mirrors of this resolution disagree on their fallback: `getEffectiveTarget` (`components/queue/queue-store/helpers.ts`) falls back to `{}`, `effectiveTarget` (`lib/actions/queue/index.ts`) falls back to `null`.
- **All reads must use `FINAL`**; there is no `UPDATE`. `updateQueueItem` (`lib/actions/queue/items.ts`) is a read-modify-write that re-inserts with a fresh `updated_at`, and its narrow input surface deliberately omits `payload` — a caller that thinks it needs to write `payload` is bypassing the immutability invariant. **Caveat: the RMW does NOT preserve `idempotency_key`** — `insertQueueItems` hardcodes `""`, so every UI PATCH wipes it. (Harmless today: ids are derived deterministically, so a same-key retry still collapses.)
- **The frontend write paths MUST pass `async_insert: 0`** (`insertQueueItems`, `copyQueueItemsToDataset`). The shared CH client defaults to `async_insert: 1, wait_for_async_insert: 0` — it never waits at all — so an async write is not visible to the next `FINAL` SELECT, and the read-modify-write would see nothing and re-insert with default `createdAt` / empty `edit`, silently destroying the current target. The table is low-volume (interactive labeling), so synchronous inserts cost nothing. The Rust ingest path uses the client defaults and is fine — it only ever inserts.
- Idempotency is **deterministic id derivation**, not a pre-flight existence check (which leaves a race window between lookup and insert): `id = Uuid::new_v5(&queue_id, idempotency_key)`, so a retry lands on the same RMT sort key and collapses. Items without a key get `Uuid::now_v7()`. **Accepted trade-off:** a same-key retry arriving AFTER the user edited or approved reverts `edit`/`status` to the seed values, because the new write has the larger `updated_at`. Retries normally fire seconds after ingest, so this is rare — but `payload` is not frozen forever.
- **Cancel the pending debounced save before any approve / unapprove / discard / push** (`orchestrator.cancel(id)`; `cancelAll()` for push-all, since windowing means the client cannot enumerate every id). Without it a late `{status: 0}` PATCH lands after approve's `{status: 1}` and RMT last-write-wins silently reverts the approval — same mechanism resurrects a discarded row past its delete tombstone. For the same reason, window eviction must SKIP any id with a pending save (`orchestrator.hasPending(id)`) so a trailing PATCH can't fire against state we no longer hold. The save orchestrator tracks timers per-item-id (`queue-store/save-orchestrator.ts`) — do not collapse it into a single shared debounce, which drops item A's edit when the user tabs to B inside the window.
- **The `new` vs `modified` split is derived in FOUR places** that must agree, using TWO different comparison mechanisms. The three SQL copies — `PROGRESS_EXPR`, `getQueueItemStates` and `getQueueProgresses` (all in `lib/actions/queue/items.ts`; the third inlines its own copy rather than reusing `PROGRESS_EXPR`) — do a raw JSON-**string** compare, `edit = JSONExtractRaw(payload, 'target')`, so they are susceptible to key-order and whitespace drift if a write path ever serialises target keys in a different order (both current paths preserve insertion order). The frontend `deriveItemState` → `isDirty` (`queue-store/helpers.ts`) instead parses `edit` and `lodash.isEqual`s it **structurally** against `payload.target`, and treats empty `edit` as `new` where the SQL would call it `modified`. The frontend is therefore the more forgiving of the two: any serialisation drift shows up as a navigator bar (structural) disagreeing with the queues-table progress counts (string). Changing one mechanism requires changing the other.
- On queue deletion, call `deleteQueueItemsByQueueIds` BEFORE the Postgres `DELETE` — FK cascades only cover Postgres. Deletes are ClickHouse lightweight `DELETE` (a tombstone that `FINAL` reads respect).
- **Bulk push** (`pushItemsToDataset`, from `/push-to-dataset`) goes through `copyQueueItemsToDataset`, which copies server-side via `INSERT INTO dataset_datapoints SELECT … FINAL` so payload bytes never cross the wire, filters to `status = 1` unless `includeUnlabelled: true`, verifies the inserted count before deleting the source rows, and returns that count. Two traps: it returns **200 with `{pushed: 0}`** when nothing matched (e.g. unapproved `itemIds` without `includeUnlabelled`), so UI must gate local removal and success toasts on `result.pushed > 0`, not `res.ok`; and datapoint ids are minted in JS and non-deterministic while `dataset_datapoints` is plain `MergeTree`, so a retry after the verify-passed-but-delete-failed window WILL duplicate rows (the UI gates the button while in-flight and accepts this). The id filter is `toString(id) IN Array(String)` because binding `Array(UUID)` through `command` empirically did not match.
- **The single-item DELETE-with-`datasetId` branch is a SEPARATE implementation** — `removeQueueItem` (`lib/actions/queue/index.ts`) reads the one row, resolves `effectiveTarget` in JS, calls `createDatapoints`, then deletes. It does NOT reuse `copyQueueItemsToDataset`, so: `status` is ignored (an unapproved item is copied as-is), payload bytes DO cross the wire, there is no verify-before-delete, and it returns `{success: true}` rather than a count. Do not reason about this path from the bulk path's semantics.
- **Progress filters are evaluated cross-datastore:** `getQueues` partitions the incoming `?filter=` array, sends progress filters to `findQueueIdsByProgress` (CH `GROUP BY … HAVING`) and feeds the resulting ids into the Postgres query as `inArray(...)`, leaving name/id filters in the Postgres WHERE. **Limitation:** the `GROUP BY` only sees queues with ≥ 1 item, so `= 0` predicates never match empty queues (`approved = 0` means "has items, none approved"). If zero-comparisons-including-empty become a real ask, branch on the operator and add an inverse `NOT IN` query rather than UNION-ing the empty set in.
- Queue hotkeys (`components/queue/hotkeys.tsx`) are scoped **per shortcut** and all are gated on `!dialogOpen`. `⌘⏎` (approve/unapprove) sets `enableOnFormTags` + `enableOnContentEditable` so it fires inside CodeMirror and `<input>`s — it's the submit-and-advance key of the labelling loop. `⌘⌫` (discard), `⌘←`, `⌘→` deliberately use the DEFAULT scope so they do NOT fire from a focused editor; otherwise `⌘⌫` discards the item while the user is deleting a JSON line, and the arrows fight cursor-to-line-start/end. `Esc` blurs `document.activeElement` to escape the editor, and bails on `e.defaultPrevented` so it doesn't steal Escape from a Radix dialog or CodeMirror's search panel.
- `created_at` / `updated_at` are `DateTime64(3, 'UTC')`; model them in Rust as `u64` epoch millis.
