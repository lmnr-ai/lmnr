## Authentication (Better Auth)

- Auth is **Better Auth** (`better-auth`), not NextAuth. Central config is `frontend/lib/auth.ts` (`auth = betterAuth({...})`); the route handler is `app/api/auth/[...all]/route.ts` via `toNextJsHandler(auth)`. Client helpers live in `frontend/lib/auth-client.ts`; the server-session wrapper is `frontend/lib/auth-session.ts` (`getServerSession()` → `auth.api.getSession({ headers: await headers() })`, shape `{ user: { id, name, email, image } } | null`). Env: `BETTER_AUTH_SECRET` / `BETTER_AUTH_URL`, falling back to `NEXTAUTH_SECRET` / `NEXTAUTH_URL` for compat.
- The drizzle adapter uses `usePlural: true`. Better Auth core appends `"s"` to each model name when `usePlural` is set (`@better-auth/core` `getModelName`), so the jwt plugin's already-plural `jwks` model becomes `jwkss` (no such table → `/api/auth/jwks` 500s). Fix is the jwt plugin's `schema: { jwks: { modelName: "jwk" } }` so pluralization yields `jwks`. Any future plugin whose default model name is already plural needs the same singular-base override.
- Better Auth's adapter writes JS `Date` objects for timestamp columns. The better-auth tables (`sessions`/`accounts`/`verifications`/`jwks`) and the `users.created_at`/`updated_at` columns MUST be declared `mode: "date"` (not `"string"`) in `lib/db/migrations/schema.ts` or user/session creation fails with `ERR_INVALID_ARG_TYPE` (Date passed where string expected). This is a TS-serialization-mode change only — the Postgres column type is unchanged, so switching mode needs no new migration.
- JWTs come from the `jwt` plugin: `definePayload` emits `{ userId, name, email }`; endpoints `/api/auth/token` (signed EdDSA JWT) and `/api/auth/jwks` (public key set). Workspace-invite tokens are still plain `jsonwebtoken` signed with `BETTER_AUTH_SECRET ?? NEXTAUTH_SECRET` (`lib/actions/workspace/invite.ts`), verified the same way in `app/(auth)/invitations/page.tsx`. The invitation expiry window (7 days) is pinned in THREE uncoordinated places that must stay in sync: the JWT `expiresIn` in `invite.ts`, `INVITATION_EXPIRY_MINUTES` in the invitations page (checked against the DB row's `createdAt`, independent of the JWT), and the human-readable copy in `lib/emails/workspace-invite.tsx`.
- Client sign-in is unified through `signInWithProvider(provider, callbackURL)` in `auth-client.ts`: github/google use `signIn.social(...)`, while azure/okta/keycloak use `signIn.oauth2({ providerId })` (genericOAuth plugin; provider ids are `microsoft-entra-id`/`okta`/`keycloak`). `signOut()` takes NO `callbackUrl` — callers MUST `window.location.href = "/"` (or equivalent) themselves after it resolves.
- Sign-in provider button icons (`components/auth/auth-provider-buttons.tsx`) MUST be inline `currentColor` SVG components from `components/ui/icons.tsx` (e.g. `IconGoogleMono`/`IconMicrosoft`/`IconOkta`/`IconKeycloak`/`IconGitHub`), NOT `next/image` of `@/assets/logo/*.svg`. `next/image` renders an `<img>`, which CSS `color`/`text-*` cannot tint — so on the dark `bg-surface-200` button a black/`currentColor` asset is invisible. The wrapper `<div>` in `provider-button.tsx` sets `text-foreground-100`, which only reaches inline SVGs. Use the monochrome `IconGoogleMono` for the button, not the multicolor `IconGoogle` (the latter is still used in `components/playground/utils.tsx`).
- `signInWithProvider` MUST pass `errorCallbackURL` (set to `/sign-in?callbackUrl=<original>`) to BOTH `signIn.social` and `signIn.oauth2`. The inline `{ error }` the client returns only covers failures BEFORE the browser redirects to the IdP; once the OAuth round-trip happens server-side, a callback failure (account-linking gate, missing-email rejection) is handled by Better Auth's `redirectOnError` (`oauth2/errors.mjs`), which redirects to the OAuth state's `errorURL`. That `errorURL` comes from the sign-in body's `errorCallbackURL` (`oauth2/state.mjs`) and DEFAULTS to `${baseURL}/error` (i.e. `/api/auth/error`) when unset — so without it, IdP failures never land back on `/sign-in?error=<code>` and the sign-in page's `searchParams.get("error")` UI never fires. Better Auth appends `?error=<code>` (separator-aware) itself, so the page reads it directly.
- Passwordless local-email sign-in (self-hosted only) is a custom plugin in `lib/auth-local-email.ts` (`POST /api/auth/sign-in/local-email`), mounted only when `Feature.EMAIL_AUTH`. Pending-invitation processing runs in a `databaseHooks` `session.create.after` hook in `lib/auth.ts`. The plugin creates users with `emailVerified: true` (NOT `false`): Better Auth's account-linking gate (`requireLocalEmailVerified`, defaults `true` — `node_modules/better-auth/dist/oauth2/link-account.mjs`) refuses to link an OAuth identity to a user whose local email is unverified, so a `false` here would brick a later GitHub/Google sign-in for the same address. Local-email is a no-password convenience with no verification state to protect. `EMAIL_AUTH` and OAuth providers are normally mutually exclusive (`features.ts` hides the dummy email input when any provider is configured), so this only bites when `FORCE_EMAIL_AUTH=true` runs both at once.
- **`callbackUrl` is attacker-controlled and must be sanitized to a same-origin relative path** before any client navigation. The local-email flow signs in via a `$fetch` POST (`signInLocalEmail`) that returns JSON and does NOT redirect — navigation is a pure client-side `router.push(callbackUrl)` (`components/auth/email-sign-in.tsx`), so Better Auth's `trustedOrigins` (which only guards its own server-side OAuth redirects) never sees it. The trust boundary is the query string entering `app/sign-in/page.tsx` and `app/sign-up/page.tsx`; both call `sanitizeCallbackUrl(searchParams?.callbackUrl)` (`lib/utils.ts`), which rejects anything not starting with a single `/` (absolute `https://evil.com/x`, protocol-relative `//evil.com`, backslash `/\evil.com`, and `\t\n\r`-obfuscated variants browsers normalise) and falls back to `/onboarding`. A `new URL(callbackUrl)`-style check is NOT sufficient — it lets absolute external URLs through (open redirect). The sanitized value also feeds `signInWithProvider`'s `errorCallbackURL`, so OAuth is covered by the same page-level guard.
- `proxy.ts` middleware calls `auth.api.getSession({ headers: req.headers })` directly (no `withAuth`). Next.js 16 middleware runs Better Auth on the Node runtime, so the Postgres session lookup works there. The unauthenticated-redirect-to-`/sign-in?callbackUrl=` behaviour for app trees is replicated inline.
- **Migration backfill for existing users** (`0089_lam_1720_better_auth.sql`): adding `users.email_verified boolean DEFAULT false` is NOT enough on its own. Pre-existing users have a `users` row but no `accounts` row, so their first OAuth sign-in hits Better Auth's account-*linking* path in `handleOAuthUserInfo`, which is gated on `requireLocalEmailVerified` (defaults to `true`). With every migrated row at `email_verified = false`, that gate returns `"account not linked"` and bricks every existing user. The migration therefore runs `UPDATE users SET email_verified = true` right after adding the column — these users were already IdP-authenticated, so they're effectively verified. The `trustedProviders` list does NOT save them (it only exempts the separate `!isTrustedProvider && !userInfo.emailVerified` term).
- **The personal `api_keys` table is obsolete and unused.** It is NOT the project-level `project_api_keys` table (which app-server auth reads on every request). The user-level `api_keys` table is referenced by **zero** code in either backend (`app-server`, `lmnr-private`) — nothing ever reads it as a credential, and no personal key is created on sign-up. The physical table still exists in the DB (kept, not dropped) with its original non-unique `api_keys_user_id_idx` index — do NOT introduce code that writes to it. If you need a per-user credential, use `project_api_keys` patterns or design a fresh table.

## CLI authentication (BetterAuth Device Flow → user-scoped tokens)

- The CLI stores **BetterAuth tokens** (user-scoped), NOT a project API key. `lmnr-cli login` walks BetterAuth's native `deviceAuthorization` flow end-to-end (no custom poll endpoint). `lmnr-cli setup` does the same login AND additionally mints a project API key that it writes ONLY to `./.env` (never into `credentials.json`) via our `POST /api/cli/api-key` endpoint.
- **Token model:**
  - **Access token** = a 15m EdDSA JWT minted by `GET /api/auth/token` (with the session token as bearer) → response `{ token }`. Verifiable via `/api/auth/jwks`. This is what app-server will eventually validate statelessly (JWKS). App-server JWT validation is a deliberate LATER phase — the CLI's JWT is NOT accepted by app-server yet, so `lmnr-cli sql`/ingestion against app-server with the JWT does not work this iteration.
  - **Refresh token** = the BetterAuth **session token**, returned as `access_token` from `POST /api/auth/device/token`. Durable (session `expiresIn` default 7 days, rolling). Refresh op = re-call `GET /api/auth/token` with the session token → fresh JWT, no browser.
- Endpoints, in `login` flow order:
  - `POST /api/auth/device/code` — BetterAuth RFC 8628 code mint. CLI sends `{client_id:"lmnr-cli", scope:"projects:rw"}`.
  - Browser → `/device?user_code=<code>` — server component at `app/(auth)/device/page.tsx`. The `(auth)` layout + `proxy.ts` matcher gate unauthenticated visitors to `/sign-in?callbackUrl=/device?user_code=...`. Server-side: claim the code via `auth.api.deviceVerify(...)`, then render **Approve / Deny only** (no project picker — the credential is user-scoped, nothing to scope at approval). Approve → `authClient.device.approve({userCode})`; Deny → `authClient.device.deny({userCode})`.
  - `POST /api/auth/device/token` — BetterAuth's NATIVE token endpoint (we own no custom poll endpoint). CLI polls here; on approval returns `{ access_token (=session token), expires_in, ... }`.
  - `GET /api/auth/token` (session bearer) → `{ token }` 15m JWT.
  - `GET /api/auth/get-session` (session bearer) → `{ user: { id, email } }` for profile metadata.
- **`POST /api/cli/api-key`** (`app/api/cli/api-key/route.ts`) — mints a project API key for the session user (the `setup` flow is the only caller today, but the endpoint is generic, not setup-bound). Auth via session bearer (`auth.api.getSession`). Body (zod `.strict()`): `{ projectId?, deviceName? }`. With `projectId` → membership-check + mint. Without → 1 project mints; >1 returns `400 {error:"project_ambiguous", projects:[{id,name,workspaceName}]}`; 0 returns `400 {error:"no_projects"}`. Returns `{apiKey, apiKeyId, projectId, projectName, workspaceId, workspaceName}`. The minted key goes to `./.env` only.
- **The `bearer()` plugin is required.** `auth.api.getSession({ headers })` only accepts cookie-borne sessions by default; without `bearer()` an `Authorization: Bearer <session-token>` header is ignored. The device-flow `access_token` IS a session token, so the bearer plugin is what lets it round-trip through `getSession()` (used by `/api/auth/token`, `/api/auth/get-session`, and `/api/cli/api-key`).
- **CLI credentials shape.** `~/.config/lmnr/credentials.json` (mode 0600, **keyed by `userId`**, version 1) stores tokens only: `sessionToken` (refresh), `accessToken` (the 15m JWT), `accessTokenExpiresAt` (from JWT `exp`), `sessionExpiresAt?` (from device token `expires_in`), `issuer`, `baseUrl`, `userEmail?`, `userId`, `createdAt`, `lastUsedAt?`. NO project API key, NO `apiKeyId`. `resolveAuth` refreshes the JWT when within ~30s of expiry (re-mint via `/api/auth/token`); a 401 means the session expired → "run `lmnr-cli login`". The returned JWT bearer is not yet accepted by app-server (later phase).
- **Logout** best-effort POSTs `/api/auth/sign-out` (session bearer) to revoke the session server-side, then deletes local creds; `--all` loops all profiles.
- **App-server later phase (two-flow validation):** the eventual design is JWT-via-JWKS for the CLI (user-scoped — so app-server must derive the project from the request path / an explicit `--project` arg, since the JWT carries no project) and project API key for the SDK. Not implemented here.
- **`validateClient: async (id) => id === "lmnr-cli"`** in `lib/auth.ts`. Multi-tenant client registration is intentionally out of scope.

## Project API Key Expiration

- `project_api_keys` carries two extra columns (migration `0094`): `user_id uuid` (FK→`users` `ON DELETE SET NULL`, records the creating user for audit — NOT cached, no UI) and `expires_at timestamptz` (null = never). The app-server `ProjectApiKey` struct (`app-server/src/db/project_api_keys.rs`) maps ONLY `expires_at` (with `#[serde(default)]` so pre-existing cache entries written before the column decode to `None`); `user_id` is frontend-only and never read by app-server.
- **Lazy expiry + cleanup** lives in `get_api_key_from_raw_value` (`app-server/src/api/utils.rs`): after resolving the key (cache-hit OR DB-read path), if `expires_at.is_some() && Utc::now() > expires_at` it removes the cache entry, `DELETE`s the DB row by hash (`delete_api_key_by_hash`), and returns an error. The expiry check is on the COMMON path (not per-validator) so both `project_auth` and `project_ingestion_auth` enforce it. A future pg_cron sweep is hygiene-only, out of scope.
- **`GET /v1/project` is project-key authed (`project_auth`), registered inside the broad `web::scope("/v1")`.** The handler (`api/v1/projects.rs::get_current_project`) carries `#[get("/project")]` (full path on the macro). It blocks ingest-only keys (that's `project_auth`'s job) — fine because `lmnr-cli setup` doesn't probe it; the CLI is logged in by setup time and resolves the project via the user-token endpoint below.
- **`POST /v1/cli/project` (`api/v1/cli/mod.rs::resolve_project`) resolves which project a project API key belongs to, for `lmnr-cli setup`.** User-token authed (`CliUserAuth`, mounted in the `/v1/cli` scope wrapped by `cli_auth`): the API key travels in the JSON body (`{ apiKey }`), NOT in `Authorization` (which carries the user JWT). It calls `get_api_key_from_raw_value` to verify the key, then `is_user_member_of_project` so a leaked key can't reveal a project the user isn't a member of (401 on bad key, 403 on non-member). Returns `{ projectId }`. The CLI side is `CliResource.resolveProjectByApiKey` in `lmnr-ts` (returns a tri-state `ProjectKeyProbe`: `ok`/`invalid` (401)/`unverifiable` (403/network/other)).
- **CLI-minted keys (`POST /api/cli/api-key`) have `expiresAt: null`** — both the explicit-`projectId` branch and the single-project fallback. A setup key that silently expired would break ingestion with no renew UI. The minting `userId` is always recorded.
- Frontend expiration UI is days-based: the dialog (`generate-key-dialog-content.tsx`) offers 1/7/30/365/Never; the route (`api-keys/route.ts`) converts `expiresDays` → absolute `expiresAt` ISO string. **The default-expiry preselection is frontend-only UX** (`handleKeyTypeChange` in `project-api-keys/index.tsx`): ingest-only keys preselect 1 day, default keys preselect 30 days. The backend has no per-key-type default; a CLI key explicitly passes `expiresAt: null`.
- The frontend `createApiKey` action caches the new key with `{ expireAt: new Date(expiresAt) }` (matching app-server's 1-day TTL ceiling) and deliberately omits `userId` from the cached payload.
