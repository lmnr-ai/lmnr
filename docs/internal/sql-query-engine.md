## In-process Query Engine (SQL validation + JSON↔SQL)

- SQL validation and JSON↔SQL conversion run **in-process inside app-server** (`app-server/src/query_engine/`), built on the `sqlparser` crate (`ClickHouseDialect` + `visitor` feature). Keep these three operations in-process — no network hop.
- `QueryEngine` is a plain struct (`query_engine/mod.rs`) with three inherent async methods: `validate_query`, `sql_to_json`, `json_to_sql`. Consumers hold `Arc<QueryEngine>`: HTTP routes (`routes/sql.rs`) and the MCP `query_laminar_sql` tool (`api/v1/mcp.rs`).
- **The validator IS a security boundary**, not just a linter — it is the only thing standing between user SQL and ClickHouse. It enforces SELECT-only, rejects `BLOCKED_FUNCTIONS` and the `project_id` column, blocks non-allowlisted tables, and rewrites allowlisted table refs to project-scoped `_v0` views (e.g. `spans` → `spans_v0(project_id = '<uuid>')`, `traces` → `traces_v0(project_id=…, start_time=…, end_time=…)`). `json_to_sql`'s raw-expression path is also a security boundary. Preserve their rejection semantics when editing.
- **The rewriter derives view arguments from the user's `WHERE`, and a predicate it cannot prove must widen, never narrow.** Several views take more than `project_id`: `traces_v0` takes `min_start_time`/`max_start_time`; `evaluation_datapoints_v0` takes those plus `eval_ids: Array(UUID)` (see ClickHouse migration 63); and `signal_events_v0`/`signal_events_all_v0`/`event_clusters_all_v0` take `signal_ids: Array(UUID)` (ClickHouse migration 65) so the internal `signal_event_summaries` scan they each do can prune on that table's `(project_id, signal_id, ...)` sort key instead of reading every signal in the project. All arguments are **mandatory** — ClickHouse parameterized views have no defaults, and omitting one fails the query with `Code: 456, Substitution 'x' is not set` — so the rewriter always passes all of them, using sentinels when it has nothing: the epoch defaults `1970-01-01`/`2099-12-31` for bounds and `[]` for `eval_ids`/`signal_ids`, which each view reads as "no filter" (`empty({eval_ids:Array(UUID)}) OR evaluation_id IN {eval_ids:Array(UUID)}`, same shape for `signal_ids`/`signal_id`). Users neither pass nor see these; hand-calling a `_v0` function is rejected, and none of `evaluation_datapoints`/`signal_events`/`signal_events_all`/`event_clusters_all` are usable as table functions. `extract_bounds` (ranges) and `extract_scalar_ids` (equality/`IN` sets, column-parameterized — `eval_ids` passes `"evaluation_id"`, `signal_ids` passes `"signal_id"`) share the boolean rule that makes this safe: under `AND` either branch's restriction holds, under `OR` one holds only if *both* branches supply it. So `evaluation_id = X OR index > 5` must widen to `[]` — narrowing it would silently drop the `index > 5` rows. Same for `!=`, `NOT IN`, a value referencing a per-row column (it cannot become a scalar view argument), and a qualifier naming another relation. A `{name: Array(...)}` bind after `IN` parses as a one-element list; pass it through as-is — wrapping it in `toUUID` produces `eval_ids = [toUUID(<array>)]`, which ClickHouse rejects. Widening only costs scan time; narrowing wrongly is a correctness bug, so when adding a predicate shape, add a `test_eval_ids_widen_to_sentinel_when_unsafe`/`test_signal_ids_widen_to_sentinel_when_unsafe` case alongside it.
- **`ARRAY JOIN` right-hand sides are validated as columns, and only then skipped.** `sqlparser` models `... ARRAY JOIN clusters AS cluster_id` as a `TableFactor::Table`, but `clusters` there is an array *column* of the joined relation. `collect_array_join_operands` (`validator.rs`) records the source span of each such occurrence, and `args` then decides how much of the pipeline looks away — a skipped node is neither allowlist-checked nor project-scoped, so the two cases must not get the same treatment:
  - **A bare name (`args.is_none()`)** is skipped by all three passes (`TableColumnChecker`, `ViewRewriter`, `PostRewriteChecker`), so it survives verbatim instead of becoming `clusters_v0(...)`. That is only sound for an identifier `resolve_array_join_column` proves is a column of a relation in scope — the `FROM` item's left relation plus its non-array joins. A qualified name (`t.tags`) is allowed **only** when the qualifier matches an alias or table name in that same `FROM` item; that is what distinguishes it from `default.spans`, which has the identical shape and is rejected. Full exemption is needed even for the qualified form, since the rewriter matches on the *last* name part and would otherwise rewrite `t.spans`.
  - **A function call (`args.is_some()`)** such as `splitByChar(',', name)` is an expression over the row's own columns. Only `TableColumnChecker` looks away; `ViewRewriter` and `PostRewriteChecker` gate their skip on `args.is_none()` and so still visit it. Keeping the rewriter in play is deliberate — it is what still rejects `ARRAY JOIN spans(1)` and still project-scopes tables nested in the arguments. Because the allowlist no longer guards this position, **`BLOCKED_FUNCTIONS` is the only thing left standing between a table-function name and ClickHouse here**, so it has to cover every table function that reads another table by name (`merge`, `loop`, `dictionary`, `view*`, `mergeTree*`, `timeSeries*`, `prometheusQuery*`) as well as every one that reaches off-box (`s3`, `url`, `iceberg*`, `deltaLake*`, `hudi*`, `paimon*`, `arrowFlight*`, `hive`, `ytsaurus`, the `*Cluster` variants). The blocked-function scan is never span-exempt. Derive that list from `system.table_functions` (it was last checked against 26.4) and re-check it when bumping ClickHouse — the `mergeTree*` family alone went from one function to six in three releases. Families go in `BLOCKED_FUNCTION_PREFIXES`, with two traps: never prefix `view` (the scan also sees CTE references, so it would reject a CTE named `view_data`) and never prefix `timeSeries` (30-odd legitimate scalar/aggregate functions share it, two of which extend `timeseriestags`) — those two are exact-matched.

  Two supporting invariants: `relation_name_span` refuses `Span::empty()`, because idents the rewriter synthesizes (every `_v0` view name) carry it and one exempted operand would otherwise exempt all of them. And when a relation in scope is a CTE or subquery its columns are unknown, so an identifier is accepted but must never be an allowlisted table name. A `TableFactor::Derived` right-hand side is deliberately left unrecorded so the rewriter still scopes tables inside it. Adding an array column to a `_v0` view therefore also requires adding it to `TableRegistry`, or `ARRAY JOIN` on it is rejected.
- **The frontend JSON contract is binding**: route response/request types use `#[serde(rename_all = "camelCase")]` and must keep matching `frontend/lib/actions/sql/types.ts` (e.g. `queryStructure`, `validatedQuery`). The `fn`/`column`/`args`/`alias` metric shape and `dimensions` array are the camelCase wire format the chart builder + SQL editor depend on.
- Tests live in `validator/tests.rs`, `json_to_sql/tests.rs`, and `sql_to_json/tests.rs`. Run with `cargo test --bin app-server query_engine -- --nocapture`. When changing validator/conversion behavior, update the corresponding test rather than relaxing the assertion.
- **`executeQuery` (`frontend/lib/actions/sql`) routes through this validator** — it POSTs to app-server's `/projects/{id}/sql/query`, so any frontend server action that builds ClickHouse SQL is constrained by the validator (SELECT-only, allowlisted-table-only) AND requires app-server HTTP (8000) to be reachable. To aggregate the `scores` JSON-string map on `evaluation_datapoints` (a ReplacingMergeTree → query with `FINAL`), do NOT use a CH-side tuple `ARRAY JOIN JSONExtractKeysAndValues(scores, 'Float64')` aggregate (the validator rejects the tuple element access `kv.1`/`kv.2`). Instead `SELECT` the raw `scores` strings and average per `(evaluation_id, name)` in JS — the same pattern as `getEvaluationTimeProgression` in `frontend/lib/clickhouse/evaluation-scores.ts` and `getScoreAveragesByEvaluationIds` in `frontend/lib/actions/debugger-sessions/index.ts`.
- **All parsing goes through `parse_clickhouse_sql` in `validator.rs`, NOT `Parser::parse_sql`** — it carries two workarounds for upstream `sqlparser` over-strictness: (1) a token-stream rewrite (`wrap_in_placeholder_lists`) that parenthesizes a `{param}` placeholder list after `IN`/`NOT IN`, and (2) a custom `ClickHouseOptionalIntervalDialect` newtype wrapping `ClickHouseDialect` that flips `require_interval_qualifier()` to `false` so `interval '1 day'` (unit inside the string literal, valid in ClickHouse/Postgres) parses. Don't "fix" the interval case at the token level — synthesizing a trailing unit token makes `Interval`'s `Display` emit `INTERVAL '1 day' SECOND` and corrupt the SQL; only the dialect flag yields `leading_field: None` which round-trips verbatim. The wrapper MUST override `dialect()` to return `self.0.dialect()` (ClickHouseDialect's `TypeId`) or `dialect_of!(self is ClickHouseDialect)` checks inside the parser (parametric aggregates like `quantile(0.9)(duration)`, etc.) silently take the non-ClickHouse path. When bumping the `sqlparser` crate, re-check the wrapper's hand-delegated method list against `ClickHouseDialect`'s overrides.

## SQL Editor Schema (autocomplete + AI generation)

- `frontend/components/sql/utils.ts` (`tableSchemas`, `enumValues`) is the frontend source of truth for the SQL editor's autocomplete AND for the schema embedded in the AI-generation system prompt (`frontend/lib/actions/sql/prompts.ts` consumes both). Backend allowlist lives in `app-server/src/query_engine/validator.rs` → `TableRegistry::new`; the two MUST stay in sync — adding a column to the v0 view + the registry without updating `tableSchemas` leaves it absent from autocomplete and invisible to the AI generator. There is a FOURTH, unrelated copy: `components/dashboards/editor/table-schemas.ts` is the chart builder's own column list, which nothing cross-checks — a column REMOVED from a view (migration 65 dropped `signal_events.summary`) has to be deleted there too, or the builder keeps offering it and generates a chart query that fails in ClickHouse.
- `app-server/src/query_engine/schema.rs` (`build_schema_prompt()`) is the single backend source of truth for the SQL schema surfaced to BOTH the MCP `query_laminar_sql` tool description (`api::v1::mcp`, injected at construction in `tool_router_with_descriptions` — NOT from the `#[tool]` doc comment) and the signals-gated Platform Agent prompt (`lmnr-private` `agent::prompts`). It must mirror `validator.rs`'s `TableRegistry` and the frontend `tableSchemas`/`enumValues`; drift breaks generation. The file is PUBLIC (no signals gating) even though its only OSS caller is the MCP tool — `query_engine/mod.rs` declares `pub mod schema;` unconditionally.
- Columns whose runtime CH type is `String` but whose values are constrained (status, span_type, trace_type, signal_runs.status / .mode) carry an `enumType: keyof typeof enumValues` field. The prompt builder appends `Allowed values: '...'` to the column's description, and the editor's `<column> = ` autocomplete filters to those literals. Without `enumType`, the model invents values (e.g. `status = 'OK'` when nothing pins the status column to `'success' | 'error'`).
- `enumValues` is keyed by enum NAME, not column name. A single column can map to one enum (`spans.status` → `status`) or different enums in different tables (`signal_runs.status` → `signal_run_status`). The autocomplete `columnEnumMap` is built by walking `tableSchemas` once at module load, so column→enum wiring stays declarative — never add column names to a hardcoded regex; just set `enumType` on the schema entry.
- The `clusters_v0` view (CH migration; latest is `65_trace_signal_clusters.sql`) intentionally does NOT expose `centroid` — the embedding vector is an internal `Array(BFloat16)` on `signal_event_clusters`, useless over SQL and expensive to ship. When recreating the view in a new migration, keep the `WHERE level > 0` L0 filter and the 9 user-facing columns (id, signal_id, name, level, parent_id, num_signal_events, num_children_clusters, created_at, updated_at). `clusters` is in `tableSchemas` (autocomplete + AI + docs); `signal_events_all` stays registry-only (queryable) and is intentionally NOT in `tableSchemas`. **`path` is deliberately NOT exposed** — the ancestor chain is internal machinery, the thing that expands a trace's leaf-only `cluster_ids` into leaf + ancestors inside `traces_v0`/`signal_events_v0`/`signal_events_all_v0`/`event_clusters_all_v0`. It lives only as a `clusters_dict` attribute, computed by walking `parent_id` recursively at dict load time and stored nowhere on disk. Callers get the ancestors as their own rows/elements and walk between them with `parent_id`, so re-adding `path` to the registry or `tableSchemas` would publish an internal detail (and, being an array column, would also make `ARRAY JOIN path` legal on `clusters`). `signal_events_v0` resolves membership through `signal_event_summaries` + `clusters_dict` (not a `FINAL` join to `events_to_clusters`). `traces` exposes `signal_events` and `clusters` the same way. `signal_events` carries the full event `payload`, so it must be listed in both `schema.rs` and the `traces` `allowed_columns` in `validator.rs` — a column in one but not the other either stays invisible to autocomplete or passes validation and then fails in ClickHouse.
- **The two other agent-facing surfaces now DERIVE their table lists — don't hand-edit them.** The MCP `query_laminar_sql` description composes `MCP_SQL_INTRO` + `build_schema_prompt()` + `MCP_SQL_EXTRAS` (`app-server/src/api/v1/mcp.rs`; only the joins/parameters/examples prose is MCP-specific), and the CLI `sql` help renders the server's `SqlSchema` response (`lmnr-ts/packages/lmnr-cli/src/commands/sql/schema.ts`, descriptions dropped). So the sync set for a new SQL-exposed table/column is FOUR places: `validator.rs` `TableRegistry` (execution gate), `schema.rs` `build_schema_prompt()`/`schema_payload()` (MCP + agent + CLI), `tableSchemas` in `components/sql/utils.ts` (SQL-editor autocomplete + AI generation — `createExtensions` builds its CodeMirror completion source from it, so there is no second autocomplete list to update), and `components/dashboards/editor/table-schemas.ts`, a DIFFERENT object that also happens to be called `tableSchemas` and drives the chart builder's metric / group-by pickers (`getAvailableColumns` filters it to `type: "number"` for sum/avg/min/max/quantile). The chart-builder list is the one that drifts — it is easy to miss precisely because of the name collision. A new `spans`/`traces` column additionally needs the CH migration to add it to the `_v0` view, or the registry entry references a column the view doesn't expose.

## SQL Editor Results Table

- The Table tab renders through `frontend/components/sql/results-table.tsx`. It owns three UX behaviours: per-cell hover copy button (copies the FULL raw value — display uses CSS truncate against the column width), the row-count indicator data (rendered in `editor-panel.tsx` next to the tabs from `results.length`), and column-width persistence.
- Column widths persist to localStorage keyed `sql-results-column-sizing-<projectId>-<templateId>`. Same pattern as chart-builder's `table-chart`: seed `defaults` (with `columnOrder` + stored `columnSizing`) at `InfiniteDataTableProvider` creation, and a thin `ColumnSizingPersistence` child (like `ColumnConfigEmitter`) writes changes back. Writes replace the stored map with the current result's `columnSizing` (prunes keys from prior query shapes — draft keys especially would grow forever under a merge). The provider remounts on every query run (loading unmounts the tree) — persistence is what carries widths across re-runs; don't lift the provider above `renderContent` to "fix" the remount.

## SQL Editor Autosave (query vs. name)

- `PUT /api/projects/[projectId]/sql/templates/[templateId]` takes `name` and `query` as INDEPENDENT optional fields (`UpdateSqlTemplateSchema` refines that at least one is present; `updateSqlTemplate` spreads only the ones that are defined). Two different UI paths write the row — the editor's autosave (`query`) and the sidebar's inline rename (`name`) — so each sends only the field it owns. Sending the whole template from either side is what made "type, then rename immediately" silently discard the typing: the rename PUT carried the SWR list's stale `query`.
- Autosave state (pending payload, debounce timer, in-flight promise) lives at MODULE scope in `components/sql/sql-editor-store.ts`, not in a component. The old `useMemo(() => debounce(...), [autoSaveTemplate])` rebuilt itself whenever the template name changed and `cancel()`ed the pending call on cleanup, so a rename or a remount dropped the queued keystrokes. Module state has exactly one lifetime (the tab's) and the only way out is a completed PUT: `runSave` serializes PUTs of the same template (awaits the in-flight one, then re-runs) and re-queues the payload on failure so the next flush retries instead of losing the edit.
- **All of that state is `Map`s keyed by template id, never single slots.** Switching queries only fire-and-forgets the previous one's flush, so two templates can legitimately have work outstanding at once: with one global slot, a failed PUT for the query you just left is dropped by (`??=`) a pending edit on the query you moved to, and its `setStatus` relabels the indicator of a query it does not belong to. `setStatus(templateId, …)` therefore no-ops unless `currentTemplate.id` matches.
- `unconfirmedQueries` (also keyed by id) holds text this tab typed but has not seen persisted. The templates list only catches up when the PUT resolves and patches SWR, so switching away and straight back inside that window would otherwise reload the pre-edit query from the cache — and the next keystroke would then save it back over the edit that just landed. `selectTemplate` prefers the unconfirmed text over the list copy; the entry is deleted once a save of that exact string succeeds (a newer edit typed mid-flight stays unconfirmed).
- Every path that can lose the debounce window flushes explicitly via `flushQuerySave()`: rename (in `query-item.tsx`, before the name PUT), running the query, switching templates (`selectTemplate`), and `visibilitychange` / `pagehide` / unmount in `template-editor.tsx` (those pass `{ keepalive: true }` so the request survives the page going away). Delete is the one path that must NOT flush — `sidebar.tsx` calls `discardQuerySave(id)` first, because navigating away from a deleted row otherwise PUTs a missing id and `updateSqlTemplate` throws `SQL template not found` (an error toast for a query the user just removed).
- After a successful query PUT the store patches the templates SWR cache (`/api/projects/<id>/sql/templates`) with `revalidate: false`. That cache is what the sidebar rows read, so skipping the patch leaves rename (and anything else reading a row) holding a query the server no longer has. `selectTemplate` keeps the editor's local `query` when the list revalidates into the SAME template id — otherwise a background revalidation overwrites in-flight keystrokes with the server copy.

## SQL Editor Chart Tab (persisted chart config)

- The chart builder persists `chartConfig` per query (`persist`, localStorage key `sql-chart-builder-<templateId>`), so a stored `x`/`y` outlives the SELECT list that produced it. Editing the query (renaming a metric, commenting a column out) used to leave the config pointing at a column that no longer exists, and `ChartRendererCore` bailed to `{chartData: [], keys: ∅}` → the misleading "No data during this period" with rows visible in the Table tab. `reconcileChartConfig` (`components/chart-builder/utils.ts`) drops selections whose columns are gone (or are no longer eligible for that axis) and re-derives defaults; it runs at `persist.merge` (rehydration), on every `syncSource` (new rows from a re-run — the store is created once, so the provider's `useEffect` is what feeds it) and on chart-type change.
- `pickDefaultAxes` prefers a time-like dimension by name (`t`, `ts`, `start_time`, `hour_bucket`, …) for the category axis and the first numeric column for the metric, then SWAPS them for `HorizontalBarChart`, where `x` is the value and `y` the category (`canSelectForXAxis` enforces the numeric side). A config is only ever empty when the result set has no usable pair, so a fresh query renders a chart without touching the controls.
- `ChartBuilder` is keyed on `storageKey` — `persist` captures its key when the store is created, so reusing one store across saved queries reads one query's config and writes it under another's. `editor-panel.tsx` passes `resultsTemplateId` and `resultsQuery`, the template and SQL that PRODUCED the rows, never the selected template or the live editor text: the store's `query` is what "Export to dashboard" posts (`export-chart-dialog.tsx`), so pairing it with another query's axes creates a dashboard chart whose config does not match its SQL.

## Rate Limiting (SQL + data ingestion)

- Two independent per-project limiters, gated by separate features: `Feature::RateLimiter` (`REDIS_URL` + `RATE_LIMIT` + `RATE_LIMIT_PERIOD_SECS`) covers the SQL surface; `Feature::IngestionRateLimiter` (`REDIS_URL` + `INGESTION_RATE_LIMIT` + `INGESTION_RATE_LIMIT_PERIOD_SECS`) covers trace ingestion on BOTH transports (gRPC + HTTP `/v1/traces`). Env names live in `app-server/src/env/rate_limit.rs`. The ingestion limit applies to every project by default (no per-project opt-in).
- **SQL** (`/v1/sql/query` + CLI twin `/v1/cli/sql/query`): `SqlRateLimiter` (`api/v1/sql.rs`) wraps a shared `actix_limitation::Limiter` (the env-default N/T) — counted inline in `handle_sql_query` with key `ratelimit:{project_id}`, not scope middleware, because `project_id` is only known after the auth extractor runs. A per-project N override read from cache on every request (`sql_rate_limit:{project_id}`, plain integer set out-of-band via `valkey-cli SET`, no app writer) swaps in an ad-hoc `Limiter` built with that N and the global period. Only N is overridable; T is global (`RATE_LIMIT_PERIOD_SECS`). Constant in `cache/keys.rs`. A changed N applies immediately; the window itself is actix-limitation's fixed window (counter key `ratelimit:{id}` with TTL set on window start — `DEL` it to reset early). Accepted trade-off shared with the ingestion limiter: the crate opens a fresh Redis connection per `count()`, outside `ResilientRedisConnection`; migrating to the shared-cache counter is planned.
- **Data ingestion:** `IngestionRateLimiter` (`traces/rate_limit.rs`, mirrors `SqlRateLimiter`) counts ONE shared quota key `ingestion_ratelimit:{project_id}` from both the gRPC path (`ProcessTracesService::export` in `traces/grpc_service.rs`, threaded as `Option<Arc<IngestionRateLimiter>>` through `::new` since tonic has no actix-style middleware; exceeded → `Status::resource_exhausted`) and the HTTP path (`api/v1/traces.rs::process_traces`, injected as `web::Data<Option<Arc<IngestionRateLimiter>>>`, checked before payload decode; exceeded → 429) — so neither transport can bypass the other. Per-project overrides in cache (plain integers via `valkey-cli SET`, no app writer, take precedence over the env defaults): `ingestion_project_rate_limit:{project_id}` for N AND `ingestion_project_rate_limit_period:{project_id}` for the window seconds — unlike the SQL limiter, the period is also overridable; either key can be set independently, the other falls back to the global default. Only `POST /v1/traces` is limited — `traces/metadata`, `/v1/spans`, `/v1/browser-sessions` etc. are not.
- Posture is fail-open on Redis/cache errors everywhere (logged, request allowed), so a Redis blip can't black-hole ingestion or SQL.
- **Rollout gotcha:** the unit is requests (OTLP export batches) per window, not spans/bytes — pick `INGESTION_RATE_LIMIT` high enough for the largest legitimate SDK batch cadence, then clamp offenders down via the per-project cache key.
- **Ingestion rejections are logged at `warn` from `check` (LAM-2111), and that is the ONLY per-project record of a gRPC 429** — the tonic server has no request logging at all (`main.rs`'s `Server::builder()` has no `.layer()`/interceptor), and actix's `Logger` records the HTTP 429's status but carries no `project_id`. Fields: `project_id`, `transport` (`grpc`/`http` via the `IngestionTransport` label arg), `limit`, `period_secs`, `reset_epoch_utc`. Keep it `warn`, not `error` — see the Sentry `event_filter` note under self-tracing; `error` would page on ordinary customer rate-limiting. `limiter_for_project` returns `(Limiter, u64)` because `actix_limitation::Status` exposes the effective N and `reset_epoch_utc` but NOT the window, and the period is per-project overridable, so a logged limit is uninterpretable without it. Allowed requests are deliberately NOT logged (16/s/project × the fleet is real volume) — so these lines give you the 429 numerator with no denominator.
- **Testing the reject path needs a fake Redis, not the in-memory `Cache` fallback.** `actix_limitation` opens its own connection from the URL per `count()` (`get_tokio_connection`), entirely outside `Cache`/`ResilientRedisConnection` — so `Cache::InMemory` does nothing for it and there is no way to force `LimitExceeded` without a server on the wire. A ~20-line `tokio::net::TcpListener` speaking RESP works: the crate sends one `MULTI`/`SET NX EX`/`INCR`/`TTL`/`EXEC` pipeline, so reply `+OK\r\n+QUEUED\r\n+QUEUED\r\n+QUEUED\r\n*3\r\n+OK\r\n:<count>\r\n:<ttl>\r\n` with `count` above the limit. Note `log::warn!` is a silent no-op under `cargo test` unless you install a logger, so assert on captured records via a `log::Log` impl rather than trusting `--nocapture` output.

## Ad-hoc SQL Endpoint Guards (`/v1/sql/query`)

- Per-query ClickHouse settings (`max_execution_time`, `max_result_bytes`, `max_memory_usage`) are applied in `app-server/src/sql/ch.rs` via `.with_setting(...)`, env-tunable through `app-server/src/env/sql.rs` (`SQL_QUERY_*`). They are tamper-proof: the query-engine validator strips any inline `SETTINGS` clause from user SQL, so a client can't override the server-applied caps.
- `max_memory_usage` (OOM protection — the lever that actually kills CH, not bytes scanned) is gated by `SqlQuerySource` (`sql/mod.rs`), threaded `execute_sql_query` → `route_and_run_query` → `ch::query`. It's applied ONLY for `SqlQuerySource::Public` (the internet-facing `/v1/sql/query`, CLI `/v1/cli/sql/query`, and the MCP query tool); the trusted frontend route (`routes/sql.rs`) and internal callers (`datasets/service.rs`, `sql/queries.rs`) pass `Frontend` and run uncapped. Default `SQL_QUERY_MAX_MEMORY_USAGE=0` means unlimited, so self-hosters are unrestricted unless they opt in. When adding a new caller of `sql::execute_sql_query`, pick the source deliberately.
- **Every ClickHouse `BadResponse` on this endpoint logs at `warn`, never `error`** — they are all client errors (malformed SQL, and `MEMORY_LIMIT_EXCEEDED`/code 241 alike), and `error` puts them in Sentry, which is pure noise at customer volume (same reasoning as the ingestion rate-limit log above). Code 241 keeps its own branch in `ch::query` only so the line can carry `project_id` + the query (truncated to 4096 chars) as a capacity signal; the classification matches the `Code: 241` prefix, not a `MEMORY_LIMIT_EXCEEDED` substring, because CH echoes user SQL back inside syntax errors (unit-tested).
- Settings only apply on the CLOUD deployment path; HYBRID forwards the raw query to a remote data plane (`sql/data_plane.rs`) which runs its own CH and is not covered by these caps.
- **Lazy materialization is set explicitly only because of `compatibility = 24.6`.** ClickHouse enables `query_plan_optimize_lazy_materialization` by default from 25.4 on, and the companion `query_plan_max_limit_for_lazy_materialization` shipped at 10, became 100 in 25.11 and 10000 in 25.12. Cloud production runs a 26.4 server with `compatibility = 24.6`, which resolves every default to its pre-25.4 value: the optimisation is **off** and the threshold is 10, below the `LIMIT 50` our list pages use. So `ch::query` sends both (`SQL_QUERY_MAX_LIMIT_FOR_LAZY_MATERIALIZATION`, default 10000). Keep the default aligned with ClickHouse's own: a lower value would *reduce* the ceiling on a current server (self-hosted compose pins 26.5) and silently disable the optimisation for `LIMIT`s between our value and 10000. Setting the var to `0` skips both — mandatory on ClickHouse older than 25.4, where the settings do not exist and an unknown setting fails the query. The frontend's ClickHouse client (`frontend/lib/clickhouse/client.ts`) reads the same var name for the queries that bypass this engine; there the escape hatch also protects the boot-time migrations that share the client.
