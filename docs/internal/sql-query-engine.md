## In-process Query Engine (SQL validation + JSON↔SQL)

- SQL validation and JSON↔SQL conversion run **in-process inside app-server** (`app-server/src/query_engine/`), built on the `sqlparser` crate (`ClickHouseDialect` + `visitor` feature). Keep these three operations in-process — no network hop.
- `QueryEngine` is a plain struct (`query_engine/mod.rs`) with three inherent async methods: `validate_query`, `sql_to_json`, `json_to_sql`. Consumers hold `Arc<QueryEngine>`: HTTP routes (`routes/sql.rs`) and the MCP `query_laminar_sql` tool (`api/v1/mcp.rs`).
- **The validator IS a security boundary**, not just a linter — it is the only thing standing between user SQL and ClickHouse. It enforces SELECT-only, rejects `BLOCKED_FUNCTIONS` and the `project_id` column, blocks non-allowlisted tables, and rewrites allowlisted table refs to project-scoped `_v0` views (e.g. `spans` → `spans_v0(project_id = '<uuid>')`, `traces` → `traces_v0(project_id=…, start_time=…, end_time=…)`). `json_to_sql`'s raw-expression path is also a security boundary. Preserve their rejection semantics when editing.
- **The frontend JSON contract is binding**: route response/request types use `#[serde(rename_all = "camelCase")]` and must keep matching `frontend/lib/actions/sql/types.ts` (e.g. `queryStructure`, `validatedQuery`). The `fn`/`column`/`args`/`alias` metric shape and `dimensions` array are the camelCase wire format the chart builder + SQL editor depend on.
- Tests live in `validator/tests.rs`, `json_to_sql/tests.rs`, and `sql_to_json/tests.rs`. Run with `cargo test --bin app-server query_engine -- --nocapture`. When changing validator/conversion behavior, update the corresponding test rather than relaxing the assertion.
- **`executeQuery` (`frontend/lib/actions/sql`) routes through this validator** — it POSTs to app-server's `/projects/{id}/sql/query`, so any frontend server action that builds ClickHouse SQL is constrained by the validator (SELECT-only, allowlisted-table-only) AND requires app-server HTTP (8000) to be reachable. To aggregate the `scores` JSON-string map on `evaluation_datapoints` (a ReplacingMergeTree → query with `FINAL`), do NOT use a CH-side tuple `ARRAY JOIN JSONExtractKeysAndValues(scores, 'Float64')` aggregate (the validator rejects the tuple element access `kv.1`/`kv.2`). Instead `SELECT` the raw `scores` strings and average per `(evaluation_id, name)` in JS — the same pattern as `getEvaluationTimeProgression` in `frontend/lib/clickhouse/evaluation-scores.ts` and `getScoreAveragesByEvaluationIds` in `frontend/lib/actions/debugger-sessions/index.ts`.
- **All parsing goes through `parse_clickhouse_sql` in `validator.rs`, NOT `Parser::parse_sql`** — it carries two workarounds for upstream `sqlparser` over-strictness: (1) a token-stream rewrite (`wrap_in_placeholder_lists`) that parenthesizes a `{param}` placeholder list after `IN`/`NOT IN`, and (2) a custom `ClickHouseOptionalIntervalDialect` newtype wrapping `ClickHouseDialect` that flips `require_interval_qualifier()` to `false` so `interval '1 day'` (unit inside the string literal, valid in ClickHouse/Postgres) parses. Don't "fix" the interval case at the token level — synthesizing a trailing unit token makes `Interval`'s `Display` emit `INTERVAL '1 day' SECOND` and corrupt the SQL; only the dialect flag yields `leading_field: None` which round-trips verbatim. The wrapper MUST override `dialect()` to return `self.0.dialect()` (ClickHouseDialect's `TypeId`) or `dialect_of!(self is ClickHouseDialect)` checks inside the parser (parametric aggregates like `quantile(0.9)(duration)`, etc.) silently take the non-ClickHouse path. When bumping the `sqlparser` crate, re-check the wrapper's hand-delegated method list against `ClickHouseDialect`'s overrides.

## SQL Editor Schema (autocomplete + AI generation)

- `frontend/components/sql/utils.ts` (`tableSchemas`, `enumValues`) is the frontend source of truth for the SQL editor's autocomplete AND for the schema embedded in the AI-generation system prompt (`frontend/lib/actions/sql/prompts.ts` consumes both). Backend allowlist lives in `app-server/src/query_engine/validator.rs` → `TableRegistry::new`; the two MUST stay in sync — adding a column to the v0 view + the registry without updating `tableSchemas` leaves it absent from autocomplete and invisible to the AI generator.
- `app-server/src/query_engine/schema.rs` (`build_schema_prompt()`) is the single backend source of truth for the SQL schema surfaced to BOTH the MCP `query_laminar_sql` tool description (`api::v1::mcp`, injected at construction in `tool_router_with_descriptions` — NOT from the `#[tool]` doc comment) and the signals-gated Platform Agent prompt (`lmnr-private` `agent::prompts`). It must mirror `validator.rs`'s `TableRegistry` and the frontend `tableSchemas`/`enumValues`; drift breaks generation. The file is PUBLIC (no signals gating) even though its only OSS caller is the MCP tool — `query_engine/mod.rs` declares `pub mod schema;` unconditionally.
- Columns whose runtime CH type is `String` but whose values are constrained (status, span_type, trace_type, signal_runs.status / .mode) carry an `enumType: keyof typeof enumValues` field. The prompt builder appends `Allowed values: '...'` to the column's description, and the editor's `<column> = ` autocomplete filters to those literals. Without `enumType`, the model invents values (e.g. `status = 'OK'` when nothing pins the status column to `'success' | 'error'`).
- `enumValues` is keyed by enum NAME, not column name. A single column can map to one enum (`spans.status` → `status`) or different enums in different tables (`signal_runs.status` → `signal_run_status`). The autocomplete `columnEnumMap` is built by walking `tableSchemas` once at module load, so column→enum wiring stays declarative — never add column names to a hardcoded regex; just set `enumType` on the schema entry.
- The `clusters_v0` view (CH migration; latest is `47_clusters_v0_drop_centroid.sql`) intentionally does NOT expose `centroid` — the embedding vector is an internal `Array(BFloat16)` on `signal_event_clusters`, useless over SQL and expensive to ship. When recreating the view in a new migration, keep the `WHERE level > 0` L0 filter and the 9 user-facing columns (id, signal_id, name, level, parent_id, num_signal_events, num_children_clusters, created_at, updated_at). `clusters` is in `tableSchemas` (autocomplete + AI + docs); `signal_events_all` stays registry-only (queryable) and is intentionally NOT in `tableSchemas`.
- **Two MORE agent-facing table lists are hardcoded and NOT generated from the registry — they drift silently.** (1) The MCP `query_laminar_sql` tool docstring + the `QuerySqlParams.query` field doc in `app-server/src/api/v1/mcp.rs`; (2) `SQL_SCHEMA_HELP` in `lmnr-ts/packages/lmnr-cli/src/commands/sql/schema.ts` (the CLI `sql` command's `--help`). Adding a table/column to the query-engine registry makes it *queryable* but invisible to MCP clients and CLI users until BOTH are hand-updated. So the full sync set for a new SQL-exposed table/column is FOUR places: `validator.rs` `TableRegistry` (execution gate), `tableSchemas` (frontend autocomplete/AI), `mcp.rs` docstring, and CLI `schema.ts`. Descriptions live only in `tableSchemas`; the other three are terse `name (Type)` lists.

## SQL Editor Results Table

- The Table tab renders through `frontend/components/sql/results-table.tsx`. It owns three UX behaviours: per-cell hover copy button (copies the FULL raw value — display uses CSS truncate against the column width), the row-count indicator data (rendered in `editor-panel.tsx` next to the tabs from `results.length`), and column-width persistence.
- Column widths persist to localStorage keyed `sql-results-column-sizing-<projectId>-<templateId>`. Same pattern as chart-builder's `table-chart`: seed `defaults` (with `columnOrder` + stored `columnSizing`) at `InfiniteDataTableProvider` creation, and a thin `ColumnSizingPersistence` child (like `ColumnConfigEmitter`) writes changes back. Writes replace the stored map with the current result's `columnSizing` (prunes keys from prior query shapes — draft keys especially would grow forever under a merge). The provider remounts on every query run (loading unmounts the tree) — persistence is what carries widths across re-runs; don't lift the provider above `renderContent` to "fix" the remount.

## Rate Limiting (SQL + data ingestion)

- Two independent per-project limiters, gated by separate features: `Feature::RateLimiter` (`REDIS_URL` + `RATE_LIMIT` + `RATE_LIMIT_PERIOD_SECS`) covers the SQL surface; `Feature::IngestionRateLimiter` (`REDIS_URL` + `INGESTION_RATE_LIMIT` + `INGESTION_RATE_LIMIT_PERIOD_SECS`) covers trace ingestion on BOTH transports (gRPC + HTTP `/v1/traces`). Env names live in `app-server/src/env/rate_limit.rs`. The ingestion limit applies to every project by default (no per-project opt-in).
- **SQL** (`/v1/sql/query` + CLI twin `/v1/cli/sql/query`): `SqlRateLimiter` (`api/v1/sql.rs`) wraps a shared `actix_limitation::Limiter` (the env-default N/T) — counted inline in `handle_sql_query` with key `ratelimit:{project_id}`, not scope middleware, because `project_id` is only known after the auth extractor runs. A per-project N override read from cache on every request (`sql_rate_limit:{project_id}`, plain integer set out-of-band via `valkey-cli SET`, no app writer) swaps in an ad-hoc `Limiter` built with that N and the global period. Only N is overridable; T is global (`RATE_LIMIT_PERIOD_SECS`). Constant in `cache/keys.rs`. A changed N applies immediately; the window itself is actix-limitation's fixed window (counter key `ratelimit:{id}` with TTL set on window start — `DEL` it to reset early). Accepted trade-off shared with the ingestion limiter: the crate opens a fresh Redis connection per `count()`, outside `ResilientRedisConnection`; migrating to the shared-cache counter is planned.
- **Data ingestion:** `IngestionRateLimiter` (`traces/rate_limit.rs`, mirrors `SqlRateLimiter`) counts ONE shared quota key `ingestion_ratelimit:{project_id}` from both the gRPC path (`ProcessTracesService::export` in `traces/grpc_service.rs`, threaded as `Option<Arc<IngestionRateLimiter>>` through `::new` since tonic has no actix-style middleware; exceeded → `Status::resource_exhausted`) and the HTTP path (`api/v1/traces.rs::process_traces`, injected as `web::Data<Option<Arc<IngestionRateLimiter>>>`, checked before payload decode; exceeded → 429) — so neither transport can bypass the other. Per-project overrides in cache (plain integers via `valkey-cli SET`, no app writer, take precedence over the env defaults): `ingestion_project_rate_limit:{project_id}` for N AND `ingestion_project_rate_limit_period:{project_id}` for the window seconds — unlike the SQL limiter, the period is also overridable; either key can be set independently, the other falls back to the global default. Only `POST /v1/traces` is limited — `traces/metadata`, `/v1/spans`, `/v1/browser-sessions` etc. are not.
- Posture is fail-open on Redis/cache errors everywhere (logged, request allowed), so a Redis blip can't black-hole ingestion or SQL.
- **Rollout gotcha:** the unit is requests (OTLP export batches) per window, not spans/bytes — pick `INGESTION_RATE_LIMIT` high enough for the largest legitimate SDK batch cadence, then clamp offenders down via the per-project cache key.

## Ad-hoc SQL Endpoint Guards (`/v1/sql/query`)

- Per-query ClickHouse settings (`max_execution_time`, `max_result_bytes`, `max_memory_usage`) are applied in `app-server/src/sql/ch.rs` via `.with_setting(...)`, env-tunable through `app-server/src/env/sql.rs` (`SQL_QUERY_*`). They are tamper-proof: the query-engine validator strips any inline `SETTINGS` clause from user SQL, so a client can't override the server-applied caps.
- `max_memory_usage` (OOM protection — the lever that actually kills CH, not bytes scanned) is gated by `SqlQuerySource` (`sql/mod.rs`), threaded `execute_sql_query` → `route_and_run_query` → `ch::query`. It's applied ONLY for `SqlQuerySource::Public` (the internet-facing `/v1/sql/query`, CLI `/v1/cli/sql/query`, and the MCP query tool); the trusted frontend route (`routes/sql.rs`) and internal callers (`datasets/service.rs`, `sql/queries.rs`) pass `Frontend` and run uncapped. Default `SQL_QUERY_MAX_MEMORY_USAGE=0` means unlimited, so self-hosters are unrestricted unless they opt in. When adding a new caller of `sql::execute_sql_query`, pick the source deliberately.
- Settings only apply on the CLOUD deployment path; HYBRID forwards the raw query to a remote data plane (`sql/data_plane.rs`) which runs its own CH and is not covered by these caps.
