## Billing and Tier Allowances

- **"Starter" is the DISPLAY name of the internal `hobby` tier.** The lowercase `hobby` key is structural and must NEVER be renamed: the TS `Tier` union / `TIERS` / `TIER_CONFIG` record keys, the Rust `WorkspaceTierName::Hobby` enum variant, Stripe lookup keys (`hobby_monthly_*`), webhook `["hobby","pro"]` comparisons, and `HOBBY_*` constants all stay as-is. Only user-facing strings say "Starter". Production `subscription_tiers.name` rows may carry EITHER "Hobby" (legacy) or "Starter" — every raw-DB-name consumption site normalizes both to the `hobby` key: `normalizeTier` + `tierDisplayName` in `frontend/lib/billing/tiers.ts`, `knownTier` in `components/workspace/usage/utils.ts`, `workspaceTierKey` in `components/workspace/billing/index.tsx`, `normalizeTierName` in `lib/actions/checkout/webhook.ts`, `getSubscriptionDetails`/`switchTier` in `lib/actions/checkout/index.ts` (the billing tab's `subscription.currentTier` comes from `getSubscriptionDetails`, so this site keeps the subscription arm of `currentTierKey` on the `hobby` key), `retentionCutoff` in `lib/billing/retention.ts`, and `getHasClusteringAccess` in `lib/features/clustering.ts`. The last two map/check `"starter"` INLINE rather than via `normalizeTier`, which would fold unknown tiers like self-hosted `unlimited` to `free` and impose a 7-day retention cutoff / clustering block on them. When rendering a raw `tierName` from the DB, route it through `tierDisplayName` (unknown names like `unlimited` pass through unchanged). The rename is frontend-display-only; if the `subscription_tiers.name` row is ever renamed to "Starter", Rust `WorkspaceTierName::from_str` in `app-server/src/db/projects.rs` must learn the `"starter"` alias or the tier falls to `Other`.
- **Signal cost is metered from three raw token counts, not a single number.** Per run we store `input_tokens`, `cache_read_tokens`, and `output_tokens` on `signal_runs` (CH); cost in micro-USD is derived at read time (`signal_token_cost_micro_usd` in `app-server/src/utils/mod.rs`, mirrored by `signalTokenCostMicroUsd` in `frontend/lib/billing/tiers.ts`) so a rate change re-prices history. **`cache_read_tokens` is a SUBSET of `input_tokens`** (the provider `prompt_token_count` already includes cached-read tokens across Bedrock/OpenAI/Gemini), so the cost fn bills `(input - cache_read)` at the input rate plus `cache_read` at a discounted cache rate — never additive, never double-charged. Rates are env-overridable: `SIGNAL_INPUT_TOKEN_PRICE_PER_MILLION` (default 0.05), `SIGNAL_OUTPUT_TOKEN_PRICE_PER_MILLION` (default 0.30), `SIGNAL_CACHE_READ_TOKEN_PRICE_PER_MILLION` (default 0.01). The accumulator threads `cache_read_tokens` through the whole pipeline (`SignalMessage` → `SignalRun` → `response_processor` accumulate/rollback → `finalize_runs` metering → CH); the Failed-arm `saturating_sub` rollback covers all three counts so a re-enqueued retry doesn't double-count.
- **`signalTokenCostMicroUsd` only honours the `SIGNAL_*_TOKEN_PRICE_PER_MILLION` overrides server-side.** Those envs are not `NEXT_PUBLIC_`, so in the client bundle they resolve to `undefined` and `resolveRate` silently falls back to published defaults — a browser-side call would diverge from metered usage whenever an operator overrides a rate. So price runs server-side: `getSignalRuns` (`frontend/lib/actions/signal-runs/index.ts`) computes `costMicroUsd` per row and the runs-table Cost column (`components/signal/runs-table/columns.tsx`) only formats that precomputed value. Don't move the cost computation back into a client component / cell.
- **Signals billing and limit checks read ClickHouse directly.** Completed runs persist their `credit_applied` decision with their raw token usage, so a long-lived token cache cannot safely represent billable usage. Cost is derived from the three raw token columns at each read.
- **Signals has no recurring tier allowance.** `TIER_CONFIG.includedSignalCostMicroUsd`, `TIERS[tier].includedSignalCostUsd`, and `subscription_tiers.signal_cost_included_micro_usd` remain as zero-valued compatibility fields. Do not put the sign-up credit in them: those values participate in monthly usage and Stripe calculations, so a nonzero value would refresh every billing period.
- **Each newly created workspace receives one $5 Signals credit that carries forward until consumed.** `workspaces.signal_credit_remaining_micro_usd` is the workspace credit balance: `NULL` means the workspace predates the grant, while new workspaces default to $5. When a run completes, the app-server atomically deducts its cost in Postgres and persists `signal_runs.credit_applied = true` only when the whole run fits; otherwise it exhausts the small remainder and persists the run as billable. This Postgres/ClickHouse sequence is intentionally non-transactional. Stripe receives cumulative current-period cost only from uncredited runs. The per-run flag makes credit independent of invoice windows, tier changes, and delayed webhooks.
- **Signal token rates are unified across tiers:** $0.05 / 1M input, $0.01 / 1M cached input, and $0.30 / 1M output. `signal_token_cost_micro_usd` (`app-server/src/utils/mod.rs`) and `signalTokenCostMicroUsd` (`frontend/lib/billing/tiers.ts`) use one set of `SIGNAL_*_TOKEN_PRICE_PER_MILLION` envs; there are no Pro-specific rate constants or overrides. Backend defaults are pinned in `app-server/src/env/private/signals.rs` and mirrored by `frontend/lib/billing/tiers.ts` — keep them in sync.
- Stripe invoice line items expose their lookup key in two places: legacy `line.price.lookup_key` and the newer `line.pricing.price_details.price.lookup_key`. Email-subject/body rendering must check BOTH before falling back to `line.description` or a generic "Subscription charge" string, otherwise the subject line silently becomes `Laminar: Payment for  is received.` (trailing empty label).
- Transactional-email "billing portal" CTAs link to `/checkout/portal?workspaceId=...` (`frontend/app/checkout/portal/page.tsx`), which mints a Stripe billing portal session via `getPaymentMethodPortalUrl` and 302s straight to Stripe. Unauthenticated clicks bounce through `/sign-in?callbackUrl=...`. `getPaymentMethodPortalUrl` requires owner/admin role on the workspace — non-admin recipients hit the catch and get redirected to the workspace billing tab as a graceful fallback. Don't link emails directly to the workspace settings page; that path requires the user to manually click "Billing portal" again.

- **The Usage tab's bill is an estimate, not the invoice** (`lib/billing/usage-estimate.ts`): Stripe charges what meters-job reports. Totals come from `getWorkspaceStats`, and the Signals bill line is only uncredited runs (`signalCostOverLimit`), not total Signals usage; daily charts from `GET /api/workspaces/[id]/usage-breakdown` (ClickHouse, priced server-side, uncached).

## Workspace Usage Warnings vs Hard Limits

- Usage enforcement lives in two separate tables, both edited via Stripe webhook when a subscription is created or a tier is switched (`frontend/lib/actions/checkout/webhook.ts`):
  - `workspace_usage_warnings` — soft limits that fire a notification once per billing cycle. Checked in `check_soft_limits` in `app-server/src/utils/limits.rs`.
  - `workspace_usage_limits` — hard caps read by `get_project_and_workspace_billing_info` as `custom_bytes_limit` / `signal_cost_hard_limit_micro_usd` and enforced by the app-server and `checkSignalRunsLimit` (frontend). Only paid-tier custom limits + the Hobby default have rows here; Free is gated by its remaining one-time Signals credit with no limit row.
  - `workspace_hard_limit_notifications` — per-`(workspace_id, usage_item)` `last_notified_at` dedup for hard-limit emails (separate table so free-tier workspaces, which have no `workspace_usage_limits` row, can still dedup once per billing cycle). Stamped by `check_notify_hard_limit`.
- On tier transition into **Hobby**, we insert a hard-limit row for `signal_cost` at `HOBBY_DEFAULT_HARD_LIMIT_SIGNAL_COST_MICRO_USD` (100,000,000). The hard cap is intentionally set to the same threshold as the overage email warning so ingestion is blocked at the same moment the user gets nudged. Pro and Free do NOT get a default hard-limit row.
- Hobby also gets two **overage warnings** ($100 signal cost / `HOBBY_OVERAGE_WARNING_SIGNAL_COST_MICRO_USD`, 40 GiB bytes / `HOBBY_OVERAGE_WARNING_BYTES`) so users accumulating a large overage bill are nudged before it grows further. These are Hobby-only rows; Pro does not get them. On transition OUT of Hobby they are cleared (matching exact value so user-adjusted thresholds are preserved) via `clearHobbyOverageWarnings`, which — like the hard-limit cleanup — runs on every transition including Hobby → Free.
- On tier transition OUT of Hobby, the default Hobby hard limit is deleted **only if it still equals a known Hobby default** — `HOBBY_DEFAULT_HARD_LIMIT_SIGNAL_COST_MICRO_USD` (100,000,000 micro-USD / $100). A user-set custom value is preserved across upgrades/downgrades. Same pattern for warnings.
- The hard-limit cleanup runs on **every** recognized tier transition — including Hobby → Free on cancellation; leaving the Hobby limit in place there would silently re-apply the Hobby cap the next time the workspace upgrades to any paid tier. Warnings, in contrast, are only written when the new tier is paid (Hobby/Pro) since Free has no warnings to carry.
- After inserting or deleting a `workspace_usage_limits` row, you MUST invalidate the per-project cache via `invalidateProjectCacheForWorkspace(workspaceId)` — the app-server caches `ProjectWithWorkspaceBillingInfo` keyed by project id and will otherwise keep enforcing stale limits until TTL.
- **Both soft warnings AND hard limits email the workspace owners.** Soft = `check_soft_limits` → `NotificationKind::UsageWarning`; hard = `check_notify_hard_limit` → `NotificationKind::UsageHardLimit`. Soft warnings fire only from the usage-update path (`update_workspace_bytes_ingested` / `update_workspace_signal_tokens` in `utils/limits.rs`), right after the cache total is bumped. Data and paid custom hard limits fire from BOTH the update path AND enforcement gates. Free Signals credit exhaustion is different: it notifies only on the update that consumes the final credit, because the credit does not reset and later monthly preflights must not send repeated exhaustion messages.
- **Hard-limit notifications dedup via a dedicated DB table, mirroring soft warnings 1-to-1 — once per billing cycle.** `check_notify_hard_limit` reads `workspace_hard_limit_notifications.last_notified_at` for `(workspace_id, usage_item)`, skips when it is `>= current_billing_period_start(reset_time)`, and after a successful enqueue upserts the row to `NOW()` (`usage_warnings::{get_hard_limit_last_notified_at, mark_hard_limit_as_notified}`). It must be a SEPARATE table from `workspace_usage_limits`, not a column on it: free-tier workspaces enforce the tier's included allowance with NO limit row yet still need dedup, and adding a phantom limit row would surface as a fake "custom limit" in the settings UI and the billing query. `check_notify_hard_limit` takes `reset_time` (passed as `project_info.reset_time` at all four call sites) exactly like `check_soft_limits`. Because the enforcement gates run on EVERY blocked request, the Postgres read is fronted by a short cache (`HARD_LIMIT_NOTIFIED_CACHE_KEY:{workspace_id}:{usage_item}`, 5-min TTL): only the SUPPRESSING state (a `last_notified_at` within the current cycle) is cached — never "not notified", which would widen the duplicate-enqueue race to the TTL. The frontend's `deleteHardLimitNotification` evicts this cache key (shared Redis) right after deleting the DB dedup row, so a raised/removed limit can re-notify immediately; the short TTL is only a backstop for a failed eviction.
- **The dedup row has no FK cascade from `workspace_usage_limits` (free tiers have no limit row), so the frontend cleans it up explicitly whenever the underlying hard limit changes** (`lib/actions/usage/utils.ts`: `deleteHardLimitNotification`, `clearHardLimitNotificationOnIncrease`). Rules: removing a limit → delete the dedup row (a re-created limit must start fresh); lowering a limit → keep the row (the prior breach still stands); raising a limit → delete only if already notified this cycle AND the new limit sits above current usage, i.e. the workspace is back under its higher cap so a future breach is a genuinely new event. Current usage MUST come from `getWorkspaceUsage` (cache→ClickHouse, returns `totalSignalCostMicroUsd` matching the micro-USD `signal_cost` limit unit + `totalBytesIngested`), NOT the `workspace_usage` table — those columns are only written on checkout/reset, aren't synced with the enforcement caches, and `signal_cost` there isn't micro-USD. Wired from BOTH the user path (`custom-usage-limits.ts` `setUsageLimit`/`removeUsageLimit` — `setUsageLimit` reads the prior `limit_value` before its upsert to tell raise from reduction) AND the automatic path (`checkout/webhook.ts` `upsertDefaultTierUsageLimits` — both the Hobby-default delete on transition-out and the `.returning()`-guarded default insert on transition-in drop the `signal_cost` dedup row).
- `NotificationKind::UsageHardLimit` and `NotificationDefinitionType::UsageHardLimit` route targets through the SAME owner-email fan-out arm as `UsageWarning` in `notifications/mod.rs::fetch_targets`. Both also acquire a handler-side race-guard lock in `NotificationHandler::handle` (`usage_send_lock_key`): warnings key on `definition_id` (the warning row); hard limits share `definition_id` (= workspace_id) across usage items, so they key on `HARD_LIMIT_SEND_LOCK_KEY:{workspace_id}:{usage_item}` to avoid a bytes notification suppressing a concurrent signal-cost one. The lock is a 5-min race guard only; the durable per-cycle dedup is the DB `last_notified_at` above. On total fan-out failure the lock is freed with `release_lock` (NOT `remove`: the in-memory cache keeps locks in a separate map).
- **Warning thresholds are absolute billing-period totals measured from zero.** The one-time Signals credit does not shift user-configured warning thresholds. Automatic Signals allowance warnings no longer exist; the migration removes the former tier allowance rows before setting recurring allowance values to zero.
- **The Warnings + Hard-limits sections (`frontend/components/workspace/usage/{warnings,limits}`) only render for paid tiers AND workspace owners** (`isOwner && tierName !== FREE` in `usage/index.tsx`). To verify them in staging (where only `Free` / `unlimited` `subscription_tiers` rows exist), temporarily insert a `Hobby` row and point the workspace's `tier_id` at it, then revert — there is no billing tab to upgrade through (the `SUBSCRIPTION` feature flag / Stripe is not wired in staging).

## Custom Model Costs (project-level pricing overrides)

- The custom-model-costs UI (`frontend/components/settings/custom-model-costs.tsx`) only edits a subset of the cost keys the Rust cost calculator understands. The `costs` JSONB is a free-form key→number map (Zod `z.record`), and `calculate_span_cost` (`app-server/src/language_model/costs/cost_calculator.rs`) already resolves many more keys (`cache_read_input_token_cost`, `cache_creation_input_token_cost`, threshold/tier/batch variants, audio, reasoning). To surface another key in the UI, add one entry to `COST_FIELDS` — display, per-million↔per-token conversion, tooltip, and the edit form all derive from that list; no backend or schema change is needed.
- Cost keys follow the litellm naming convention (`input_cost_per_token`, `cache_read_input_token_cost`, …) because the universal `model_costs` table is seeded from litellm data; custom costs must use the same key names to be picked up by the shared calculator.
