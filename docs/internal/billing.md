## Billing and Tier Allowances

- **Display names are shifted one tier up from the internal keys: `hobby` shows as "Pro" and `pro` shows as "Scale"** (renamed 2026-11, LAM-2521; `hobby` was "Starter" before that). The lowercase keys are structural and must NEVER be renamed: the TS `Tier` union / `TIERS` / `TIER_CONFIG` record keys, the Rust `WorkspaceTierName::{Hobby,Pro}` variants, Stripe lookup keys (`hobby_monthly_*`, `pro_monthly_*`), webhook `["hobby","pro"]` comparisons, `HOBBY_*` constants, internal identifiers like `startStarterTrial`, and raw-DB-name checks like `WorkspaceTier.PRO` / `w.tierName === "Pro"` (these mean the Scale tier). So "Pro" in a raw `subscription_tiers.name` is the Scale tier, while "Pro" in user-facing copy is the `hobby` tier: always render through `TIERS[tier].name` / `tierDisplayName`, never a raw DB name. Display names live in `TIERS` (`lib/billing/tiers.ts`), `LOOKUP_KEY_DISPLAY_NAMES` (invoices), and the Rust `WorkspaceTierName::display_name` (usage-warning emails); retention (3 months / 1 year, enforced as 90 / 365 days) in `TIER_RETENTION` (`lib/billing/retention.ts`), which drives the API query cutoff (`retentionCutoff`) AND the date-picker limit (`getProjectDetails` → `logRetentionDays` via `retentionDays`; `subscription_tiers.log_retention_days` is only the fallback for custom tiers like self-hosted `unlimited`, so don't edit DB rows to change a known tier's window). Windows are whole days because the picker is day-based: calendar months would let it offer ranges the API 403s; per-GB overage display rates in `TIERS[*].dataOverageRatePerGB` — the billed rate is the Stripe price behind the `*_overage_megabytes` lookup key, so a rate change must also be made in Stripe. Production `subscription_tiers.name` rows may carry EITHER "Hobby" (legacy) or "Starter" — every raw-DB-name consumption site normalizes both to the `hobby` key: `normalizeTier` + `tierDisplayName` in `frontend/lib/billing/tiers.ts`, `knownTier` in `components/workspace/usage/utils.ts`, `workspaceTierKey` in `components/workspace/billing/index.tsx`, `normalizeTierName` in `lib/actions/checkout/webhook.ts`, `getSubscriptionDetails`/`switchTier` in `lib/actions/checkout/index.ts` (the billing tab's `subscription.currentTier` comes from `getSubscriptionDetails`, so this site keeps the subscription arm of `currentTierKey` on the `hobby` key), `asTier` in `lib/actions/onboarding/resume-defaults.ts`, `retentionCutoff` in `lib/billing/retention.ts`, and `getHasClusteringAccess` in `lib/features/clustering.ts`. The last two map/check `"starter"` INLINE rather than via `normalizeTier`, which would fold unknown tiers like self-hosted `unlimited` to `free` and impose a 7-day retention cutoff / clustering block on them. When rendering a raw `tierName` from the DB, route it through `tierDisplayName` (unknown names like `unlimited` pass through unchanged). The rename is frontend-display-only; if the `subscription_tiers.name` row is ever renamed to "Starter", Rust `WorkspaceTierName::from_str` in `app-server/src/db/projects.rs` must learn the `"starter"` alias or the tier falls to `Other`.
- **Signal cost is metered from three raw token counts, not a single number.** Per run we store `input_tokens`, `cache_read_tokens`, and `output_tokens` on `signal_runs` (CH); cost in micro-USD is derived at read time (`signal_token_cost_micro_usd` in `app-server/src/utils/mod.rs`, mirrored by `signalTokenCostMicroUsd` in `frontend/lib/billing/tiers.ts`) so a rate change re-prices history. **`cache_read_tokens` is a SUBSET of `input_tokens`** (the provider `prompt_token_count` already includes cached-read tokens across Bedrock/OpenAI/Gemini), so the cost fn bills `(input - cache_read)` at the input rate plus `cache_read` at a discounted cache rate — never additive, never double-charged. Rates are env-overridable: `SIGNAL_INPUT_TOKEN_PRICE_PER_MILLION` (default 0.05), `SIGNAL_OUTPUT_TOKEN_PRICE_PER_MILLION` (default 0.30), `SIGNAL_CACHE_READ_TOKEN_PRICE_PER_MILLION` (default 0.01). The accumulator threads `cache_read_tokens` through the whole pipeline (`SignalMessage` → `SignalRun` → `response_processor` accumulate/rollback → `finalize_runs` metering → CH); the Failed-arm `saturating_sub` rollback covers all three counts so a re-enqueued retry doesn't double-count.
- **`signalTokenCostMicroUsd` only honours the `SIGNAL_*_TOKEN_PRICE_PER_MILLION` overrides server-side.** Those envs are not `NEXT_PUBLIC_`, so in the client bundle they resolve to `undefined` and `resolveRate` silently falls back to published defaults — a browser-side call would diverge from metered usage whenever an operator overrides a rate. So price runs server-side: `getSignalRuns` (`frontend/lib/actions/signal-runs/index.ts`) computes `costMicroUsd` per row and the runs-table Cost column (`components/signal/runs-table/columns.tsx`) only formats that precomputed value. Don't move the cost computation back into a client component / cell.
- **Signals billing and limit checks read ClickHouse directly.** Cost is derived from the three raw token columns at each read. Queries keep `credit_applied = false`: runs covered by the retired one-time credit were free and must stay out of bills and limits.
- **Scale (internal `pro`) includes $50 of Signals usage every billing period; Pro (`hobby`) includes none.** The allowance lives in `TIER_CONFIG.includedSignalCostMicroUsd`, `TIERS[tier].includedSignalCostUsd`, `subscription_tiers.signal_cost_included_micro_usd` and Rust `WorkspaceTierName::included_signal_cost_micro_usd`; keep all four equal. Billable Signals = period cost minus the allowance (`billableSignalCostMicroUsd`, `getWorkspaceStats` → `signalCostOverLimit`, the tier-switch meter baseline). The external meters-job must subtract the same allowance before reporting to Stripe. Scale also gets a default usage warning at the allowance (`insertNewTierUsageWarnings`), whose email says the included Signals usage is used up.
- **The one-time $5 Signals credit is retired (LAM-2521).** Migration `0132` cleared every `workspaces.signal_credit_remaining_micro_usd` and dropped its default, so `apply_signal_credit` (still called by the private Signals code) always returns false and every new run is stored `credit_applied = false`. The column, the CH flag and that function stay until the private callers are removed.
- **Signal token rates are unified across tiers:** $0.05 / 1M input, $0.01 / 1M cached input, and $0.30 / 1M output. `signal_token_cost_micro_usd` (`app-server/src/utils/mod.rs`) and `signalTokenCostMicroUsd` (`frontend/lib/billing/tiers.ts`) use one set of `SIGNAL_*_TOKEN_PRICE_PER_MILLION` envs; there are no Pro-specific rate constants or overrides. Backend defaults are pinned in `app-server/src/env/private/signals.rs` and mirrored by `frontend/lib/billing/tiers.ts` — keep them in sync.
- Stripe invoice line items expose their lookup key in two places: legacy `line.price.lookup_key` and the newer `line.pricing.price_details.price.lookup_key`. Email-subject/body rendering must check BOTH before falling back to `line.description` or a generic "Subscription charge" string, otherwise the subject line silently becomes `Laminar: Payment for  is received.` (trailing empty label).
- Transactional-email "billing portal" CTAs link to `/checkout/portal?workspaceId=...` (`frontend/app/checkout/portal/page.tsx`), which mints a Stripe billing portal session via `getPaymentMethodPortalUrl` and 302s straight to Stripe. Unauthenticated clicks bounce through `/sign-in?callbackUrl=...`. `getPaymentMethodPortalUrl` requires owner/admin role on the workspace — non-admin recipients hit the catch and get redirected to the workspace billing tab as a graceful fallback. Don't link emails directly to the workspace settings page; that path requires the user to manually click "Billing portal" again.

- **The Usage tab's bill is an estimate, not the invoice** (`lib/billing/usage-estimate.ts`): Stripe charges what meters-job reports. Totals come from `getWorkspaceStats`, and the Signals bill line is only cost past the plan's allowance (`signalCostOverLimit`), not total Signals usage; daily charts from `GET /api/workspaces/[id]/usage-breakdown` (ClickHouse, priced server-side, uncached). During a trial the same overview renders with `trialEndsAt`: each line shows its plan-rate cost struck through as "Free" and the total is $0, since trial usage is never billed.

- **Pricing feature claims must match the real plan gates.** `TIERS[*].securityFeatures` (cards on landing + workspace billing) and the comparison table in `components/landing/pricing/tier-data.ts` are marketing copy with no enforcement behind them, so check each claim against the gate. **"Trace-level RBAC" in pricing means query-engine-level trace access** (the `AccessPolicy` that `spans_v1`/`traces_v1` enforce: `maskPii` + `traceFilters`, see `rbac.md`), NOT workspace owner/admin/member roles, which every paid plan has (invites are blocked only on Free, `lib/actions/workspace/invite.ts`). RBAC is listed as Scale-and-up only; the audit log is Scale-and-up (`AUDIT_LOG_EXCLUDED_TIERS` in `lib/actions/usage/plan-gates.ts`); PII redaction, including role-based PII masking, is Scale-and-up (`PRO_TIER_GATES` in `lib/actions/project/settings.ts`).
- **The pricing page's billing highlight cards** (`components/landing/pricing/billing-highlights.tsx`) make two claims. (1) Data is billed after compression: true because metering uses `size_bytes`, which `charge_span_sizes` computes after message and tool-definition dedup (`original_size_bytes` is the raw size); "2–50x" is the range from the compression blog post. (2) `AVG_TRACE_ANALYSIS_COST_USD` ($0.002) is the observed average Signals cost per analyzed trace, model inference included; update it if real averages move. The Free card lists "Signals" even though Free workspaces can't run them (see the Free bullet below), matching the comparison table's Platform row.

## Free trial (of the `hobby` tier, shown as "Pro")

- **A trial is a real Stripe subscription in `trialing` status**, created by `startStarterTrial` (`lib/actions/checkout/trial.ts`) with `trial_period_days: 14`, no card, and `trial_settings.end_behavior.missing_payment_method: "cancel"`. No card by day 14 → Stripe cancels → the existing `subscription.deleted` path moves the workspace to Free. Available wherever `Feature.SUBSCRIPTION` is on.
- **The only local state is `workspaces.trial_ends_at`**, set while trialing and cleared by `endTrial` on conversion, expiry or cancel; Stripe holds the trial's history. Eligibility needs no extra state: the workspace has no `subscription_id` (a trial sets it and it is never cleared) and the user owns no workspace that has one. Only owners can start a trial, so that rule always checks the owner who is billed.
- **Trials never carry metered prices.** `addOveragePricesToSubscription` skips `trialing`; `handleTrialConversion` attaches them, resets `workspace_usage` / `reset_time` to the EXACT trial end (`handleInvoiceFinalized(..., { exactStart: true })`; rounding to midnight would roll that day's trial usage, or the whole trial on a same-day Start now, into the first paid period). The `invoice.finalized` path keeps the workspace's own time of day (`date_trunc('day', period_end) + reset_time's time of day`), because the app-server derives billing periods as monthly anniversaries of `reset_time`: rounding a non-midnight `reset_time` (trial conversion, or `now()` on a Free → paid upgrade) back to midnight counts the hours before the boundary in both periods, then clears `trial_ends_at`. Conversion is keyed on "subscription active + `trial_ends_at` still set", not `previous_attributes.status`, so a day-14 charge that succeeds on retry (`past_due → active`) still converts.
- **Trials are uncapped (acquisition choice, LAM-2521)**: a trial ingests past 3 GB and runs Signals without limit, like paid Pro. Only Free is capped (`is_capped_at_allowance` in `app-server/src/utils/limits.rs`; Free also has no Signals at all). No tier gets a default hard limit, so a trial is bounded only by hard limits the owner sets. Trial usage is never billed: no metered prices while trialing, meters-job must skip workspaces with `trial_ends_at IS NOT NULL`, and conversion restarts the usage window at the trial end. `trialing` otherwise survives only as `overage_billable = false` on usage-warning emails.
- **The reminder rides Stripe's `customer.subscription.trial_will_end`** (3 days before the end; not configurable on this account). `handleTrialWillEnd` emails only trials that won't convert on their own (no card, or "Cancel subscription"). `sendWelcomeEmail` adds a trial note when `trial_ends_at` is set. `handleTrialDeleted` sends the "trial ended, now on Free" email (`trial-ended-email.tsx`) once per trial (gated on `endTrial`'s return, so webhook retries don't resend), for every non-converting end: expiry, cancel, failed payment. Both trial emails share `trial-email-layout.tsx` (incl. the Starter→Free change list).
- **Billing shows Add payment method until a card is on file, then Start now (`startStarterNow`, `trial_end: now`) and Cancel subscription.**
- **The project sidebar shows a trial card to every member** (`trial-card.tsx`, from `ProjectDetails.trialEndsAt`). Its popover reads `GET .../subscription/trial` (`trialConvertsToPaid`, no role check) so a trial with a card on file isn't told it will drop to Free.
- **PostHog funnel: server-side `trial:started` → `trial:card_added` → `trial:converted` | `trial:ended`** (`trial-analytics.ts`), all from the Stripe webhook so card-less expiries are counted too. `distinctId` is the workspace id (personless, no lookups on the webhook path); `source` (`onboarding`/`billing`/`cli`) rides the subscription's `trialSource` metadata, `other` when absent (backfill, dashboard). `ended.reason`: `canceled` (Cancel subscription), `payment_failed`, `expired` (no card). `converted.trial_days` < 14 means Start now. Onboarding starts the trial for every eligible signup; the sidebar's one-time intro fires client `billing:trial_intro_shown`.
- **"Cancel subscription" is `cancel_at_period_end`** (`setTrialContinues`): the trial runs to its end, then the deleted webhook drops the workspace to Free. Start now and adding a card clear it.
- **A Free workspace that ever had a subscription is owner-only** (non-owners blocked until it upgrades; Free has one seat). The same SQL condition sits in every frontend membership check (`lib/authorization/index.ts`, so the proxy blocks API routes too) and in the app-server CLI membership queries (`project_has_member`, `get_projects_for_user`); pages redirect locked members to `/trial-ended`.
- **One path per transition, and each clears the caches it changes.** Trial start, conversion and upgrades/downgrades all go through `manageWorkspaceSubscriptionEvent` (project billing-info, bytes usage, usage warnings; membership caches on any move in or out of Free; the `project_member` key is shared with the app-server CLI routes). `endTrial` additionally clears the project billing-info cache, since it carries `trialing`. A trial cancel only cancels in Stripe; the `subscription.deleted` webhook does the downgrade for both cancels and expiries, and sends the trial-ended email. `syncTrialEndFromSubscription` makes the webhook authoritative for `trial_ends_at`.
- **Free has no Signals, Slack alerts or clustering** (cloud only, i.e. `Feature.SUBSCRIPTION`). The Signals page and the Integrations/Alerts settings tabs show an upgrade notice instead (`components/common/upgrade-notice.tsx`); existing signals stay reachable by URL but are inert. Free can connect Slack (onboarding asks before the commit) but gets no deliveries. Gates: frontend `lib/actions/usage/plan-gates.ts` (signal create/template/trigger/execute, Slack test message) plus `checkSignalRunsLimit`; app-server `service::create_signal` (`CrudError::FreePlan`), `get_workspace_signal_runs_limit_exceeded` (Free → exceeded, which also starves clustering), and `handle_slack` in `notifications/delivery.rs`. Match the raw tier name `free`, never `normalizeTier`, so self-hosted `unlimited` is untouched. New cloud workspaces start Free, so `seedFirstProject` no longer seeds the Failure Detector there; onboarding queues the picked templates and creates them when leaving the Slack step starts the trial. A CLI signup (`/device` approve with no project) starts the trial and the default templates directly.

## Workspace Usage Warnings vs Hard Limits

- Usage enforcement lives in two separate tables, both edited via Stripe webhook when a subscription is created or a tier is switched (`frontend/lib/actions/checkout/webhook.ts`):
  - `workspace_usage_warnings` — soft limits that fire a notification once per billing cycle. Checked in `check_soft_limits` in `app-server/src/utils/limits.rs`.
  - `workspace_usage_limits` — hard caps read by `get_project_and_workspace_billing_info` as `custom_bytes_limit` / `signal_cost_hard_limit_micro_usd` and enforced by the app-server and `checkSignalRunsLimit` (frontend). Only paid-tier custom limits (plus a legacy $100 Hobby default on older workspaces) have rows here; Free is capped by its tier allowance and has no Signals, with no limit row.
  - `workspace_hard_limit_notifications` — per-`(workspace_id, usage_item)` `last_notified_at` dedup for hard-limit emails (separate table so free-tier workspaces, which have no `workspace_usage_limits` row, can still dedup once per billing cycle). Stamped by `check_notify_hard_limit`.
- **No tier gets a default hard-limit row** (the $100 Hobby Signals default was dropped in LAM-2521). Existing Hobby workspaces may still carry it (`LEGACY_HOBBY_DEFAULT_HARD_LIMIT_SIGNAL_COST_MICRO_USD`, 100,000,000); `clearLegacyHobbyHardLimit` deletes it on every transition OUT of Hobby, including Hobby → Free on cancellation (otherwise it would re-apply on a later upgrade), and only when it still equals that exact value, so a user-set limit survives.
- Hobby gets two **overage warnings** ($25 signal cost / `HOBBY_OVERAGE_WARNING_SIGNAL_COST_MICRO_USD`, 40 GiB bytes / `HOBBY_OVERAGE_WARNING_BYTES`) so users accumulating a large overage bill are nudged before it grows further. These are Hobby-only rows; Pro does not get them. On transition OUT of Hobby they are cleared (matching exact values, plus the legacy $100 Signals warning, so user-adjusted thresholds are preserved) via `clearHobbyOverageWarnings`, which runs on every transition including Hobby → Free. Warnings are only written when the new tier is paid (Hobby/Pro) since Free has no warnings to carry.
- After inserting or deleting a `workspace_usage_limits` row, you MUST invalidate the per-project cache via `invalidateProjectCacheForWorkspace(workspaceId)` — the app-server caches `ProjectWithWorkspaceBillingInfo` keyed by project id and will otherwise keep enforcing stale limits until TTL.
- **Both soft warnings AND hard limits email the workspace owners.** Soft = `check_soft_limits` → `NotificationKind::UsageWarning`; hard = `check_notify_hard_limit` → `NotificationKind::UsageHardLimit`. Soft warnings fire only from the usage-update path (`update_workspace_bytes_ingested` / `update_workspace_signal_tokens` in `utils/limits.rs`), right after the cache total is bumped. Data and paid custom hard limits fire from BOTH the update path AND enforcement gates.
- **Hard-limit notifications dedup via a dedicated DB table, mirroring soft warnings 1-to-1 — once per billing cycle.** `check_notify_hard_limit` reads `workspace_hard_limit_notifications.last_notified_at` for `(workspace_id, usage_item)`, skips when it is `>= current_billing_period_start(reset_time)`, and after a successful enqueue upserts the row to `NOW()` (`usage_warnings::{get_hard_limit_last_notified_at, mark_hard_limit_as_notified}`). It must be a SEPARATE table from `workspace_usage_limits`, not a column on it: free-tier workspaces enforce the tier's included allowance with NO limit row yet still need dedup, and adding a phantom limit row would surface as a fake "custom limit" in the settings UI and the billing query. `check_notify_hard_limit` takes `reset_time` (passed as `project_info.reset_time` at all four call sites) exactly like `check_soft_limits`. Because the enforcement gates run on EVERY blocked request, the Postgres read is fronted by a short cache (`HARD_LIMIT_NOTIFIED_CACHE_KEY:{workspace_id}:{usage_item}`, 5-min TTL): only the SUPPRESSING state (a `last_notified_at` within the current cycle) is cached — never "not notified", which would widen the duplicate-enqueue race to the TTL. The frontend's `deleteHardLimitNotification` evicts this cache key (shared Redis) right after deleting the DB dedup row, so a raised/removed limit can re-notify immediately; the short TTL is only a backstop for a failed eviction.
- **The dedup row has no FK cascade from `workspace_usage_limits` (free tiers have no limit row), so the frontend cleans it up explicitly whenever the underlying hard limit changes** (`lib/actions/usage/utils.ts`: `deleteHardLimitNotification`, `clearHardLimitNotificationOnIncrease`). Rules: removing a limit → delete the dedup row (a re-created limit must start fresh); lowering a limit → keep the row (the prior breach still stands); raising a limit → delete only if already notified this cycle AND the new limit sits above current usage, i.e. the workspace is back under its higher cap so a future breach is a genuinely new event. Current usage MUST come from `getWorkspaceUsage` (cache→ClickHouse, returns `totalSignalCostMicroUsd` matching the micro-USD `signal_cost` limit unit + `totalBytesIngested`), NOT the `workspace_usage` table — those columns are only written on checkout/reset, aren't synced with the enforcement caches, and `signal_cost` there isn't micro-USD. Wired from BOTH the user path (`custom-usage-limits.ts` `setUsageLimit`/`removeUsageLimit` — `setUsageLimit` reads the prior `limit_value` before its upsert to tell raise from reduction) AND the automatic path (`checkout/webhook.ts` `clearLegacyHobbyHardLimit` drops the `signal_cost` dedup row when it deletes the legacy Hobby default).
- `NotificationKind::UsageHardLimit` and `NotificationDefinitionType::UsageHardLimit` route targets through the SAME owner-email fan-out arm as `UsageWarning` in `notifications/mod.rs::fetch_targets`. Both also acquire a handler-side race-guard lock in `NotificationHandler::handle` (`send_lock`): warnings key on `definition_id` (the warning row); hard limits share `definition_id` (= workspace_id) across usage items, so they key on `HARD_LIMIT_SEND_LOCK_KEY:{workspace_id}:{usage_item}` to avoid a bytes notification suppressing a concurrent signal-cost one. The lock is a 5-min race guard only; the durable per-cycle dedup is the DB `last_notified_at` above. On `fetch_targets` error or total fan-out failure the lock is freed with `release_lock` (NOT `remove`: the in-memory cache keeps locks in a separate map).
- **Warning thresholds are absolute billing-period totals measured from zero**, including usage covered by the plan's allowance.
- **The Warnings + Hard-limits sections (`frontend/components/workspace/usage/{warnings,limits}`) only render for paid tiers AND workspace owners** (`isOwner && tierName !== FREE` in `usage/index.tsx`). To verify them in staging (where only `Free` / `unlimited` `subscription_tiers` rows exist), temporarily insert a `Hobby` row and point the workspace's `tier_id` at it, then revert — there is no billing tab to upgrade through (the `SUBSCRIPTION` feature flag / Stripe is not wired in staging).

## Custom Model Costs (project-level pricing overrides)

- The custom-model-costs UI (`frontend/components/settings/custom-model-costs.tsx`) only edits a subset of the cost keys the Rust cost calculator understands. The `costs` JSONB is a free-form key→number map (Zod `z.record`), and `calculate_span_cost` (`app-server/src/language_model/costs/cost_calculator.rs`) already resolves many more keys (`cache_read_input_token_cost`, `cache_creation_input_token_cost`, threshold/tier/batch variants, audio, reasoning). To surface another key in the UI, add one entry to `COST_FIELDS` — display, per-million↔per-token conversion, tooltip, and the edit form all derive from that list; no backend or schema change is needed.
- Cost keys follow the litellm naming convention (`input_cost_per_token`, `cache_read_input_token_cost`, …) because the universal `model_costs` table is seeded from litellm data; custom costs must use the same key names to be picked up by the shared calculator.
