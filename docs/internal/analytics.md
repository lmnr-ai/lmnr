## Analytics / PostHog

- Client-side analytics is centralized in `frontend/lib/posthog/`. Feature code should import `track` from `@/lib/posthog` — never import `posthog-js` directly.
- Server-side PostHog client lives at `@/lib/posthog/server` (separate import path to avoid bundling `posthog-node` into client bundles).
- The `AnalyticsProvider` (in `lib/posthog/provider.tsx`) handles both PostHog init and user identification. It wraps `PostHogProvider` from `posthog-js/react` so `usePostHog()` still works as an escape hatch.
- Custom events use `track(feature, action, properties?)` which emits `${feature}:${action}`. The `Feature` type is defined in `lib/posthog/client.ts` — add new categories there before using them. Use `'sessions'` for trace sessions and `'debugger_sessions'` for CLI debugger sessions — these are distinct features.
- All tracking is no-op when PostHog is disabled (`POSTHOG_TELEMETRY !== "true"`). No conditional checks needed in feature code.
- For page-view tracking on server-component pages, use the `PageViewTracker` client component at `components/common/page-view-tracker.tsx` — server components cannot call `track` directly (no hooks). For server-action buttons that need tracking, wrap them in a dedicated `"use client"` component that calls `track` before invoking the server action (see `components/invitations/invitation-actions.tsx`).
- `PageViewTracker` deliberately uses an empty `useEffect` dependency array so it fires exactly once on mount. Callers pass inline `properties` object literals (`{ slug }`, `{ traceId }`), which would otherwise create a new reference on every render and re-fire the event.
- Auth flows (sign-in/sign-up) track `*_attempted` before the provider redirect, not on success — the OAuth/email flows navigate away before any success callback runs, so the attempt is the last reliable hook. `EmailSignInButton` takes an `action` prop (`sign_in_attempted` | `sign_up_attempted`) because the same component is rendered on both `/sign-in` and `/sign-up`.
- Tracking calls must be guarded by success (`res.ok`). Firing `track(...)` after an unchecked `await res.text()` records events for failed requests and corrupts metrics.
- `track(...)` accepts a 4th arg `{ sendInstantly: true }` that maps to posthog-js's `send_instantly` and bypasses the batching queue. Use it whenever the very next line can tear down the page before the batch flushes: OAuth/email `signIn()` redirects (`components/auth/*`), `router.refresh()` after a mutation (`switch-tier-dialog.tsx`), or any `window.location.assign/href` navigation. Batched events are lost because the request is aborted when the page unloads.
- Server-side captures from Better Auth database hooks (e.g. `auth:user_created` in `lib/auth.ts`) are fire-and-forget: `posthog-node`'s default 10s `flushInterval` schedules a background flush from the active `setTimeout` (which keeps the per-request `PostHog` instance alive until the flush fires), so the Next.js container delivers the event without an explicit `shutdown`/`flush`. Do NOT `await client.shutdown(...)` on the request path — it adds up to the shutdown timeout to the login response if PostHog ingest is degraded. Wrap the block in try/catch so analytics failures cannot break login.
- `auth:user_created` fires exactly once per brand-new account, from the `databaseHooks.user.create.after` hook in `lib/auth.ts`.
- PostHog `distinctId` across the codebase is the user's **email**, not the DB user id. The single source of identification is the client-side `identify(email, { email })` call in `lib/posthog/provider.tsx` (mounted from the root `app/layout.tsx` so it runs on every authenticated page). Per PostHog's docs, server-side `posthog.identify(...)` only updates the person profile and CANNOT do the anonymous→identified linking the browser SDK does (the server has no anonymous session), so we deliberately don't call `identify` from `posthog-node` — it would just add redundant `$identify` events without contributing any new info. Any server-side `client.capture(...)` (e.g. from Better Auth database hooks) must still pass `distinctId: email` directly on each capture — passing the DB user id creates a separate PostHog person profile and detaches `$set_once` properties and funnel events from the real user.
- Workspace grouping uses the client-side `WorkspaceGroupTracker` (`components/common/workspace-group-tracker.tsx`), which calls `posthog.group("workspace", workspace.name, { name, id })` on mount. Per PostHog's web-SDK docs, `posthog.group(...)` does two things in one call: emits `$groupidentify` to register/update the group entity's properties AND associates every subsequent session event with `$groups: { workspace: <name> }`. We rely on this so client-side `track(...)` events are auto-tagged for workspace-level analytics — do not use server-side `posthog.groupIdentify(...)` instead, since that only updates the group entity and does NOT propagate group context to client events. The tracker is rendered in `app/workspace/[workspaceId]/page.tsx` (inside `WorkspaceMenuProvider`) and `app/project/[projectId]/layout.tsx` (inside `ProjectContextProvider`); render it in a component that already fetches the workspace so we don't add a duplicate query just to access `workspace.name`. Group key is `workspace.name` (readable in the PostHog UI) — do NOT key by id, PostHog group filters display the key directly. The tracker's `useEffect` is gated on `[workspaceName, workspaceId]` so it only re-fires on workspace switch, not every render.
- **The npm module build of `posthog-js` does NOT buffer pre-init calls** — `capture`/`identify`/`reset` called before `posthog.init()` are dropped with a console warning (only the snippet-injected `array.js` build has the `_execute_array` queue). React runs child effects before parent effects, so init must NOT live in a `PostHogProvider` `useEffect`: every child `track()` on first mount of a full page load (e.g. `auth:sign_in_page_viewed`) would fire pre-init and be lost. Init runs during the provider's render via a lazy `useState` initializer (`lib/posthog/provider.tsx`), guarded `typeof window !== "undefined"` for SSR and idempotent via `posthog.__loaded` so StrictMode double-invocation can't re-init.
- **`posthog.identify(newId)` on a browser that is still identified as a DIFFERENT user silently skips the `$identify` event** (posthog-js only takes the merge path when the persisted user_state is "anonymous") — it just switches `distinct_id` and sends a `$set`, so the pre-signup anonymous history (blog/landing pageviews) is never merged into the new user. The `identify()` wrapper in `lib/posthog/client.ts` therefore calls `posthog.reset()` first when `_isIdentified() && get_distinct_id() !== userId`, forcing the anonymous→identified merge path for the new account. Logout paths (`account-menu.tsx` `handleLogout`, `session-sync-provider.tsx` cross-tab listener) also call `reset()` per PostHog's recommended practice, so this wrapper guard is the backstop for sessions that ended via an expired session rather than an explicit logout.
- `AdvancedSearch` submit tracking lives in a single place: the store's `submit` function (`components/common/advanced-search/store/index.tsx`). `removeTag` and `applyRecentSearch` funnel through `submit`, so they are covered automatically; do not instrument them separately. `addCompleteTag` and `clearAll` do NOT funnel through `submit` — we intentionally accept under-counting there in exchange for one consistent metric definition (same `filterCount`/`hasSearch` logic everywhere). The `resource` prop is threaded into the store so the event can label its origin (`traces` / `spans` / `unknown`).
- `AdvancedSearch` autocomplete fetching is gated in `components/common/advanced-search/index.tsx`: SWR only hits `/api/projects/<id>/<resource>/autocomplete` when `resource === "traces" | "spans"` AND no `suggestions` map was passed. Omit the `resource` prop (or pass anything else) on pages that have no autocomplete endpoint (e.g. evaluations) to suppress the request. Tag-level suggestions in `components/common/advanced-search/components/tag.tsx` also silently degrade to `[]` when `AUTOCOMPLETE_FIELDS[resource]` is undefined, so no backend endpoint is required for non-traces/spans consumers.

## Loops Audience Sync (cloud-only)

- `frontend/lib/loops/index.ts` (`createLoopsContact`) upserts new sign-ups into the Loops audience via `PUT https://app.loops.so/api/v1/contacts/update` (NOT the create endpoint — create 409s when the email already exists, e.g. a marketing subscriber, and their `userId` would never be attached; update upserts), wired from the same `databaseHooks.user.create.after` hook in `lib/auth.ts` as `auth:user_created`. Gated by `Feature.LOOPS` = `LAMINAR_CLOUD === "true"` AND `LOOPS_API_KEY` set, so self-hosted installs never call out.
- Mapping: `email` → Email, `id` → `userId`, `name` split on first whitespace → `firstName`/`lastName` (no whitespace → empty `lastName`; blank name → both omitted), `createdAt` → ISO string (Better Auth `user.createdAt`, falls back to `new Date()`).
- The request carries a 5s `AbortSignal.timeout` (the hook `await`s it on the sign-up path, so a slow Loops API must not stall account creation) and the whole call is try/caught — audience sync failures log via `console.warn` and never break sign-up.

## Self-hosted Telemetry (anonymous usage heartbeat)

- `frontend/lib/telemetry/` emits an anonymous `self_hosted_heartbeat` PostHog event for Helm/self-hosted deployments. Gated by `Feature.TELEMETRY` (`lib/features/features.ts`): on by default — only off when `LAMINAR_TELEMETRY_DISABLED === "true"` (operator opt-out) OR `LAMINAR_CLOUD === "true"` (cloud has first-party analytics). Deliberately does NOT gate on `ENVIRONMENT`, so the many self-hosted installs that don't set `ENVIRONMENT=FULL`/`PRODUCTION` are still observed; the `environment` property on every event lets dev/staging be filtered downstream instead of dropped at the source. Distinct from `Feature.POSTHOG` (that's cloud product analytics keyed on email) — telemetry keys on an opaque per-deployment UUID and never carries PII/customer content.
- Identity lives in a **separate `telemetry` Postgres schema** (NOT public), created via boot-time DDL in `lib/telemetry/instance.ts`, NOT a drizzle migration — so it can't break installs where the app role lacks CREATE on public, and the OSS migration set stays telemetry-free. The `telemetry.instance` table is a singleton (boolean PK `id` always true) holding `instance_id uuid` + `last_reported_at`.
- Cross-replica dedup is a CAS window-claim: `claimReportingWindow(intervalMs)` does an atomic `UPDATE ... WHERE last_reported_at IS NULL OR last_reported_at < now() - interval`, returning a row only to the winner. The job timer polls hourly but the 6h cadence is enforced by this DB claim, so multiple frontend pods + restarts can't over-report. Wired fire-and-forget from `instrumentation.ts::register()` (outside the `LOCAL_DB` gate, after Laminar init).
- **Counting the exposed `_v0` views directly is impossible** — every view in `4_views.sql` etc. is a project-parameterized view function (`WHERE project_id={project_id:UUID}`), so `count() FROM spans_v0` errors. `lib/telemetry/stats.ts` instead maps each exposed view to its physical backing table (`spans_v0`→`spans`, `traces_v0`→`traces_agg`, `clusters_v0`→`signal_event_clusters`, `event_clusters_all_v0`→`events_to_clusters`, etc.) and reads `system.tables.total_rows` — instant, no FINAL scans, no per-project iteration. Keep `VIEW_BACKING_TABLES` in sync with the query-engine `TableRegistry` (`validator.rs`). Counts are emitted as exact integers (`count_<view>_v0`); they are PRE-merge row counts, so folding tables (`traces_agg`'s per-batch partials, the RMTs) read above their logical entity count — fine for a usage-magnitude signal.
- Version comes from `NEXT_PUBLIC_APP_VERSION` (baked at Docker build, set as runtime ENV) — `npm_package_version` is empty in prod because the container starts via `node server.js`, not an npm script. Optional `LAMINAR_TELEMETRY_LABEL` lets an operator opt into being identifiable. The capture sets `$ip: null` (drops the source IP entirely, not just geoip enrichment) plus `disableGeoip: true`, so no IP is ever stored against the deployment.
