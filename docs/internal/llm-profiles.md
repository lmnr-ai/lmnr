# LLM profiles

<!-- Detailed working notes for coding agents and developers. -->

- **What they are.** Workspace-scoped, encrypted LLM credentials + a model list (`llm_profiles`, `llm_profile_models`; Settings → Workspace → LLM profiles). A signal pins one profile and one of its models (`signals.llm_profile_id` / `llm_model`, `CHECK (both NULL or both set)`, composite FK `→ llm_profile_models(profile_id, name) ON DELETE RESTRICT`, so deleting a profile/model in use fails with 23503 and the UI disables the action). Names are `UNIQUE (workspace_id, name)`, case-sensitive. Any workspace member reads and writes — there is no owner/admin gate anywhere (UI, frontend API, project API key, CLI); a project API key manages every profile of its project's workspace.
- **Writes live in the app-server** (`app-server/src/llm/profiles/service/`: `mod.rs` persistence + error mapping, `validate.rs` input rules, `secrets.rs` prune/merge/mask), mirroring `signals::service`: one `create/update/delete/list/get/probe` set behind three auth surfaces that only translate auth + HTTP — internal `POST/PATCH/DELETE /api/v1/workspaces/{workspace_id}/llm-profiles[/{id}]` + `POST …/llm-profiles/test` (`routes::llm_profiles`, called server-to-server by the Next.js actions after `checkUserWorkspaceRole` membership), project-API-key `GET/POST /v1/llm-profiles`, `GET/PATCH/DELETE /v1/llm-profiles/{id}` (`api::v1::llm_profiles`, project → workspace via `service::workspace_for_project`), and CLI `…/v1/cli/llm-profiles[/{id}]` (`api::v1::cli::llm_profiles`, `CliProjectAuth`; both project surfaces share `api::v1::llm_profiles::handlers`). Profiles are addressed by UUID everywhere. Bodies are flat `{ name, provider, config, secrets, models }` with PLAINTEXT secrets (the Next action flattens the form's `{ profile: { provider, config } }` and no longer encrypts anything — `secrets.ts` keeps only `decryptSecrets` for the read side); the service normalizes `config` per provider (drops fields the provider does not use, same rules as the Zod union), prunes secrets to the ones the config needs, merges omitted keys from the stored blob on PATCH/probe, encrypts under the profile id, diffs `llm_profile_models` (delete only removed names so the RESTRICT FK fires for in-use ones) and `cache.remove`s `llm_profile:{ws}:{id}`. PATCH: every field optional; `provider` without `config` is a 400; `models` replaces the list. Reads for the UI (`listLlmProfiles`, `listProjectLlmProfileOptions`) stay in the frontend against Drizzle. `CrudError` → `Validation` 400, `DuplicateName`/`InUse` 409 (23505 / 23503 / pre-counted signals), `NotFound` 404, else 500; `frontend/lib/actions/llm-profiles/app-server.ts` (`callAppServer`, `AppServerError`) carries the status back so the Next routes pass it through instead of flattening to 500. The `LlmProfile` response (`LlmProfileResponse`) is the frontend `LlmProfile` shape with masks in `secrets`; `ProfileConfig`/`ProfileSecrets` skip `None` on the wire because the Zod schemas reject `null`. `LlmProfile.created_at` was added for this; a Redis entry written before it fails to deserialize and is simply refetched.
- **One flag.** Profile CRUD (UI, internal + project + CLI APIs) is never gated: profiles back the playground everywhere, so there is no `LlmProfiles` feature. `Feature::SignalLlmProfiles` / `Feature.SIGNAL_LLM_PROFILES` `= !LAMINAR_CLOUD` (`env::connections::LAMINAR_CLOUD`, `BoolEnv`, default false) gates only *pinning a profile on a signal*: on Cloud signals run on Laminar's own keys and the signal APIs 400 any profile field with `Signals run on Laminar's own keys on Laminar Cloud`. `Feature::Signals` is `has_llm_backend() || SignalLlmProfiles`, so a self-hosted deployment with NO `LLM_PROVIDER` still spawns the signal workers; `LlmClient::new(store)` then constructs with no env provider and a request that finds no feature route fails per call with `No LLM configured for feature 'signals': set LLM_PROVIDER or add an LLM feature route`. Clustering, input extraction, SP regex extraction and the frontend AI features resolve through the same `llm_feature_routes` table (see `docs/internal/ai-features.md` → "LLM feature routes").
- **Wire shapes** (Zod in `frontend/lib/actions/llm-profiles/schema.ts`, serde in `app-server/src/llm/profiles/mod.rs`; the Rust tests round-trip literal frontend JSON — keep them in lockstep). `provider` ∈ `openai_completions | openai_responses | anthropic | gemini | groq | mistral | bedrock | azure_chat_completions | azure_responses | azure_anthropic | custom | custom_responses` (`anthropic` reuses `AzureAnthropicClient` pointed at `api.anthropic.com` via `AzureAnthropicClient::direct`; `groq` / `mistral` are the `OpenAIClient` with fixed hosts). Non-secret fields live in plaintext `config` jsonb with a tagged `auth: { type }` (`api_key`, or for bedrock `aws_keys` | `bearer_token`); Writes reject (400) any `config` field the provider never sends (e.g. `baseUrl`/`headerNames` on `azure_*` or `openai_*`, `region` off Bedrock) and header values for a non-gateway provider or an unlisted header name, instead of silently dropping them (`provider_fields.rs::reject_unused_fields`, `validate.rs::validate_secrets`). `custom` (Chat Completions) and `custom_responses` (Responses API) are OpenAI-compatible gateways: `baseUrl` + API key, optional `headerNames`; every custom-header check goes through `LlmProfileProvider::is_custom_gateway` / `isCustomProvider`, and the form collapses both into one entry with an API-shape select. The frontend wraps `custom_responses` with `store: false` so multi-step AI SDK calls resend prior items instead of `item_reference` ids a non-storing gateway cannot resolve. Every secret (API key, AWS secret, bearer token, all custom header VALUES) lives in one XChaCha20-Poly1305 blob `secrets = { nonce, value }` (hex) encrypted with `AEAD_SECRET_KEY`, **AAD = the profile id** (`crypto.rs::decrypt`, whose `aad` is a plain string; the data plane and Slack pass the workspace id) — a blob copied to another row will not decrypt. A malformed `AEAD_SECRET_KEY` is logged at app-server startup (`crypto::check_key`), and profile writes, probes and stored-secret decrypts return its decode error as `CrudError::Misconfigured` (500 with the message, never the key); the frontend's `hexKeyFromEnv` rejects anything but 64 hex characters, since `Buffer.from(hex)` would silently truncate. Secrets are write-only: GET returns a `first3***last3` mask per stored value (fully starred when too short) plus header names, which `SecretField` renders as its placeholder so a user can tell which key a profile holds; PATCH keeps a secret when it is omitted/blank, so the form never has to re-send credentials. The mask is why every read decrypts each row, and why a plain `member` can see a key's edges. The Zod union groups providers that share a config (`API_KEY_PROVIDERS`, `AZURE_PROVIDERS`) into one branch each via `z.literal([...])` — the Rust `ProfileConfig` is one flat all-`Option` struct, so the branch count is a frontend validation choice, not a wire constraint.
- **Runtime path.** `ProviderRequest.route: LlmRoute` is either `Profile(LlmProfileRoute { profile_id, model, project_id })` — the pin, which wins over every feature route (one model serves every call in the run) — or `Feature { feature, project_id }`, which `LlmProfileStore::resolve_feature` looks up in `llm_feature_routes` before falling back to env. `LlmClient::resolve` is async: a profile route goes to `LlmProfileStore::resolve`, which takes the project's workspace id from the shared `project:{id}` billing entry (`get_workspace_info_for_project_id`, already warm from limits checks), reads the row through Redis scoped to that workspace (`llm_profile:{workspace_id}:{id}`, TTL 7d, `service.rs` removes it on every write; the DB query also filters on `workspace_id`, so a foreign profile reads as not found), checks the model is listed, decrypts, builds the `ProviderClient` (`build.rs`, explicit-config constructors on each client) and caches it in-process keyed `(profile_id, updated_at)` so credentials are only decrypted when the row changed. Reported provider names for spans/cost are the `model_costs` provider prefixes, shared with the env path in `LlmClient::resolve_model_provider` (`openai_completions` / `openai_responses` / `custom` → `openai`, `azure_chat_completions` / `azure_responses` → `azure`, `azure_anthropic` → `azure_ai`; `anthropic` / `gemini` / `groq` / `mistral` / `bedrock` verbatim).
- **Failure posture.** Every store error is `ProviderError::ConfigError` (non-retryable): missing row, cross-workspace, unlisted model, decrypt failure, client build failure. Existing signals with `NULL` route keep working on env vars; the edit form shows a warning banner and leaves the selects optional, while new signals require the pair (UI, frontend API `CreateSignalSchema`, CLI). The frontend write schemas take the pair as `.optional()` only, NOT `.nullable()` — absent means "keep the stored route", and no caller sends null (the form omits both fields unless both are filled, and the profile select has no "None" entry). The columns stay nullable and `Signal`/`ManageSignalForm` still read `string | null`, so there is no API-level way to move a signal back off profiles onto env credentials; re-add `.nullable()` plus a clearing branch in `resolveLlmRoute` if that is ever wanted. Validation is split three ways on purpose: pair completeness and the Cloud rejection are Zod refines on both schemas (`llmRouteIsPaired`, `llmRouteIsAllowed`), "a new signal must pin a profile" is one check in `createSignal` because `requireLlmProfile: false` is a caller trust level rather than input, and `resolveLlmRoute` only does the workspace/model DB join — do not move that join into a refine. `resolveLlmRoute` also re-checks `Feature.SIGNAL_LLM_PROFILES` and returns undefined so a caller that skips the refines still cannot pin a route on Cloud; the refine owns the 400, the function owns the write. Default signals seeded at workspace creation pass `requireLlmProfile: false`.
- **CLI surface.** `lmnr-cli signal create` / `signal update` accept `--llm-profile-id <uuid>` + `--model <name>` (wire fields `llmProfileId` / `model` on `SignalInput` / `UpdateSignalInput`), and every `signal get` / `signal list` response echoes `llmProfileId` + `llmProfileName` + `model` (all `null` for env-routed signals). `lmnr-cli llm-profile` (aliased `llm-profiles`) has full CRUD — `list` / `get <id>` / `create` / `update <id>` / `delete <id>` — backed by `api::v1::cli::llm_profiles` (`CliProjectAuth`; list returns `{ llmProfiles: LlmProfileResponse[] }`, the other routes return a bare `LlmProfileResponse`). The CLI maps flags to the flat `{ name, provider, config, secrets, models }` body and does no validation of its own: feature-gating, pair completeness, workspace membership, unlisted-model, in-use (RESTRICT) and duplicate-name errors are all surfaced verbatim via the CLI's error-envelope unwrapping. The profile routes themselves are available on Cloud too (profiles back the playground); only `signal create/update` with a profile is rejected there.
