## Slack OAuth Broker

- Lets self-hosted instances use Laminar's official Slack app with their enterprise license key instead of recreating the Slack app + 5 env vars. The broker runs both OAuth legs and hands the bot token back to the calling instance; message content never transits the broker ("direct-send").
- Instance auth is the enterprise license, verified offline: `authenticateInstance` in `lib/actions/slack/broker.ts` runs `verifyLicense` and returns `license:<licenseId>` as the `instanceId`, or null for anything that doesn't verify or has passed its `expiresAt`. No database lookup and no per-instance row. The `slack_broker_instances` table (migration 0088, shared with OSS) is no longer read; drop it in OSS so the migration lands in both repos.
- Three routes under `app/api/broker/slack/`: `/start` (POST, server-to-server) and `/redeem` (POST, server-to-server) both take the instance key in `Authorization: Bearer`; `/cb` (GET) is the ONLY browser-facing leg (Slack's registered redirect target). The bot token never appears in a browser-visible URL — `/cb` mints a one-time claim and redirects with only the claim + team name.
- Env vars: `SLACK_BROKER_STATE_SECRET` (HMAC-SHA256 key for the signed `state` blob), `SLACK_CLIENT_ID`/`SLACK_CLIENT_SECRET` (official app creds for `oauth.v2.access`, HTTP Basic auth), and `NEXT_PUBLIC_URL` (derives the registered `redirect_uri` `${NEXT_PUBLIC_URL}/api/broker/slack/cb` — must exactly match between authorize and token exchange).
- Security invariants: `state` is HMAC-signed and binds `returnUrl` so a claim can only redirect back to the originating instance; the claim is single-use, stored in Redis cache with a 5-min TTL, removed on redeem, and bound to `instanceId` (`/redeem` rejects claims whose `instanceId` ≠ authenticated caller).
- The claim ALSO binds `workspaceId` (carried in signed `state`, copied into `ClaimPayload` at `/cb` mint, echoed by `/redeem`). `instanceId` binding alone can't separate workspaces (one instance key for all), and the callback's `workspaceId` rides the public redirect as a mutable query param. Instance-side `redeemBrokeredSlackToken` rejects any claim whose echoed `workspaceId` ≠ URL `workspaceId` (cross-workspace claim substitution) — the broker-bound complement to the callback's `isUserMemberOfWorkspace` check.
- `state` is also single-use: `mintState` records the nonce server-side (`slack_broker_state:<nonce>` → `{instanceId, codeVerifier}`, 10-min TTL) and `/cb` calls `consumeState` (atomic `getAndRemoveIfMatch`, matched by `instanceId`) before code exchange — the HMAC alone is replayable. `mintState` is `async`; await it in `/start`.
- PKCE (S256) defends against OAuth token injection (single-use state alone doesn't stop an attacker who leaks a victim's `state`, wins the race to `/cb`, and completes it with their own Slack `code`; a session cookie can't bind the flow since `/start` is server-to-server). `mintState` generates the PKCE pair, stores the secret `verifier` in the server-side nonce record (NEVER in `state`), returns the public `challenge` for the authorize URL; `/cb` reads the verifier via `consumeState` and passes it to `oauth.v2.access`. The direct flow uses PKCE too (see below), so `exchangeSlackOauthCode` requires a `codeVerifier`.
- Single-use state/claim records live in `cache` (`lib/cache.ts`), which falls back to **per-process memory** when `REDIS_URL` is unset — a scaled broker without Redis routes `/start`/`/cb`/`/redeem` to different workers and never finds the record. `mintState` calls `assertSharedStore()` to fail loudly at `/start` when `REDIS_URL` is missing. Broker is Cloud-only (Redis always set); the guard catches misconfigured self-hosted deployments.

### Instance-side brokered consumer (self-hosted)
- The instance-side caller lives in the SAME OSS repo and is inert unless `SLACK_BROKER_URL` is set and a license key resolves (`getBrokerLicenseKey`: env license that verifies → key saved in Settings → License). The broker routes and the consumer routes coexist in one codebase: broker routes activate where the official app creds exist (Cloud); consumer routes activate where the two broker env vars are set (self-hosted). A given deployment is one or the other, decided purely by env. The bearer is the signed enterprise license. See `docs/internal/licensing.md`.
- Connect flow: `SlackConnectButton` is double-duty — **brokered mode takes precedence**: when `brokerEnabled` it links to `/api/integrations/slack/broker-start`; otherwise cloud mode links to `/api/integrations/slack/start` (see the direct-flow bullet below); `slackClientId`/`slackRedirectUri` props only signal that the direct flow is configured. Broker must win because a broker-configured deployment has no usable Slack app of its own — leftover `SLACK_CLIENT_ID`/`SLACK_REDIRECT_URL` env vars must not divert it into the broken direct flow (the button is a client component and can't see `ENVIRONMENT`/secret vars to replicate the server-side `cloudEnabled` gate). On Laminar Cloud the broker vars are never set, so the direct flow still wins there. Wired ONLY through the workspace integration page chain (`page.tsx` → `WorkspaceComponent` → `WorkspaceIntegrations` → `SlackConnectionCard`), NOT onboarding (which calls `buildSlackConnectUrl` without `brokerEnabled`, so it's cloud-only).
- `/api/integrations/slack/broker-start` (GET) POSTs the broker `/start` with the Bearer instance key (key never enters the browser) and 302s the browser to the returned `authorizeUrl`. The `returnUrl` it sends the broker points back at `/api/integrations/slack` with `workspaceId` (and optional `returnPath`) embedded — the broker echoes only claim + team on the way back, so the instance must carry its own workspace context in the returnUrl.
- `/api/integrations/slack` (the callback) has a brokered branch alongside the `code` branch, keyed on the `workspaceId` query param (the direct path never sets it — it carries context in `state`): it calls `redeemBrokeredSlackToken({claim, workspaceId})` (`lib/actions/slack/index.ts`), which POSTs the broker `/redeem` with the Bearer key, then persists via the shared `persistSlackIntegration` (same encrypt + upsert as the direct path). The stored `slack_integrations` row is identical regardless of path, so the Rust send path is path-agnostic. Both success (with `claim`) and broker-error (`slack=error`, no `claim`) route through this branch so the error lands on the workspace integrations card, not the `/projects` fallback.
- **Direct (Cloud) flow state is server-minted.** `/api/integrations/slack/start` (GET, browser-facing) checks session + membership, then `mintSlackOauthState` (`lib/actions/slack/oauth-state.ts`) stores `{userId, workspaceId, returnPath, codeVerifier}` under `slack_oauth_state:<nonce>` (10-min TTL) and redirects to `buildSlackAuthorizeUrl(nonce, challenge, SLACK_REDIRECT_URL)`. The `state` Slack echoes back is only that opaque nonce. The callback calls `consumeSlackOauthState(state, session.user.id)` (atomic `getAndRemoveIfMatch` on `userId`): single-use, and bound to the user who started the flow, which blocks login-CSRF where a victim is lured onto an attacker's `code`+`state`. Workspace/returnPath/verifier come only from the record. NEVER put workspace context back into `state`. Like the broker, the record lives in `cache`, so a multi-replica deployment using the direct flow needs `REDIS_URL` (the per-process fallback misses across pods). States minted before a deploy of this flow fail once; the user just reconnects.
- **Every callback branch MUST authorize the workspace against the caller's session** (`isAuthorizedForWorkspace` in the route: `z.guid()` + `getServerSession` + `isUserMemberOfWorkspace`). The callback is a public OAuth redirect target outside the `proxy.ts` matcher, and both the brokered `workspaceId` param and the direct-flow `state` are attacker-controlled. Without the gate, anyone could install the public Laminar Slack app into their own Slack with `state=<victim workspace uuid>` and the upsert on `workspace_id` would replace the victim's integration (LAM-2465). On Cloud that also feeds the team-scoped in-Slack project picker (`lmnr-private`), so it escalated to the agent reading the victim's traces. The gate runs BEFORE the error branches too: `buildRedirectUrl` resolves the workspace's newest project id, which leaked to anonymous callers. Unauthorized callers get the generic `/projects?slack=error`.
- Local repro of the callback needs `NEXT_PUBLIC_URL` set (`prefixedBase()` throws `Invalid URL` → 500 otherwise). Staging Postgres may lag the schema (e.g. `users.preferences` missing) so a DB-backed session fails; Better Auth's compact cookie cache (`better-auth.session_data` = base64url `{session, expiresAt, signature}`, HMAC-SHA256 of `JSON.stringify({...sessionData, expiresAt})` with `BETTER_AUTH_SECRET`) skips the user read.
- Crypto: `getSlackKeyFromEnv` (frontend `lib/crypto.ts`) and `decode_slack_token` (`app-server/src/notifications/slack.rs`) both require `SLACK_ENCRYPTION_KEY`. Self-hosters don't set a second key — the Helm chart (`lmnr-ai/lmnr-helm`) maps the cluster's `AEAD_SECRET_KEY` secret onto `SLACK_ENCRYPTION_KEY`, so the env var is always populated without an in-code fallback. BOTH sides must stay in sync or encrypt/decrypt diverge.
- `Feature.SLACK` is enabled when EITHER all cloud vars OR `SLACK_BROKER_URL` is set. Whether the brokered connect button shows is decided per page (`slackBrokerEnabled = !!(await getBrokerLicenseKey())`), since the key may live in Postgres.
