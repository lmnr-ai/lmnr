## Evaluations Page (groups + table)

- **Evaluation-level `name`/`group_id`/`metadata` live ONLY in Postgres `evaluations`** — ClickHouse `evaluation_datapoints` carries per-datapoint data (its `metadata` column is the datapoint's, not the evaluation's). So SDK-facing evaluation updates (`POST /v1/evals/{eval_id}`, `api/v1/evals.rs::update_eval`) are a pure Postgres UPDATE with no CH write. `group_id` is deliberately immutable there (ClickHouse datapoint rows denormalize `group_id` at insert time via `get_evaluation_group_id`, so changing it post-hoc would desync the two stores).
- **`evaluation_datapoints_v0` sources trace-level columns from `traces_agg` + `traces_static`** (migration `55`): costs/tokens/`start_time`/`end_time`/`duration` + `trace_status` (`has(statuses,'error')`) + `trace_tags` from a `traces_agg` GROUP BY, `trace_metadata` + `top_span_id` from `traces_static FINAL`. The view takes only `project_id` (no time params), so both joins carry a semi-join on `id IN (SELECT trace_id FROM evaluation_datapoints WHERE project_id = …)` to prune on the `(project_id, id)` PK instead of scanning every trace in the project.
- **Two type traps when recreating this view**, both caught by diffing `system.columns` against the previous definition: the `traces_agg` aggregates leak their `SimpleAggregateFunction(min|max, …)` wrapper into the exposed type (cast with `CAST(min(start_time) AS DateTime64(9,'UTC'))`), and `trace_status` must be `toLowCardinality(...)` to stay `LowCardinality(String)`.
- **`trace_spans.duration` must be an explicit expression** — the physical `spans` table has NO `duration` column, so a bare `duration` inside that subquery resolves against the OUTER `end_time - start_time AS duration` alias (which then rebinds the names to the spans columns — it only works by accident), and qualifying the outer alias (`t.end_time - t.start_time`) breaks that resolution with `Unknown expression identifier 'duration'` / `Correlated subqueries are not supported in JOINs`. Compute it inline: `(toUnixTimestamp64Nano(end_time) - toUnixTimestamp64Nano(start_time)) / 1000000000`.
- **`task_id` groups trials** (CH migration `80_task_id.sql`; queryable as `evaluation_trials.task_id`, see `sql-query-engine.md`). A Task is a test case; each `evaluation_datapoints` row is one Trial of it. Rows sharing `(evaluation_id, task_id)` are repeated trials — the server never dedupes or renames them; `id` stays the per-trial UUID (RMT key) and `index` is still written for backwards compat. Ingestion (`POST /v1/evals/{id}/datapoints`) takes optional `taskId`, else `toString(index)`; parts written before the column existed read the same value from its `DEFAULT toString(`index`)`. Eval comparison (`buildComparisonQuery`, trial-comparison route) joins on `task_id`, so old index-based runs still match each other but not runs keyed by dataset task ids. `dataset_datapoints.task_id` defaults to `toString(id)`; the v1 dataset push renames duplicates within a dataset to `<task_id>#2`, `#3`, ... and frontend writes that re-insert an existing id (edit, version restore) must carry the stored `task_id` or it resets to the default.
- **`created_at` is the Trial's first save** (migration `80`). The SDK saves each Trial twice under one `id` (pending, then with output), so `insert_evaluation_trials` looks up `min(created_at)` for the incoming ids (`get_trial_created_ats`) and carries it over; the update path's INSERT…SELECT copies `existing.created_at`. Parts older than the column read `DEFAULT updated_at`; the migration `MATERIALIZE`s `task_id` and `created_at` (cloud runs these ALTERs by hand). Trials sort by `created_at` within a Task and are labelled by their id's first 8 hex chars (both SDKs mint UUIDv4). There is no per-Task Trial number: a `row_number()` in `evaluation_datapoints_v0` blocks filter pushdown past the window (whole-project scans when `eval_ids` isn't derived), and ClickHouse has no write-time counter without Keeper.
- The evaluations list page (`frontend/components/evaluations/evaluations.tsx`) is split into the groups sidebar (`groups-list/`) and the table. The selected group is the `groupId` URL query param; the groups list defaults it to the first group via an effect on load. The table fetch is gated on `!isGroupDefaultPending` — without that gate the table fires one fetch with `groupId=null` (returns ALL groups' evals) BEFORE the default groupId is applied, then re-fetches filtered, briefly flashing the wrong (unfiltered) rows. `isGroupDefaultPending = isGroupsLoading || (!groupId && groups.length > 0)`; both components hit `/evaluation-groups` via SWR so the request dedupes.
- **InfiniteDataTable icon columns need `size` ≥ 60.** `cell.tsx` renders every cell with `px-4` (32px) padding and wraps content in an `overflow: hidden` truncate div, so a 28px (`h-7 w-7`) icon button in a `size: 40` column gets clipped — clicks land on the row instead of the button and trigger `getRowHref` navigation. Use `size: 64` for a single icon-button column and `e.stopPropagation()` in its `onClick` (same pattern as `createCheckboxColumn` in `utils.tsx`).
- `useDefaultLayout` from `react-resizable-panels` dereferences `localStorage` at call time in its default storage — throws during SSR. Pass a window-guarded `LayoutStorage` and gate the `ResizablePanelGroup` mount on a client check (`useSyncExternalStore` pattern, see `evaluations.tsx` / `queue-content.tsx`) so the persisted layout is available at Group registration time.
- Chart preferences persist per `(projectId, groupId)` in localStorage: `evaluations-chart-hidden:<pid>:<gid>` (evaluations hidden via the locked `__chart_visibility` eye column) and `evaluations-chart-hidden-scores:<pid>:<gid>` (scores deselected in the chart legend). Both store the HIDDEN set, not the visible set, so newly-appearing evals/scores default to visible. The progression chart is combined-only (per-score min-max-normalized lines); a constant score (max === min) draws at 0.5 so it isn't pinned to a clipped plot edge.

## JSON/string cell rendering (`JsonTooltip`)

- `frontend/components/ui/json-tooltip.tsx` is the single renderer behind every free-form cell across the tables: traces Input/Metadata, evaluations Target/Data/Metadata/custom columns (via `evaluation/columns/data-cell.tsx`), and dataset Data/Target/Metadata. A change there hits all three tables at once — verify against all of them, not just the one in the ticket.
- It JSON-parses string `data` first, so a value that isn't JSON stays a plain string. Both the cell preview and the tooltip body must branch on `typeof === "string"` and render the raw string; `JSON.stringify` on a string re-adds the surrounding `"` quotes (LAM-2130). Objects/arrays/numbers still go through `JSON.stringify(…, null, 2)`.
- The landing-page eval mock (`components/landing/sections/did-my-fix-work/eval-comparison-mock.tsx`) hardcodes its cell strings and does NOT use `JsonTooltip` — keep it visually in sync by hand when cell formatting changes.

## Advanced Search filter tags

- The search-bar filter tag (`frontend/components/common/advanced-search/components/tag.tsx`) and the field dropdown (`.../components/select.tsx`) must render filters whose `column` is NOT in the registered `ColumnFilter[]` (`filters` prop). A shared/bookmarked URL can carry a filter for a column the current user hasn't configured — most commonly a per-user `custom:<name>` column that lives only in the URL-author's table config. If `getColumnFilter` returns undefined, synthesize a fallback `{ name: field, key: field, dataType: tag.dataType ?? "string" }` instead of returning `null`; otherwise the tag silently disappears while the filter stays ACTIVE on the query (invisible + un-removable). Applies to every `AdvancedSearch` consumer (traces/spans/sessions/signal-events).
- Recent-search chips (`.../components/suggestions.tsx`) and the tag remove label must show enum **labels**, not stored values (`displayFilterValue`). The live tag already does this via `EnumValueInput`; recents were rendering `has_event = event` instead of `Has event = Yes`.

## Add-filter popover (`datatable-filter`)

- `FilterPopover` (`frontend/components/ui/infinite-datatable/ui/datatable-filter/ui.tsx`) dedups only EXACT duplicates (`isEqual` against the active list); duplicate columns with different values are legitimate (multiple `metadata` key=value filters combine with AND server-side; param keys are indexed per filter in `buildColumnFilters`), and the `AdvancedSearch` bar already allows them. After apply, it MUST clear `filter.value` (keeping column/operator) — otherwise popover state persists, a re-click re-submits the same filter, and the dedup makes it a silent no-op.

## Dataset datapoints filters + custom columns

- The dataset datapoints table supports metadata key=value filtering AND user-defined custom SQL-expression columns, built in `frontend/lib/actions/datapoints/utils.ts` mirroring the traces-table pattern. Custom columns are threaded as a JSON `customColumns` URL param (`{id, sql, filterSql?, dbType?}`, ids prefixed `custom:`); the metadata filter uses ClickHouse `simpleJSONExtractString`/`simpleJSONExtractRaw` splitting `filter.value` on `=`, identical to `lib/actions/traces/utils.ts`. `dataset_datapoints` is already in the query-engine validator allowlist AND the frontend SQL schema, so this is frontend-only (no Rust/migration).
- **Datapoint action functions (`getDatapoints`/`countDatapoints` in `lib/actions/datapoints/index.ts`) must destructure `input` DIRECTLY — never re-call `Schema.parse(input)`.** The API route handlers already run `parseUrlParams(searchParams, Schema)`, which applies `FiltersSchema`'s `filter` transform that JSON.parses each filter string into a Filter OBJECT. Re-parsing in the action then fails because the Zod schema's `filter` field still expects an array of STRINGS → `ZodError: expected string, received object` → 500 on every filtered request. `getTraces` in `lib/actions/traces/index.ts` is the reference: it destructures `input` directly. The schemas (`ListDatapointsSchema`/`CountDatapointsSchema`) are still used by the routes via `parseUrlParams`, just not re-applied downstream.

## Saved views (`infinite-datatable/views/`)

- **Column visibility is absolute, not a diff.** `reconcileConfig` uses `loaded.columnVisibility ?? defaults.columnVisibility`, so a view without the key falls back to the table's default visibility, and tables like the eval datapoints table (`DEFAULT_HIDDEN_COLUMNS` in `evaluation.tsx`) hide columns by default. `normalizeViewConfig` must therefore persist the full map, explicit `true` and `{}` included. Dropping them made "show all columns → save" silently revert the view to the default column set (LAM-2357). `resetColumns` restores `defaults.columnVisibility`; resetting to `{}` would show every column.
- The view `PATCH` replaces `config` wholesale (no merge), so anything `normalizeViewConfig` omits is lost on save.

## Dashboard Time Grouping

- Time-range-to-grouping logic is duplicated in three places that must stay in sync: `getGroupByInterval` (`frontend/lib/utils.ts`), `inferGroupByInterval` (`frontend/lib/time.ts`), and `getOptimalDateFormat` (`frontend/components/chart-builder/charts/utils.ts`). When changing grouping thresholds, update all three.
- Time-series chart utils are ALSO duplicated in two places that must stay in sync: `frontend/components/charts/time-series-chart/utils.ts` (the shared `TimeSeriesChart` used by traces/signal-clusters/alerts) and `frontend/components/traces/traces-chart/utils.ts` (a legacy copy whose `chart.tsx` is currently unmounted but still type-checked). `isValidZoomRange`/`normalizeTimeRange`/`calculateOptimalInterval` exist in both. Drag-zoom minimum range is 5 minutes (`isValidZoomRange` `minMinutes` default); `calculateOptimalInterval` clamps sub-minute buckets to `1 minute` (a 0-value interval would make ClickHouse `toInterval(0, 'minute')` bucket everything together).

## Dashboard chart editor: freeform SQL fallback

- Charts with a saved `settings.queryStructure` open in the visual form. Charts without it try `/sql/to-json`; if conversion fails or the best-effort parser loses a CTE/JOIN/other unsupported clause or yields a table not in the visual builder, the editor shows the saved SQL in `freeform-form.tsx`, not an empty visual form. A saved freeform chart keeps `queryStructure: null`, and on reopening gets another conversion attempt (so legacy charts that can round-trip still use the visual builder).
- Freeform edits run through the same `/sql` route and chart preview, but do not call `/sql/from-json` or apply generated form defaults. Save persists raw `query` and current `settings.config` with `queryStructure: null`; the shared save button also preserves the visual editor's hidden ID metrics when saving a form. Freeform table previews run the SQL verbatim without appending pagination, since the raw query may already contain `LIMIT`.
- A query/parameter edit aborts an in-flight dashboard-editor preview and clears its result; the user explicitly runs the updated freeform query. Unset/conflicting placeholders are shown in the parameter chips and block Run, not Save.

## Dashboard Refresh

- The dashboard header's Refresh button bumps `refreshKey` in `components/dashboards/dashboard-refresh-context.tsx`; each `Chart` includes it in its fetch effect deps, so only per-chart `/sql` requests re-run. The chart list (the charts SWR in `grid-layout.tsx`) is deliberately NOT revalidated and the page is not reloaded, so scroll position is kept. Grid cells have fixed heights, so the per-chart skeleton during refetch doesn't shift the layout.

## Dashboards & Dashboard Charts API

- A project has many `dashboards`; each `dashboard_charts` row has a NOT NULL `dashboard_id` (ON DELETE CASCADE). Migration `0115_multiple_dashboards` backfilled one "main" dashboard per project that had charts. Projects with no dashboard get one lazily via `getOrCreateDefaultDashboard` (the oldest dashboard is the landing one); it and `deleteDashboard` share a `pg_advisory_xact_lock(hashtext('dashboards:'||projectId))`, so the last dashboard can't be deleted (409 `LastDashboardError`) and concurrent first visits don't create two defaults.
- Routes: `/dashboards` redirects to the last-visited dashboard (`last-dashboard-id` cookie, path-scoped to `/project/<id>/dashboards`, written client-side by `dashboards.tsx`), falling back to the default, `/dashboards/[dashboardId]` shows it, and `/dashboards/[dashboardId]/charts/[chartId|new]` is the editor. The pre-multi-dashboard URLs `/dashboards/new` and `/dashboards/<chartId>` are redirected by the `[dashboardId]` page (non-uuid → default dashboard; a chart id → that chart's dashboard). Keep that fallback; old links live in Slack and docs.
- API: `app/api/projects/[projectId]/dashboards` (GET list with `chartCount`, POST create), `.../[dashboardId]` (PATCH rename, DELETE), and `.../[dashboardId]/charts` with `GET` (list), `POST` (create), and `PATCH` (bulk layout update). There is NO `PUT` on the collection. Creating a chart from the chart-builder/sql-editor must use `POST`, not `PUT` (which would silently 405 and never reach `createChart`). Build URLs with `getDashboardsUrl`/`getChartsUrl` from `components/dashboards/types.ts`; the charts URL is also the SWR key that every chart mutation revalidates. The switcher's per-dashboard `chartCount` comes from the dashboards list, not from the charts key, so anything that adds or removes a chart (preset dropdown, chart-header delete/duplicate, editor save of a new chart) must revalidate `getDashboardsUrl` too or the counts go stale.
- **CLI writes (`lmnr-cli dashboard …`) go through `/v1/cli/dashboards` (`api/v1/cli/dashboards.rs`, `CliProjectAuth`):** `POST` create, `PATCH /{id}` rename, `DELETE /{id}`, `PUT /{id}/charts` batch upsert (body `{charts}`), `DELETE /{id}/charts` (body `{chartIds}`). All call the same `crate::dashboards` service as the frontend's app-server routes. Responses carry a `dashboardUrl` built from `NEXT_PUBLIC_URL`. There are no CLI reads: the CLI reads through `lmnr-cli sql query` (`dashboards` / `dashboard_charts`).
- **Chart query checks live in `dashboards/chart_query.rs` and run on the CLI path and in the Laminar agent's `upsert_chart` tool (lmnr-private `agent/dashboard_tools.rs`, which calls `check_charts`).** The frontend `PUT …/charts` route stores whatever the editor sends, because the editor has already run the query. `check_charts` runs before any DB access. It requires `{start_time:DateTime64}` + `{end_time:DateTime64}` and allows no other params, requires `{interval_unit:String}` for line/bar charts over `time`, and requires x/y on non-table charts. It test-runs each query over the last 24h with the caller's `AccessPolicy` (`Actor::Cli`), then checks `x/y/breakdown` against the result columns and flags repeated `x` values that are missing a breakdown. An empty 24h window is a *warning*, not an error. Both callers send the same `ChartInput` JSON entries (`id`/`name`/`query`/`config`/`layout`); only the dashboard id's location differs (URL path vs tool arg). Change the rules here, never in the agent, and keep the agent's `QUERY_DESCRIPTION` tool text in step with them. `SqlQueryError::message()` gives the user-facing text without `Display`'s `{"error": …}` JSON wrapper.
- Route handlers spread the body FIRST and path params after (`{ ...body, projectId, dashboardId }`), so a body can't retarget a chart to another project/dashboard. Every chart action filters by both `projectId` and `dashboardId`.
- Dashboard links carry the current search params (`getDashboardHref` in `dashboard-switcher/use-dashboard-actions.ts`), so switching dashboards keeps the date range and grouping.
- The header (`DateRangeFilter`, `GroupByPeriodSelect`, picker) lives in the `(view)` layout and stays mounted across dashboard switches, so nothing in it may capture `usePathname()` at mount (e.g. in a `useState` store initializer) — it goes stale and navigates back to the first dashboard (LAM-2437). For search-param-only updates push a query-only href (`router.push(\`?${params}\`)`); Next resolves it against the current URL and leaves base paths alone.
- UI-testing dashboards: staging `public` has no `dashboards` table (tracker stops before `0115`) and lacks `users.preferences`, so sign-in 500s. Use a throwaway local Postgres instead (`apt-get install postgresql-15`, `initdb` as a non-root user, run drizzle's `migrate()` from `frontend/` with a small node script, seed `subscription_tiers` from `lib/db/initial-data.json`) and start `next dev` with `DATABASE_URL=postgresql://postgres:<pw>@localhost:<port>/postgres`. The URL MUST carry a password (`getDatabaseConfig` throws "Invalid database URL" otherwise). Keep the sandbox's `ENVIRONMENT=PRODUCTION` + `FORCE_RUN_MIGRATIONS=false` (they disable the `Feature.LOCAL_DB` boot init) so the boot doesn't repoint staging ClickHouse's `pg` engine at your local DB.
- Testing migrations locally: sandbox `.env.local` disables migrations against shared staging (`FORCE_RUN_MIGRATIONS=false`). Run against an isolated Postgres schema (`POSTGRES_SCHEMA=<name> FORCE_RUN_MIGRATIONS=true`, the same `POSTGRES_SCHEMA` for the app-server) instead of applying a new migration to `public`.

## Recharts

- On v3 (`^3.10.1`). `recharts/types/chart/generateCategoricalChart` no longer exists — `CategoricalChartFunc` is defined locally in `frontend/components/chart-builder/charts/line-chart.tsx` from the exported `MouseHandlerDataParam` and imported from that module in all consumers (`traces-chart`, `time-series-chart`, `dashboards/chart`).
- `MouseHandlerDataParam.activeLabel` is typed `string | number | undefined` (was `string`). Any state setter or store that stores it as `string` must wrap with `String(e.activeLabel)` AND use `!= null` checks (not truthy) so the numeric 0 is not dropped.
- `<YAxis width="auto">` sizes the axis to its ticks. Rounded stacked bars use the native `<BarStack radius={[4,4,4,4]}>` wrapper — do NOT reintroduce a custom `shape` just to round stacked-bar corners.
- Radial progress rings (`RadialBarChart`) must sweep a full circle (`startAngle={90} endAngle={-270}`) and encode the value via `<PolarAngleAxis type="number" domain={[0, max]}>`. v3 fits the polar viewbox to the chart's own sweep, so the v2 trick of shrinking `endAngle` to the used fraction now resizes and re-centres the whole disc instead of filling part of it. Use `<RadialBar background>` for the track — v3's `PolarGrid` hardcodes `fill="none"` on each concentric circle, so the shadcn `first:fill-muted last:fill-sidebar` + `polarRadius` trick no longer draws one. See `components/workspace/usage/index.tsx`.
- The `ChartTooltipContent` in `components/ui/chart.tsx` intersects `Omit<RechartsPrimitive.DefaultTooltipContentProps<TooltipValueType, TooltipNameType>, 'accessibilityLayer'>` to type `payload`/`label`. Filter payload arrays with `item.type !== 'none'` before rendering. Custom `shape={...}` render props on `<Bar>` receive recharts-internal props that must not land on a DOM node. Use recharts `<Rectangle>` as the shape (it already filters to SVG attrs + event handlers) — do not spread onto a raw `<rect>` or maintain an internals denylist. See `horizontal-bar-chart.tsx`.
