## Evaluations Page (groups + table)

- **Evaluation-level `name`/`group_id`/`metadata` live ONLY in Postgres `evaluations`** — ClickHouse `evaluation_datapoints` carries per-datapoint data (its `metadata` column is the datapoint's, not the evaluation's). So SDK-facing evaluation updates (`POST /v1/evals/{eval_id}`, `api/v1/evals.rs::update_eval`) are a pure Postgres UPDATE with no CH write. `group_id` is deliberately immutable there (ClickHouse datapoint rows denormalize `group_id` at insert time via `get_evaluation_group_id`, so changing it post-hoc would desync the two stores).
- **`evaluation_datapoints_v0` sources trace-level columns from `traces_agg` + `traces_static`** (migration `55`): costs/tokens/`start_time`/`end_time`/`duration` + `trace_status` (`has(statuses,'error')`) + `trace_tags` from a `traces_agg` GROUP BY, `trace_metadata` + `top_span_id` from `traces_static FINAL`. The view takes only `project_id` (no time params), so both joins carry a semi-join on `id IN (SELECT trace_id FROM evaluation_datapoints WHERE project_id = …)` to prune on the `(project_id, id)` PK instead of scanning every trace in the project.
- **Two type traps when recreating this view**, both caught by diffing `system.columns` against the previous definition: the `traces_agg` aggregates leak their `SimpleAggregateFunction(min|max, …)` wrapper into the exposed type (cast with `CAST(min(start_time) AS DateTime64(9,'UTC'))`), and `trace_status` must be `toLowCardinality(...)` to stay `LowCardinality(String)`.
- **`trace_spans.duration` must be an explicit expression** — the physical `spans` table has NO `duration` column, so a bare `duration` inside that subquery resolves against the OUTER `end_time - start_time AS duration` alias (which then rebinds the names to the spans columns — it only works by accident), and qualifying the outer alias (`t.end_time - t.start_time`) breaks that resolution with `Unknown expression identifier 'duration'` / `Correlated subqueries are not supported in JOINs`. Compute it inline: `(toUnixTimestamp64Nano(end_time) - toUnixTimestamp64Nano(start_time)) / 1000000000`.
- The evaluations list page (`frontend/components/evaluations/evaluations.tsx`) is split into the groups sidebar (`groups-list/`) and the table. The selected group is the `groupId` URL query param; the groups list defaults it to the first group via an effect on load. The table fetch is gated on `!isGroupDefaultPending` — without that gate the table fires one fetch with `groupId=null` (returns ALL groups' evals) BEFORE the default groupId is applied, then re-fetches filtered, briefly flashing the wrong (unfiltered) rows. `isGroupDefaultPending = isGroupsLoading || (!groupId && groups.length > 0)`; both components hit `/evaluation-groups` via SWR so the request dedupes.
- **InfiniteDataTable icon columns need `size` ≥ 60.** `cell.tsx` renders every cell with `px-4` (32px) padding and wraps content in an `overflow: hidden` truncate div, so a 28px (`h-7 w-7`) icon button in a `size: 40` column gets clipped — clicks land on the row instead of the button and trigger `getRowHref` navigation. Use `size: 64` for a single icon-button column and `e.stopPropagation()` in its `onClick` (same pattern as `createCheckboxColumn` in `utils.tsx`).
- `useDefaultLayout` from `react-resizable-panels` dereferences `localStorage` at call time in its default storage — throws during SSR. Pass a window-guarded `LayoutStorage` and gate the `ResizablePanelGroup` mount on a client check (`useSyncExternalStore` pattern, see `evaluations.tsx` / `queue-content.tsx`) so the persisted layout is available at Group registration time.
- Chart preferences persist per `(projectId, groupId)` in localStorage: `evaluations-chart-hidden:<pid>:<gid>` (evaluations hidden via the locked `__chart_visibility` eye column) and `evaluations-chart-hidden-scores:<pid>:<gid>` (scores deselected in the chart legend). Both store the HIDDEN set, not the visible set, so newly-appearing evals/scores default to visible. The progression chart is combined-only (per-score min-max-normalized lines); a constant score (max === min) draws at 0.5 so it isn't pinned to a clipped plot edge.

## JSON/string cell rendering (`JsonTooltip`)

- `frontend/components/ui/json-tooltip.tsx` is the single renderer behind every free-form cell across the tables: traces Input/Metadata, evaluations Target/Data/Metadata/custom columns (via `evaluation/columns/data-cell.tsx`), and dataset Data/Target/Metadata. A change there hits all three tables at once — verify against all of them, not just the one in the ticket.
- It JSON-parses string `data` first, so a value that isn't JSON stays a plain string. Both the cell preview and the tooltip body must branch on `typeof === "string"` and render the raw string; `JSON.stringify` on a string re-adds the surrounding `"` quotes (LAM-2130). Objects/arrays/numbers still go through `JSON.stringify(…, null, 2)`.
- The landing-page eval mock (`components/landing/sections/did-my-fix-work/eval-comparison-mock.tsx`) hardcodes its cell strings and does NOT use `JsonTooltip` — keep it visually in sync by hand when cell formatting changes.

## Advanced Search filter tags

- The search-bar filter tag (`frontend/components/common/advanced-search/components/tag.tsx`) and the field dropdown (`.../components/select.tsx`) must render filters whose `column` is NOT in the registered `ColumnFilter[]` (`filters` prop). A shared/bookmarked URL can carry a filter for a column the current user hasn't configured — most commonly a per-user `custom:<name>` column that lives only in the URL-author's table config. If `getColumnFilter` returns undefined, synthesize a fallback `{ name: field, key: field, dataType: tag.dataType ?? "string" }` instead of returning `null`; otherwise the tag silently disappears while the filter stays ACTIVE on the query (invisible + un-removable). Applies to every `AdvancedSearch` consumer (traces/spans/sessions/signal-events).

## Add-filter popover (`datatable-filter`)

- `FilterPopover` (`frontend/components/ui/infinite-datatable/ui/datatable-filter/ui.tsx`) dedups only EXACT duplicates (`isEqual` against the active list); duplicate columns with different values are legitimate (multiple `metadata` key=value filters combine with AND server-side; param keys are indexed per filter in `buildColumnFilters`), and the `AdvancedSearch` bar already allows them. After apply, it MUST clear `filter.value` (keeping column/operator) — otherwise popover state persists, a re-click re-submits the same filter, and the dedup makes it a silent no-op.

## Dataset datapoints filters + custom columns

- The dataset datapoints table supports metadata key=value filtering AND user-defined custom SQL-expression columns, built in `frontend/lib/actions/datapoints/utils.ts` mirroring the traces-table pattern. Custom columns are threaded as a JSON `customColumns` URL param (`{id, sql, filterSql?, dbType?}`, ids prefixed `custom:`); the metadata filter uses ClickHouse `simpleJSONExtractString`/`simpleJSONExtractRaw` splitting `filter.value` on `=`, identical to `lib/actions/traces/utils.ts`. `dataset_datapoints` is already in the query-engine validator allowlist AND the frontend SQL schema, so this is frontend-only (no Rust/migration).
- **Datapoint action functions (`getDatapoints`/`countDatapoints` in `lib/actions/datapoints/index.ts`) must destructure `input` DIRECTLY — never re-call `Schema.parse(input)`.** The API route handlers already run `parseUrlParams(searchParams, Schema)`, which applies `FiltersSchema`'s `filter` transform that JSON.parses each filter string into a Filter OBJECT. Re-parsing in the action then fails because the Zod schema's `filter` field still expects an array of STRINGS → `ZodError: expected string, received object` → 500 on every filtered request. `getTraces` in `lib/actions/traces/index.ts` is the reference: it destructures `input` directly. The schemas (`ListDatapointsSchema`/`CountDatapointsSchema`) are still used by the routes via `parseUrlParams`, just not re-applied downstream.

## Dashboard Time Grouping

- Time-range-to-grouping logic is duplicated in three places that must stay in sync: `getGroupByInterval` (`frontend/lib/utils.ts`), `inferGroupByInterval` (`frontend/lib/time.ts`), and `getOptimalDateFormat` (`frontend/components/chart-builder/charts/utils.ts`). When changing grouping thresholds, update all three.
- Time-series chart utils are ALSO duplicated in two places that must stay in sync: `frontend/components/charts/time-series-chart/utils.ts` (the shared `TimeSeriesChart` used by traces/signal-clusters/alerts) and `frontend/components/traces/traces-chart/utils.ts` (a legacy copy whose `chart.tsx` is currently unmounted but still type-checked). `isValidZoomRange`/`normalizeTimeRange`/`calculateOptimalInterval` exist in both. Drag-zoom minimum range is 5 minutes (`isValidZoomRange` `minMinutes` default); `calculateOptimalInterval` clamps sub-minute buckets to `1 minute` (a 0-value interval would make ClickHouse `toInterval(0, 'minute')` bucket everything together).

## Dashboard Charts API

- `app/api/projects/[projectId]/dashboard-charts/route.ts` exposes `GET` (list), `POST` (create), and `PATCH` (bulk layout update). There is NO `PUT`. Creating a chart from the chart-builder/sql-editor must use `POST`, not `PUT` (which would silently 405 and never reach `createChart`).

## Recharts

- Pinned at v2 (`^2.15.4`). A previous v3 upgrade was reverted due to a runtime bug; do NOT bump to v3 without revalidating it. Use only v2 APIs.
- `<YAxis width="auto">` is v3-only — on v2 `width` must be a number (omit it for the default). `CategoricalChartFunc` imports from `recharts/types/chart/generateCategoricalChart`, which exists in v2.
