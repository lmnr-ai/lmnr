## Signals and Alerts

- Alerts reference signals via `alerts.source_id`. There is NO FK constraint from `source_id` to `signals.id` because `source_id` may reference other entity types in the future. When deleting signals, associated alerts must be deleted in application code within the same transaction (see `deleteSignal`/`deleteSignals` in `frontend/lib/actions/signals/index.ts`).
- The Signals sidebar item is behind a feature flag (`Feature.SIGNALS`) which requires `SIGNALS_ENABLED=true` AND a configured AI provider (`LLM_PROVIDER` set to `openai`/`gemini`/`bedrock`/`azure_chat_completions`/`azure_responses`/`azure_anthropic` with matching credentials). See "AI Features Model Setup" in `docs/internal/ai-features.md`.
- Alert metadata is stored as JSONB in `alerts.metadata`. For `SIGNAL_EVENT` alerts, it contains `{severity: 0|1|2}` (info/warning/critical). The Rust backend reads this in `postprocess.rs` to filter events by severity threshold, defaulting to CRITICAL (2) when metadata is absent (historical alerts default to the most restrictive level). The frontend edit form also defaults to CRITICAL for alerts without metadata.
- Creating a signal auto-creates a CRITICAL-severity alert and subscribes all workspace member emails as alert targets.
- **`db/utils.rs::evaluate_array_contains_filter` is PURE SET SEMANTICS: `Includes` = ANY listed item present, `NotIncludes` = NONE present, and an EMPTY array legitimately satisfies `NotIncludes`.** "State unknown / read failed" must be resolved by the CALLER before calling — an earlier version rejected an empty array under both operators to make one caller fail closed, which silently dropped every legitimate "field does not contain X" alert filter. The pre-`includes` `eq`/`ne` shape is REJECTED rather than coerced: migration 0107 rewrote every stored row, so a surviving scalar means the migration didn't run, and failing closed makes that visible instead of silently evaluating. The one guard that belongs here is on the TARGET (each entry trimmed; an empty or all-blank list rejects both operators), because the shared frontend `FilterSchema` accepts a whitespace-only value (`z.string().min(1)`) and `not_includes [" "]` would otherwise match every row. Contract pinned by tests in the same file — `#[cfg(test)]` and deliberately NOT gated on `signals`, so a plain `cargo test` runs them.
- **Signal FILTER columns are `total_token_count` / `status` / `span_names` / `tags`, and `span_names` (plural, filter) is a DIFFERENT column from `span_name` (singular, trigger)** — the trigger matches only the firing span batch, the filter asks whether the name appears anywhere in the trace. Both set-valued columns are UI `dataType: "array"`, so they offer `includes` / `not_includes` only (`ARRAY_OPERATORS`) and their value is always a LIST — `normalize_value`'s `ValueRule::NonBlankList` rejects a bare string instead of wrapping it, since every writer already sends an array. `=`/`!=` read as a claim about one span and are actively misleading on a set, which is why migration 0107 converted the persisted operators rather than relabelling them in the UI; do NOT relabel the shared `OperatorLabelMap` to that end — every table filter in the app renders from it. Evaluation itself is enterprise-only (see "Signal Triggers").
- New-cluster notifications render as a per-alert DIGEST: `NotificationKind::NewCluster` carries enrichment fields (`first_seen`/`last_seen: Option<String>`, `severity_counts: [u64; 3]`, `example_events: Vec<ClusterExampleEvent>`), all `#[serde(default)]` so already-queued legacy messages deserialize. The email/Slack renderers (`render_new_cluster_email` / `format_new_cluster_blocks`) take `&[&NotificationKind]` and render every `NewCluster` in a message's `notifications` vec as one digest. Slack caps at 50 blocks (2 per cluster), so `format_new_cluster_blocks` renders at most `MAX_CLUSTERS_PER_DIGEST` (20) clusters + an "…and N more" overflow section; per-cluster text goes through the 3000-char section budget. `Option<String>` fields are `None` when absent (never empty-string sentinels) — renderers gate with `if let Some`. OSS ships the enum and the renderers; the CH stat/sample helpers and the enriching producer are not part of OSS.
- The `NEW_CLUSTER` alert type and the `skipSimilar` metadata option depend on the clustering service. Gate both the auto-creation of `NEW_CLUSTER` alerts in `createSignal` and UI affordances in `manage-alert-sheet.tsx` behind `isFeatureEnabled(Feature.CLUSTERING)` / `useFeatureFlags()[Feature.CLUSTERING]`. When clustering is disabled, force `skipSimilar: false` on submit so the backend doesn't silently drop notifications.
- **Activate/deactivate.** Both signals and alerts carry an `enabled` flag in their JSONB metadata; **absence means enabled** (historical rows default to active). Signal sampling lives in the SAME `signals.metadata` jsonb as `metadata.sampleRate`. There is NO `enabled` boolean column on either table — it's purely a metadata key, only persisted when `false` (the UI omits it when active to keep metadata clean). Rust side: `SignalMetadata` (`db/signals.rs`) and `AlertMetadata` (`db/alert_targets.rs`) each expose an `enabled()` helper returning `self.enabled.unwrap_or(true)`. Disabled **signals** are skipped in `processor_hook.rs` (gate `!trigger.signal.metadata.enabled()` before evaluating triggers, and exclude them from the `any_has_sampling` sampling-factor fetch); disabled **alerts** are skipped in `postprocess.rs` (SIGNAL_EVENT loop) and `clustering/private/handler.rs` (both `notify_new_l0_clusters` skip-similar filter and the NEW_CLUSTER notification loop). Toggling a signal's enabled state MUST invalidate the `signal_triggers:{projectId}` cache (`updateSignal` already does); alert enabled needs no Rust cache invalidation because `get_alerts_for_signal` reads `alerts.metadata` fresh (only filter *rules* are cached, per-`(projectId, alertId)`). Frontend: the alert metadata Zod validators in `lib/actions/alerts/index.ts` must allow `enabled` — note `NewClusterMetadataSchema` is `.strict()`, so `enabled` had to be added there explicitly or NEW_CLUSTER toggles 400.
- In `manage-alert-sheet.tsx`, the `severities` Controller uses `shouldUnregister`. When its render condition (`selectedSignal && alertType === SIGNAL_EVENT`) flips to false — e.g. after a successful save resets `selectedSignal` — react-hook-form removes the field from form state and `watch("severities")` returns `undefined`. Any `useMemo` that reads `watch`ed values must null-check them (don't call `.length`/`.map` directly) or it will throw synchronously and break the whole page into the error boundary.
- Alert Slack targets persist a channel `id` in `alertTargets.channelId` and the display name in `alertTargets.channelName`. Both columns are populated for every row written by the form, so `resetFormFromSignals` in `manage-alert-sheet.tsx` filters to rows where both are present and uses them directly.
- `getSlackChannels` in `frontend/lib/actions/slack/index.ts` paginates through Slack `conversations.list` via `response_metadata.next_cursor` (limit=500/page) and returns `{ channels, rateLimited }`. On rate-limit (HTTP 429 OR a 200 OK with `{ok:false, error:"ratelimited"}`) it does NOT retry — it returns whatever was collected so far with `rateLimited: true`. The consumer (`manage-alert-sheet.tsx`) toasts when `rateLimited` is true so the user knows the list may be incomplete. We don't cache — each request fetches fresh so new/renamed channels appear immediately. The picker (`slack-channel-picker.tsx`) leverages cmdk's `Command` for filtering with a custom `filter` that scores against the channel name (passed via `keywords`); `value` holds the channel id so duplicate names aren't possible.
- The `types` query parameter on `conversations.list` must include both `public_channel,private_channel` — dropping `private_channel` silently breaks existing alert targets that point at private channels (they disappear from the picker and can't be re-selected).
- Slack section block `text` fields are hard-capped at 3000 chars — Slack rejects the whole `chat.postMessage` call if any block exceeds this. When building alert payloads in `app-server/src/notifications/slack.rs`, feed any user-sourced text (extracted event info, report summaries) through `truncate_to_slack_section_limit` rather than dropping overflowing entries. Count chars, not bytes, and slice on `chars()` to stay on char boundaries (multi-byte payloads will panic on byte-indexed slicing).
- The manage-alert UI is a **directory** (`frontend/components/settings/alerts/manage-alert-sheet/`): `index.tsx` (loader/sheet shell), `alert-form.tsx` (the form — owns the `severities` shouldUnregister and `Feature.CLUSTERING` gating described above), `alert-section.tsx`, `build-default-values.ts`, `types.ts`, `skeleton.tsx`. The shared `AlertsManager` (`frontend/components/settings/alerts/alerts-manager.tsx`) is the table+sheet+delete-dialog used by BOTH project settings (`settings/alerts/index.tsx`) and the signal settings "Alerts" tab. Pass `fixedSignalId` to scope the list to one signal (`sourceId === fixedSignalId`), drop the Signal column, and hide the alert-type + signal selectors in the sheet. Rows are click-to-edit; delete is a hover-revealed trash button with `stopPropagation`.
- **Slack channel platform-agent (`slack_channel_projects` table + `chat_messages.external_id`).** Lets a workspace bind a Slack channel to a project so `@mention`ing the bot drives the Platform Agent in-thread. The agent itself (`app-server/src/agent/slack_events.rs`, the `/api/v1/slack` scope in `main.rs`, the `cli/agent.rs` route) is **enterprise-only and lives in `lmnr-private`** behind `#[cfg(feature = "signals")]` — OSS does NOT have `app-server/src/agent/`. OSS ships only the PUBLIC scaffolding: the `slack_channel_projects` table + `chat_messages.external_id` partial-unique index (`chat_messages_chat_external_key`, exempts NULL so live non-Slack rows don't collide), the DB helpers in `db/slack_integrations.rs` (`get_channel_binding` — the deterministic channel→project router that joins through the binding's own `integration_id` FK rather than resolving a workspace from the non-unique `team_id`; returns at most one row because `slack_channel_projects.channel_id` is UNIQUE instance-wide via `slack_channel_projects_channel_id_idx`, so an inbound `@mention` can never resolve to >1 project; `ChannelProjectBinding`; `get_integration_by_team_id` used ONLY to obtain a token for the unbound-channel setup-hint reply — all `#[cfg_attr(not(feature = "signals"), allow(dead_code))]`), the `notifications/slack.rs` reply/backfill helpers (`post_thread_reply`, `fetch_thread_replies`, `ThreadMessage` — dead-code without signals), `pub mod slack` exposure, and the frontend channel-project CRUD/UI (`frontend/lib/actions/slack/channel-projects.ts`, the `[workspaceId]/slack/channel-projects` route, `slack-channel-projects.tsx`, app_mention scopes/event in `lib/actions/slack/{types,webhook}.ts`). Slack signature verification lives in the frontend webhook handler, which forwards verified events to the cluster-internal `/api/v1/slack/process` (no HTTP auth, same as agent/chat).
- **Custom alert filters (`alert_filters` table).** Optional per-alert rules that further filter which extracted signal events fire an alert — orthogonal to and ANDed *after* the severity gate. Minimal table: `(id, alert_id FK→alerts CASCADE, project_id FK→projects CASCADE, value jsonb, created_at)`; the rule lives entirely in `value` (a `Filter[]`, same shape as `signal_triggers.value`). An alert with NO filters fires on every severity-matching event; with filters it fires only when at least one filter's conditions ALL match the event's extracted output. Frontend: `alert-filters-section.tsx` derives `ColumnFilter[]` from the signal's `structuredOutput` JSON schema (`jsonSchemaToSchemaFields` → `schemaToFilterColumns`) under `name="alertFilters"`; on save `sync-alert-filters.ts` diffs and issues DELETE/PUT/POST to `/api/projects/:id/alerts/:alertId/filters`. CRUD + per-`(projectId, alertId)` cache invalidation in `frontend/lib/actions/alert-filters/index.ts` (key `${ALERT_FILTERS_CACHE_KEY}:${projectId}:${alertId}`); `updateAlert`/`deleteAlert` also invalidate it. **The firing/evaluation logic lives in the enterprise `lmnr-private` repo** (`signals/private/postprocess.rs` + `trigger.rs`), NOT in OSS — OSS only ships the table, the cache key (`ALERT_FILTERS_CACHE_KEY` in `app-server/src/cache/keys.rs`, `allow(dead_code)` without `signals`), the `evaluate_boolean_filter` helper in `db/utils.rs`, and the frontend CRUD/UI.

## Built-in signal templates

- **The "Failure Detector" built-in is defined in TWO files that must stay in sync**: `frontend/lib/db/default-signals.ts` (`DEFAULT_SIGNAL`, seeded on workspace/project creation via `lib/actions/workspaces/index.ts` and `instrumentation.ts` — both go through `createSignal` so the seed gets its trigger row, v1 and alerts in one transaction) and `frontend/components/signals/prompts.ts` (the create-drawer template picker). Nothing enforces the sync — both carry a sync comment; edit both or the seeded signal and the template silently diverge. The seed stores `structuredOutputSchema` as an object, the template as a `JSON.stringify`'d string.
- **Template schemas are frontend data only** — no code reads individual schema properties. Consumers either spread the whole object (`...DEFAULT_SIGNAL`) or hand the parsed schema to `jsonSchemaToSchemaFields` (`components/signals/utils.ts`), so adding/removing a property needs no migration and no backend change. Existing projects keep their stored prompt/schema; only new seeds and fresh template applications pick up an edit.

## Signal Triggers

- Trigger/filter evaluation is **enterprise-only** (`lmnr-private` `signals/private/evaluate.rs`).
- OSS ships only the call site: `process_span_messages` → `check_and_push_signals(&[TraceAggregation], &spans, …)`, placed AFTER the batch's ClickHouse inserts because triggers decide from the in-memory batch delta while filters read the trace's cumulative state back out of `traces_agg`. It returns `()`; a metadata-only flush produces no aggregation, so it evaluates nothing and can't refire an already-triggered signal.

## Signal versioning (`signal_versions`, LAM-2211)

- **`signal_versions` is an append-only log of the live-trace snapshot** — `{ name, prompt, structuredOutputSchema, trigger, filters, mode, sampleRate, disabled, llmProfileId, llmModel }`, serialized from `SignalDefinition` in `app-server/src/db/signals.rs` and `mintSignalVersion` in `lib/actions/signal-versions/`. `trigger`/`filters` are the stored Filter[] JSON (`signal_triggers.value` / `filters`), not the CLI tagged `Trigger` enum, so shapes that enum cannot express (`span_name` + `ne`) round-trip without becoming `rootSpanFinished`. `mode` is `"batch"` / `"realtime"`. `llmProfileId` + `llmModel` are the pinned self-hosted route (both `null` = env `LlmClient`; Cloud signals stay `null`). An alert edit does NOT mint. Never hand-build that JSON at a call site: new fields go on the struct with `#[serde(default)]` so old rows still deserialize, and the blob shape can grow without a migration.
- **One Save is one version.** Frontend `createSignal` / `updateSignal` write trigger rows in the same transaction as the mint (the General form sends `triggers` on the signal POST/PUT). CLI `update_signal` patches the trigger row first, then mints from the merged snapshot. Independent `/triggers` CRUD still mints: it `SELECT … FOR UPDATE`s the signal, writes, then `mintSnapshotAndBump`.
- **The definition is stored verbatim, but compared in application code with set-valued arrays SORTED and ops absences filled** (`comparable` in `db/signals.rs` and in `lib/actions/signal-versions/`). `structuredOutputSchema.required`, `trigger`, and `filters` are AND-sets (nested `value` arrays of span names too); jsonb reorders `required` when the drawer rebuilds it from key-sorted `properties`. `disabled: false` ≡ missing, `sampleRate: null` ≡ missing, missing `mode` ≡ `"realtime"`, missing `name` ≡ `""`, missing `llmProfileId`/`llmModel` ≡ `null`. Object key order needs no handling: both `isDeepStrictEqual` and `serde_json::Value ==` compare objects as maps. A new definition field that is semantically a set needs the same sort.
- **`project_id` on `signal_versions` is scoping, not identity.** It is deliberately outside the PK (`(signal_id, version)`); every read must be `WHERE project_id = $1 AND signal_id = $2` so a signal id lifted from a URL can't reach another project's prompts.
- **`signals.version` is the one denormalized field here.** The version insert and the `version` bump must stay in the same transaction as the existing `SELECT … FOR UPDATE` on the signals row (both `db::signals::update_signal` and the frontend `updateSignal`), or two concurrent saves race for the same version number. Both update paths mint — frontend `updateSignal` AND `PATCH /v1/cli/signals/{id}`; a partial PATCH falls back to the stored name/prompt/schema/trigger/filters/mode/sampleRate/disabled/llm route so it can't mint spuriously.
- **The ClickHouse column is `signal_version`, NOT `version`.** `signal_runs` is a `ReplacingMergeTree(updated_at)`; a column literally named `version` sitting next to an RMT version column is a trap for the next reader.
- **`signal_version UInt32 DEFAULT 0` means "predates versioning", not version zero.** Old rows are deliberately NOT backfilled to 1 — the v1 minted at migration time is *today's* definition, and an old event may predate several edits of it. Render 0 as an em dash (`components/signal/signal-version.tsx`).
- **New fields on `CHSignalEvent` / the `signal_runs` row struct go LAST.** `ALTER TABLE … ADD COLUMN` appends, and the `clickhouse` crate's `Row` derive decodes RowBinary **positionally** — inserting a field mid-struct silently misaligns every column after it.
- **Exposing the column takes four separate edits, and the view is only the first.** `query_engine/schema.rs` (user SQL), `signalRunsSelectColumns` (`lib/actions/signal-runs/utils.ts`) and `eventsSelectColumns` (`lib/actions/events/utils.ts`) are explicit lists, and `eventsColumnFilterConfig` needs an **explicit processor** — its `defaultProcessor` treats any column it doesn't recognize as a payload JSON field, so a native column silently filters as `simpleJSONExtract(payload, 'signal_version')`.
- **The same trace can carry both a v3 and a v4 event.** That's the intended comparison, but it means `signal_events` counts stop being one-per-trace — anything counting events across a version boundary must `GROUP BY signal_version`.
- **Clusters deliberately have no version.** A cluster legitimately spans versions; a cluster's version mix is a `GROUP BY` over its events.
- **Settings → Versions is a read-only changelog.** Newest first; v1 expands to the stored JSON snapshot, later rows expand to a `DiffView` against the previous mint. The collapsed summary lists the fields that changed (`components/signal/versions-section/changelog.ts`). Chart markers (`v2+`) link to `?tab=settings&section=versions&version=N`.

## Signal CRUD in app-server (`signals/service.rs`, `/v1/cli/signals`, `/v1/signals`)

- **Two auth front-ends, one service.** `/v1/cli/signals` (user token, `CliProjectAuth`) and `/v1/signals` (project API key, `ProjectApiKey`) call the identical `signals::service` functions, so validation, version minting and error mapping cannot drift. Two deliberate differences: the project-key `POST` subscribes nobody to the auto-created alert (`subscriber_email: None` — a key has no user) and answers **201**, while the CLI twin subscribes the creator and answers 200. Both surfaces expose the same five reads/writes plus `GET /signals/{id}/versions`; a new route on one is a bug on the other.

- **Signal CRUD is ungated by the `signals` cargo feature and lives in `signals/service.rs` + `db/signals.rs` + `db/signal_triggers.rs`.** Writing a signal row is a plain DB write; only signal *processing* is enterprise. `db/signals.rs` was previously `#[cfg(feature = "signals")]` — ungating it exposes `SignalMetadata` / `Signal` / `get_signal` as dead code in OSS, so those carry `#[cfg_attr(not(feature = "signals"), allow(dead_code))]`.
- **`GET /v1/cli/signals/{id}/versions`** returns the append-only snapshot log (`{ versions: [{ version, definition, createdAt }, …] }`, oldest first). 404 if the signal is missing in this project. The scalar `version` on `GET /v1/cli/signals/{id}` is still just the current pointer. `definition.trigger` is Filter[] (drawer JSON), not the tagged `Trigger` on GET `/signals`.
- **Every signal write path must lock the `signals` row (`SELECT … FOR UPDATE`) BEFORE touching `signal_triggers`.** With no FK there is nothing else serializing them, so a delete that went straight for the child rows would not block a concurrent trigger replace — the replace inserts rows the delete already scanned past and they survive as orphans (reproduced deterministically, 3/3 runs). `update_signal` and `delete_signal` both take that lock first; any new path that writes triggers must too.
- **`signal_triggers` has NO foreign key on `signal_id`** (verified against the live schema — `pg_constraint` returns zero FK rows for the table). Deleting a signal does NOT cascade to its triggers, so `db::signals::delete_signal` deletes them explicitly in the same transaction. `alerts.source_id` likewise has no FK (deliberate — it may reference other entity types), so alerts are deleted explicitly too; only `alert_targets` genuinely cascades (from `alerts`). **The frontend `deleteSignal`/`deleteSignals` path still has this gap** — staging holds orphan `signal_triggers` rows because of it. Fix that or add the FK before trusting "deleting a signal cleans up its triggers" anywhere.
- The service validates payloads the CLI/UI write: identifier field names, sampleRate 1..95, name trimmed-then-capped at 255 CHARACTERS, and `required` listing exactly the property names (the drawer marks every field required). Descriptions on payload fields are optional (the drawer does not require them). Extra JSON Schema keys (`additionalProperties`, `format`, …) are stored as-is — the drawer never emits them and ignores them on load. Numeric-string thresholds are TRIMMED before storage because the evaluator's `parse::<f64>()` does not trim, and non-finite values are rejected (Rust parses `"NaN"`/`"inf"`, which would make every comparison false).
- **The API models a signal's firing config as three sibling fields — `trigger` / `filters` / `mode` — while storage stays one `signal_triggers` row.** `Trigger` is a serde-tagged ENUM (`{"type":"rootSpanFinished"}` / `{"type":"spanName","spanNames":[…]}`) rather than a `{column,operator,value}` list, because those two shapes are the only ones `evaluate.rs` has an arm for. `Trigger::to_conditions` / `from_conditions` map to the stored `value` column (the same JSON the drawer writes). **`filters` stay `{column,operator,value}` JSON on purpose** (deliberately NOT collapsed into a DSL) so new operators and richer value types need no client change. There is no "no trigger" state: create omits/`null` `trigger` → `rootSpanFinished`; GET always serializes a `Trigger`.
- **`from_conditions` returns `None` for anything it cannot faithfully describe** (empty list, a filter column stored as a condition, all-blank span names, `span_name` + `ne`). `evaluate_trigger_condition` implements `ne` as "fires when NONE of these finished"; `Trigger::SpanName` can only say the positive case and `to_conditions` writes `includes`, so reporting one would invert it if a later write round-tripped. GET maps that `None` to `rootSpanFinished` rather than JSON `null` — PATCH omit still leaves storage alone. Widening `SPAN_NAME_POSITIVE_OPERATORS` requires a new variant first. Surviving span names are NOT trimmed — the evaluator compares them literally.
- **`mode` is `"batch"` / `"realtime"` on the wire, never the raw 0/1 discriminant** (`Mode::to_i16` / `from_i16` mirror `SignalMode::from_u8`, including "anything unknown is batch"). Create omits/`null` `mode` → realtime (same as the drawer).
- **One trigger row per signal is the API contract, but nothing in the schema enforces it** — pre-split rows and the frontend's `syncTriggers` could create several. Reads take the newest (`ORDER BY created_at DESC, id DESC`) and `patch_signal_trigger` collapses the extras onto the row it locked. The `id` tiebreak is load-bearing: rows inserted in one transaction share a `created_at`, so without it a signal can report a different trigger per request.
- **New filter column:** picker (`trigger-filter-field.tsx`) + evaluator (`evaluate.rs`) + `ch/private/trace_stats.rs` + one row on `FILTER_COLUMNS` in `signals/service.rs`. A new TRIGGER kind is a new `Trigger` variant plus an `evaluate_trigger_condition` arm.
- `PATCH /v1/cli/signals/{id}` is a true partial patch: an absent **or `null`** key leaves the stored value alone (`Option` + `#[serde(default)]`), **except `sampleRate`**. `sampleRate` uses a double `Option` so omit leaves the stored rate, a number sets it (1..95), and JSON `null` clears sampling (removes the metadata key — evaluate every matching trace). Create omits `sampleRate` (or sends `null`) to mean no sampling — the key is not stored. Create omits/`null` `trigger` to seed `rootSpanFinished`; there is no "no trigger" state. `filters` still uses `[]` to mean "run on every firing trace". Metadata merging preserves unknown keys; `disabled: false` REMOVES the key (absence is enabled).
- Auto-created `NEW_CLUSTER` alert and `skipSimilar` follow `Feature::Clustering` (= `has_llm_provider()`, env-only; it no longer aliases `Feature::Signals`, which is also on when LLM profiles are), same gate as clustering worker spawn. With clustering off `skipSimilar` MUST be false or the backend silently drops notifications. Frontend still keys the same affordances on `CLUSTERING_ENABLED`.
- `llmProfileId` (profile **UUID**) + `model` on create/patch; every response echoes `llmProfileId` + `llmProfileName` (display only) + `model` (all `null` for env-routed signals). `resolve_llm_route` applies the rules: on self-hosted (`Feature::SignalLlmProfiles`) create requires the complete pair, patch accepts the pair or neither (absent = leave stored), the id is resolved within the project's workspace (`db::llm_profiles::get_llm_profile_route_info`) and the model must be one of the profile's (400 listing the available ones otherwise); on Laminar Cloud any profile field is a 400. Ids come from `lmnr-cli llm-profile list` / the UI.

## LLM Profiles (self-hosted signal routing)

- **What they are.** Workspace-scoped, encrypted LLM credentials + a model list (`llm_profiles`, `llm_profile_models`; Settings → Workspace → LLM profiles). A signal pins one profile and one of its models (`signals.llm_profile_id` / `llm_model`, `CHECK (both NULL or both set)`, composite FK `→ llm_profile_models(profile_id, name) ON DELETE RESTRICT`, so deleting a profile/model in use fails with 23503 and the UI disables the action). Names are `UNIQUE (workspace_id, name)`, case-sensitive. Any workspace member reads and writes — there is no owner/admin gate anywhere (UI, frontend API, project API key, CLI); a project API key manages every profile of its project's workspace.
- **Writes live in the app-server** (`app-server/src/llm/profiles/service/`: `mod.rs` persistence + error mapping, `validate.rs` input rules, `secrets.rs` prune/merge/mask), mirroring `signals::service`: one `create/update/delete/list/get/probe` set behind three auth surfaces that only translate auth + HTTP — internal `POST/PATCH/DELETE /api/v1/workspaces/{workspace_id}/llm-profiles[/{id}]` + `POST …/llm-profiles/test` (`routes::llm_profiles`, called server-to-server by the Next.js actions after `checkUserWorkspaceRole` membership), project-API-key `GET/POST /v1/llm-profiles`, `GET/PATCH/DELETE /v1/llm-profiles/{id}` (`api::v1::llm_profiles`, project → workspace via `service::workspace_for_project`), and CLI `…/v1/cli/llm-profiles[/{id}]` (`api::v1::cli::llm_profiles`, `CliProjectAuth`; both project surfaces share `api::v1::llm_profiles::handlers`). Profiles are addressed by UUID everywhere. Bodies are flat `{ name, provider, config, secrets, models }` with PLAINTEXT secrets (the Next action flattens the form's `{ profile: { provider, config } }` and no longer encrypts anything — `secrets.ts` keeps only `decryptSecrets` for the read side); the service normalizes `config` per provider (drops fields the provider does not use, same rules as the Zod union), prunes secrets to the ones the config needs, merges omitted keys from the stored blob on PATCH/probe, encrypts under the profile id, diffs `llm_profile_models` (delete only removed names so the RESTRICT FK fires for in-use ones) and `cache.remove`s `llm_profile:{ws}:{id}`. PATCH: every field optional; `provider` without `config` is a 400; `models` replaces the list. Reads for the UI (`listLlmProfiles`, `listProjectLlmProfileOptions`) stay in the frontend against Drizzle. `CrudError` → `Validation` 400, `DuplicateName`/`InUse` 409 (23505 / 23503 / pre-counted signals), `NotFound` 404, else 500; `frontend/lib/actions/llm-profiles/app-server.ts` (`callAppServer`, `AppServerError`) carries the status back so the Next routes pass it through instead of flattening to 500. The `LlmProfile` response (`LlmProfileResponse`) is the frontend `LlmProfile` shape with masks in `secrets`; `ProfileConfig`/`ProfileSecrets` skip `None` on the wire because the Zod schemas reject `null`. `LlmProfile.created_at` was added for this; a Redis entry written before it fails to deserialize and is simply refetched.
- **One flag.** Profile CRUD (UI, internal + project + CLI APIs) is never gated: profiles back the playground everywhere, so there is no `LlmProfiles` feature. `Feature::SignalLlmProfiles` / `Feature.SIGNAL_LLM_PROFILES` `= !LAMINAR_CLOUD` (`env::connections::LAMINAR_CLOUD`, `BoolEnv`, default false) gates only *pinning a profile on a signal*: on Cloud signals run on Laminar's own keys, the columns exist but the runtime ignores them (`StepConfig::for_signal` drops the route when the flag is off) and the signal APIs 400 any profile field with `Signals run on Laminar's own keys on Laminar Cloud`. `Feature::Signals` is `has_llm_provider() || SignalLlmProfiles`, so a self-hosted deployment with NO `LLM_PROVIDER` still spawns the signal workers; `LlmClient::new(Some(store))` then constructs with zero env providers and every env-routed request fails per call with `No LLM configured for this signal — select an LLM profile`. Clustering, input extraction, SP regex extraction and the frontend AI features stay env-only (follow-up: a "default profile").
- **Wire shapes** (Zod in `frontend/lib/actions/llm-profiles/schema.ts`, serde in `app-server/src/llm/profiles/mod.rs`; the Rust tests round-trip literal frontend JSON — keep them in lockstep). `provider` ∈ `openai_completions | openai_responses | anthropic | gemini | groq | mistral | bedrock | azure_chat_completions | azure_responses | azure_anthropic | custom` (`anthropic` reuses `AzureAnthropicClient` pointed at `api.anthropic.com` via `AzureAnthropicClient::direct`; `groq` / `mistral` are the `OpenAIClient` with fixed hosts). Non-secret fields live in plaintext `config` jsonb with a tagged `auth: { type }` (`api_key`, or for bedrock `aws_keys` | `bearer_token`); `custom` is OpenAI chat-completions only and needs `baseUrl` + API key, optional `headerNames`. Every secret (API key, AWS secret, bearer token, all custom header VALUES) lives in one XChaCha20-Poly1305 blob `secrets = { nonce, value }` (hex) encrypted with `AEAD_SECRET_KEY`, **AAD = the profile id** (`crypto.rs::decrypt`, whose `aad` is a plain string; the data plane and Slack pass the workspace id) — a blob copied to another row will not decrypt. Secrets are write-only: GET returns a `first3***last3` mask per stored value (fully starred when too short) plus header names, which `SecretField` renders as its placeholder so a user can tell which key a profile holds; PATCH keeps a secret when it is omitted/blank, so the form never has to re-send credentials. The mask is why every read decrypts each row, and why a plain `member` can see a key's edges. The Zod union groups providers that share a config (`API_KEY_PROVIDERS`, `AZURE_PROVIDERS`) into one branch each via `z.literal([...])` — the Rust `ProfileConfig` is one flat all-`Option` struct, so the branch count is a frontend validation choice, not a wire constraint.
- **Runtime path.** `ProviderRequest.llm_profile: Option<LlmProfileRoute { profile_id, model, project_id }>` takes precedence over `provider` / `model_size` (`SIGNALS_PARSING_LLM_PROVIDER` and `ModelSize` are ignored on profile-backed runs; one model serves every call in the run). `LlmClient::resolve` is async: a route goes to `LlmProfileStore::resolve`, which takes the project's workspace id from the shared `project:{id}` billing entry (`get_workspace_info_for_project_id`, already warm from limits checks), reads the row through Redis scoped to that workspace (`llm_profile:{workspace_id}:{id}`, TTL 7d, `service.rs` removes it on every write; the DB query also filters on `workspace_id`, so a foreign profile reads as not found), checks the model is listed, decrypts, builds the `ProviderClient` (`build.rs`, explicit-config constructors on each client) and caches it in-process keyed `(profile_id, updated_at)` so credentials are only decrypted when the row changed. Reported provider names for spans/cost are the `model_costs` provider prefixes, shared with the env path in `LlmClient::resolve_model_provider` (`openai_completions` / `openai_responses` / `custom` → `openai`, `azure_chat_completions` / `azure_responses` → `azure`, `azure_anthropic` → `azure_ai`; `anthropic` / `gemini` / `groq` / `mistral` / `bedrock` verbatim).
- **Where the route is set.** `StepConfig { llm_profile_id, model }` (camelCase on the wire, `StepConfig::llm_route(project_id)`); the realtime driver builds it with `StepConfig::for_signal(&message.signal)` (the cached `signal_triggers` payload carries the two columns), `prepare.rs` puts it on the evaluator request, and `CompressContext.llm_route` carries it into `filter.rs::generate_and_cache_keep_rules` and `system_prompts.rs::process_system_prompts` (which then skip `parsing_provider()`). The run root span's provider/model labels come from `LlmClient::resolve_model_provider(&config.routing_request(project_id))` (`StepEngine::route_labels` in the driver, called directly in `enqueue.rs`) — the same resolution as the call, not env. `signal-test` / `signal-eval` take `llmProfileId` + `model`, validate through `validate_llm_profile_route` (half pair / Cloud / wrong workspace / unlisted model → 400) and `signal-test` with a `signalId` defaults to the stored signal's route. `EffectiveConfig.llmProfileId` echoes it.
- **Failure posture.** Every store error is `ProviderError::ConfigError` (non-retryable): missing row, cross-workspace, unlisted model, decrypt failure, client build failure. The realtime driver's non-retryable path writes the run FAILED with `Realtime API failed (LLM profile '<name>'): …` so a bad key is diagnosable from the Runs tab; transient provider errors keep the existing retry ladder. Existing signals with `NULL` route keep working on env vars; the edit form shows a warning banner and leaves the selects optional, while new signals require the pair (UI, frontend API `CreateSignalSchema`, CLI). The frontend write schemas take the pair as `.optional()` only, NOT `.nullable()` — absent means "keep the stored route", and no caller sends null (the form omits both fields unless both are filled, and the profile select has no "None" entry). The columns stay nullable and `Signal`/`ManageSignalForm` still read `string | null`, so there is no API-level way to move a signal back off profiles onto env credentials; re-add `.nullable()` plus a clearing branch in `resolveLlmRoute` if that is ever wanted. Validation is split three ways on purpose: pair completeness and the Cloud rejection are Zod refines on both schemas (`llmRouteIsPaired`, `llmRouteIsAllowed`), "a new signal must pin a profile" is one check in `createSignal` because `requireLlmProfile: false` is a caller trust level rather than input, and `resolveLlmRoute` only does the workspace/model DB join — do not move that join into a refine. `resolveLlmRoute` also re-checks `Feature.SIGNAL_LLM_PROFILES` and returns undefined so a caller that skips the refines still cannot pin a route on Cloud (same posture as `StepConfig::for_signal` dropping the route backend-side); the refine owns the 400, the function owns the write. Default signals seeded at workspace creation pass `requireLlmProfile: false`.
- **CLI surface.** `lmnr-cli signal create` / `signal update` accept `--llm-profile-id <uuid>` + `--model <name>` (wire fields `llmProfileId` / `model` on `SignalInput` / `UpdateSignalInput`), and every `signal get` / `signal list` response echoes `llmProfileId` + `llmProfileName` + `model` (all `null` for env-routed signals). `lmnr-cli llm-profile` (aliased `llm-profiles`) has full CRUD — `list` / `get <id>` / `create` / `update <id>` / `delete <id>` — backed by `api::v1::cli::llm_profiles` (`CliProjectAuth`; list returns `{ llmProfiles: LlmProfileResponse[] }`, the other routes return a bare `LlmProfileResponse`). The CLI maps flags to the flat `{ name, provider, config, secrets, models }` body and does no validation of its own: feature-gating, pair completeness, workspace membership, unlisted-model, in-use (RESTRICT) and duplicate-name errors are all surfaced verbatim via the CLI's error-envelope unwrapping. The profile routes themselves are available on Cloud too (profiles back the playground); only `signal create/update` with a profile is rejected there.

## Signal events column sorting

- The signal events table sorts via the shared `InfiniteDataTable` machinery: `defaultColumn.enableSorting` is `false`, so sorting is **opt-in per column** — `columns.tsx` sets `enableSorting: true` on `timestamp`, `severity`, and typed payload columns (number/boolean/enum); string payloads stay unsortable (free-text lexical sort is surprising). Sort state lives in the views layer (`effective.sortBy`/`sortDirection` via `useTableView().setSort`), persisted to URL + DB like filters/search.
- The events ORDER BY is resolved server-side by `resolveEventsSortColumn` in `frontend/lib/actions/events/utils.ts`, NOT bound as a param (ClickHouse can't bind ORDER BY expressions). Payload field names are interpolated into `simpleJSONExtract{Float,Bool,String}(payload, '<field>')`, so the field name is the injection boundary — it's regex-gated by `PAYLOAD_SORT_FIELD_RE` (`^[a-zA-Z_][a-zA-Z0-9_]*$`, same rule as `search_signal_events`); a non-matching name falls back to the default `timestamp DESC` rather than erroring. The frontend sends `sortType` (number/boolean/string; enum→string) so the cast matches; the backend never trusts it for native columns.
- Sort params thread through three call sites that all hit `buildEventsQueryWithParams`: `getEventsPaginated`, `getEventsByEmergingClusterPaginated`, and the GET route's `GetEventsPaginatedSchema` (which already inherits `sortBy`/`sortDirection` from `PaginationFiltersSchema → SortSchema`; only `sortType` is added). When adding a new events fetch path, thread all three (`sortBy`, `sortDirection`, `sortType`).

## Signal Event Payloads

- Signal event payloads (generated enterprise-side in `lmnr-private`, the OSS `app-server/src/signals` is just public stubs) embed markdown-formatted trace links (`[Label](https://lmnr.ai/project/<pid>/traces/<tid>?spanId=<sid>&chat=true)` or `laminar.sh` equivalent). Parse them with `parseSpanLinks` from `@/lib/traces/span-link-parsing`. The trace-view's `renderSpanReferences` (`@/components/traces/trace-view/span-reference`) wraps that parser; the signals events table renders payload cells through `renderSpanReferences` from `createPayloadColumnDef` (`frontend/components/signal/events-table/columns.tsx`). When rendering there, open the trace via `useSignalTraceParams` (`history: "replace"`) so the drawer is derived from the URL rather than copied into the signal store. Stop propagation on the anchor click so the table row click doesn't also fire.
- **A signal fires MULTIPLE events per trace** — one per distinct finding (the enterprise `submit_identification` tool emits a `findings` array, each finding → one `signal_events` row). The trace-view signal panel renders ALL of them: `getTraceSignals` (`frontend/lib/actions/signals/trace.ts`) groups events by signal and attaches **per-event** `leafClusters` (via `pickLeafClusters`). There is deliberately **no signal-level cluster field**: one signal's events routinely land in unrelated clusters, so any single representative is arbitrary. A `TraceSignal.leafCluster` (latest event's first leaf) did exist to tint the panel, but its only reader — `getSignalAccentColor` in `signal-events-panel/utils.ts` — was never imported, and the panel chrome is a hardcoded `bg-blue-400/12` / `border-blue-400/30` in `panel-body.tsx`; the field and the helper are both gone. Cluster color lives per pill instead, via `getClusterColorById(cluster.id)` in `signal-details.tsx`. If you want a per-signal accent back, derive it in the component — do not re-add a server field. `signal-details.tsx` renders one `FindingCard` per event (severity badge + a pill per leaf cluster + payload fields); do NOT collapse to `events[0]`. The store type `TraceSignal.events: TraceSignalEvent[]` (`trace-view/store/base.ts`) and the header's fetch-mapping (`trace-view/header/index.tsx`) both carry per-event `leafClusters` through.
- **One event can belong to SEVERAL clusters at the same level, so a leaf is a LIST, not a single node (LAM-2142).** `events_to_clusters` has no uniqueness beyond `(project_id, event_id, cluster_id)` and the enterprise clusterer legitimately files one event under multiple L1 clusters. `pickLeafClusters` therefore keeps EVERY node at the minimum level rather than `.sort((a,b) => a.level - b.level)[0]`, which silently dropped the siblings; the coarser entries in `signal_events_v0.clusters` are those leaves' ancestor chain and stay hidden. Sort the result by name — `clusters` comes from a ClickHouse `groupArray`, so its order is not stable across requests and the pills would otherwise reshuffle.
