## App-server env vars (`src/env/`)

- Every env var the app-server reads is registered in `app-server/src/env/` (one submodule per domain: `server`, `workers`, `batching`, `clickhouse`, `database`, `mq`, `quickwit`, `llm`, `secrets`, `connections`, `rate_limit`, `observability`, `notifications`, `storage`, `sql`, `debugger`, `mock`). Do NOT inline a string literal env name or hand-roll a `std::env::var(...).parse().unwrap_or(...)` chain at a call site — add/look up the entry here.
- `env/private/` holds the enterprise-only descriptors (`clustering`, `signals`, `agent`), gated behind the `signals` feature and absent in OSS.
- **`mod env` shadows `std::env`.** Inside any file that does `use crate::env;`, you MUST write `std::env::var(...)` (fully-qualified) for bare reads — a plain `env::var` resolves to this module and won't compile.
- Two kinds of entry:
  - **Typed descriptors** `NumEnv<T>` / `StringEnv` / `BoolEnv` for vars with a static default — `pub const FOO: NumEnv<u32> = NumEnv::new("FOO", 4);`, read via `env::workers::FOO.get()`. `.get()` trims, treats empty string as unset, parses, and falls back to the default (empty-string-as-unset matters for k8s ConfigMap keys). `BoolEnv` accepts `true/1/yes/on` + `false/0/no/off` case-insensitively. Float types work too (`NumEnv<f32>` for `EXTERNAL_TRACING_SAMPLE_RATE`), since `.get()` is generic over `FromStr`.
  - **`NumEnv::clamp(min, max)`** for a var whose valid range is narrower than its type (a 0.0-1.0 probability, a bounded worker count) — `SAMPLE_RATE.clamp(0.0, 1.0)`. Use it instead of `f64::clamp` / `Ord::clamp` at the call site: those PANIC when `min > max` and `f64::clamp` propagates NaN, and an env descriptor must never be able to take the process down. A non-finite parse (`NaN`, `inf`, or an overflowing literal like `1e999` — `f64::from_str` returns `inf` for that, it does NOT error) falls back to the DEFAULT rather than clamping to a bound, because clamping would silently promote a typo to the most extreme legal setting (for a sample rate: "keep everything", the exact cost blowup the clamp exists to prevent). Note the Sentry SDK's own `sample_should_send` already clamps internally, so for `EXTERNAL_TRACING_SAMPLE_RATE` the clamp is defence-in-depth rather than panic-prevention. The generic bound needs the local `FiniteNum` trait (impl'd true for every int, real check for `f32`/`f64`) because `is_finite` lives on the float types, not on a shared numeric trait in std.
  - **Bare-name `&str` constants** (`pub const URL: &str = "CLICKHOUSE_URL";`) for required secrets/connection strings that `expect()` at boot and for vars consumed only inside multi-var feature detection — forcing a default onto those would be misleading, so they keep their read logic at the call site and only borrow the name.
  - `env::num_with_default(name, default)` free fn for the rare var whose default is a runtime value (a crate const) and so can't be a `NumEnv` const.
- **`LAMINAR_CLOUD` (`env::connections`, `BoolEnv`, default false) is the self-hosted switch.** `Feature::SignalLlmProfiles = !LAMINAR_CLOUD` lets signals pin a workspace LLM profile (profile CRUD itself is ungated — the playground uses profiles everywhere); `Feature::Signals = has_llm_backend() || SignalLlmProfiles`, so self-hosted boots signal workers with no `LLM_PROVIDER` at all (`LlmClient::new(store)` tolerates a missing env provider). `Feature::Clustering` and `Feature::InputExtraction` are `has_llm_backend()` on their own — never alias one feature's flag to another's. Set `LAMINAR_CLOUD=true` on both services in Cloud; the existing `ENVIRONMENT`-based checks are untouched.
- **`has_llm_backend()` = `has_llm_provider() || has_system_workspace()`** (`features/mod.rs`): a complete `LLM_PROVIDER` config, or `LLM_SYSTEM_WORKSPACE_ID` parsing as a UUID (the workspace whose profiles back global `llm_feature_routes`; see `docs/internal/ai-features.md` → "LLM feature routes"). The per-feature provider vars (`SIGNALS_PARSING_LLM_PROVIDER`, `INPUT_EXTRACTION_LLM_PROVIDER`, `SP_EXTRACTION_LLM_PROVIDER`, `AGENT_LLM_PROVIDER`) no longer exist; per-feature routing is table-driven.
- **An incompletely-configured `LLM_PROVIDER` degrades silently, it does not fail boot.** `has_llm_provider()` mirrors `LlmClient::new`'s credential checks; when `has_llm_backend()` returns false the log says `No LLM-backed feature enabled - skipping LLM client initialization` followed by `LLM provider not available - skipping ...` per worker, and ingestion keeps running. Grep the startup log for `Initialized <provider> provider ... at <url>` to confirm which client actually registered (it prints the resolved base URL). Model-capability gates that match on the model string (`bedrock::requires_adaptive_thinking` / `supports_sampling_params`) also govern the `azure_anthropic` provider, where the model is an arbitrary **deployment name** — a deployment not named after its model silently misses those gates and 400s on `thinking`/`temperature`. When adding a provider, extend BOTH that match arm and `LlmClient::new` or the workers never spawn.
- **`cargo fmt` and `cargo check --features signals` both fail in OSS** because the `signals` feature gates modules whose files live only in `lmnr-private`. `cargo fmt` walks the module tree and errors on the missing `mod agent`. To format `main.rs` (or anything that triggers the tree walk), `touch` empty stubs and run `rustfmt --edition 2024 <file>`, then delete the stubs. Current stub set: `src/agent.rs`, `src/license.rs`, `src/clustering/private.rs`, `src/signals/private.rs`, `src/traces/previews.rs`, `src/traces/sampling.rs`, `src/api/v1/cli/agent.rs`, `src/ch/private.rs`, `src/db/private.rs`, `src/env/private.rs` (rustfmt names each missing mod one at a time, so just iterate). Note `rustfmt --check` on `main.rs` with stubs also reports diffs in OTHER files it pulls in (including the empty stubs themselves) — filter the output to `Diff in .*main.rs` before concluding main.rs needs changes. Per-file `rustfmt` on leaf files works without stubs. Default-feature `cargo check`/`cargo fmt` is the real gate.
- **`rustfmt --edition 2024 <file>` is per-file ONLY for leaf modules — pointed at a `mod.rs` it follows every `mod` declaration and rewrites the whole subtree**, which is exactly the unrelated-diff problem the no-`cargo fmt` rule exists to prevent. `git diff --stat` after any `rustfmt` on a `mod.rs` and `git checkout --` the files you didn't touch.
- **A `cargo` failure that names a rustc version is a toolchain problem, not a code problem.** The `aws-*` crates in `Cargo.lock` set `rust-version = 1.94.1`, so an older toolchain fails during *resolution* — before compiling anything — and no source change will help. Fix it with `rustup update stable` (`--ignore-rust-version` on every invocation also works, but silently builds against an unsupported compiler). Also: `app-server` is a **bin-only** package, so `cargo test --lib <module>` dies with `no library targets found` — always `cargo test --bin app-server <module>` (the filter takes a single path prefix, not a list).
- **A shared file that only PRIVATE consumers call still belongs in OSS verbatim** — it will emit a `dead_code` warning there, and that's the accepted convention (`db/projects.rs::get_project_name`). Don't "fix" it by adding an OSS-only `#[allow(dead_code)]`: that re-creates the drift. Only add `#[cfg_attr(not(feature = "signals"), allow(dead_code))]` when you're adding it to BOTH repos (as `worker/mod.rs` / `batch_worker/mod.rs` do for their enum variants).

## Retries (`utils/retry.rs`, `backon`)

- **Never build an `ExponentialBuilder` from `ExponentialBuilder::default()` at a call site.** Use `retry::bounded_delay` / `retry::bounded_attempts` / `retry::unbounded` (`app-server/src/utils/retry.rs`). The default fails open in three ways at once: jitter is OFF (a fleet retries in lockstep against one sick dependency), `max_times` is `Some(3)` (silently truncates any loop meant to be budget-bounded or unbounded), and `factor` is 2.0 rather than the 1.5 every call site inherited from the old `backoff` crate. The helper module's tests pin all three.
- **`backon`'s retryability lives INSIDE the error value**, via `.when(|e| ...) -> bool`. `backoff` carried it in a side channel (`Result<T, backoff::Error<E>>`), so a closure that flattened its error to `anyhow::Error` before returning still kept the transient/permanent bit. Under `backon` that bit is destroyed: if the closure erases the discriminant, `.when()` can't see it and everything becomes retryable. Either return the rich error whole (`.when(HandlerError::should_requeue)`, `.when(|e| e.retryable)`, `.when(ProviderError::is_retryable)`) or introduce a file-local enum to carry the split (`mq/rabbitmq/mod.rs`'s `PublishError`). A retry site with no `.when()` retries on EVERY error — check that's what you want.
- **`with_total_delay` is NOT `backoff`'s `max_elapsed_time`.** It caps the SUM OF SLEEPS and excludes time spent inside the operation; `max_elapsed_time` measured wall clock including it. For fast operations the drift is negligible (`bounded_delay` is fine); for slow ones it is not — two 5-retry LLM sites would stretch from a ~300s budget to ~20 min. Those use `bounded_attempts` plus an explicit `tokio::time::timeout` around the whole retry (`traces/input_extraction/generate.rs`, `traces/static_sp_extraction/agent.rs`). The timeout is also strictly stronger: it CANCELS an attempt in flight, where `max_elapsed_time` only declined to schedule the next one.
- **Jitter widens delays UPWARD and is applied after the clamp**, so a realized sleep can reach `2 * max_delay` (`backon` jitters into `[d, 2d)`). `backoff` jittered symmetrically into `[0.5d, 1.5d)`. Any test asserting a delay ceiling needs `max_delay * 2`.
- The `tokio-sleep` feature makes `backon` sleep through tokio, so retry loops fast-forward under `#[tokio::test(start_paused = true)]`. Attempt-count bounds are deterministic there; a `total_delay` bound terminates without sleeping at all, since the iterator sums its own yielded delays.
- `retry_query_offset` (`mq/stream/reader.rs`) steps the built iterator by hand rather than using `Retryable` — the combinator's future isn't `Sync`, which the stream client's `consumer_update` closure requires. `BackoffBuilder::build()` yields a plain `Iterator<Item = Duration>`, so hand-driving keeps the crate's schedule.

## TLS / crypto backend (`Cargo.toml`)

- **aws-lc-rs is the only crypto backend; keep `ring` and OpenSSL out.** AWS SDK (`default-https-client`), reqwest 0.13 (`rustls`), clickhouse (`rustls-tls`), lapin, our rabbitmq-stream fork (`tokio-rustls` defaults) and `jsonwebtoken` (no ring option, only `aws_lc_rs` / `rust_crypto`) all hard-wire aws-lc, so moving to ring would mean rewiring every one of them. When adding a TLS dep, pick its aws-lc / `rustls` variant and turn off `default-features` if they include `native-tls`. Check with `cargo tree -i ring -e normal,build` (empty) and `cargo tree -i openssl-sys` (no match). `ring` stays in `Cargo.lock` as an unbuilt optional dep, which is fine.
- **reqwest picks native-tls over rustls whenever both are enabled** (`TlsBackend::default`), across every client in the process. A single dep whose defaults include `native-tls` (sentry's `transport`, resend-rs's `default`) silently moves all outbound HTTPS to OpenSSL.

## MCP server (`api/v1/mcp/`, `auth/mcp_oauth.rs`)

- **Two credentials on `/v1/mcp`.** The `mcp_auth` middleware (not `project_auth`) takes a project API key (64 alphanumerics, no dots) or an OAuth access token (anything JWT-shaped) and inserts an `McpCaller`. Tokens are verified against the frontend JWKS (shared `JwksCache`) with `typ=at+jwt`, `iss`, `aud` ∋ `MCP_RESOURCE_URL`, `azp` and a UUID `sub` (frontend side: `docs/internal/auth.md` "MCP OAuth"). Every 401 carries `WWW-Authenticate: Bearer resource_metadata=".../.well-known/oauth-protected-resource/v1/mcp"`, which is what makes Claude Code start the OAuth flow. OAuth is on only when `MCP_RESOURCE_URL` is set; the issuer defaults to `<NEXT_PUBLIC_URL origin>/api/auth` (`MCP_AUTHORIZATION_SERVER_URL` overrides). Locally: `NEXT_PUBLIC_URL=http://localhost:3000 MCP_RESOURCE_URL=http://localhost:8000/v1/mcp cargo run`.
- **Every project-scoped tool takes `#[serde(flatten)] project: ProjectParam` and is one `self.run(tool, &context, project_id, audit, |scope: X| async move { .. })` call.** The runner resolves the project, checks access, runs the body, emits the audit event and renders the result; the body returns `Result<ToolOutput, ToolError>` and uses `?` (`ToolError::Message` is shown to the model, `Internal` is logged and shown as "Internal server error"). An API key is bound to its project (a different `projectId` is an error). An OAuth user must pass `projectId` (no header or sole-project fallback, so every call names its project); membership is checked on every call (`is_user_member_of_project`, shared cache key with the frontend). A new tool file adds `#[tool_router(router = <area>_tools, vis = "pub(super)")]` and must be summed into `all_tools`, or it is silently missing (the `router_exposes_expected_tools` test lists every name).
- **Every tool declares a `title` and all four `annotations(...)` hints, and every input has a doc comment**: the Claude and ChatGPT directories require them. Keep each description and `SERVER_INSTRUCTIONS` under 2 KB, since Claude Code truncates past that; that is why the SQL schema is `get_sql_schema`'s result, not `query_laminar_sql`'s description. A struct's doc comment becomes its schema description, so a shared type documented for developers gets a model-facing `#[schemars(description = "...")]`.
- **`GET /v1/mcp/server-card` is the public MCP Server Card** (SEP-2127), registered before the authenticated `/v1/mcp` scope. It advertises `MCP_RESOURCE_URL`, so it 404s when OAuth is off; `server_info()` feeds both it and `initialize` (the card caps `description` at 100 characters).
- **Every tool admits project API keys and OAuth users alike**, matching the `/v1` API-key surface (`/v1/signals`, `/v1/llm-profiles`, `/v1/tag`); `run` hands the body a `ProjectScope`. `create_signal` subscribes the alert to the caller's email only for OAuth users (keys have none, like `/v1/signals`). Writes pass `Some(Audit::new(resource, action))` (source `mcp`, actor = key or user; a failed call's target comes from `Audit::target`, a successful one's from `ToolOutput::target`); reads and tags pass `None`, mirroring `audit::middleware::classify` (the `/mcp` route itself is `Skip`). Access failures are not audited. Policy: keys → `Actor::ApiKey`, users → `Actor::Cli`.
- **Enterprise tools (`get_trace_context`, `ask_agent`) live in `mcp/enterprise.rs`, compiled only with `signals`.** OSS builds don't list them, rather than listing a stub that answers "unavailable".
- Tool inputs reuse the service input types where possible (`SignalInput`, `UpdateSignalInput`, `CreateLlmProfileInput`, ... derive `schemars::JsonSchema`, flattened into the params). Their doc comments become the field descriptions clients send to the model, so keep them accurate for callers, not just for the service.
- **Never let `null` mean "clear" in a tool input.** Schema-driven clients (strict tool calling) send `null` for every optional field they leave unset, so a flattened `double_option` field like `UpdateSignalInput.sample_rate` would wipe data on unrelated updates. The tool maps `null` to "leave stored" and takes an explicit flag (`clearSampleRate`, `UpdateSignalParams::try_into_update`). Likewise anything a read tool returns masked (LLM-profile secrets) must survive being echoed back into the update: `merge_secrets` drops an incoming value equal to the stored value's own mask. The same clients also break any non-`Option` `#[serde(default)]` field (`bool`, `Vec`, map, struct): `serde(default)` covers only an absent key, so a `null` fails the whole call before the handler runs. Add `deserialize_with = "crate::utils::null_as_default"` to every such field a tool advertises, nested ones included (`tests::null_optional_fields_read_as_absent`). On an update that **replaces** a nested object, `null` → default is still a reset, so give the tool an all-`Option` patch type laid over the stored value instead (`ProfileConfigPatch` for `update_llm_profile`: the service replaces `config` whole, and a defaulted `headerNames` would also prune the stored header secrets).
- **Never advertise a trace/span id param as a plain `Uuid` schema.** schemars emits `format: "uuid"`, and zod-based MCP clients (`z.fromJSONSchema`, `json-schema-to-zod`) turn it into the RFC-strict `z.uuid()`, which rejects most OTel ids (random version/variant nibbles), so the call fails client-side before reaching us. Keep the Rust field `Uuid` but override the schema with `#[schemars(with = "String", regex(pattern = ...))]` (see `TRACE_ID_PATTERN` / `GetTraceContextParams`). The pattern accepts exactly hyphenated (36 chars) or bare 32-hex; don't use optional `-?` hyphens, since `Uuid` rejects partially hyphenated strings with a confusing server error. Doc-comment line breaks survive into the advertised `description`. Check the advertised schema with `npx @modelcontextprotocol/inspector --cli http://localhost:8000/v1/mcp --transport http --header "Authorization: Bearer <key>" --method tools/list` (`--strict` reports portability warnings).

## Local dev env quirks (full detail)

- **`PORT` env inheritance can silently break the app-server HTTP listener (8000).** `dotenv::dotenv()` does NOT override an already-set env var, so a shell that exports `PORT` (e.g. an agent sandbox using `PORT=3005`) beats `.env`'s `PORT=8000` and the HTTP server fails to bind — gRPC (8001) and SSE (8002) still come up. The bind error is swallowed (`main` joins the never-returning consumer handle before the http handle), so you get "Spinning up full HTTP server" with no "starting service ...:8000" line and no panic. Launch with an explicit `PORT=8000 ./target/debug/app-server` (or `env -u PORT`) and verify with `tr '\0' '\n' < /proc/<pid>/environ | grep ^PORT`. The same shadowing hits `next dev` (`EADDRINUSE`) — use `PORT=3000 pnpm run dev` — and node `--env-file` (a sandbox-exported `LMNR_PROJECT_API_KEY` wins over the scratch `.env` one → 401s); run `env -u <VAR> node --env-file .env ...`.

- **The binary must be launched with `app-server/` as the cwd.** `NameGenerator::new()` reads `data/adjectives.txt` / `data/nouns.txt` relative to the process cwd and `unwrap()`s, so running `./app-server/target/debug/app-server` from the repo root panics the `http` thread (`NotFound`) while the rest of the process keeps running — same symptom as the `PORT` quirk above: gRPC and 8002 come up, 8000 never binds, and the only trace is one `panicked at src/names/mod.rs` line in the log.

- **ClickHouse ≥ 26 breaks every app-server read: "decompression error: incorrect magic number".** Its default `network_compression_method` is ZSTD, while `clickhouse` 0.15 (the Rust client) asks for compressed responses and only decodes LZ4. Inserts still succeed, so it looks like data is written and never readable. Fix it on the server side with `ALTER USER <user> SETTINGS network_compression_method='lz4'` (or the same key in the user's settings profile). Check this before any ClickHouse upgrade in Cloud.

## Local `/v1/cli/*` testing in the sandbox

- **CLI-auth JWKS defaults to `https://laminar.sh`**, so every `/v1/cli/*` request 401s locally with an otherwise-valid token. Launch app-server with `NEXT_PUBLIC_URL=http://localhost:3000 NEXT_INTERNAL_URL=http://localhost:3000` (the JWKS URL is derived as `{base}/api/auth/jwks`). Mint a token with `POST /api/auth/sign-in/local-email` (`{"email":"agent@lmnr.ai"}`, `FORCE_EMAIL_AUTH=true` is set) then `GET /api/auth/token` with the session token as bearer.
- **Staging Postgres lags the migrations (checked 2026-10-28).** It has no `users.preferences` column, so `local-email` sign-in 500s from the dev frontend. To mint a token, temporarily comment that column out of `frontend/lib/db/migrations/schema.ts`, sign in, then `git checkout` the file; the session token stays valid. Staging also has no `dashboards` table, and `dashboard_charts` has no `dashboard_id` (migration 0115 is not applied). Every dashboard write therefore 500s there, as does SQL over `dashboard_charts` (`Unknown table function dashboard_charts_v0`). Logic that runs before the DB is still testable, e.g. the chart query checks (`lib/actions/dashboard/chart-query.ts`, which run before the dashboard lookup) with a placeholder dashboard id. For checks that need result rows from an idle project, use `WHERE (<time-param filter>) OR 1 = 1`.
- **The sandbox clock can run behind file mtimes**, so freshly-edited sources look OLDER than the built binary and `cargo build` reports "Finished" without recompiling — the running server then 404s routes that exist in the source. `touch` the changed files (or verify with `strings target/debug/app-server | grep -c '<a route literal>'`) before concluding a route is broken.
- **Never kill app-server with `pkill -f app-server` or a `ps | grep` loop** — the pattern matches the agent's own shell and terminates the turn. Match on `readlink /proc/<pid>/exe` against the binary path (including the `" (deleted)"` suffix a rebuild leaves behind, which is why a plain path equality check misses the old process) and skip anything sharing your own PGID.
