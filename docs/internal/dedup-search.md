## Group-scoped content dedup (`deduped_content_v2` / `spans_v0`)

- **Code lives in `app-server/src/traces/dedup/`**: `mod.rs` (group id, hashing, `SeenMarks`, `SharedContentBatch`), `session.rs` (session resolution + Redis hint), `messages.rs` (`MessageDedup`, `build_message_dedup`, `MessageBatch`), `tools.rs` (`ToolDedup`, tool-definition extraction). `ch/deduped_content.rs` is the row type + `get_content_by_hash`. The old `traces/input_dedup.rs` / `traces/tool_dedup.rs` are gone.
- **Why v2 exists (LAM-2234):** `deduped_content` is keyed `(project_id, content_hash)`, so reconstructing one trace touches one granule per distinct hash scattered over the whole project. `deduped_content_v2` (`63_deduped_content_group_scope.sql`) is keyed `(project_id, group_id, content_hash)` where **group = the span's `session_id` if it has one, else `toString(trace_id)`** (hyphenated lowercase — `Uuid::to_string()` and CH `toString(UUID)` agree). One conversation's content is one contiguous key range; a trace read is one or a few adjacent granules. Same content in two groups = two rows (deliberate: locality beats cross-conversation dedup, which was rare anyway). `index_granularity_bytes = 2 MiB` (default 10 MiB) trims range-boundary waste; smaller buys nothing since compressed blocks are ~1 MiB.
- **The group is derived from the span row, never stored.** `dedup::group_id(session_id, trace_id)` in Rust is the mirror of `WITH if(session_id != '', session_id, toString(trace_id)) AS dedup_group` in `spans_v0` / `build_snippet_query`. Adding a `group_id` column to `spans` was rejected — the invariant "storage group == what the span row says" is what makes the view correct with no extra column.
- **Session resolution runs on the producer, before hashing** (`dedup::session::resolve_session` in `preprocess_for_queue`). Any span carrying its own `session_id` writes the hint `trace_session:{project}:{trace}` → session (TTL 6h) — this is the ONE place the producer writes Redis, and it's a hint, not a seen-mark. An LLM span WITHOUT a session reads the hint and, on a hit, stamps `lmnr.association.properties.session_id` into `raw_attributes` so `spans.session_id` carries it and the row's derived group matches the storage group. Spans ingested before the session was known stay trace-grouped — consistent with their own row, so they still resolve. `trace_outputs_v0` is the exception: `traces_static.session_id` may have arrived after the output hashes were written, so that view tries the session group, then the trace group, then v1.
- **Forward-only migration, two dictionaries.** `deduped_content` (v1) gets no new writes and is read only as a fallback. Readers use `if(isNull(dictGetOrNull(v2)), dictGetOrDefault(v1, ..., 'null'), assumeNotNull(dictGetOrNull(v2)))`. Measured on CH 26.4: `if` short-circuits (0 v1 lookups on a v2 hit, also inside `arrayMap`) and the two identical `dictGetOrNull(v2)` calls are CSE'd into one lookup; **`coalesce`/`ifNull` evaluate every argument eagerly**, so never use them for dict fallback chains. `system.dictionaries.query_count` moves +2 per `dictGetOrNull` and +1 per `dictGetOrDefault`; probe with the output consumed (`sum(length(v))`) — `SELECT count() FROM (subquery)` prunes the expressions.
- **The `llm_messages_dict` leg is dropped from every reader** (spans_v0, trace_outputs_v0, search snippets, `get_content_by_hash`). Spans from before migration 46 whose hashes only exist in `llm_messages` now reconstruct to literal `null` placeholders (staging: 34 of 1457 dedup'd spans). `llm_messages` + `llm_messages_dict` are NOT dropped yet — that's a follow-up migration; if those spans matter, backfill `INSERT INTO deduped_content_v2 SELECT project_id, toString(trace_id), message_hash, content FROM llm_messages` first (covers spans with no session_id).
- **Dictionaries are created at frontend boot**, not by migration (`ensureContentDicts` in `frontend/instrumentation.ts`, table-driven `CONTENT_DICTS`). `CREATE OR REPLACE` with env creds interpolated into `SOURCE` — clickhouse-migrations MD5-checksums `.sql` files, so creds can't live there. `CREATE VIEW` does NOT validate dictionary existence (verified: views were created on staging before the dict), but SELECTing the view fails with `Dictionary not found` until boot creates it — a fresh-install window of one boot. Dict attrs can't be `FixedString(N)`; `content_hash` is `String` and CH coerces the table's `FixedString(32)`.
- **Two Redis seen-scopes, two semantics** (`cache/keys.rs`): `s2:{project}:{group}:{hex}` = storage presence in v2 (drives wire content + the `deduped_content_v2` insert); `tn:{project}:{trace}:{hex}` = trace-scoped first occurrence (drives `*_new_message_indices` for search). Independent in BOTH directions: storage-hit + trace-new (same session, new trace) and trace-seen + storage-miss (group changed mid-trace — a later span adopts a `trace_session` hint, or the hint expired). The producer therefore checks both axes for every message and never lets a `tn:` hit skip the `s2:` check; this is what guarantees every `(group, hash)` a `spans` row references exists in v2, so `spans_v0` needs no cross-group fallback. The old `s:` prefix is retired; it MUST NOT be reused — a stale `s:` hit would suppress a v2 insert that never happened. TTL 1h on both.
- **Stamping invariant**: `SeenMarks::stamp` is the only seen-mark writer and runs on the consumer **only after BOTH `deduped_content_v2` AND `spans` inserts succeed** (last step of the span branch). `tn:` keys are backed by `spans.*_new_message_indices`, not by the content table, so stamping before the spans insert could orphan the trace-new marker. Insert failure → transient error → Rabbit redelivers → no phantom keys.
- **`SharedContentBatch`** collapses `(project_id, group_id, hash)` across input + output + tools in one consumer batch (key MUST match the table ORDER BY; a batch can mix projects and groups) and bills content bytes to the first referrer. **Cross-direction collapse** (span A's output = span B's input in the same group) emits one row.
- **Tool definitions** are normalized into one canonical JSON array per span by `dedup::tools::extract_tool_definitions` from `ai.prompt.tools` (Vercel AI SDK), `gen_ai.tool.definitions` (OTel GenAI), or `llm.request.functions.{N}.*` (OpenLLMetry/LangChain); hashed as one blob into `CHSpan.tool_definitions_hash FixedString(32)` (zero hash = no tools). `spans_v0` exposes `tool_definitions` via the same v2→v1 chain with `''` as the default. `should_keep_attribute` strips those attributes at the consumer so legacy spans don't double-count / surface stale tools; the producer strips them at extraction too.
- **Wire shape**: `RabbitMqSpanMessage` carries `input_dedup` / `output_dedup: Option<MessageDedup>` and `tool_dedup: Option<ToolDedup>` (`serde(default)`; `MessageDedup` = `hashes` + `trace_new_indices` + `storage_miss_indices` + `contents: BTreeMap<position, JSON>` covering every position in either list — a plain derive with `serde(default)` on the optional fields, no custom deserializer). Nothing about the group rides the wire. `None` = "no dedup applies": `CHSpan.input` keeps raw JSON and `spans_v0` falls through via `if(notEmpty(input_message_hashes), <reconstruct>, input)`.
- **Checkpoints** carry `session_id` (`serde(default)`) so the consumer's `get_content_by_hash` can rebuild the group with `dedup::group_id`; it queries v2 then v1.
- **`lmnr.span.input` / `lmnr.span.output` are `remove`d from `raw_attributes` by `parse_and_enrich_attributes`** (LAM-2116) — the payload used to ride the queue twice. `should_keep_attribute` still lists them as the legacy backstop for `pre_processed = false` spans. Same rule for any attribute copied into a struct field: strip at the producer, keep the consumer entry.
- **Frontend**: `Span.tools?: string` from `spans_v0`; `resolveTools(span)` prefers the column and falls back to attribute extraction. Project deletion lists `default.deduped_content_v2` AND `default.deduped_content` (and `llm_messages` until it's dropped).
- **Billing accounting** in `process_span_messages`: dedup'd LLM spans pay `32 * num_hashes + span_content_bytes` (newly inserted v2 content only, first referrer); non-recordable LLM spans (e.g. CC Bash `anthropic.messages`) are charged from their own dedup verdict; everything else `estimate_json_size(span.input)`. Output bytes are added only when there's an output verdict. The loop MUST run AFTER `convert_span_to_provider_format`.
- **Search snippets** (`search/snippets.rs::build_snippet_query`) read raw `spans` with the same `dedup_group` CTE and v2→v1 chain, scoped to `*_new_message_indices` so search semantics stay "first occurrence per trace". CH arrays are 1-indexed, hence `[i + 1]`.
- **Hashing**: BLAKE3-256 over sorted-key canonical JSON (`dedup::content_hash`); stored `content` is original-order `to_string` through `sanitize_string`, so reconstruction is byte-identical. CH views can't do correlated scalar subqueries (`NOT_IMPLEMENTED` at SELECT time) — dictionary lookups are the only option. `spans_v0` reads `span_kind` (DEFAULT-derived shadow of `span_type`, migration 43); don't drop `span_type`, ingestion writes it.
- **Ingest order** in `process_span_messages`: build `SharedContentBatch` + `MessageBatch`es synchronously, then `tokio::join!` (a) trace upsert and (b) the **sequential** span path `deduped_content_v2 → spans → SeenMarks::stamp`. Sequential because `spans` is plain MergeTree: inserting it first and failing the content insert would double-store every span on retry.

### Producer-side dedup

- The producer (`preprocess_for_queue` in `traces/producer.rs`) is the ONLY dedup site: `resolve_session` → `build_tool_dedup` → `build_message_dedup` (input, then output). Already-seen messages are stripped from the wire; the consumer never re-hashes or re-checks Redis. Runs sequentially per span — Redis `exists()` is cheap and we don't want to thunder-herd on large batches.
- `span.input = None` on the wire when a verdict exists — EXCEPT root spans (`parent_span_id.is_none()` OR `is_top_span`), because `TraceAggregation::from_spans` reads `root_span_input` for the trace-list preview. Use `is_top_span` (`pub(crate)` in `traces::utils`), don't duplicate the heuristic.
- `RabbitMqSpanMessage.pre_processed = true` makes the consumer skip `parse_and_enrich_attributes` + `convert_span_to_provider_format`; running the LangChain rewrite twice would replace `span.input` and break hash alignment.
- Consumer-side `MessageBatch::build` is bounds-checked against malformed verdicts (`get(..)` + `continue`), so a corrupt dedup skips entries instead of panicking the whole flush.
- Quickwit indexing reads the pre-built `span_trace_new_contents` (aligned with the batch) rather than projecting indices onto `span.input`, which is `None` on the producer path.

## Quickwit indexing of LLM spans

- Quickwit only indexes the **new** subset of an LLM span's input — the messages this span was first to introduce in its trace. Older repeated history is searchable via the earlier span that introduced it. `MessageBatch::span_new_indices` (0-based positions inside `span_hashes[i]`) drives this; `QuickwitIndexedSpan::from_span` indexes the resulting array. Non-LLM spans / non-array input fall through to raw `span.input`.
- The same indices land in ClickHouse as `spans.input_new_message_indices Array(UInt16) CODEC(ZSTD(3))` (migration `44_spans_input_new_message_indices.sql`). `CHSpan` only populates them when `input_message_hashes` is non-empty; legacy rows have an empty array, which the snippet query handles gracefully (empty `arrayMap` → empty input snippet, output / attributes still match).
- Search snippets read directly from the raw `spans` table (NOT `spans_v0`): for spans with `notEmpty(input_message_hashes)` the input snippet is built from `arrayMap(i -> <v2→v1 chain on input_message_hashes[i + 1]>, input_new_message_indices)` joined with `,`; non-LLM spans fall back to `extract(input, ...)`. Output / attributes use `extract(...)` unconditionally. Single CH query, no parallel split. See `build_snippet_query` in `app-server/src/search/snippets.rs`.
- Cleaning runs at `from_span` build time, not in the consumer. `clean_for_indexing(s, strip_roles)` in `app-server/src/quickwit/preprocess.rs` chains `ANSI strip → strip_noise (base64 images, signature / thought_signature values) → optional strip_role_keys → clean_whitespace (collapse real + literal `\n\t\r`, drop other backslashes) → unicode whitespace classes → NFC`. LLM spans pass `strip_roles=true` for input/output; attributes always pass `false`. The chain only removes / collapses chars (never adds), so the snippet `extract()` regex with `[\s\S]{0,50}` context and `[^a-zA-Z0-9]+` token gaps still matches the reconstructed-and-cleaned text.
- Events keep their own `preprocess_text` path (`PreprocessForIndexing` impl on `QuickwitIndexedEvent`); spans' `PreprocessForIndexing` is a no-op because cleaning already happened upstream.

## Quickwit indexing of signal events

- Signal events get their own Quickwit index `signal_events` (`frontend/lib/quickwit/indexes/signal_events.yaml`, applied at boot by `initializeQuickwitIndexes`). `mode: dynamic` (like `spans_v2.yaml`); the free-text content field is `payload`, declared `type: json`. `default_search_fields` is `[]` because the json field type **rejects bare root queries** — every search addresses subfields (`payload.foo:"…"`), built by the search route. Structural ids (`project_id`, `signal_id`, `trace_id`, `id`) are tokenizer:raw + fast; `severity` is `u64` (Quickwit rejects `u8`).
- **`payload` ships as a raw JSON object**, not flattened/filtered: `QuickwitIndexedSignalEvent.payload` is `serde_json::from_str(&event.payload).unwrap_or(Value::Null)`. The json field type is used instead of flatten-with-allow-list because: (1) **per-subfield position streams** — each key gets its own positions so phrase queries (all user queries are phrases via `escape_quickwit_query`) can't span field boundaries (a space-join produces cross-field adjacency false positives); (2) **type inference** — numeric/boolean subfields indexed under inferred types, so a string-path `OR` can't match a numeric column; (3) **keys are field paths, not tokens** — searching `"prompt"` doesn't false-match every event with a `prompt` column.
- Producer hook `publish_signal_events_for_indexing(events, queue)` in `app-server/src/quickwit/producer.rs` mirrors the span/event indexer (`IndexerQueuePayload::SignalEvents` in `quickwit/mod.rs`, routed by `QuickwitIndexerHandler` in `consumer.rs`). Called in the private signals handler (`app-server/src/signals/private/response_processor.rs`, after `insert_signal_events` succeeds, before clustering). Errors logged + swallowed (a Quickwit hiccup never blocks signal-event creation).
- `flatten_json` is a no-op (ships `Value` as-is for per-subfield indexing); `preprocess_for_indexing` walks the `Value` and applies `preprocess_text` (ANSI strip + whitespace collapse + NFC) to every string LEAF via `preprocess_json_strings` (`quickwit/utils.rs`). Leaf-aware because collapsing the whole JSON to a string would break per-subfield indexing.
- **`payloadFields` is load-bearing for search, not just snippets.** Used for (1) building the Quickwit query `payload.f1:"…" OR payload.f2:"…"` (json field has no searchable root) and (2) per-field CH `extract()` for snippet offsets. Frontend filters to `f.type === "string"` before sending. `search_signal_events` short-circuits to empty hits when `payload_fields.is_empty()` (a query with no clauses is rejected by Quickwit) — there is NO all-fields fallback; new callers MUST send a non-empty list.
- **Field-name injection is blocked at query construction:** `search_signal_events` filters every `payload_fields` entry against `PAYLOAD_FIELD_NAME_RE` (`^[a-zA-Z_][a-zA-Z0-9_]*$`) before interpolating into `payload.{name}:{escaped_query}`. The form rule in `schema-field-row.tsx` is the only prior validation (server zod is `z.record(z.string(), z.unknown())`), so without the Rust filter a name like `f1:"x") OR (payload.f1` would escape the parenthesised tenant scope and search the whole index cross-tenant. Failing names are silently dropped (unsearchable but still render). Mirror this filter anywhere user-derived field names hit Quickwit syntax.
- `CHSignalEvent.timestamp` is `i64` nanos-since-epoch (CH `DateTime64(9,'UTC')`); `from_event` reconstructs via the infallible `DateTime::<Utc>::from_timestamp_nanos`, and Quickwit's `timestamp` field accepts the RFC3339 serialisation natively.
- Search route `POST /api/v1/projects/{projectId}/signal-events/search` (`app-server/src/routes/signal_events.rs`) wraps `crate::search::signal_events::search_signal_events`. Returns `{ hits: SignalEventSearchHit[] }`, each `{ id, fieldSnippets: Record<fieldName, SnippetInfo> }`. With `payloadFields: string[]` it runs a CH `extract()` per field over the real `signal_events.payload` for highlight offsets; empty `payloadFields` returns ids only. No `snippetsCount`/`+N` badge (every matching field renders in its own column).
- Snippet fetch `fetch_signal_event_snippets` (`app-server/src/search/snippets.rs`): `SELECT id, array(extract(coalesce(nullIf(JSONExtractString(payload,'<f>'),''), toString(JSONExtractRaw(payload,'<f>'))), '<regex>'), …) AS field_snippets ... WHERE project_id=? AND signal_id=? AND id IN (…)`. Positional `Array(String)` zipped against the field-name list. `JSONExtractString` unescapes so offsets land on glyphs; `JSONExtractRaw` fallback covers non-string fields. `signal_events` is plain MergeTree scoped by `(project_id, signal_id)` — no FINAL. `build_search_regexes` / `post_process_snippet` / `escape_quickwit_query` (pub(crate) re-export from `search/mod.rs`) are shared with the spans path — don't fork. Quickwit query: `project_id:{pid} AND signal_id:{sid} AND (payload.f1:"…" OR …)`; `search_field` not set (each clause carries its path).
- **Filter vs highlight can disagree on tokenisation edge cases** (unicode whitespace, hyphenation — Quickwit `default` tokenizer ≠ CH regex byte-for-byte) → a row with no highlighted cell. Do NOT re-filter hits against snippet emptiness — it drops valid matches.
- Time bounds attached to the Quickwit body only when supplied; the events CH query is unbounded with no params, so a default window in search would drop older matches. Backfill NOT included — pre-existing events show in the table but aren't searchable until re-indexed.
- **Frontend flow:** `searchSignalEvents` (`frontend/lib/actions/events/search.ts`) returns `SignalEventSearchHit[]`; `getEventsPaginated` / `getEventsByEmergingClusterPaginated` build `idFilter` from hit ids, retain the list, then `attachSnippets` merges `fieldSnippets` onto each `EventRow` by id. The events route accepts repeated `payloadField=<name>` params (only when `search` active). `createPayloadColumnDef` (`frontend/components/signal/events-table/columns.tsx`) renders `<HighlightedSnippet>` (UTF-16 `<mark>` slices) when `fieldSnippets?.[field.name]` is set, else the normal cell. Table UI uses `AdvancedSearch` (`events-table/index.tsx`); `resource` widened to include `"signal-events"` (`advanced-search/types.ts`), which disables autocomplete (no endpoint; `autocompleteResource` gate restricts to `"traces"|"spans"`). Recent searches persist via Zustand keyed `signal-events-${signal.id}`.
