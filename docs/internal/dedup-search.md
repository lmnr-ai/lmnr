## Project-scoped shared content dedup (`shared_content` / `spans_v0`)

- **`shared_content` table** (`46_shared_content_project_scope.sql`) is `(project_id, content_hash) → content` — project-scoped, not trace-scoped. Same content shared across traces collapses to one row. Backs three paths: input messages, output messages, and tool-definition blobs (hash space is shared; the table doesn't know which path produced a row).
- **Forward-only migration**: `llm_messages` (trace-scoped) is NOT dropped; `spans_v0` reads with `coalesce(dictGetOrNull('shared_content_dict', ...), dictGetOrNull('llm_messages_dict', ...))` so legacy spans keep resolving via the trace-scoped dict. New writes only go to `shared_content`. Backfill is optional / future work; dropping `llm_messages` is a separate later migration.
- **`shared_content_dict`** is created at frontend boot (`ensureSharedContentDict` in `frontend/instrumentation.ts`), same `CREATE OR REPLACE` env-driven pattern as `llm_messages_dict` and for the same reason (clickhouse-migrations checksum guard rules out baking creds into a migration). Recreating both on boot is cheap (DDL only); both are `COMPLEX_KEY_CACHE(SIZE_IN_CELLS 131072)` with `LIFETIME(MIN 30 MAX 60)`.
- **Two Redis scopes, two semantics**: `s:{project}:{hash}` is project-scoped storage presence (drives wire content + `shared_content` insert). `tn:{project}:{trace}:{hash}` is trace-scoped first-occurrence (drives `*_new_message_indices` for search). They are independent: a message can be storage-hit + trace-miss (don't ship content, but DO mark trace-new) — that's the cross-trace case that keeps span search returning the right span per trace under project-scoped storage.
- **Stamping invariant**: producer never writes Redis. `mark_seen` is the sole writer and runs on the consumer **only after BOTH the `shared_content` AND the `spans` inserts succeed** (last step of the span branch). The two key axes have different backing tables: `s:` (storage) keys are backed by `shared_content`, but `tn:` (trace-new) keys are backed by `spans.*_new_message_indices`. Stamping `tn:` before the spans insert leaves a window where a permanently-dropped spans insert orphans the trace-new marker — later spans in the same trace see the `tn:` key and ship empty `*_new_message_indices`, so no span records the first occurrence. Insert failure → return transient → Rabbit redelivers → no phantom keys for data that didn't land in CH.
- **Output dedup uses the same `shared_content` table**. CHSpan gets `output_message_hashes Array(FixedString(32))` + `output_new_message_indices Array(UInt16)`. The `seen_storage_in_batch` HashSet is shared across input + output + tools so a hash that appears as input in span A, output in span B, and inside a tool blob in span C emits exactly one row, billed to the first referrer in batch order.
- **Tool definitions** are normalized into a single canonical JSON array per span by `traces/tool_dedup.rs::extract_tool_definitions` from `ai.prompt.tools` (Vercel AI SDK), `gen_ai.tool.definitions` (OTel GenAI), or `llm.request.functions.{N}.*` (OpenLLMetry/LangChain). The producer hashes the array as one blob and stores it on `CHSpan.tool_definitions_hash FixedString(32)`. Empty/zero hash = no tools. Attributes-tab does NOT show tool definitions anymore; `spans_v0` exposes a virtual `tool_definitions` column reconstructed via `dictGet('shared_content_dict', 'content', (project_id, tool_definitions_hash))`.
- **`should_keep_attribute`** strips `ai.prompt.tools`, `gen_ai.tool.definitions`, and any key starting with `llm.request.functions.` so that legacy spans reaching the consumer without a producer-built `tool_dedup` verdict don't surface tool defs in `CHSpan.attributes` (avoids double-counting bytes AND prevents stale tool data in the attributes tab). Producer also strips them at extraction time so they don't ride the wire.
- **`lmnr.span.input` / `lmnr.span.output` are `remove`d from `raw_attributes` by `parse_and_enrich_attributes`, not just read** (LAM-2116). They used to be copied into `span.input` / `span.output` and left in place, so the whole payload rode the queue twice; `should_keep_attribute` dropped them at the consumer anyway, so nothing downstream could ever read them. **This attribute shape is NOT LLM-only** — it's the manual/SDK path for every span type (`observe`, `cua`, `kernel`, `skyvern`, `browser_use`, `openai_agents`), so the saving applies to Default/Tool spans too. The `remove` is safe because the ONLY reader of either key is that one block in `spans.rs`: everything between it and the consumer-side drop reads `span.input`/`span.output` instead (provider conversion, dedup, PII redaction, Quickwit, previews, `traces_agg`/`traces_static`, input-extraction, signals triggers, which only see `span.name` + aggregations). `should_keep_attribute` still lists both keys — that's the fallback for legacy spans reaching the consumer with `pre_processed = false`, so don't delete it as now-dead. Same reasoning applies to any future attribute whose value is copied into a struct field: strip at the producer, keep the `should_keep_attribute` entry as the legacy backstop.
- **Frontend**: `Span.tools?: string` from `spans_v0`. `extractToolsFromColumn(tools)` is the primary path; `extractToolsFromAttributes(attrs)` is the legacy fallback. `resolveTools(span)` (in `tool-list.tsx`) prefers the column and falls back to attribute extraction; call sites use `resolveTools(span)`.
- **Wire shape**: `RabbitMqSpanMessage` carries three `Option<...>` fields with `serde(default)`: `input_dedup: Option<MessageDedup>`, `output_dedup: Option<MessageDedup>`, `tool_dedup: Option<ToolDedup>`. Legacy producers (no dedup fields) still work — the consumer's per-span resolution treats `None` as "no dedup applies", so `CHSpan` falls through to raw `input` / `output` / no `tool_definitions_hash`.
- **Search snippets** (`search/snippets.rs::build_snippet_query`) tries `shared_content_dict` first then falls back to `llm_messages_dict` for input. Output snippets read only `shared_content_dict` (no legacy data exists). Both still scope to `*_new_message_indices` so search semantics are "first occurrence per trace" — preserved across project-scoped storage exactly because trace-new is its own Redis scope.
- **Billing accounting** in `process_span_messages`: input bytes follow the existing model (32B/hash + first-referrer content_bytes for dedup'd, raw JSON otherwise). Output bytes added on top — only counted when there's an output dedup verdict; non-dedup output is already in `estimate_size_bytes` via `span.output`. Tool bytes: 32B for the hash + first-referrer content if any; `should_keep_attribute` removed the source attribute bytes from `attributes` accounting so this isn't double-counted.

## LLM span input deduplication (`llm_messages` / `spans_v0`)

- LLM span `input` is structurally deduplicated: each message in the JSON array is BLAKE3-256 hashed over **sorted-key canonical JSON** (so field-order-only diffs collapse), emitted as a row in `llm_messages` (ReplacingMergeTree, `ORDER BY (project_id, trace_id, message_hash)`, **trace-scoped** — same content in two traces = two rows), and referenced via `spans.input_message_hashes Array(FixedString(32))` while `spans.input` is stored empty. Stored `content` is the message's **original-order** `serde_json::to_string` run through `sanitize_string` (serde built with `preserve_order`), so reconstruction is byte-identical to the non-dedup path; the hash is over canonical JSON for stable dedup identity. Non-LLM / tool-span `input` is never touched.
- `spans_v0` reconstructs via `arrayMap(h -> dictGetOrDefault('llm_messages_dict', 'content', (project_id, trace_id, h), 'null'), input_message_hashes)`, falling through to raw `input` when `input_message_hashes` is empty. The `llm_messages_dict` is a COMPLEX_KEY_CACHE dictionary **created at frontend boot** (`ensureLlmMessagesDict` in `frontend/instrumentation.ts`, `CREATE OR REPLACE` with `CLICKHOUSE_USER/PASSWORD/DB` interpolated into `SOURCE`), NOT by migration — `clickhouse-migrations` MD5-checksums `.sql` files and would break on credential rotation. Boot recreate is cheap (lazy cache, `LIFETIME(MIN 30 MAX 60)` refreshes within ~1min) and runs before Next.js serves traffic. Use `dictGetOrDefault` keyed on `(project_id, trace_id, message_hash)`, not a LEFT JOIN + `groupArray` (CH can't push the outer `trace_id` predicate through `GROUP BY`, so it aggregates all project messages). Dict attrs can't be `FixedString(N)` on CH 25.12 (`UNKNOWN_TYPE`) — `message_hash` is `String` and CH coerces the `FixedString(32)` transparently.
- `spans_v0` exposes `multiIf(...) AS span_type` which collides with `spans.span_type UInt8` under CH 25.x's analyzer. Migration 43 sidesteps this without a rename via `ALTER TABLE spans ADD COLUMN span_kind UInt8 DEFAULT span_type`; the view reads `span_kind`, ingestion keeps writing `span_type` (`CHSpan.span_type` in `app-server/src/ch/spans.rs`). Do NOT drop `span_type` — ingestion depends on it; `span_kind` is the DEFAULT-derived shadow column.
- **Billing / size attribution:** `span.estimate_size_bytes()` does NOT count `input`; the post-dedup input-bytes loop in `process_span_messages` (`app-server/src/traces/processor.rs`) owns it for every span (runs before both `CHSpan::from_db_span` and `update_workspace_bytes_ingested`, covers non-recorded spans too). Branches: dedup'd LLM spans pay `32 * num_hashes + span_content_bytes` (`span_content_bytes` = newly-inserted `llm_messages.content` only, so a shared message is billed once to the first referrer; `build_dedup_batch` returns it aligned with `span_hashes`); non-recordable LLM spans (e.g. CC Bash `anthropic.messages` via `is_skip_cc_span`, excluded from `recordable_indices` so no `dedup_lookup` entry) are charged from their own `dedups[span_idx]` (`hashes.len()*32 + sum(new_contents lens)`) — a naïve `estimate_json_size(span.input)` fall-through would charge 0; everything else pays `estimate_json_size(span.input)`. `estimate_size_bytes` filters `raw_attributes` via `should_keep_attribute` (matching `CHSpan.attributes`) because parsers COPY input-bearing attributes into `span.input` without removing them from `raw_attributes` — without the filter every OTel LLM/tool span double-bills. The loop MUST run AFTER `convert_span_to_provider_format` (LangChain conversion rewrites `span.input` to a differently-sized `Value::Array`).
- CH 25.x views do NOT support correlated scalar subqueries (both `SELECT (SELECT content FROM llm_messages WHERE message_hash = h)` and `WITH (SELECT ... WHERE trace_id = s.trace_id)` fail `NOT_IMPLEMENTED: can't find correlated column` at SELECT time though `CREATE VIEW` succeeds) — use the dictionary lookup.
- Redis key `m:{project_id_simple}:{trace_id_simple}:{hex(hash)}` TTL 1h, hot-path "seen recently" filter. MUST include `trace_id` (table is trace-scoped; a project-scoped key would suppress an insert for a message seen in another trace, leaving dangling `input_message_hashes`). Best-effort: on `exists()` error always insert, RMT merges. `mark_seen` is the only Redis writer, runs AFTER a successful `llm_messages` insert; never stamp before insert (a transient failure would leak `m:` keys whose rows don't exist, surfacing as literal `null` in reconstructed input).
- Ingest order in `process_span_messages`: build dedup batch synchronously, then `tokio::join!` two branches — (a) trace upsert (PG `traces` → CH `traces` → realtime) and (b) the **sequential** span path `shared_content → spans → mark_seen`. Span path stays sequential because `spans` is plain MergeTree (NOT RMT): inserting `spans` before `shared_content` and having `shared_content` fail would double-store every span on retry. `mark_seen` is LAST so `tn:` keys aren't stamped until backing rows are durable. `build_dedup_batch` dedupes `(project_id, trace_id, hash)` triples via HashSet (key MUST match table ORDER BY; a batch can mix projects). Do NOT collapse into a 3-way join.

### Producer-side dedup

- Hashing + Redis-existence checks ALSO run on the producer (HTTP / gRPC ingest in `publish_span_messages`) BEFORE the message hits Rabbit. Already-seen LLM input messages are stripped from `span.input`; the wire payload carries a `MessageDedup` (see `traces/input_dedup.rs`) instead. Wire savings grow linearly with conversation history depth, which is the point.
- `RabbitMqSpanMessage` carries two new fields with serde defaults: `pre_processed: bool` (consumer skips `parse_and_enrich_attributes` + `convert_span_to_provider_format` when true) and `input_dedup: Option<MessageDedup>` (the producer's hash + Redis-status verdict).
- Consumer ordering invariant: `prepare_span_for_recording` runs unconditionally (handles usage / span path / status), `convert_span_to_provider_format` runs ONLY when `pre_processed=false` — running it twice would double-apply the LangChain rewrite (which replaces `span.input` with a fresh `Value::Array`) and the producer's hashes would no longer match the consumer's view of the input.
- `span.input = None` on the wire when a plan was produced — EXCEPT for spans the consumer would render as the trace's root, because `TraceAggregation::from_spans` reads it for `root_span_input` (truncated preview rendered in the trace list). The producer carve-out matches the consumer's promotion logic, not just OTel parentage: keep `input` if `parent_span_id.is_none()` (natural OTel root) OR `is_top_span(span, &span.attributes)` (Laminar SDK top span — `span_id == ids_path[0]` AND `name == path[0]`; `prepare_span_for_recording` will later null its `parent_span_id`). A naïve `parent_span_id.is_some()` check lets an OTel-parented top span ride the wire with `input = None` and then get promoted to root on the consumer, silently erasing `root_span_input`. `is_top_span` is `pub(crate)` in `traces::utils` for this reason; do not duplicate the heuristic. Root spans are 1 per trace; dedup savings come from the long tail of nested LLM spans either way.
- **Producer is the only dedup site.** `preprocess_for_queue` in `producer.rs` is the one place that runs `build_dedup`; the consumer never re-mints. A `None`-dedup span reaching `build_dedup_batch` is treated as "no dedup applies": empty hashes, `CHSpan.input` keeps the raw JSON written by `from_db_span`, and `spans_v0` falls through to raw `input` via its `if(notEmpty(input_message_hashes), <reconstruct>, input)` branch. This means any ingest path that bypasses `publish_span_messages` (currently only `routes/spans.rs::create_span`, which always writes `input: None` anyway) is stored the old way without dedup — correct, just uncompressed. Adding a new bypass path that ships populated array input would silently miss dedup compression; if that becomes a concern, gate it with an `assert!` / `log::warn!` at the consumer rather than re-introducing the mint loop.
- `build_dedup_batch` is hardened against malformed dedups: `dedup.hashes.get(pos as usize)` and `dedup.new_contents.get(i)` are bounds-checked with `else continue`, so a corrupt-on-deserialise dedup or a future producer bug skips the bad entries instead of panicking and looping the entire flush on requeue.
- Quickwit indexing reads pre-built `dedup.span_new_message_values` (a `Vec<Vec<Value>>` aligned with the spans batch) instead of projecting indices back onto `span.input` — required because `span.input` is `None` on the producer path.
- Producer NEVER writes Redis. `mark_seen` is the only writer, runs only on the consumer, AFTER a successful `llm_messages` insert. The "stamp only after success" invariant is preserved exactly — the producer's Redis check is read-only and best-effort (errors fall through to "treat as new", same as the consumer's prior behaviour).
- `preprocess_for_queue` in `app-server/src/traces/producer.rs` runs sequentially per-span (NOT parallel via rayon) — Redis `exists()` calls are cheap and we don't want to thunder-herd Redis on large batches. Most ingest calls carry 1-N spans; per-span async loop is the right granularity.

## Quickwit indexing of LLM spans

- Quickwit only indexes the **new** subset of an LLM span's input — the messages this span was first to introduce in its trace. Older repeated history is searchable via the earlier span that introduced it. Implementation: `build_dedup_batch` in `app-server/src/traces/input_dedup.rs` returns `span_new_indices: Vec<Vec<u16>>` (0-based positions inside `span_hashes[i]`); `process_span_messages` projects those indices back onto `span.input` (`build_new_messages_subset`) and `QuickwitIndexedSpan::from_span` indexes the resulting array. Non-LLM spans / non-array input fall through to raw `span.input`.
- The same indices land in ClickHouse as `spans.input_new_message_indices Array(UInt16) CODEC(ZSTD(3))` (migration `44_spans_input_new_message_indices.sql`). `CHSpan` only populates them when `input_message_hashes` is non-empty; legacy rows have an empty array, which the search snippet query handles gracefully (empty `arrayMap` → empty input snippet, output / attributes still match).
- Search snippets read directly from the raw `spans` table (NOT `spans_v0`): for spans with `notEmpty(input_message_hashes)` the input snippet is built by `arrayMap(i -> dictGetOrDefault('llm_messages_dict', 'content', (project_id, trace_id, input_message_hashes[i + 1]), 'null'), input_new_message_indices)` joined with `,`; non-LLM spans (empty `input_message_hashes`) fall back to `extract(input, ...)` so their raw `spans.input` is still searchable. Output / attributes use `extract(...)` unconditionally. Single CH query, no parallel split. CH arrays are 1-indexed, hence `[i + 1]`. See `build_snippet_query` in `app-server/src/search/snippets.rs`.
- Cleaning runs at `from_span` build time, not in the consumer. `clean_for_indexing(s, strip_roles)` in `app-server/src/quickwit/preprocess.rs` chains `ANSI strip → strip_noise (base64 images, signature / thought_signature values) → optional strip_role_keys → clean_whitespace (collapse real + literal `\n\t\r`, drop other backslashes) → unicode whitespace classes → NFC`. LLM spans pass `strip_roles=true` for input/output; attributes always pass `false`. The chain only removes / collapses chars (never adds), so the snippet `extract()` regex with `[\s\S]{0,50}` context and `[^a-zA-Z0-9]+` token gaps still matches the reconstructed-and-cleaned text.
- Events keep their own `preprocess_text` path (`PreprocessForIndexing` impl on `QuickwitIndexedEvent`); spans' `PreprocessForIndexing` is a no-op because cleaning already happened upstream.

## Quickwit indexing of signal events

- Signal events get their own Quickwit index `signal_events` (`frontend/lib/quickwit/indexes/signal_events.yaml`, applied at boot by `initializeQuickwitIndexes`). `mode: dynamic` (like `spans_v2.yaml`); the free-text content field is `payload`, declared `type: json`. `default_search_fields` is `[]` because the json field type **rejects bare root queries** — every search addresses subfields (`payload.foo:"…"`), built by the search route. Structural ids (`project_id`, `signal_id`, `trace_id`, `id`) are tokenizer:raw + fast; `severity` is `u64` (Quickwit rejects `u8`).
- **`payload` ships as a raw JSON object**, not flattened/filtered: `QuickwitIndexedSignalEvent.payload` is `serde_json::from_str(&event.payload).unwrap_or(Value::Null)`. The json field type is used instead of flatten-with-allow-list because: (1) **per-subfield position streams** — each key gets its own positions so phrase queries (all user queries are phrases via `escape_quickwit_query`) can't span field boundaries (a space-join produces cross-field adjacency false positives); (2) **type inference** — numeric/boolean subfields indexed under inferred types, so a string-path `OR` can't match a numeric column; (3) **keys are field paths, not tokens** — searching `"prompt"` doesn't false-match every event with a `prompt` column.
- Producer hook `publish_signal_events_for_indexing(events, queue)` in `app-server/src/quickwit/producer.rs` mirrors the span/event indexer (`IndexerQueuePayload::SignalEvents` in `quickwit/mod.rs`, routed by `QuickwitIndexerHandler` in `consumer.rs`). Called in the private signals handler (`app-server/src/signals/private/response_processor.rs`, after `insert_signal_events` succeeds, before clustering). Errors logged + swallowed (a Quickwit hiccup never blocks signal-event creation).
- `flatten_json` is a no-op (ships `Value` as-is for per-subfield indexing); `preprocess_for_indexing` walks the `Value` and applies `preprocess_text` (ANSI strip + whitespace collapse + NFC) to every string LEAF via `preprocess_json_strings` (`quickwit/utils.rs`). Leaf-aware because collapsing the whole JSON to a string would break per-subfield indexing.
- **`payloadFields` is load-bearing for search, not just snippets.** Used for (1) building the Quickwit query `payload.f1:"…" OR payload.f2:"…"` (json field has no searchable root) and (2) per-field CH `extract()` for snippet offsets. Frontend filters to `f.type === "string"` before sending. `search_signal_events` short-circuits to empty hits when `payload_fields.is_empty()` (a query with no clauses is rejected by Quickwit) — there is NO all-fields fallback; new callers MUST send a non-empty list.
- **Field-name injection is blocked at query construction:** `search_signal_events` filters every `payload_fields` entry against `PAYLOAD_FIELD_NAME_RE` (`^[a-zA-Z_][a-zA-Z0-9_]*$`) before interpolating into `payload.{name}:{escaped_query}`. The form rule in `schema-field-row.tsx` is the only prior validation (server zod is `z.record(z.string(), z.unknown())`), so without the Rust filter a name like `f1:"x") OR (payload.f1` would escape the parenthesised tenant scope and search the whole index cross-tenant. Failing names are silently dropped (unsearchable but still render). Mirror this filter anywhere user-derived field names hit Quickwit syntax.
- `CHSignalEvent.timestamp` is `i64` nanos-since-epoch (CH `DateTime64(9,'UTC')`); `from_event` reconstructs via the infallible `DateTime::<Utc>::from_timestamp_nanos`, and Quickwit's `timestamp` field accepts the RFC3339 serialisation natively.
- Search route `POST /api/v1/projects/{projectId}/signal-events/search` (`app-server/src/routes/signal_events.rs`) wraps `crate::search::signal_events::search_signal_events`. Returns `{ hits: SignalEventSearchHit[] }`, each `{ id, fieldSnippets: Record<fieldName, SnippetInfo> }`. With `payloadFields: string[]` it runs a CH `extract()` per field over the real `signal_events.payload` for highlight offsets; empty `payloadFields` returns ids only. No `snippetsCount`/`+N` badge (every matching field renders in its own column).
- Snippet fetch `fetch_signal_event_snippets` (`app-server/src/search/snippets.rs`): `SELECT id, array(extract(coalesce(nullIf(JSONExtractString(payload,'<f>'),''), toString(JSONExtractRaw(payload,'<f>'))), '<regex>'), …) AS field_snippets ... WHERE project_id=? AND signal_id=? AND id IN (…)`. Positional `Array(String)` zipped against the field-name list. `JSONExtractString` unescapes so offsets land on glyphs; `JSONExtractRaw` fallback covers non-string fields. `signal_events` is plain MergeTree scoped by `(project_id, signal_id)` — no FINAL. `build_search_regexes` / `post_process_snippet` / `escape_quickwit_query` (pub(crate) re-export from `search/mod.rs`) are shared with the spans path — don't fork. Quickwit query: `project_id:{pid} AND signal_id:{sid} AND (payload.f1:"…" OR …)`; `search_field` not set (each clause carries its path).
- **Filter vs highlight can disagree on tokenisation edge cases** (unicode whitespace, hyphenation — Quickwit `default` tokenizer ≠ CH regex byte-for-byte) → a row with no highlighted cell. Do NOT re-filter hits against snippet emptiness — it drops valid matches.
- Time bounds attached to the Quickwit body only when supplied; the events CH query is unbounded with no params, so a default window in search would drop older matches. Backfill NOT included — pre-existing events show in the table but aren't searchable until re-indexed.
- **Frontend flow:** `searchSignalEvents` (`frontend/lib/actions/events/search.ts`) returns `SignalEventSearchHit[]`; `getEventsPaginated` / `getEventsByEmergingClusterPaginated` build `idFilter` from hit ids, retain the list, then `attachSnippets` merges `fieldSnippets` onto each `EventRow` by id. The events route accepts repeated `payloadField=<name>` params (only when `search` active). `createPayloadColumnDef` (`frontend/components/signal/events-table/columns.tsx`) renders `<HighlightedSnippet>` (UTF-16 `<mark>` slices) when `fieldSnippets?.[field.name]` is set, else the normal cell. Table UI uses `AdvancedSearch` (`events-table/index.tsx`); `resource` widened to include `"signal-events"` (`advanced-search/types.ts`), which disables autocomplete (no endpoint; `autocompleteResource` gate restricts to `"traces"|"spans"`). Recent searches persist via Zustand keyed `signal-events-${signal.id}`.
